# 可转债安全性财务数据增量同步整改方案

> 文档状态：已完成评审修订，待研发实施  
> 编制日期：2026-09-03  
> 最近修订：2026-09-04  
> 适用项目：`portfolio-server`  
> 影响范围：可转债安全性、股票分析、共享财务标准层、自动任务编排  
> 上位文档：`docs/技术架构.md`、`docs/自动任务重复执行与API调用保护整改方案_20260815.md`
> 本次修订：补充生产快照预检、正式发布状态、Tushare 接口差异、披露计划、版本哈希、游标兼容和任务状态语义；本次仅修订方案，不进入研发实施。

## 1. 背景

可转债列表的“安全性”列当前大量显示“未评级”。后台后来手动执行 `bond_safety_refresh` 时显示成功，但前端没有恢复正常评级。

问题并非前端缓存或页面没有刷新，而是后台任务虽然生成并发布了快照，输入财务数据实际上是空的。现有安全性任务已经切换为只读取共享标准数据层，不再直接调用 Tushare；但负责向共享标准层持续写入财务数据的任务没有真正落地，最终形成以下断链：

```text
Tushare 财务接口
      × 缺少正式增量采集任务
fundamental.financial_reports
      ↓ 数据覆盖不足
bond_safety_refresh
      ↓ 仍被判定为成功
全量“未评级”快照
      ↓
可转债列表前端
```

本方案解决两个问题：

1. 补齐当前可转债正股所需财务数据，恢复安全性评级。
2. 建立低调用量、可续跑、可审计的财务增量同步机制，避免每次计算或打开页面都重新请求财务接口。

## 2. 本次核查结论

### 2.1 数据现状

截至 2026-09-03，本机当前数据库核查结果如下：

| 项目 | 核查结果 |
| --- | ---: |
| 当前可转债正股公司 | 约 309 家 |
| `fundamental.financial_reports` 已有公司 | 12 家 |
| 已有财务数据与当前可转债正股匹配 | 0 家 |
| 最新安全性快照结果 | 312 条 |
| 最新快照“未评级” | 312 条 |
| 最新快照财务数据不完整公司 | 309 家 |
| 上一份正常快照 | 2026-08-18，共 312 条，其中 14 条未评级 |
| 财务数据集发布分区 | 0 个 |

现有 12 家公司的标准财务数据来自历史的股票分析直接刷新，最后成功时间为 2026-08-18。它不是面向持仓、自选和可转债正股的共享财务同步链路。

其中 312 条是转债记录数，309 家是正股公司数；一家公司可能对应多只可转债，因此两个数字不要求相等。最新快照诊断中的 `unmatched_stock_count=0`，说明当前 309 家正股的公司身份关系整体可解析，本次主要故障是标准财务数据未覆盖这些公司，而不是公司关系整体断链。正式回填前仍需重新执行公司身份预检，把少量缺失或歧义关系单独列出。

### 2.2 后台“成功”的真实含义

最新一次 `bond_safety_refresh`：

- 状态为成功；
- 外部 API 调用数为 0；
- 只读取本地数据库并进行本地计算；
- 因所有正股都缺少标准财务输入，最终全部输出“未评级”。

因此，当前后台的“成功”只表示代码执行完成并写出了 312 条结果，不代表财务数据已补齐，也不代表评级结果通过质量检查。

### 2.3 根因

#### 根因一：共享财务生产任务没有落地

专项方案中已经规划 `company_financial_incremental_sync`，但当前代码的任务定义、调度器和 Runner 中都没有该任务。`stock_financial_reports` 被安全性和股票分析声明为输入数据集，却没有正式生产者。

#### 根因二：手动安全性刷新被强制设为只读

当前自动刷新和管理员手动刷新都会以 `readOnly=true` 运行。该设计本身是正确方向：计算任务不应直接调用外部接口。但上游财务采集任务缺失后，反复手动执行安全性任务不会产生任何补数效果。

#### 根因三：质量门禁只检查“有无结果”，没有检查“结果是否可用”

当前安全性服务只要可转债列表和公司列表不是空数组，就允许保存新快照。它没有检查：

- 财务覆盖率；
- 有评级记录数；
- 与上一份成功快照相比是否异常下降；
- 输入财务报告是否处于同一报告期；
- 关键字段是否缺失。

因此，全量“未评级”结果仍然覆盖了之前的有效快照。

#### 根因四：文档目标与当前代码状态不一致

现有文档要求“标准层数据不足时保留上一份有效快照”，并规划了公司财务增量任务；实际代码尚未完整落实这两项要求。

## 3. 整改目标

### 3.1 业务目标

1. 可转债安全性恢复正常评级，不再因为全局财务数据缺失而全部显示“未评级”。
2. “未评级”只用于单家公司确实缺少必要数据的情况，不能代表整批任务故障。
3. 上游异常或财务覆盖不足时，前端继续展示上一份有效评级，并明确标注数据时间和异常状态。

### 3.2 数据目标

1. 财务数据统一写入 `fundamental.financial_reports` 和 `fundamental.financial_facts`。
2. 按公司、报表类型、报告期、公告日和版本保存，禁止覆盖历史版本；原始报表和标准财务事实在同一事务中写入。
3. 首次回填后只做增量同步，不反复全量获取。
4. 同一公司关联多只证券或多只转债时只获取一次财务数据。

### 3.3 调用量目标

1. 页面查询财务 API 调用数：0。
2. 安全性计算财务 API 调用数：0。
3. 股票分析计算财务 API 调用数：0。
4. 非财报披露期、无补漏对象时，财务报表接口调用数：0。
5. 财报披露期只获取新公告、更正、缺失或失败重试对象。

## 4. 非目标

本次不调整以下内容：

- 不修改现有安全性三指标的业务评分阈值。
- 不改变前端表格结构和排序规则。
- 不新增第二套数据库、服务或调度器。
- 不让浏览器页面直接调用 Tushare。
- 不恢复“计算任务内部临时补数”的旧模式。
- 不把旧 `bond_safety_financial_cache` 直接冒充为标准财务报表原始数据。

## 5. 总体架构

整改后的链路如下：

```text
                 ┌──────────────────────────────┐
                 │ company_financial_incremental_sync │
                 │ 只获取新增、变更、缺失和重试对象    │
                 └──────────────┬───────────────┘
                                │
                                ▼
                  fundamental.financial_reports
                  fundamental.financial_facts
                                │
                       完整度校验并发布分区
                                │
             ┌──────────────────┴──────────────────┐
             ▼                                     ▼
     bond_safety_refresh                   stock_analysis_refresh
     只读数据库，本地计算                   只读数据库，本地计算
             │                                     │
             ▼                                     ▼
     bond_safety_snapshots                 stock_analysis_snapshot
             │
             ▼
       可转债列表前端

实时价格：腾讯行情缓存独立更新
日终行情：共享市场任务每个交易日更新一次
财务报表：只在披露、更正、缺失或新增公司时增量更新
```

## 6. 财务数据使用范围

### 6.1 公司范围

财务同步任务每天从数据库生成目标公司集合，取以下范围的并集并按 `company_id` 去重：

1. 当前持仓股票；
2. 自选或关注股票；
3. 当前上市可转债的正股；
4. IPO、新股分析明确需要的公司；
5. 最近同步失败、仍需补偿的公司。

公司退出上述范围后不删除历史财务数据，只停止常规跟踪。

### 6.2 报表范围

共享财务层统一维护：

| 报表 | Tushare 接口 | 主要用途 |
| --- | --- | --- |
| 利润表 | `income` / `income_vip` | 利润、利息费用、盈利分析 |
| 资产负债表 | `balancesheet` / `balancesheet_vip` | 现金、负债、资产结构 |
| 现金流量表 | `cashflow` / `cashflow_vip` | 股票分析、现金流质量 |
| 财务指标 | `fina_indicator` / `fina_indicator_vip` | 利息保障倍数、ROE、扣非指标等 |

可转债安全性当前主要使用利润表、资产负债表、财务指标及日终市值。现金流量表虽然不是当前安全性三指标的必需输入，但应进入同一共享财务链路，避免股票分析另建重复采集任务。

## 7. 首次回填方案

首次回填属于一次性专项任务，不计入常规定时任务调用基线，但仍必须受统一调用保护和批次上限约束。

### 7.1 阶段一：恢复安全性更新能力

P0 实施前先对生产库执行只读核查，确认安全性快照总数、最近一份已发布有效快照及其覆盖率。2026-08-18 仅是本机当前数据库中的有效快照证据，不能写死为生产回退目标。读取接口应动态返回生产库最近一份 `published` 快照；如果生产库不存在有效快照，则使用受控的旧缓存只读降级，或明确展示“安全性数据暂不可用”，不得继续展示全量“未评级”结果。

本阶段的目标是补齐标准财务数据并恢复安全性持续更新能力，不以抢时间为由降低数据质量门禁。

执行范围：

- 当前约 309 家可转债正股；
- 明确回填 2026-03-31 和 2026-06-30 两个报告期；
- 利润表、资产负债表、财务指标；
- 同期存在更正或重述时保存最新版本，同时保留旧版本。

选择两个报告期是为了在 2026-06-30 半年报或财务指标尚未齐全时，可以回退到 2026-03-31，并校验三类报表能否按同一报告期关联。半年报通常未经审计，验收时应单独检查 `fina_indicator` 是否存在延迟，不允许为了满足覆盖率而混用两个报告期。

### 7.2 阶段二：补齐共享分析历史

安全性恢复后，在后台可续跑地补齐持仓、自选和可转债正股的历史财务数据。历史深度按股票分析现行业务所需确定，最长指标需要十年数据时，按年度和季度分批回填，不阻塞安全性恢复。

### 7.3 回填执行策略

1. 先对主 Token 的四个财务 VIP 接口做一次受控权限探测。
2. 主 Token 的 VIP 接口可用时，按“报告期＋公司类型＋报表类型”批量获取；利润表、资产负债表和现金流量表的自动采集固定使用 `report_type=1`。
3. VIP 接口不可用时，改用普通接口按待补公司逐一获取；利润表、资产负债表和现金流量表同样显式传入 `report_type=1`。
4. 备用 Token 仅用于普通接口的定点补漏，不绕过主 Token 的统一调用保护。
5. 每完成一个报告期或公司批次立即入库、记录游标，支持中断后续跑。
6. 每个接口单独维护返回上限和拆分策略；已由官方文档确认 `fina_indicator` 单次最多 100 行。任何接口返回数量达到其已确认上限时，必须判定为可能截断，继续按接口明确支持的参数拆分，不能把截断结果发布为完整数据。
7. 空结果、字段异常、单位异常或关键字段覆盖不足时保留旧数据，记录质量问题。

权限探测直接复用现有 `server/scripts/probeTusharePermissions.js`，不新增重复探测工具。

阶段一回填使用独立的一次性脚本 `server/scripts/backfillCompanyFinancials.js`，参考现有可续跑回填脚本的批次模式实现，不注册进 `JOB_DEFINITION_SOURCE`。普通接口的日期参数必须按接口分别解释：`income`、`balancesheet`、`cashflow` 的 `start_date/end_date` 是公告日范围，`fina_indicator` 的 `start_date/end_date` 是报告期范围，禁止共用一套日期过滤逻辑。若各接口一次公司级请求均覆盖目标范围且未触发拆分，三类报表调用量基线约为 `309 × 3 = 927` 次；如同时回填现金流量表则约为 `309 × 4 = 1236` 次。该数字不包含权限探测、截断拆分和失败重试，不得当成硬上限。无论哪种情况都不得塞进默认 30 分钟的日常任务槽位，必须设置批次上限、保存游标并支持断点续跑。

## 8. 日常增量同步设计

### 8.1 新增任务

新增正式任务：

```text
company_financial_incremental_sync
```

任务职责：

- 生成需要检查的公司队列；
- 获取新增或发生变化的财务报表；
- 保存原始响应、标准报表、财务事实和同步游标；
- 校验并发布 `stock_financial_reports` 数据分区；
- 不计算安全性或股票分析结果。

建议任务契约：

| 字段 | 建议值 |
| --- | --- |
| 调度时间 | 每日 06:30 |
| 是否依赖交易日 | 否，按自然日运行 |
| `catchupMode` | `latest_only`，停机恢复后只补最新应执行槽位 |
| `dataDatePolicy` | `latest_available`，不要求财务分区水位等于当天 |
| `requiresDataWatermark` | `false`，新鲜度由披露计划、报告期覆盖和质量门禁判断 |
| `timeoutMinutes` | `30`，只约束单次日常增量批次；专项回填不进入该槽位 |
| `strictDatasetPublication` | `true`，只有完整度校验通过才发布新分区 |
| 生产数据集 | `stock_financial_reports` |
| 消费数据集 | `stock_master`、财报披露计划或公告事实 |
| 外部接口 | `disclosure_date`；`income(_vip)`、`balancesheet(_vip)`、`cashflow(_vip)`、`fina_indicator(_vip)` |
| 失败策略 | 保留上一发布分区，失败对象进入重试队列 |
| 并发策略 | 数据库锁保证同一时间只运行一个实例 |

每日运行不等于每日全量调用。没有待更新对象时任务应返回 `{ ok: true, changed: false, externalCallCount: 0, publishDatasets: false }` 并以 `succeeded` 正常结束，不使用 `skipped`，也不伪造当天财务分区。

### 8.2 增量队列生成规则

满足任意一项的公司进入待同步队列：

1. 新进入目标公司范围；
2. 标准财务表中没有任何数据；
3. 缺少安全性要求的利润表、资产负债表或财务指标；
4. 同一报告期的必要报表不齐；
5. 到达或超过预计披露日期，但数据库尚无对应报告；
6. 上游公告了新的报告期；
7. 上游出现同报告期的更正或重述版本；
8. 上次同步失败且达到下一次重试时间；
9. 数据质量检查发现关键字段缺失，需要定点补取。

### 8.3 非披露期策略

- 不循环请求所有公司。
- 只处理新增公司、历史缺口、重试和更正对象。
- `disclosure_date` 是正式的队列输入，不再作为“必要时”才使用的可选接口。按活跃报告期获取披露计划：披露季可每日更新，非披露季降低频率；每个活跃报告期一次请求后在本地筛选目标公司。
- 没有任何待办时不请求四类财务报表接口。

### 8.4 披露期策略

- 根据本地披露计划和已公告事实生成到期对象。
- VIP 可用时优先按近期报告期批量拉取，再只保留目标公司数据。
- 普通接口模式下只对到期公司请求，不扫描全部公司。
- `income`、`balancesheet`、`cashflow` 的普通接口按公告日维护 30 天重叠窗口；`fina_indicator` 按报告期检查最近两个报告期。
- 30 天窗口不能保证发现窗口外的迟发更正，因此每月轮转复核目标公司最近两个报告期；只对版本摘要变化或历史缺口对象补取完整报表。

### 8.5 幂等键与版本规则

报表的逻辑唯一身份至少包含：

```text
company_id
+ report_kind
+ period_end
+ source
+ source_version / announcement_date
```

处理规则：

- 同一版本重复运行只更新采集元数据，不新增重复报表。
- 同一报告期出现新公告日或更正版本时新增版本。
- `is_current_version` 只指向当前最新有效版本。
- 历史时点查询只能读取当时已经公告的版本。
- 禁止把不同报告期的三类报表拼在一起计算安全性。

日常自动采集对利润表、资产负债表和现金流量表明确传入 `report_type=1`，只获取合并报表，不在常规任务中遍历 `report_type=2～12`。历史上已经采集到的非 1 类型报表继续保留，不删除；`report_type=4/5` 等版本只用于人工对账或专项审计，不作为安全性自动计算的降级数据源。

当前 `rowVersion()` 已包含报告期、公告日、`report_type`、公司类型和更新标记等元数据，但还必须加入规范化原始报文的内容哈希。否则上游在元数据不变时修正数值，会覆盖旧 `raw_payload`，无法满足版本可追溯要求。相同元数据且相同内容哈希视为重复采集；内容哈希变化时新增 `source_version`，旧版本保留。

### 8.6 同步游标

复用 `ops.sync_cursors`，不新增 `report_kind` 列。每个公司和报表类型使用以下范围键：

```text
scope_key = company:{companyId}:{reportKind}
dataset_code = financial
```

每个范围至少记录：

- 最近成功报告期；
- 最近成功公告日或上游更新时间；
- 最近尝试时间；
- 最近错误；
- 重试次数；
- 对应公司、证券和数据集范围。

下一次检查时间可由“预计披露日期＋最近尝试时间＋重试规则”动态计算，避免为每家公司每天调用一次接口。

现有股票分析链路已使用 `scope_key={instrumentId}:{companyId}`、`dataset_code=financial` 写入同一张游标表。该旧游标继续保留，新任务不读取、不覆盖旧 `scope_key`；新旧格式以完整 `scope_key` 隔离，后续退出旧采集链路时再单独清理，禁止在本次整改中批量迁移或删除。

## 9. Tushare 权限和调用路由

当前策略表状态：

- 主 Token 的四个 VIP 接口配置为启用，但权限状态是 `unknown`；
- 备用 Token 的 VIP 接口被禁用；
- 主、备用 Token 的普通财务接口已配置，但权限状态仍需以真实探测结果为准。

因此上线前必须先使用现有 `server/scripts/probeTusharePermissions.js` 执行权限探测，不允许仅根据配置推断权限。

接口契约以 Tushare 官方文档和上线时权限探测为准：

- 普通财务接口需要 2000 积分，按单个 `ts_code` 获取；VIP 财务接口需要 5000 积分，可按报告期获取。
- `income`、`balancesheet`、`cashflow` 及对应 VIP 接口的常规自动采集显式使用 `report_type=1`；不能依赖默认值，也不遍历全部报表类型。
- `income`、`balancesheet`、`cashflow` 普通接口的 `start_date/end_date` 是公告日范围；`fina_indicator` 的同名参数是报告期范围。
- `fina_indicator` 官方单次返回上限为 100 行，达到上限必须拆分并复核完整度。
- `disclosure_date` 需要 2000 积分，单次最多返回 6000 行；以 `end_date` 按报告期查询，可使用 `pre_date`、`ann_date`、`actual_date`、`modify_date` 生成披露和变更队列。

### 9.1 主路由

主 Token 的 VIP 接口探测通过后：

- 财务回填按报告期批量获取；
- 日常增量按近期有效报告期和公司类型切片；
- 每个切片通过完整度检查后独立发布；
- 单个切片失败不影响上一份有效数据。

### 9.2 降级路由

VIP 不可用时：

- 普通接口按 `ts_code` 获取；
- 只处理待同步队列；
- 每批设置公司数和最大调用数；
- 批次完成后保存游标；
- 失败批次按退避时间续跑，不从头开始。

### 9.3 禁止行为

- 禁止安全性任务调用财务接口。
- 禁止股票分析任务调用财务接口。
- 禁止页面请求触发财务补数。
- 禁止每次手动刷新都重新获取已有报告期。
- 禁止用备用 Token 静默绕过限额或熔断。
- 禁止因上游返回空数组而删除已入库数据。

## 10. 股价与财务数据解耦

不同数据应按变化频率分别处理：

| 数据 | 更新频率 | 获取方式 | 是否触发财务接口 |
| --- | --- | --- | --- |
| 页面实时价格 | 按现有腾讯行情缓存 TTL | 腾讯批量行情 | 否 |
| 股票、转债日行情 | 每个交易日收盘后一次 | 共享市场日终任务 | 否 |
| 日终市值 | 每个交易日一次 | `daily_basic` 标准分区 | 否 |
| 财务报表 | 新披露、更正、缺失时 | 财务增量任务 | 是 |
| 安全性评级 | 日终行情和财务分区就绪后本地计算 | 数据库 | 否 |

安全性中的负债、市值比例可能因日终市值变化而变化，因此安全性可以每天重新计算；但每天计算时只读取最近有效财务报告和当天已发布市值，不重新获取财务报表。

前端实时股价更新不应改变安全性快照。安全性统一以最近一个完整日终市场分区计算，避免盘中价格变化造成评级频繁跳动。

## 11. 财务数据质量门禁

### 11.1 报表级校验

每家公司用于安全性计算的财务数据必须满足：

1. 利润表、资产负债表、财务指标来自同一 `period_end`；
2. 利润表和资产负债表必须使用 `report_type=1` 的合并报表；没有合并报表时该公司本期数据视为不完整，不自动降级到母公司或其他报表类型；
3. 报表公告日不晚于安全性快照计算时点；
4. 单位已经统一，金额不得混用元和万元；
5. 安全性关键字段存在且能转换为有效数字；
6. 更正版本已正确替代当前版本，但旧版本仍可追溯。

当前 `bondSafetyTushare.js` 对 indicator、balance、income 各自独立执行“取最新一期”，必须改为：先按公司求出三类报表共同存在的最大 `period_end`，再读取该报告期三类 `raw_payload`。利润表和资产负债表查询同时限定 `report_type=1`。不能只增加事后门禁而不修改这段取数 SQL，否则三类报表发布时间不一致时任务会持续降级。

`financial_available` 必须表示“同一报告期的利润表、资产负债表、财务指标全部存在”，不能继续使用当前“任意一类报表存在即为 true”的判断。

### 11.2 数据集级校验

`stock_financial_reports` 发布前检查：

- 目标公司总数；
- 有完整安全性输入的公司数；
- 缺失公司清单；
- 各报表类型覆盖率；
- 各报告期数量分布；
- 疑似截断切片；
- 单位和异常值诊断；
- 与上一发布分区相比的覆盖变化。

安全性恢复阶段建议以 95% 作为最低发布覆盖率。剩余未覆盖公司必须有明确缺失原因，不能把采集链路故障算作正常缺失。

## 12. 安全性快照防覆盖

安全性快照表增加正式字段 `publication_status`，最小取值为：

- `published`：通过质量门禁，可被前端读取；
- `rejected`：未通过门禁，只用于诊断，不得作为前端当前快照。

迁移时先新增可空字段，再依据历史诊断、评级覆盖率和任务记录执行一次性分类；已确认的全量“未评级”快照标记为 `rejected`，确认有效的历史快照标记为 `published`，不能使用默认值把全部历史记录直接标记为有效。分类完成后再增加非空约束，新写入路径必须显式设置状态。`getLatestSnapshot` 只按 `publication_status='published'` 查询。

现有“按 ID 只保留最近 30 份”的清理规则改为保留最近 30 份 `published` 快照。失败尝试优先记录在任务运行和数据分区诊断中；如同时保存 `rejected` 快照，其保留策略独立计算，不能挤掉可回退的有效快照。

### 12.1 发布条件

新安全性快照必须同时满足：

1. 可转债记录数达到预期完整度；
2. 财务完整公司覆盖率不低于 95%；
3. 有评级数量不低于目标数量的 95%；
4. “未评级”数量没有异常突增；
5. 对“上一份有效快照与当前快照共有的转债集合”比较，有评级覆盖率下降不超过 2%；
6. 输入数据集均为 `published` 状态；
7. 三类财务报表报告期一致。

新增转债单独统计覆盖率和缺口，不进入第 5 条的下降比较分母；但新增转债仍计入当前整体 95% 覆盖率，不能借此放宽整批异常保护。

### 12.2 失败行为

任一门禁失败时：

- 当前任务状态标记为 `failed` 或 `degraded`，不能标记为完整成功；
- 不写入新的 `published` 快照；诊断结果写入任务记录，确需保留快照时显式标记为 `rejected`；
- 继续向前端提供上一份有效快照；
- 记录缺失公司、缺失字段、报告期和数据源；
- 生成财务补数待办；
- 管理后台展示“沿用上一成功数据”和失败原因。

P0 实施时还必须让读取接口能够跳过当前已存在的全量“未评级”快照，动态回退到生产库最近一份 `published` 快照；本机数据库中的 2026-08-18 快照只作为验证样本。只阻止未来错误快照写入不能恢复当前前端显示。

### 12.3 “未评级”的正确语义

“未评级”只允许表示单只转债对应公司存在以下情况：

- 上游确实没有有效财务报告；
- 必要字段在已发布报告中为空；
- 特殊行业当前评分模型不适用；
- 公司身份关系待人工核验。

整批财务数据缺失必须视为任务故障，不能全部转换为“未评级”。

## 13. 前端展示策略

前端继续只读取已发布的安全性快照，不直接参与补数。

建议增加以下元数据展示：

- 当前评级快照时间；
- 当前使用的财务报告期；
- 是否沿用上一份成功快照；
- 最近一次刷新失败原因的简短提示。

示例：

```text
安全性数据截至 2026-08-31
本次更新因财务数据覆盖不足未发布，当前沿用上一份有效结果。
```

本次不要求调整表格布局；提示可复用现有页面状态区域。

## 14. 任务依赖和执行顺序

建议日常顺序：

| 时间 | 任务 | 说明 |
| --- | --- | --- |
| 06:30 | `company_financial_incremental_sync` | 只处理增量、缺口和重试 |
| 08:00 | `convertible_bond_universe_refresh` | 生产上一交易日市场标准分区 |
| 08:30 | `bond_safety_refresh` | 读取已发布市场和财务数据，0 次外部调用 |
| 20:30 | `stock_analysis_refresh` | 读取共享标准层，0 次外部调用 |
| 盘中 | 腾讯最新行情同步 | 与财务任务完全独立 |

财务任务保留在 06:30。Tushare 官方口径是财务数据随财报实时更新，没有“每天 20:00 前全部更新完成”的保证；06:30 更适合完整承接前一晚公告，也能在 08:30 安全性任务前完成。若以后实测确认固定更新时间，再依据连续观测调整，不先增加晚间重复调用。

调度不能只依赖固定时间，还必须检查依赖数据集状态：

```text
stock_master 已发布
        +
stock_financial_reports 已发布或仍有上一有效分区
        +
stock_daily / stock_valuation 已发布
        ↓
允许生成安全性快照
```

## 16. 数据库设计

原则上复用现有表，不新增重复财务表：

- `ops.ingestion_runs`：记录每次批次范围、状态和行数；
- `ops.raw_records`：保存必要的上游原始记录；
- `ops.sync_cursors`：保存公司和数据集同步水位；
- `ops.dataset_partitions`：保存财务数据集发布状态和质量诊断；
- `fundamental.financial_reports`：保存报表身份、报告期、公告日和版本；
- `fundamental.financial_facts`：保存标准化财务事实；
- `analytics.bond_safety_snapshots` 或现有同义表：增加 `publication_status`，保存通过门禁的正式快照及必要的拒绝诊断。

现有唯一约束是 `(scope_key, dataset_code)`，本方案用 `company:{companyId}:{reportKind}` 表达公司和报表类型，不增加游标字段，不新建第二套财务缓存表。股票分析旧格式 `{instrumentId}:{companyId}` 保持原样，新任务与旧路径互不读写对方游标。

## 17. 旧缓存迁移策略

当前 `bond_safety_financial_cache` 中仍有部分可转债正股的聚合财务结果，但它不一定完整保存原始报表、报告期、公告日和版本。

处理原则：

1. 不直接将聚合缓存伪装成标准财务报表写入 `financial_reports`。
2. P0 优先动态沿用生产库最近一份 `published` 安全性快照；2026-08-18 只是本机已确认样本，不为恢复显示重新引入旧采集路径。
3. 如果标准层回填耗时超出预期、业务确实需要期间继续生成新日终评级，可以临时允许安全性任务只读旧缓存；必须标记 `data_source=legacy_cache`、财务报告期、缓存时间和退出日期，且不得触发旧缓存的外部更新逻辑。
4. 当前旧缓存共有 315 条，其中约 308 条字段理论上可计算；按最新 309 家公司名称只能匹配约 290 家，因此只能作为过渡降级来源，不能宣称完整覆盖。
5. 新旧结果双读对比，确认评级差异和单位转换正确。
6. 新链路连续通过验收后，旧缓存退出运行链路。
7. 旧缓存暂不删除，保留审计和回滚用途；删除需另行授权。

## 18. 异常与重试策略

| 异常 | 处理方式 |
| --- | --- |
| 无权限 | 停止对应接口，记录权限状态，不自动反复探测 |
| 限流 | 按 Guard 返回时间等待，下个批次续跑 |
| 网络超时或上游 5xx | 有限重试，仍失败则保留旧数据 |
| 返回空数组 | 不删除旧数据，记录为空并待人工或后续核验 |
| 返回数量达到上限 | 判定疑似截断，继续按合法条件拆分 |
| 单家公司失败 | 记录公司级游标，不回滚其他成功公司 |
| 单个报告期失败 | 不发布该分区，不影响上一成功分区 |
| 财务覆盖不足 | 阻止安全性快照发布，沿用上一有效快照 |
| 重复手动执行 | 幂等读取或续跑，不重复获取已有版本 |

连续失败超过任务最大次数后进入人工关注状态，不进行无限重试。

## 19. 管理后台语义调整

任务状态需要区分“代码执行完成”和“数据可用”：

| 状态 | 含义 |
| --- | --- |
| `succeeded` | 获取、校验和发布完成；无待办时同样正常成功，但返回 `changed=false`、0 次外部调用且不发布伪分区 |
| `degraded` | 部分对象失败，未达到正式发布条件，继续沿用旧分区 |
| `failed` | 权限、接口、程序或质量门禁失败 |
| `waiting_external` | 正在等待上游限流窗口或下一重试时间 |
| `skipped` | 仅沿用现有调度器中的“不配置、旧槽位被取代或明确放弃执行”等语义，不表示正常无变化 |

安全性任务如果生成了 312 条“未评级”，但没有通过覆盖率门禁，状态必须是 `degraded` 或 `failed`，不能显示“成功”。

上述状态已经存在于当前数据库约束中，实施时直接复用现有枚举，不新增第二套任务状态。“检查后无变化”属于成功执行，避免被现有告警和旧失败槽位处理逻辑误判为放弃执行。

## 20. 研发实施步骤

### P0：阻止错误快照继续覆盖

1. 先对生产库执行只读核查，确认快照总数、最近有效快照、全量“未评级”快照和当前保留范围；没有可用快照时明确记录降级路径。
2. 为安全性快照增加 `publication_status`，按历史诊断一次性分类并让读取接口只返回 `published`。
3. 为安全性快照增加覆盖率和异常下降门禁，全量未评级直接失败。
4. 将清理规则改为保留最近 30 份 `published` 快照，失败记录不得挤掉回退快照。
5. 读取接口跳过当前全量未评级快照，动态返回生产库最近一份有效快照及状态说明。
6. 增加对应回归测试。

完成标准：即使财务标准层仍为空，前端也不会再被新的全量未评级快照覆盖。

### P1：一次性补齐当前可转债正股并恢复更新能力

1. 固化当前正股公司集合和预期数量，先统计 `stock_instrument_id → company_id` 可解析数量、缺失数量和歧义数量；身份缺口单独修复，不把“标准财务数据缺失”误判为身份断链。
2. 执行主 Token 财务接口权限探测。
3. 使用独立回填脚本按阶段一范围回填 2026-03-31 和 2026-06-30 两个报告期。
4. 校验报告期、单位、关键字段和公司身份。
5. 发布第一份有效 `stock_financial_reports` 分区。
6. 重新运行安全性计算并发布快照。

完成标准：至少 95% 当前可转债正股具备同报告期完整安全性财务输入；新快照在新旧共有转债集合中的有评级数量不得低于上一份有效快照。

### P2：正式落地财务增量任务

1. 注册 `company_financial_incremental_sync`。
2. 实现目标公司并集和公司级去重。
3. 正式接入 `disclosure_date`，实现公告日、报告期、缺口、更正复核和重试队列。
4. 接入普通接口和 VIP 接口权限路由；日常报表固定 `report_type=1`，日期参数按各接口语义分别处理。
5. 接入统一调用保护、批次游标和数据分区发布；新旧游标格式保持隔离。
6. 注册 `bond_safety_snapshot` 后移除服务内手动分区发布，保证每个数据集只有一个发布入口。
7. 保持股票分析定时任务只读，并将手动刷新、新增关注股票后的刷新改为只读标准层；财务缺口进入增量队列。

完成标准：无财报变化时运行任务，四类财务接口调用数为 0。

### P3：历史补齐与旧缓存退出

1. 分批补齐股票分析需要的历史财务数据。
2. 新旧安全性输入和评级结果双读对账。
3. 连续稳定运行后让旧安全性财务缓存退出读取链路。
4. 更新技术架构、任务矩阵和运维文档。

## 21. 测试方案

### 21.1 单元测试

- 无待办对象时不调用财务接口，以 `succeeded`、`changed=false` 结束且不发布伪分区。
- 新公司进入范围后只拉该公司。
- 已有完整报告期时重复运行不拉取、不重复入库。
- 新公告日对应同报告期时生成新版本。
- 元数据相同但原始报文数值变化时，内容哈希生成新 `source_version`，旧版本不被覆盖。
- 日常利润表、资产负债表和现金流量表只请求并使用 `report_type=1`。
- 不同报表报告期不一致时禁止进入安全性计算。
- 上游空数组不删除旧数据。
- 全量未评级结果禁止发布。
- 覆盖率下降超过阈值时保留旧快照。
- 新旧 `scope_key` 游标互不覆盖。

### 21.2 集成测试

- 普通接口模式下按公司游标续跑。
- VIP 模式下按报告期切片并检测截断。
- 财务分区发布后安全性任务可以正常消费。
- 财务分区失败时安全性任务继续返回上一份快照。
- 同一公司对应多只转债时只产生一次财务获取请求。
- 任务重启后从最后成功批次继续。
- `bond_safety_snapshot` 只由任务编排发布一次，服务层不重复发布。
- 股票分析手动刷新和新增关注股票不直接调用财务接口，缺口正确进入增量队列。
- 快照清理后仍保留最近 30 份 `published` 快照，连续失败或拒绝记录不会挤掉它们。

### 21.3 数据验收

- 当前可转债正股身份匹配准确。
- 财务覆盖率不低于 95%。
- 安全性有评级覆盖率不低于 95%。
- 按行业、规模和风险等级分层抽查 20～30 家公司，确认报告期、报表类型、金额单位和三项安全指标正确。
- 与上一正常快照对比，评级变化有财务版本或市值变化依据。

## 22. 上线与回滚

### 22.1 上线顺序

1. 对生产库只读核查快照保留范围、最近有效快照、财务覆盖和现有分区状态。
2. 备份相关财务、游标和安全性快照表。
3. 部署 P0 快照状态迁移、读取过滤、保留策略和质量门禁。
4. 执行权限探测和阶段一专项回填。
5. 只读检查财务覆盖和异常清单。
6. 发布财务数据分区。
7. 运行安全性任务。
8. 验证 API 和前端展示。
9. 再启用每日财务增量调度。

### 22.2 回滚方式

- 停用 `company_financial_incremental_sync` 调度；
- 不删除已经写入的版本化财务数据；
- 将财务分区状态回退到上一发布版本；
- 安全性继续读取上一份有效快照；
- 旧财务缓存保留只读，作为对账依据。

## 23. 验收标准

以下条件全部满足才算整改完成：

1. 当前可转债正股财务完整覆盖率不低于 95%。
2. 可转债列表不再因整批数据故障显示全部“未评级”。
3. 安全性手动刷新和自动刷新均为 0 次外部财务接口调用。
4. 股票分析自动刷新、手动刷新和新增关注股票后的刷新均为 0 次外部财务接口调用。
5. 财务增量任务是 `stock_financial_reports` 的唯一正式生产者。
6. 非披露期且没有缺口时，财务增量任务以 `succeeded`、`changed=false` 结束，财务接口调用数为 0，且不发布伪造的当天分区。
7. 新财报公布后只同步相关公司、报告期或批量切片。
8. 同一报表版本重复运行不产生重复数据。
9. 更正和重述保留历史版本并正确切换当前版本。
10. 财务覆盖不足时，新安全性快照不会覆盖上一有效快照。
11. 管理后台能够区分“运行完成”和“数据发布成功”。
12. 连续观察至少 3 次日常调度，任务调用统计、分区状态和前端结果一致。
13. 在上一有效快照与当前快照共有的转债集合中，新快照有评级数量不得低于上一有效快照；新增转债覆盖率单独列示。
14. 前端只读取 `publication_status='published'` 的快照，最近 30 份有效快照不会被失败尝试挤掉。
15. `bond_safety_snapshot` 每次结果只发生一次统一分区发布。
16. 上游元数据不变但报文内容变化时生成新版本，旧 `raw_payload` 可追溯。
17. 日常报表采集只使用 `report_type=1`，各接口日期参数按官方语义处理。
18. 新旧游标格式互不覆盖，历史股票分析游标未被误迁移或删除。

## 24. 预期结果

整改完成后的正常行为应为：

```text
没有新财报：
财务任务本地检查 → 0 次财务接口调用 → 安全性读取旧财务＋新日终市值重新计算

有新财报：
财务任务只拉新增/变更对象 → 保存新版本 → 发布财务分区 → 安全性本地重新计算

财务接口故障：
新分区不发布 → 新安全性快照不发布 → 前端继续显示上一份有效评级并提示数据时间
```

最终实现“实时价格高频更新、财务报表低频增量更新、计算任务零外部调用、异常不覆盖有效数据”。
