## 2. 根因（不是"没跑任务"，而是缺一条链路）

1. **选股输入补齐不补估值**：`server/services/stockSelectionInputsSync.js` 的 `classifyGaps` 把缺口分成
   financial / industry / valuation / unclassified，但补齐只处理 industry 与 fundamental；
   valuation 明确按设计"本任务不补，只如实记为剩余（等共享行情任务）"（该文件第 33 行注释）。
2. **A 股有"共享行情任务"补估值，港股没有**：A 股的 `market.daily_valuations` 来自历史全量回填
   （`server/scripts/backfillStockValuationsOfficial.js`）与日常行情链；港股收盘任务
   （`market_close:港股`）只写 `account_daily_prices`（持仓行情，腾讯源），不写全市场估值。
3. 因此港股无论是跑 `selection_quarterly` 还是 `selection_inputs`，估值缺口永远补不上，
   `pendingCount` 永远大于 0，正式组合永远发不出去；生产上连一条 HK 批次记录都没有。

## 5. 链路设计（对齐现有架构，不新增平行事实）

1. **目标池**：新增"港股选股对象池"解析（`hk/index/constituents` → `core.instruments` 归一），
   结果落 `ops` 参考数据，供同步任务与缺口审计共同消费；不把指数成分塞进 `core.instruments` 的业务字段。
2. **同步任务**：不新建平行定时任务，扩展现有 `stock_analysis_refresh` 的港股分支或
   `market_close:港股` 的估值写入能力；二选一须在实施方案里写明"现有任务为何不能承载"。
   任务契约须声明本次发布的数据集（`market_daily_valuations_hk`、`market_daily_bars_hk`）与质量门禁。
3. **写入**：估值走 `market.daily_valuations`（币种 HKD 原币 + `total_market_cap` 单位按既有铁律），
   日线走 `market.daily_bars`；财报/分红走既有 `persistCollectedData` 与标准层。
4. **缺口收敛**：跑完后 `auditInputs({market:'HK'})` 的 valuation 缺口应下降；
   仍缺的对象留在 `remaining_valuation_gap`，不得用 0 或估算值填。
5. **选股**：先由 `company_financial_incremental_sync: selection_inputs`（`market=HK`）补数，
   再按需运行 `stock_analysis_refresh` 的 `selection_inputs`（缺口审计与覆盖证据）和 `selection_quarterly`（季度计算）；
   只有 `published_at` 非空才在页面下拉出现（页面已只列已发布组合）。
   两个任务都有同名 `selection_inputs` 模式，只有财务任务那一个会外采，见第 8 节契约归属说明。

**任务契约归属（2026-11-05 静态核查后修正）**（该契约文件 `jobDefinitions.js` 与生成矩阵由并行会话单独提交，本对话未改该契约，只在此记录边界）：两个任务各有一个同名 `selection_inputs` 模式，含义不同，不能混用。

- `stock_analysis_refresh: selection_inputs`（`stockAnalysisRefresh.js:125`）只审计库内选股输入缺口、保存可续跑队列并发布覆盖证据，调用链没有补数采集。因此它的 `externalApis: []`、`maxExternalCallsPerRun: 0`、`modeExternalCallLimits.selection_inputs: 0`、`mayConsumeQuota: false` 与代码一致，**保持 0**：Runner 会把该上限传给外呼保护器，上限为 0 时经过保护器的外部请求会被阻止；改成 `null` 会放宽现有约束，当前代码没有证据支持。
- 真正外采的是 `company_financial_incremental_sync: selection_inputs`（`companyFinancialIncrementalSync.js:341` → `stockSelectionInputsSync.js:332`），管理接口 `/backfills` 也把补数请求排进财务任务（`stockSelection.js:279`）。该任务已是 `mayConsumeQuota: true`、任务级 `maxExternalCallsPerRun: null`；本次按实际路径补齐其 `externalSources`、官方接口清单（按 `lixingerEndpoints.json` 的 key 逐项核实，含分红备 Tushare、A 股行业备 Tushare、港股日线备腾讯）与 `manualTargetScope` 说明，**未知额度仍保持 `null`**，不编造调用上限。

**不得据「个股分析刷新契约写 0」推断整个补数链路不产生外部调用**；反过来也不得把个股分析刷新的 0 改成 null 来"对齐"外采事实。

## 15. 用户质疑后的复核（2026-11-05 21:30，0.9.2.20 发布前）

- **质疑**：用户贴理杏仁网页分红截图，指出「每股现金和分红总额都有值……理杏仁这些都有，你是不是没有找到」。截图表头为公告日期／分红方案(每10股)／除净日／分红到账日／财报时间／累计分红金额／归母净利润／分红率／年度分红率；「分红方案」列全是现金金额（8.5000 元、4.3000 元等，含「不计入累计（特别股息）」），顶部写「暂不考虑实物股息收益率」，**全表没有送股／红股／转增记录**。
- **澄清**：上一轮汇报里「不是落库丢字段，是源头不给」只针对**送转比例**，不是每股现金／分红总额；这两项一直有（生产 13,676 行港股分红中 13,672 行有每股现金，13,631 行来自理杏仁官方），截图展示的正是这两项。原句含混，容易被读成「源头什么都不给」，已改写 CHANGELOG 与四份文档。
- **官方文档核对**：[hk/company/dividend](https://www.lixinger.com/api/open-api/html-doc/hk/company/dividend) 与 [cn/company/dividend](https://www.lixinger.com/api/open-api/html-doc/cn/company/dividend) 都列 `bonusSharesFromProfit`（送股）／ `bonusSharesFromCapitalReserve`（转增）；A 股文档示例逐行返回这两项（含 0），港股文档示例不返回。此前只凭 1 只纯现金分红股实测就断言「源头不提供」，证据不足，用户质疑成立。
- **决定性实测（本地真实凭据，6 只港股 / 2016—2026）**：纯现金分红 00001、00700、00939，以及**确实送过红股**的 01211（2024 年度 10 送 8 转增 12）、01171（2023 年度红股 3:10）、00754（2023 年红股 1:10），返回行里**连这两个字段名都不出现**，`content` 方案原文也只写「末期息 CNY 3.974(HKD 4.33596)」这类现金方案、无送转字样。即：公司确有送转，但本端点不下发。
- **生产侧佐证**：13,631 条理杏仁港股分红 `raw_payload` 中 `stk_bo_rate` / `stk_co_rate` 全为 null，`fundamental.corporate_actions` 两列也全 NULL；`syncOfficialDividends` 的 INSERT 与适配器映射都写了这两列，`unwrapPayload` 不做字段过滤 → **不是落库丢字段**。
- **结论边界**：只能说「项目当前接入的 `hk/company/dividend` 端点，对已采集港股未返回送转比例」；不能说「理杏仁没有送转数据」（网页／公告里有），也不能据纯现金分红样本外推。R04 仍按「官方每股现金、不做 A 股式送转折算」处理，不新增平行数据源。
- **顺带修掉的隐患**：原实现 `shareUnitBasis` 按市场一刀切，万一将来端点开始下发送转比例，留证会失真。改为按实际数据判定（有比例即按同一因子折算）；新增真库回归（0.3 + 0.5/1.5 = 0.6333、`adjustmentFactor=1.5`、留证 `verified_split_ratio`），破坏性验证改回按市场一刀切为 5/6、恢复 6/6。
- **已知信息损失（未改）**：适配器未把 `content`（分红方案原文）写进 `raw_payload`，网页上的方案细节无留证；本次实测确认该字段对送转也无记录，故不影响口径，留作后续改进项。
