## 19. 新股判不可评估与 PB 窗口性能优化（2026-11-07，0.9.2.31）

### 19.3 PB 窗口 SQL 性能优化

### 21.3 性能四方案实测（生产，只读 + 一次可回滚 DDL 实验）

`loadPbWindow` 是唯一大头（占 `computeSelection` 65%）。四种写法实测：

| 方案 | 实测耗时 | 结论 |
|---|---|---|
| 现状（CASE 表达式排序 + `ARRAY_AGG ... ORDER BY pb`） | **60.7s** | 基线 |
| 物化 `source_priority` 列 + 复合索引 | 62.4s | **更慢**：DISTINCT ON 的 Sort 确实消失，但索引扫描 1220 万行比 Seq Scan + Sort 更贵 |
| 改哈希聚合（两次扫描取代 `ARRAY_AGG` 排序） | 60.4s | 无收益：省下的排序被多出的两次千万行扫描抵消 |
| 两者组合 | **56.2s** | 最优，仅省 7%，且需重写 96.8% 的行才能建列 |

**实验已完全回滚**（`DROP INDEX` + `DROP COLUMN`，生产表回到 2659 MB / 1274 万行），代码恢复原写法并在 SQL 处留下注释禁止重复该优化。

**真正的成本结构**（EXPLAIN 实测）：`loadPbWindow` 60.7s ≈ Seq Scan 4.3s + join 15.3s + DISTINCT ON 排序 27.1s（外部合并 380MB）+ 证据字段组内排序 33.7s。前两块是「一千多万行必须排一次序」的量级成本，换排序键写法无效。

**结论：要实质提速只能做按年预聚合**（把 1220 万逐日行压成 5749×10 的「证券×年度」极值行，查询从 60s 降到秒级），属独立数据工程，不在本次范围。附带实测：`computeSelection` 其余 6 条查询（财报/分红/权益）合计约 53s，均为「一次传 5750 个 company_id」的批量取数，索引齐备（`financial_facts` 已有 `(metric_code, report_id)` 与 `(report_id, metric_code)`），不是缺索引问题。
