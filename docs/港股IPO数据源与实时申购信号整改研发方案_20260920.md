## 1. 结论

AiPO Token 无法取得不影响港股 IPO 基础功能继续研发，但不能据此声称“实时认购倍数、实时孖展”已经解决。

1. **可以不依赖 AiPO 完成**：港交所申请/聆讯/招股/配售结果、发行价区间、每手股数、招股日期、上市日期、最终公开发售超额认购倍数、首日及五日表现、历史最终结果和基础回测。
2. **需要第三方动态源才能完成**：上市前不断变化的券商孖展金额、预计孖展倍数、申购期热度曲线。港交所不会发布券商实时孖展汇总；第三方所谓“实时”通常也是定时汇总，不是逐笔订单流。
3. **当前不能承诺实时可用**：利弗莫尔现用接口返回升级提示；华盛公开接口当前可访问，但核查时有效认购/杠杆字段为空；LiveReport 只确认到前端应用壳，未证明匿名网页可直接批量取得历史或实时数据；AiPO 还存在 Token 与 TLS 可用性问题。
4. **当前系统有 4 个已确认代码问题，其中前 2 个为 P0**：港股日历漏掉正在招股项目、同日动态快照被覆盖；另有完整度 JSON 与真实列值不一致、可选市场信号和核心事实状态边界不彻底两项质量问题。
5. **正式申购建议继续关闭**：本整改只解决事实与信号链路，不放宽既有历史样本、回测、破发率、扣费净收益、来源稳定性和双环境探针门禁。

本次生产验收已完成：提交 `828f76a` 已按标准流程发布；迁移 161 执行成功，发布前加密备份为 `/var/backups/portfolio/portfolio_20260920_161441.sql.gz.gpg`；Web/Worker/健康检查定时器均为 `active/enabled`，`/health` 返回 `0.8.1.73`，`/ready` 的数据库和 Redis 检查通过，港股日历接口及新版 `ipo.js` 返回 200。生产动态信号快照和动态分区均为 0，未启用附加盘中槽位，也未执行历史动态补档。

目标不是寻找一个“万能网站”，而是建立以下分层链路：

```text
港交所官方事实（唯一核心事实）
  + 获授权结构化动态源（优先）
  + 经许可的公开网页补充源（可降级）
  -> 统一 Guard / 原始响应审计
  -> ipo_history + hk_ipo_market_snapshots
  -> 现有 API / 打新页面 / as-of 回测
```

## 2. 先统一数据口径

| 数据名称 | 正确定义 | 可用时间 | 权威落点 | 禁止混用 |
|---|---|---|---|---|
| IPO 官方事实 | 招股区间、每手股数、招股/截止/定价/配售/上市日期、发售结构、基石、保荐人等 | 港交所文件发布后 | `ipo_history` | 第三方页面不得覆盖已有官方值 |
| 申购期认购信号 | 招股期内第三方展示的认购热度或预计认购倍数 | 上市前、动态变化 | `analytics.hk_ipo_market_snapshots` | 不得写入最终超购字段 |
| 孖展金额/倍数 | 券商或聚合平台统计的融资认购金额及相对公开发售额倍数 | 上市前、动态变化 | `analytics.hk_ipo_market_snapshots` | 不等于港交所最终公开认购倍数 |
| 最终公开发售超额认购倍数 | 配售结果公告披露的公众认购结果 | 截止后、配售结果发布时 | `ipo_history.oversubscribe_multiple` | 不得倒填为申购期实时值 |
| 历史盘中曲线 | 当时真实采集并带时间戳的多次快照 | 从开始采集之日起 | 快照表 | 不得用最终结果反推或伪造历史曲线 |
| 暗盘信号 | 券商暗盘价格/涨跌幅 | 暗盘时段 | 快照表 `signal_type='grey_market'` | 不是港交所官方收盘价，不作为首期正式评分依赖 |

页面文案统一使用“申购期预计倍数”“孖展金额/倍数”“最终公开发售超购倍数”，不能继续笼统显示成一个“认购倍数”。

## 3. 现状与根因核查

### 3.1 当前已有能力

- 已有三段任务：`hk_ipo_preopen` 08:30、`hk_ipo_postclose` 18:10、`hk_ipo_enrichment` 19:40。
- 港交所事实写入现有 `ipo_history.market_code='HK'`，动态申购与暗盘信号写入现有 `analytics.hk_ipo_market_snapshots`。
- API 已区分 `subscription_live_multiple` 与 `public_oversubscription`，页面能显示来源、采集时间和过期状态。
- 原始第三方响应进入 `ops.raw_records`，外部访问经过统一 Guard；来源失败不会清空上一份有效快照。
- 港交所、Tushare、腾讯、利弗莫尔、华盛和富途已在既有任务中登记，不需要另建第二套调度器或页面。

### 3.2 已确认的代码问题（前两项为 P0）

1. **正在招股项目被日历漏掉**
   `server/routes/ipo.js` 的 `loadStockCalendar()` 对 HK 申购事件使用 `offer_open_at` 作为唯一事件日，并要求该日期不早于今天。项目已经开始、尚未截止时，开始日已过去，因此不会出现在今日日历。修复不能只改 `WHERE`：两个端点都存在时，筛选必须使用上海业务日口径的 `offer_open_date < 查询窗口结束` 且 `offer_close_date >= 查询窗口开始`，展示日期固定为 `GREATEST(上海业务日 offer_open_date, 查询窗口起始日)`；任一端点为空则不生成 `apply` 事件。`loadStockCalendar()` 返回行的 `event_date` 使用该钳制日期，随后 `groups` 和最终 `apply_stocks` 均以该值分组；原始开始/截止时间作为独立字段返回，不能用分组日覆盖事实时间。首期不把同一项目复制到窗口内每一天，避免日历重复；“今天可申购”由 `offer_phase` 和截止时刻另行判断。

2. **同日动态快照被覆盖**
   当前唯一键为 `(security_code, source_code, signal_type, data_date)`，写入使用同键更新。因此一天只能保留每个来源的一条结果，无法回答“10:00、12:00、15:00 孖展如何变化”。

3. **完整度 JSON 可能与真实列值不一致**
   `hkexIpo.js` 的 upsert 会把旧 `data_completeness` 与新结果合并，而不是在所有来源合并完成后按数据库最终行重新计算；已有列被补齐后，旧的 `missing/retryable` 仍可能残留。`prospectus` 子状态已有独立终态治理，但顶层完整度仍需统一重算。

4. **可选市场信号与核心事实边界仍需彻底隔离**
   券商或网页源失败只能让 `hk_ipo_subscription_signals` 降级，不能让港交所核心事实分区失败；核心事实、资料补全、动态信号必须分别给出状态。

### 3.3 前序生产证据（只作为 2026-09-17 基线）

前序只读核查曾发现：`/api/ipo/calendar?market=HK` 在存在招股窗口内项目时仍返回空；181 条港股记录中部分发行价、每手金额、申请费、公开发售比例、中文名等字段缺失；完整度 JSON 大量标记待补，但部分对应列实际已有值；市场快照主要是暗盘信号，没有稳定的申购期快照。以上数字是当日基线，实施前必须重新只读测量，不能当作 2026-09-20 之后的实时数量。

## 4. 数据源可行性核查

- **可接入**：已确认当前可访问、字段口径明确，并能在既有合规边界内开发。

## 5. 数据源分层和准入规则

### 5.1 分层

1. **L0 官方事实**：HKEX。发行事实冲突时只认官方披露，第三方只记录差异。
2. **L1 获授权结构化源**：已开通的 Tushare、腾讯、未来可能获批的 Futu OpenAPI、TradeGo OpenAPI/导出。
3. **L2 公开补充源**：华盛、利弗莫尔、富途公开页、致富、AASTOCKS、ETNet、集思录。只保存来源、时间和口径，随时允许降级。
4. **L3 研究线索**：GitHub 项目、搜索结果和人工资料。不能直接写正式事实或训练样本。

### 5.2 新来源上线前必须同时通过

- 服务条款或书面授权允许当前用途；需要账号/Token 时只从 `.env` 或密钥服务读取。
- 本地与生产网络都能完成只读探针，连续 5 个工作日响应结构无漂移；无招股项目时，来源明确返回合法空结果也计入结构探针，不因市场空窗期无限阻塞。
- 开发阶段至少准备一个脱敏正样本夹具和一个空结果夹具，可据此完成适配器、入库与降级回归并进入关闭页面输出的影子模式；夹具不能代替真实来源验收。
- 遇到下一次真实招股窗口时，必须取得至少一个“正在招股且字段非空”的真实正样本，并完成本地/生产网络字段、单位和时间核对；只有此后才允许启用盘中附加槽位和页面动态信号。若真实窗口仍无正样本，继续保持影子模式。
- 字段能明确区分“来源更新时间”和“本地采集时间”，数值单位、币种和倍数基数可解释。
- 空响应、429、5xx、登录过期、HTML 改版和字段异常均不会清空旧数据或阻断 HKEX 核心事实。
- 未公布官方额度时不虚构“官方频率”；采集节奏由来源条款、页面更新时间和统一 Guard 控制。

## 6. 目标数据架构

### 6.1 继续复用现有表和任务

- 不新增平行调度器，不新增第二套港股 IPO 事实表。
- `ipo_history` 继续保存 HKEX 官方事实和最终结果。
- `analytics.hk_ipo_market_snapshots` 继续保存申购期、孖展和暗盘等时点信号，但需要兼容式扩展。
- `hk_ipo_preopen` 继续负责招股期事实和动态信号；盘中采集通过同一任务的 `additionalSchedules` 扩展，不另造任务。
- `hk_ipo_postclose` 继续收配售结果和最终超购；`hk_ipo_enrichment` 继续补官方文件、日线和历史信号。

### 6.2 快照表兼容式整改

在现有表上增加字段，不另建表：

| 字段 | 用途 |
|---|---|
| `source_observed_at` | 上游明确给出的更新时间；没有则为空 |
| `last_seen_at` | 同一内容最后一次被本地看见的时间 |
| `margin_amount_hkd` | 孖展总金额，统一 HKD |
| `margin_multiple` | 来源明确给出的孖展倍数 |
| `signal_kind` | `subscription_estimate/margin_estimate/grey_market_quote`；允许 `NULL` 表示历史记录口径未确认 |
| `source_record_hash` | 对证券、来源、信号口径、规范化数值和上游时间做哈希，用于幂等 |
| `quality_status` | 只保存采集当时的 `valid/empty/rejected`；`stale` 不落库，由查询时派生 |

迁移要求：

1. 新增独立的 **161 号迁移**。必须使用 `ALTER TABLE analytics.hk_ipo_market_snapshots ADD COLUMN IF NOT EXISTS ...` 和独立索引/约束变更；只修改迁移 148 中的 `CREATE TABLE IF NOT EXISTS` 对服务器已有表无效，禁止把它当作升级路径。
2. 在 161 号迁移的事务内先查询 `pg_constraint`，按表 OID、`contype='u'` 和组成列精确找到旧 `(security_code,source_code,signal_type,data_date)` 唯一约束，再对查得的真实约束名执行 `DROP CONSTRAINT`；不得猜测 PostgreSQL 自动生成的约束名。若不存在约束，再用 `pg_indexes/pg_index` 查询列顺序完全相同且不受约束依赖的独立唯一索引，并仅在唯一命中时 `DROP INDEX`。约束和独立索引都未找到、同时找到多个候选或索引仍受约束依赖时，迁移失败关闭，不继续建新索引。
3. 现有 `signal_type` 的 CHECK 继续保持 `subscription/grey_market` 两类，不扩枚举；新增可空的 `signal_kind TEXT` 及 CHECK，限定为 `subscription_estimate/margin_estimate/grey_market_quote`。历史记录没有足够证据时保持 `NULL`，不能按来源名称猜测。
4. 旧行保留且不强制反推哈希，`source_record_hash` 可为空；新写入必须生成非空哈希。新建部分唯一索引 `(security_code,source_code,signal_type,data_date,source_record_hash) WHERE source_record_hash IS NOT NULL`，保证跨业务日相同内容各自保留，同时允许同一日出现多个真实变体。
5. 哈希只使用规范化后的业务字段，不直接哈希整份原始载荷，避免无关字段变化制造假快照：金额四舍五入为 HKD 整数元，倍数、价格和涨跌幅统一为 4 位小数，代码/来源/类型去空格并按固定大小写，上游时间转 UTC 并截到秒。哈希输入至少包含证券、来源、`signal_type`、`signal_kind`、全部标准数值和 `source_observed_at`；上游无时间时不人为填入当前时间。
6. 以 `data_date + source_record_hash` 幂等：同一业务日内规范化数值或上游时间变化时新增快照，内容未变化时只更新 `last_seen_at`；跨业务日即使内容相同也新增当日记录。`observed_at` 保留为本地首次采集时间，查询最新值按 `data_date DESC, COALESCE(source_observed_at, observed_at) DESC` 排序。
7. `quality_status` 不允许保存 `stale`。可识别到具体证券和来源记录的空值/拒收可落 `empty/rejected` 供审计；整个来源返回空数组或结构错误时写入 `ops.raw_records` 和任务诊断，不制造无证券快照。API 查询只选择 `valid` 快照，再按来源新鲜度阈值派生 `valid/stale/unavailable`。
8. 现有 `subscription_multiple` 继续兼容；`raw_payload.signal_kind` 迁移到新列只处理有直接证据的记录。原始响应仍进入 `ops.raw_records`，标准数值只保存通过范围、单位和时间校验的记录。

### 6.3 完整度重新计算

每一阶段合并来源后，从数据库最终行重新计算 `data_completeness`，不再拿某个来源的局部对象判断全局完整性：

- 招股期：区间价、每手股数、开始/截止时间和官方文件证据；最终发行价、配售结果和最终超购属于 `pending_not_due`。
- 定价/配售期：到期字段未出现时才进入 `retryable`，介绍上市、GEM 转主板、De-SPAC、正式取消等保持已有终态。
- 上市后：最终发行价、配售结果、首日/五日行情按各自到期时间校验。
- `prospectus` 已有嵌套终态继续保留，顶层状态从真实列和子状态重新汇总。

### 6.4 迁移前置备份与回滚

161 号迁移属于结构性约束变更，生产执行前必须完成：

1. 按标准生产流程生成加密全库备份，并对 `analytics.hk_ipo_market_snapshots` 做独立表级导出；记录总行数、按 `signal_type/source_code` 分组行数、旧唯一键重复数及最新 `observed_at`。
2. 迁移、约束删除、新列和新索引创建放在同一事务；任一步失败则整笔回滚，应用不得切换到新写入逻辑。
3. 部署后先只读核对 161 迁移登记、列/约束/索引、历史行数和旧记录可读性，再开放动态写入。
4. 尚未写入同日多快照时，可在确认无重复后撤销新索引并重建旧唯一约束；一旦新结构已产生同日多快照，禁止为恢复旧约束而删除或合并记录。此时优先回退应用到“只读最新有效快照”并保留新表结构；只有明确决定恢复迁移前状态时，才使用专表导出或全库备份恢复。
5. 失败判据包括：旧约束无法唯一识别、历史行数变化、部分索引创建、旧 API 无法读取、首个真实写入出现重复哈希或同一内容重复增行。任一命中即停止发布，不继续跑补档。

### 6.5 快照保留策略

- 港股 IPO 数量和计划采集频率较低，首期不启用在线自动删除；标准快照至少保留 5 个完整自然年，保证 as-of 回测和来源争议复核。
- 超过 5 年的数据只允许在完成行数、哈希和时间范围核对后转入冷归档，不直接硬删除；归档方案、恢复演练和生产授权另行制定，不纳入 P0/P1。
- `ops.raw_records` 的原始响应保留由统一原始层治理决定，本方案不另造第二套清理任务。

## 7. 采集与调度方案

### 7.1 官方事实

- 08:30：HKEX 当日发行项目、状态、招股窗口和官方文件增量。
- 18:10：配售结果、延期/取消、最终发行价和最终公开超购。
- 19:40：历史报表、招股书/配售 PDF、上市后日线和缺口续批。
- 同一官方文档按 URL、正文哈希和解析器版本幂等；错误文档分类不进入成功终态。

### 7.2 动态认购/孖展

首期仍挂在 `hk_ipo_preopen`：

1. 只对 `offer_open_at <= 当前时间 <= offer_close_at` 的公众招股项目采集。
2. 来源准入前保持现有 08:30 一次；至少一个来源通过第 5.2 节后，才为同一 `hk_ipo_preopen` 增加 11:00、14:00、16:00 三个 `additionalSchedules`，连同原 08:30 共四个时点。项目内部业务日和调度统一使用 `Asia/Shanghai`；来源原始时间若声明为香港时区，只在解析时转换并把原文留在 `raw_payload`。最终频率必须服从来源条款和实际更新时间。
3. 同一来源内容未变只更新 `last_seen_at`，不制造重复快照；上游时间或数值变化才新增记录。
4. 主源失败时按白名单顺序尝试一次备源，不做多源连环重试；来源级熔断后本轮立即停止。
5. 动态信号单独输出 `succeeded/degraded/waiting_external`，不得改变 `hk_ipo_facts` 的成功状态。
6. 附加槽位继续调用已有 `preopen` Runner，显式声明 `mode='preopen'`、`freshnessGate=false`，避免较早快照把盘中采集短路；`catchupMode='latest_only'`、截止时间、最大尝试、无进展保护和来源 Guard 继续沿用，禁止在启动追赶时补造已过去的盘中时点。
7. `hk_ipo_subscription_signals` 已在任务契约中声明为产出数据集，实施时还须登记到 `DATASET_PARTITION_REGISTRY`，按 `HK + business_date` 发布并记录活跃招股数、有效信号数、最近来源时刻和降级原因。无活跃招股可发布“已核验零行”；有活跃招股但没有有效信号时只能 `degraded/stale`，不能伪装为完整。
8. 数据质量告警绑定 `dataset:hk_ipo_subscription_signals:HK:<business_date>`；具体上游异常绑定精确 `source:api_name`。恢复时分别核对真实分区或该接口探针，普通任务成功、其他来源成功或通配 `source:*` 均不能代替原作用域证据。

首期动态源顺序建议：

```text
已获授权的结构化源（如未来 Futu/TradeGo OpenAPI）
  -> 已验证公开源（VBKR / ChiefGroup / ETNet 中通过准入者）
  -> 最近有效快照并标记 stale
  -> 无数据（绝不显示 0）
```

利弗莫尔必须区分两个接口：当前申购接口在升级提示恢复前只保留受控探针，不再作为首选；历史接口继续按现有代码承担暗盘补充，以及“记录截止日仍覆盖业务日”时的申购期兜底，但统一标记为历史窗口兜底，不得冒充实时。AiPO 不进入顺序。

## 8. API 与页面整改

### 8.1 日历

- HK 申购窗口统一按上海业务日转换：使用 `timezone('Asia/Shanghai', h.offer_open_at)::date` 和 `timezone('Asia/Shanghai', h.offer_close_at)::date` 比较、钳制及格式化，禁止继续用裸 `to_char(timestamptz, ...)` 依赖数据库会话时区。完整窗口先按“招股窗口与查询窗口相交”筛选，再把展示分组日设为 `GREATEST(timezone('Asia/Shanghai', h.offer_open_at)::date, 查询窗口起始日)`；`apply_stocks` 使用该钳制日期分组，原始 `offer_open_at/offer_close_at` 单独返回。
- HK `apply` 事件不再使用旧的 `COALESCE(offer_open_at, ipo_date)` 兜底：`offer_open_at` 或 `offer_close_at` 任一为空，都不进入 `apply_stocks`。介绍上市、GEM 转主板、De-SPAC 等无公众招股窗口项目仍可按官方 `listing_at/listing_date` 进入 `list_stocks`，不能因无招股窗口从整个日历消失；CN 现有 `ipo_date` 逻辑保持不变。
- 每只项目返回 `offer_phase`：`upcoming/open/closed/priced/allotted/listed/postponed/cancelled/not_applicable/pending_window`。无公众招股窗口的介绍上市/GEM 转主板/De-SPAC 为 `not_applicable`；普通公众项目窗口不完整为 `pending_window`；有正式押后公告且尚未公布新窗口为 `postponed`。
- 阶段判定优先级固定为：`cancelled` → 尚无新窗口的 `postponed` → 非公众项目 `not_applicable` → `listed/allotted/priced` → 普通公众项目窗口不完整 `pending_window` → 完整窗口的 `upcoming/open/closed`，避免同一记录因缺日期被误归到较低优先级。
- 押后后重新招股继续复用同一 `security_code`、`instrument_id` 和同一 `ipo_history` 行，以新官方文件更新当前 `offer_open_at/offer_close_at`，阶段重新计算为 `upcoming/open`；旧窗口、押后公告和新窗口证据保留在 `source_documents`、`ops.raw_records` 及解析证据中，不新建第二条证券记录。
- “今天可申购”必须同时满足当前时间未超过官方截止时间；只有日期没有时刻时明确显示“截止时刻待核”。

### 8.2 列表和详情

API 分开返回：

```json
{
  "current_subscription_signal": {
    "multiple": null,
    "source": null,
    "source_observed_at": null,
    "collected_at": null,
    "status": "unavailable"
  },
  "current_margin_signal": {
    "amount_hkd": null,
    "multiple": null,
    "source": null,
    "source_observed_at": null,
    "collected_at": null,
    "status": "unavailable"
  },
  "final_public_oversubscription": null
}
```

- API 的当前信号 `status` 只有 `valid/stale/unavailable`：存在未超过该来源阈值的有效快照为 `valid`，存在有效但已超过阈值的快照为 `stale`，不存在有效快照为 `unavailable`。采集层的 `empty/rejected` 只用于审计和诊断，不直接冒充页面当前信号。
- 页面分别显示“预计认购”“孖展”“最终超购”，并显示来源和更新时间。
- 来源超过自身新鲜度阈值时显示“可能过期”，不能只用统一固定天数判断所有来源。
- 来源失败或字段为空时显示“暂无可验证数据”，不能显示 0 倍、0 港元或沿用旧值而不标记过期。
- 页面请求只读数据库，禁止点击页面时直接抓第三方网站。

## 9. 历史数据与回测边界

### 9.1 能补什么

- HKEX 配售结果可补最终公开超购、一手中签率、最终发售价和发售结构。
- HKEX/Tushare/腾讯可补上市日期及首日、五日表现。
- 集思录、AASTOCKS、ETNet、LiveReport 授权导出可作为历史交叉源，但必须保留来源时间和字段口径。

### 9.2 不能补什么

- 没有带采集时刻或上游时刻的历史数据，不能恢复当年盘中孖展曲线。
- 最终超购倍数不能复制成招股期任一时点的认购倍数。
- 只有网页当前值、没有发布时间的记录不能用于严格 as-of 回测。
- 历史第三方数据与官方结果冲突时，官方事实覆盖标准字段，第三方值只保留为审计信号。

整改上线后从当日开始积累真实时序；历史回填只接收来源明确提供的时间戳记录。回测按申购截止时点做 as-of 切片，任何截止后数据都禁止进入特征。

## 12. 风险和停止条件

- **授权风险**：网页公开可见不等于允许自动化批量抓取；条款不明确时停止接入，转官方 API/导出或商务授权。
- **认证风险**：AiPO Token、Futu/TradeGo 账号等敏感信息只放 `.env`/密钥服务，不硬编码、不绕过登录或验证码。
- **稳定性风险**：SPA、HTML 和内部接口随时会变；解析器必须用夹具和结构断言失败关闭。
- **口径风险**：不同券商的孖展覆盖范围不同，跨来源数值不能直接相加；页面必须显示来源。
- **历史偏差**：缺少盘中历史时只能从整改上线日起积累，不为赶回测进度制造数据。
- **连续失败纪律**：同一来源连续两次开发探针仍无法取得正样本时，停止猜测，记录为阻塞或更换候选源。

## 13. 最终实施决策

1. AiPO 从首期研发白名单移除；未来只有在官方授权、Token 获取和生产 TLS 均验证后再评估。
2. LiveReport 不采用“BeautifulSoup 直接抓页面”的方案；当前页面是 SPA。优先争取 OpenAPI、CSV/Excel 导出或明确的匿名数据许可，Selenium 也不能解决授权和长期稳定性问题。
3. 先完成 P0，使日历、完整度和多时点快照正确；否则换任何来源都会继续漏数或覆盖数据。
4. P1 只在 VBKR、ChiefGroup、ETNet 中选通过准入的一主一备；Futu/TradeGo 获正式接口权限时优先替换网页源。
5. 港交所官方事实、最终超购和上市后表现可以独立交付；实时认购/孖展作为可降级增强能力单独验收。
6. 所有动态数据首次成功调用即入库，后续只增量采集和更新 `last_seen_at`，页面永不直接回源。
