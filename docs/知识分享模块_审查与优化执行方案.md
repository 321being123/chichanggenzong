# 知识分享模块审查与优化执行方案

> 编写日期：2026-07-26  
> 适用范围：知识分享页面、文章与分类接口、评论、公开分享、链接/文件导入、后台管理、数据库迁移及第三方依赖  
> 当前结论：模块分层方向合理，但存在部署、越权和内容安全阻断项，完成 P0 后才能部署。

## 一、执行原则

1. 按 P0 → P1 → P2 → P3 顺序处理，不把低优先级重构混入安全修复。
2. 只局部修改知识分享链路及其直接依赖，不重构现有持仓、打新、股债分析等业务。
3. 每项修改必须同时补自动测试；不能只依赖手工页面验证。
4. 所有数据库变更通过新迁移完成，不修改已经执行过的 012～014 迁移。
5. 第三方包必须使用 npm 正式安装并写入 `package.json`、`package-lock.json`，禁止依赖本机“额外安装”的包。
6. 密码、Token、代理凭据等敏感信息只能从 `.env` 读取，禁止写入代码、日志或文档。

## 二、当前架构概览

| 层级 | 当前文件 | 主要职责 |
|---|---|---|
| 前台页面 | `public/index.html` | 知识分享入口、目录、文章列表、阅读和编辑区域 |
| 前台逻辑 | `public/js/knowledge.js` | 文章、分类、评论、编辑器、导入操作 |
| 公开分享 | `public/share-knowledge.html` | 免登录阅读分享文章、登录后评论 |
| 样式 | `public/css/knowledge.css` | 知识分享页面样式 |
| 后端路由 | `server/routes/knowledge.js` | 文章、分类、评论、分享、文件和链接导入 |
| 后台管理 | `server/routes/admin.js`、`public/js/admin.js` | 全站文章、评论和写权限管理 |
| 数据库 | `server/db/migrations.js` | 文章、分类、评论及用户写权限表结构 |
| 用户数据 | `server/db/users.js` | 写权限字段、用户删除、管理员初始化 |
| 首页摘要 | `public/js/home-dashboard.js` | 首页最新文章 |
| 集成测试 | `test-knowledge-extend.js` | 依赖本地服务的知识分享测试，当前未接入 CI |

合理之处：

- 前端、后端、后台和数据库职责已经基本分开。
- SQL 参数使用占位符，未发现直接拼接用户输入的 SQL 注入问题。
- 分享 Token 使用安全随机数生成。
- Vditor 使用本地静态资源，避免运行时依赖公共 CDN。
- 后台知识分享接口统一经过管理员鉴权。

## 三、P0：部署前必须完成

### P0-1 补齐并锁定生产依赖

#### 当前问题

`server/routes/knowledge.js` 使用了以下直接依赖，但它们没有完整写入正式依赖清单：

- `multer`
- `mammoth`
- `turndown`
- `undici`
- `jschardet`
- `@mozilla/readability`
- `iconv-lite`
- `jsdom`

当前本机多数包处于 `extraneous` 状态。生产部署执行 `npm ci --omit=dev` 时会移除这些包。尤其 `multer` 在路由模块顶层加载，会导致整个应用启动失败；`jsdom` 当前属于开发依赖，生产环境也不会安装。

#### 执行建议

1. 使用 npm 官方命令安装上述运行依赖，并把 `jsdom` 调整为生产依赖。
2. 使用 npm 正式安装并锁定 `vditor`，不要只保留来源不明的复制文件。
3. 更新 `package-lock.json`，使根版本与 `package.json` 一致。
4. 增加干净安装冒烟检查：

   ```bash
   npm ci
   node -e "require('./server/routes/knowledge')"
   ```

5. 生产依赖检查必须使用与服务器相同的：

   ```bash
   npm ci --omit=dev
   ```

#### 验收标准

- 删除本机 `node_modules` 后执行 `npm ci`，服务仍能加载知识分享路由。
- `npm ls --depth=0` 不再把知识分享所需包标记为 `extraneous`。
- CI 能在全新环境完成安装和测试。
- `package.json` 与 `package-lock.json` 的项目版本一致。

---

### P0-2 增加文章级归属权限

#### 当前问题

当前只有全局 `knowledge_enabled` 写权限，没有文章归属校验，导致：

- 任意登录用户可以看到所有作者的草稿。
- 任意获得写权限的用户可以编辑、发布、撤回、删除其他作者的文章。
- 登录用户的文章列表会返回草稿的 `share_token`。
- 前端只根据 `canWrite` 显示编辑和删除按钮，没有判断是否为文章作者。

#### 推荐权限矩阵

| 操作 | 游客 | 普通登录用户 | 获得写权限的作者 | 管理员 |
|---|---:|---:|---:|---:|
| 阅读已发布文章 | 允许 | 允许 | 允许 | 允许 |
| 阅读自己的草稿 | 不允许 | 不适用 | 允许 | 允许 |
| 阅读他人草稿 | 不允许 | 不允许 | 不允许 | 允许 |
| 新建文章 | 不允许 | 不允许 | 允许 | 允许 |
| 编辑/发布/撤回/删除自己的文章 | 不允许 | 不允许 | 允许 | 允许 |
| 管理他人文章 | 不允许 | 不允许 | 不允许 | 允许 |
| 管理全局分类 | 不允许 | 不允许 | 不允许 | 允许 |

#### 执行建议

1. 新增文章归属中间件或统一函数：

   - 查询 `articles.author_username`。
   - 当前用户是作者时放行。
   - 当前用户是管理员时放行。
   - 其他情况返回 403。

2. 应用于以下接口：

   - `PUT /api/knowledge/articles/:id`
   - `DELETE /api/knowledge/articles/:id`
   - `POST /api/knowledge/articles/:id/publish`
   - `POST /api/knowledge/articles/:id/unpublish`

3. 文章列表查询规则：

   - 游客和普通登录用户：只返回已发布文章。
   - 写作者：返回全部已发布文章，加上自己的草稿。
   - 管理员：可通过明确的后台接口查看全部草稿。

4. 文章详情查询使用同一套规则，禁止通过猜测 ID 读取他人草稿。
5. 普通文章列表不要返回 `share_token`；仅在作者本人或管理员读取单篇已发布文章时返回。
6. 前端根据接口返回的 `can_edit`、`can_delete` 等明确字段显示操作按钮，不再只依赖全局 `canWrite`。
7. 分类新增、改名、删除接口调整为管理员权限；写作者只读取和选择分类。

#### 验收标准

- A 作者无法查看、编辑、发布或删除 B 作者的草稿。
- A 作者无法修改 B 作者的已发布文章。
- 管理员仍能管理全部文章。
- 未登录和普通登录用户的响应中不包含草稿及其分享 Token。
- 越权请求统一返回 403，前端不会显示“操作成功”。

### P0-3 修复评论删除越权并记录评论作者

#### 当前问题

评论接口要求登录，但评论表只保存昵称和 IP 哈希，没有保存登录用户名。删除接口只校验“是否登录”，所以任何登录用户都能删除任意评论。

#### 执行建议

1. 新增迁移，为 `article_comments` 增加：

   ```sql
   author_username TEXT REFERENCES users(username) ON DELETE SET NULL
   ```

2. 新评论必须从 `req.session.user` 写入 `author_username`，不能接受前端传入用户名。
3. 删除评论规则：

   - 评论作者本人允许删除。
   - 管理员允许删除全部评论。
   - 其他用户返回 403。

4. 前端仅在 `can_delete=true` 时显示删除按钮。
5. 昵称只作为展示名称，不参与权限判断。
6. 历史评论的 `author_username` 可保持为空，只允许管理员删除。

#### 验收标准

- 普通用户不能删除其他人的评论。
- 评论作者可以删除自己的评论。
- 管理员可以从后台删除全部评论。
- 仅登录状态不能成为删除任意评论的依据。

### P0-4 统一净化文章正文，消除存储型 XSS

#### 当前问题

Vditor 默认启用了 Markdown 净化，但 Vditor 加载失败或超时时，前台和公开分享页会直接执行：

```js
element.innerHTML = marked.parse(markdown);
```

`marked` 会保留原始 HTML，例如图片 `onerror`、`javascript:` 链接等危险内容。当前 CSP 又允许内联脚本，因此兜底路径可以形成存储型 XSS。

#### 执行建议

1. 在 `public/index.html` 和 `public/share-knowledge.html` 中加载项目已有的本地 DOMPurify。
2. 所有 Markdown 兜底统一使用：

   ```js
   DOMPurify.sanitize(marked.parse(markdown || ''), {
     USE_PROFILES: { html: true }
   })
   ```

3. 封装一个公共 Markdown 安全渲染函数，前台和公开分享页共同使用，避免两份逻辑漂移。
4. 不信任数据库中的 `html_content`；如果继续保留该字段，也必须在展示前重新净化。
5. 增加以下攻击载荷测试：

   - `<script>`
   - `<img onerror>`
   - `javascript:` 链接
   - `<svg onload>`
   - `<iframe>`
   - 带事件属性的 HTML

#### 验收标准

- Vditor 正常和加载失败两条路径都不能执行危险 HTML。
- 主站阅读页和公开分享页使用相同净化策略。
- 安全测试能够证明危险标签、属性和协议已被移除。

## 四、P1：高优先级修复

### P1-1 修复首页加载中断和重复实现

#### 当前问题

- `public/js/home-dashboard.js` 调用了不存在的 `loadHomeArticles()`，实际函数名是 `renderHomeArticles()`。
- 异常发生在 `try` 之前，会中断首页 IPO 和转债数据加载。
- `public/index.html` 又内联复制了一份最新文章加载逻辑，导致重复请求和双重维护。

#### 执行建议

1. 统一函数名。
2. 只保留 `public/js/home-dashboard.js` 中的实现。
3. 删除 `public/index.html` 中的最新文章内联兜底代码。
4. 最新文章失败只能影响文章区域，不能影响 IPO、转债和持仓区域。
5. 为首页增加一个纯函数或 DOM 单元测试，确保入口函数存在且只请求一次。

#### 验收标准

- 首页无未处理的 `ReferenceError`。
- 每次加载首页只请求一次 `/api/knowledge/latest`。
- 最新文章接口失败时，IPO 和转债卡片仍能正常加载。

### P1-2 保留文章原发布时间

#### 当前问题

更新文章前只查询了 `status`，后续却读取不存在的 `published_at`，导致编辑已发布文章时总是把发布时间更新为当前时间，文章不断被顶到列表最前。

#### 执行建议

1. 查询当前文章时同时读取 `status`、`published_at` 和 `author_username`。
2. 更新规则：

   - 草稿首次发布：设置 `published_at=now()`。
   - 已发布文章普通编辑：保留原 `published_at`。
   - 明确撤回：按产品规则决定是否清空发布时间。
   - 再次发布：明确决定使用原发布时间还是重新发布时间，并在测试中固定。

3. 推荐在 SQL 中使用明确的 `CASE`，不要在 JavaScript 中拼接发布时间 SQL 片段。

#### 验收标准

- 编辑已发布文章不会改变原发布时间。
- 首次发布一定有发布时间。
- 撤回和再次发布行为固定且有自动测试。

---

### P1-3 修复用户删除与文章作者外键冲突

#### 当前问题

`articles.author_username` 为非空外键，默认禁止删除被引用用户；现有 `deleteUser()` 没有处理文章，所以删除写过文章的用户会失败。

#### 推荐方案

保留文章，允许用户注销：

1. 新迁移把 `author_username` 调整为可空，并使用 `ON DELETE SET NULL`。
2. 页面在作者为空时显示“已注销用户”。
3. 用户删除后，文章只能由管理员管理。
4. 如果业务必须保留作者名，可额外增加不参与权限判断的作者展示快照字段。

不建议级联删除文章，因为删除用户不应意外删除其公开知识内容。

#### 验收标准

- 删除写过文章或评论的用户不会触发外键错误。
- 删除用户不会自动删除文章。
- 文章仍能正常公开阅读，作者显示符合产品规则。

---

### P1-4 加固链接导入的 SSRF 防护

#### 当前问题

当前只按 URL 主机字符串排除部分 IPv4，仍缺少：

- DNS 解析后的真实 IP 检查。
- IPv6 回环、内网、链路本地地址检查。
- DNS 重绑定防护。
- 响应体大小和内容类型限制。
- 外部服务和本地回退的一致安全策略。

#### 执行建议

1. 只允许 `http`、`https`。
2. 默认只允许 80、443 端口，其他端口明确拒绝。
3. 请求前使用 DNS 解析全部地址，并拒绝：

   - IPv4 回环、私网、链路本地、保留地址。
   - IPv6 `::1`、`fc00::/7`、`fe80::/10` 等非公网地址。

4. 如果将来允许自动重定向，每次跳转都必须重新验证目标。
5. 设置连接、响应和总耗时超时。
6. 限制响应体最大字节数，超限立即终止。
7. 仅接受适合正文提取的内容类型。
8. 不在错误响应中返回底层网络或代理敏感信息。
9. 增加 DNS 指向内网、IPv6 内网、超大响应、超时等测试。

#### 验收标准

- 无法通过域名解析访问数据库、Redis、云元数据地址或本机服务。
- 超大响应不会被完整读入内存。
- 外部抓取超时后能及时释放连接。

### P1-5 禁止日志输出代理凭据

#### 当前问题

`fetchWithProxy()` 会原样打印 `HTTPS_PROXY` 或 `HTTP_PROXY`。代理 URL 可能包含用户名、密码或 Token。

#### 执行建议

1. 删除代理环境变量原文日志。
2. 如确需诊断，只记录：

   ```text
   proxy_enabled=true
   ```

3. 目标 URL 日志只保留域名，必要时对完整路径和查询参数脱敏。
4. 检查历史日志是否已经包含敏感代理地址；如包含，清理日志并轮换相关凭据。

#### 验收标准

- 代码、控制台和结构化日志均不出现完整代理地址或凭据。

---

### P1-6 修复评论限流的 IP 获取和多进程失效问题

#### 当前问题

- 代码直接信任 `X-Forwarded-For`，绕过了应用的 `trust proxy` 安全配置，用户可以伪造请求头绕过限流。
- 限流数据保存在进程内 `Map`，重启即丢失，多进程之间不共享。
- 当前注释称“匿名评论限流”，但评论接口实际要求登录，规则描述不一致。

#### 执行建议

1. 只使用 Express 处理后的 `req.ip`，让 `trust proxy` 决定是否信任代理头。
2. 优先按登录用户名 + 文章 ID 限流，IP 作为辅助维度。
3. 使用项目已有 Redis 保存短期限流计数，设置自动过期。
4. 明确规则，例如同一用户对同一文章 5 分钟最多 3 条。
5. 删除或修正“匿名评论”的错误注释。

#### 验收标准

- 伪造 `X-Forwarded-For` 不能绕过限流。
- 多进程和服务重启不会立即清空有效限流。
- 返回 429 时包含明确但不过度暴露内部规则的提示。

## 五、P2：结构和数据质量优化

### P2-1 统一文章单一数据源

#### 当前问题

文章同时保存 `content` 和由前端提交的 `html_content`，但读取时主要使用 Markdown。两个字段可能漂移，而且服务端不能信任前端生成的 HTML。

#### 执行建议

- 推荐以 Markdown `content` 为唯一权威来源。
- `html_content` 如无实际用途应逐步停用；不要在本次安全修复中直接删除旧列。
- 如果未来需要渲染缓存，应由服务端从 Markdown 生成、净化并带版本号保存，不能由前端直接提交。
- `summary` 建议由服务端根据正文生成，避免被客户端伪造或超长写入。
- `slug` 当前未实际使用：要么实现稳定文章地址，要么标记为暂不使用，避免形成半成品逻辑。

---

### P2-2 增加输入长度和格式限制

建议先按当前小站规模采用简单上限，具体值可在实现前确认：

| 字段 | 建议上限 |
|---|---:|
| 文章标题 | 255 字符 |
| 摘要 | 500 字符 |
| 分类名称 | 100 字符 |
| 评论昵称 | 50 字符 |
| 评论正文 | 2,000 字符 |
| 导入 URL | 2,048 字符 |
| Markdown 正文 | 2～5MB |
| 单张图片 | 5MB |

要求：

- 前端提示只用于体验，后端必须再次验证。
- 超限返回 400 或 413，不能依赖数据库报错后返回 500。
- 不把数据库错误详情直接返回给普通用户。

---

### P2-3 加固文件导入

1. 同时校验扩展名、MIME 类型和必要的文件特征。
2. DOCX 必须限制解压后的正文体积，防止小体积压缩包解出超大内容。
3. 解析完成后限制最终 Markdown 长度。
4. 文件名只用于展示和标题建议，不参与服务器路径拼接。
5. Mammoth 输出视为不可信内容；转为 Markdown 后仍走统一安全渲染。
6. 对解析超时、格式损坏和内存上限提供明确错误。

---

### P2-4 调整图片存储方案

#### 当前问题

编辑器把图片直接转成 Base64 写入 Markdown，导致：

- 数据库体积快速增长。
- 单篇文章响应变大。
- 图片无法独立缓存、去重和清理。
- 数据库备份和迁移成本增加。

#### 分阶段建议

短期：

- 限制图片类型、单图大小和单篇总图片大小。
- 禁止 SVG 等可执行内容格式，除非经过专门净化。

长期：

- 增加受控图片上传接口。
- 文件保存到明确的静态资源目录或对象存储。
- 数据库保存资源元数据，文章只保存图片 URL。
- 删除文章时通过引用关系清理孤立图片。

---

### P2-5 完善数据库约束

通过新的版本化迁移逐步增加：

- `articles.status`：`NOT NULL` 和 `CHECK (status IN ('draft','published'))`。
- `articles.view_count`：`NOT NULL DEFAULT 0` 和非负约束。
- `article_comments.article_id`：`NOT NULL`。
- `article_comments.author_username`：登录用户关联。
- 分类名称空字符串限制。
- 防止分类把自己设为父级。
- 防止分类父子关系形成循环。
- 根据产品规则防止同级分类重名。

迁移必须先检查和修正历史异常数据，再增加严格约束。

---

### P2-6 默认分类改为迁移初始化

#### 当前问题

公开读取分类的 GET 请求会在数据库为空时写入默认分类。并发首次请求可能重复创建分类，读取接口也产生了隐藏副作用。

#### 执行建议

- 将默认分类种子放入新迁移或明确的初始化函数。
- 使用唯一约束和幂等插入。
- `GET /categories` 只负责读取，不写数据库。

---

### P2-7 完善阅读量逻辑

#### 当前问题

- `/view` 可以被无限调用，任何文章 ID 都可能被刷阅读量。
- 公开分享页当前没有增加阅读量。
- 草稿也可能被错误增加阅读量。

#### 执行建议

1. 仅已发布文章允许计数。
2. 公开分享页和站内阅读页使用同一计数接口。
3. 使用 Redis 按文章 + 会话/用户/IP 做短期去重。
4. 不要求绝对精确，但要避免刷新一次加一次和脚本无限刷。
5. 文章不存在时返回 404，不返回成功。

---

### P2-8 完善接口错误处理

当前前台和后台部分删除、发布操作未检查 `response.ok`，即使后端返回 403 或 500，页面仍会提示“已删除”或“已发布”。

要求：

- 所有写请求统一检查 HTTP 状态。
- 只在后端确认成功后显示成功提示。
- 401 提示登录，403 提示无权限，404 提示目标不存在。
- 网络错误和业务错误分开提示。
- 不向用户展示数据库、文件路径或代理内部错误。

---

### P2-9 增加操作审计

后台管理已经有审计日志，普通作者的重要操作也建议记录：

- 文章新建、发布、撤回、删除。
- 分类新建、改名、删除。
- 链接和文件导入结果。
- 管理员修改写权限。
- 管理员删除文章和评论。

日志只记录用户、对象 ID、动作、结果和时间；不记录完整文章正文、评论正文、代理地址或敏感 URL 参数。

## 六、P3：规模增长后再做

### P3-1 列表分页

当前普通文章列表固定最多 200 篇，评论详情一次加载全部评论。数据增长后建议：

- 文章接口统一支持 `limit`、`offset` 或游标分页。
- 评论先分页加载一级评论，再按需加载回复。
- 后台总数查询与状态筛选使用一致的 WHERE 条件。

### P3-2 数据库索引

数据量增长后评估增加：

- `articles(status, published_at DESC)`
- `articles(author_username, status, updated_at DESC)`
- `articles(category_id, status, published_at DESC)`

标题模糊搜索数据量较大时再考虑 PostgreSQL `pg_trgm`，当前小规模无需提前引入。

### P3-3 分类树能力

- 点击父分类是否包含所有子分类文章，需要明确产品规则。
- 编辑器分类下拉框应支持并缩进展示子分类。
- 后端必须防止分类循环。
- 分类删除前提示受影响文章数量。

### P3-4 最新文章缓存

当前规模可以直接查数据库。确认查询成为热点后，再使用 Redis 做 30～60 秒短缓存，并在发布、撤回、删除时主动失效；不要提前增加复杂缓存。

## 七、第三方工具专项建议

### 7.1 Vditor

当前检测到的版本为 3.11.2，整个本地目录约 42.37MB、1056 个文件，其中约一半为未使用的重复源码、类型声明和非 `dist` 文件。

执行建议：

1. 使用 npm 正式安装并锁定版本。
2. 只发布运行需要的 `dist` 文件。
3. 保留 Vditor 及其子依赖的 LICENSE。
4. 在项目文档记录版本、来源和同步方式。
5. 升级前执行编辑、预览、代码块、表格、公式、图片和 XSS 回归测试。

> 版本与同步方式（2026-07-26 落地）：固定版本 **3.11.2**；因 `npm install` 受锁文件内腾讯云镜像地址与网络环境限制无法稳定拉取，改为把已核对的 `public/vendor/vditor`（仅浏览器加载的静态资源，服务端 `require` 不依赖它）直接纳入 git 跟踪，随代码走现有 git 部署流程下发，并从 `package.json` 移除该依赖，`package-lock.json` 保持不含 vditor。升级时重新核对 `dist` 文件与 LICENSE 后提交。

### 7.2 DOMPurify

- 项目已有 DOMPurify，知识分享模块应直接复用。
- 主站和公开分享页必须加载同一版本。
- 不再维护另一套手写 HTML 过滤器。

### 7.3 Jina AI Reader

- 链接会被发送给第三方服务，应在界面或文档中说明。
- 做成可配置开关；第三方不可用时允许安全回退。
- 记录成功率和耗时，不记录完整敏感 URL。
- 外部返回内容必须继续按不可信文本处理。
- 不把 Jina 当作 SSRF 防护替代品，本地回退仍需独立校验目标地址。

### 7.4 Readability、JSDOM、Turndown、Mammoth

- 全部作为正式运行依赖锁定版本。
- 对网页 HTML、DOCX 输出继续执行长度限制和安全净化。
- 定期执行 `npm audit --audit-level=high`。
- 不直接依赖其他包间接带入的 `iconv-lite` 等模块。

## 八、自动测试与 CI 补充

### 8.1 接入统一测试入口

当前 `test-knowledge-extend.js` 不在 `server/test/*.test.js` 中，也没有被 `npm run test:all` 自动发现。

建议：

- 将知识分享测试整理为 `server/test/knowledge.test.js`。
- 使用测试数据库和独立测试用户。
- 使用 `try/finally` 清理测试文章、评论和用户，失败时也不能残留脏数据。
- 避免依赖人工提前启动的固定 `localhost:3000` 服务。

### 8.2 必测场景

#### 权限

- 游客只能读取已发布文章。
- 普通登录用户看不到任何草稿。
- 写作者只能管理自己的文章。
- 管理员可以管理全部文章。
- 用户只能删除自己的评论。
- 管理员可以删除全部评论。

#### 安全

- Markdown XSS 载荷被净化。
- DNS 指向内网的 URL 被拒绝。
- IPv6 内网 URL 被拒绝。
- 超大网页、正文、评论和文件被拒绝。
- 伪造 `X-Forwarded-For` 不能绕过限流。
- 日志不包含代理凭据。

#### 数据库

- 空库可以完整执行迁移。
- 重复执行迁移保持幂等。
- 删除写过文章、评论的用户不报外键错误。
- 删除文章级联删除评论。
- 删除分类后文章按设计变为未分类。
- 分类循环和非法状态被拒绝。

#### 功能

- 首页最新文章只请求一次。
- 编辑已发布文章不改变发布时间。
- 分享页能正确计入去重后的阅读量。
- 后端失败时前端不显示成功。
- 文件和链接导入失败不会覆盖编辑器原有内容。

### 8.3 CI 增加的门禁

1. 干净 `npm ci`。
2. 知识分享路由加载冒烟测试。
3. 知识分享权限和 XSS 自动测试。
4. `npm audit --audit-level=high`。
5. 检查所有 `require()` 的直接依赖是否出现在 `package.json`。
