# 数据层 SQL 可执行性验收（2026-10-30）

一句话结论：数据层 1090 条写死的 SQL 里，987 条能在真实库结构上被数据库解析，其中 970 条通过；**17 条解析失败，全部是引用 migration008 已删除旧表的历史写入路径**；另有 1 条潜伏的类型错配在本次修复。验收命令 `npm.cmd run acceptance:repo-sql`，测试 `server/test/repository-sql-coverage.test.js`（11 项，连库）。

## 1. 为什么单独做这件事

分层静态门禁回答的是「代码放在哪一层、有没有越界」，回答不了「这条 SQL 数据库能不能执行」。两者可以同时成立与不成立：

- 2026-10-30 发现：补「持仓基准快照」的 INSERT 自 0.9.1.2 上线起从未成功执行——`daily_prices.date` 是 TEXT 列却写成 `d.date::text=$3`，与同一语句里的 `$3::date` 争抢参数类型（PG 报「操作符不存在: text = date」），`round(double precision, int)` 也不存在。当时的分层扫描是 505 文件、越界/待登记/解析失败 0/0/0，全绿。
- 那次只覆盖了一条链路（导入旅程），方案第 5 节留着「更广范围的仓储 SQL 可执行性仍未系统覆盖」。本文件交付的就是这个覆盖。

## 2. 方法

`PREPARE <名称> AS <SQL>` 只让数据库做语法、名称解析和类型推断，**不产生行、不写数据、不需要真实参数值**，因此可以在隔离库上安全地逐条跑。

- 扫描范围：`server/repositories/`（84 个文件）+ `server/db/`（14 个文件），共 86 个文件。
- 提取规则：`.query(` 后面的引号字面量，且内容以 `select/insert/update/delete/with/values` 开头。
  - 还原 JS 转义（`\'` → `'`、`\\` → `\`），否则 PG 会报「语法错误在 "\" 或附近」这类假失败；
  - `query(` 与 SQL 之间夹注释也要能穿透，否则加一行注释就等于这条 SQL 免检（实测踩到过）；
  - 模板插值 `${...}` 与「字面量后紧跟 `+`」的拼接一律记为动态、不参与校验，单独统计。
- 隔离要求：脚本拒绝在库名不含 `test/ci/accept` 的库上运行，避免误连业务库。
- 已知失败清单：`governance/repository-sql-known-failures.json`。规则是**清单必须与事实一致**——出现未登记失败算回归（红），登记了但本次通过算清单过期（也红，要求删登记）。

## 4. 发现

### 4.1 已修：一条潜伏的类型错配

`server/db/accounts.js` 的 `saveAccountData` 里：

```sql
DELETE FROM nav_history WHERE username=$1 AND account_name=$2 AND NOT (date = ANY($3::date[]))
```

`nav_history.date` 是 **TEXT** 列，`date = ANY($3::date[])` 变成 `text = date`，PG 没有这个操作符。它藏在 `if (lockedDates.length)` 分支里——只有存在「锁定净值」记录时才走到。当前生产 `is_locked=true` 记录为 0 条，所以一直没炸，属于典型的「等哪天开始锁净值就炸」。已改为 `$3::text[]`。

### 4.2 已登记未修：17 条引用已删除的旧表

全部错误码 `42P01`（关系不存在），集中在两个文件，指向 migration008 明确 `DROP` 的 7 张表（`stock_daily_valuations`、`stock_dividends`、`stock_forecasts`、`stock_events`、`stock_data_sync_state`、`stock_analysis_stocks`、`stock_analysis_snapshots`）。业务库实测这 7 张表均不存在。

| 文件 | 条数 | 所在函数 | 调用方核查 |
|---|---|---|---|
| `server/repositories/stockAnalysisRepository.js` | 6 | `saveMetadata`、`saveAux`、`saveValuations`、`setSyncState`、`latestDividendEndDate`、`latestForecastAnnDate` | 前 4 个只在 `services/stockAnalysis.js` 里被包一层，**这四个包装函数没有出现在该模块的 `module.exports` 里**，也无任何路由/任务调用；后 2 个同样无外部调用 |
| `server/repositories/stockProjectionRepository.js` | 11 | `syncRawRecords`、`syncMarket`(×4)、`syncFundamentals`(×2)、`syncEvents`、`syncCursors`、`listLegacyStockCodes`、`readLegacySnapshot` | 全部只在 `financialDataArchitecture.syncStockToArchitecture` 里使用，而该函数**除测试文件里的字符串名之外没有任何引用** |

结论：这 17 条不在活跃调用链上，属历史迁移（股票分析 → 标准化层）半成品留下的死路径，不是用户可感知故障——这也解释了为什么一直没人发现。**本次不删**：删代码要连带清理导出面与测试，改指新表则要动股票估值/财务写入的口径，都属独立批次，需要单独立项和样本。

风险提示：死代码不会自己消失。如果以后有人「复用」`syncStockToArchitecture` 或补回 `saveValuations` 的调用，这条链会立刻在事务里抛错并整批回滚。

## 5. 覆盖边界（明确没做到的）

- **103 条动态拼接**（模板插值 97、多段拼接 6）无法静态还原，未校验。它们在报告里逐条列出（文件、行、函数、原因），可人工抽查。
- **helper 拼装的 SQL 不在扫描范围**：如 `db/accounts.js` 的 `bulkInsert(client, table, columns, rows, ..., onConflict)`、各类 `buildXxxSql()`，SQL 由运行期拼接，静态文本里没有完整语句。
- `scripts/`、`ipo-report/`、迁移文件里的 SQL 未纳入（迁移有独立执行与回滚路径）。
- **PREPARE 只证明「能解析」**：不证明语义正确、索引命中、结果符合业务口径。金融口径正确性仍由各域专项回归负责。

## 6. 怎么用

```bash
# 需要本地 PostgreSQL（用隔离库；不存在的库会被拒绝）
PGPREPAREDB=portfolio_test npm.cmd run acceptance:repo-sql
# 想要机器可读结果
PGPREPAREDB=portfolio_test npm.cmd run acceptance:repo-sql -- --json _probe/repo-sql-report.json
```

- 新增 SQL 写错（列名、类型、表名）→ 命令非零退出，并在输出里点明 `文件:行 [错误码] 函数`。
- 修好某条已登记的失败 → 命令会报「已登记但本次通过」，要求同步删除 `governance/repository-sql-known-failures.json` 里对应条目；测试同样会红，避免清单变成摆设。
- 不允许为了让命令变绿而往清单里加条目：清单里每条都要写 `status`、`reason` 和发现日期。

## 7. 验收与反例

- 测试：`server/test/repository-sql-coverage.test.js`，11 项——7 项提取器纯函数（模板串、`\'` 转义、`''`、插值、拼接、非 SQL 文本、白名单比对），3 项连库断言（无未登记失败、清单与事实一致、可校验语句数下限），1 项真实源码规模下限。

- 无可用 PostgreSQL 时打印 `[SKIP]`，不冒充通过（沿用 `run-all.js` 的跳过协议）。
