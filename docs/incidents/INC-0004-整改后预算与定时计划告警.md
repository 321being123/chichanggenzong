# INC-0004：整改后预算与定时计划告警

状态：跟踪中
日期：2026-09-02

## 现象与影响

2026-09-02 早间生产出现大量后台告警。查询生产 `ops.alert_notifications` 的开放记录后，10 条记录实际收敛为约 6 个计划实例问题，主要集中在 IPO 依赖、下修动机输入、强赎公告、公告历史、可转债主链和安全评分；不是 10 个独立的上游故障。

## 根因链路

Tushare/CNInfo/港交所接口 → PostgreSQL 外部预算与熔断 → Worker 持久化计划队列 → 任务子进程 → 任务告警/后台汇总。

1. 补跑 2026-09-01 数据时，Python Guard 原来用 `JOB_BUSINESS_DATE` 作为预算日键，导致 2026-09-01 的历史预算记录持续污染 2026-09-02 的补跑；业务日期和请求发生日期被错误混用。
2. IPO Python 子进程只返回文本错误，Node 没有稳定拿到 `BUDGET_WAIT`、`JOB_BUDGET_EXCEEDED` 和 `recoverAt`；同时业务错误会继续尝试下一 Python 候选解释器，造成同一失败再次调用。
3. 任务单次上限和每日预算计入值没有分开表达。部分任务实际需要多个市场、分页或关键词请求，却仍沿用 2～4 次的单次上限；达到任务批次边界后又被通用重试当成可重试错误，重复消耗每日预算。
4. 可转债安全评分排在共享主链之前（原 06:30，而主链 08:00），依赖数据尚未发布，形成确定性失败；不是安全评分公式或上游接口本身故障。
5. 同一计划实例的 `failure_warning` 与 `failure`、`late` 与 `dependency_blocked` 同时计入开放告警，放大了告警数量。

## 直接原因、根本原因与保护机制失效原因

- Tushare 的接口权限/额度是按接口区分的：生产当时 `top10_cb_holders`、`cb_price_chg` 等接口存在权限限制，`rt_min` 等接口也有单独频率规则；不能把一个接口的失败解释为整套 Tushare Token 都受限。
- 本次强赎与套利记录中的“达到本任务声明的外部请求上限”是本系统任务上限，不是 CNInfo/港交所返回的限流；公告历史和主链的部分失败则属于任务预算边界或既有熔断/权限状态。
- 原保护机制只在“单次进程”内计数，Node 与 Python 子进程间没有把累计调用数传递回下一次尝试；任务定义又把单次上限当成每日预算，导致保护策略和实际批量工作量不一致。
- 调度依赖虽已存在，但安全评分没有声明主链依赖，且执行时间早于主链，依赖门禁无法阻止确定性失败。

## 同类范围与核查结果

已核查生产开放告警、对应计划实例、最近运行记录、任务定义、Node/Python Guard、任务调度依赖和 Tushare 权限熔断状态。重点同类任务均已覆盖：

- IPO：核心同步、日报依赖和 Python 解释器候选链；
- Tushare：主备 Token、接口级熔断、日/分钟预算、跨进程计数；
- CNInfo/港交所：强赎、公告历史、套利的单次请求边界；
- 可转债：主链→安全评分→估值的早间依赖顺序；
- 告警：同一 `slot_id` 的预警/最终失败、逾期/依赖阻断归并。

## 修复与回归证据

已在代码中完成：

1. Python/Node 预算日统一使用请求实际发生的上海自然日；保留业务日期仅用于数据集锁和业务分区。
2. Node 将累计 `externalCallCount` 注入 Python 子进程；Python 结构化返回错误码、来源、接口、恢复时间和累计调用数。
3. `JOB_BUDGET_EXCEEDED` 识别为不可重试的批次边界；IPO 仅在解释器不存在（`ENOENT`）时切换候选解释器。
4. 为批量任务区分单次上限与每日预算计入值，矩阵从 `JOB_DEFINITIONS` 自动生成；单次上限按实际批量规模提高，整体每日计入仍为 72 次。
5. 安全评分调整为收盘日次日 08:30，并声明依赖 `convertible_bond_universe_refresh`；确保主链发布后再计算。
6. 开放告警查询归并同一计划实例的低级预警和下游重复告警。
7. 下修动机持有人/质押同步遇到本批次上限时保留游标、不记为单债失败，返回部分完成并等待下一批，不触发同一批次的无效重试。

验收要求：运行 `npm.cmd run check:knowledge`、`npm.cmd run check:data-architecture`、`npm.cmd run test:all`，并核对 `git diff --check`；本次仅完成本地代码和文档整改，尚未部署生产。

## 2026-09-02 生产复核与新增日期缺陷

生产已发布版本 `0.7.0.7`（提交 `2a4ca5d`），Web、Worker、健康检查定时器均 active/enabled，健康接口返回版本一致。发布后按授权补跑安全评分与被中断强赎公告：安全评分槽位 `397522` 成功生成快照47，来源日期和分区均为 `2026-09-01`；强赎公告槽位 `383588` 成功发现304条、匹配260条并发布252条。Tushare 当日请求预算仍为 100/100，未发现探测租约卡死。

安全评分主链行情分区实际已到 2026-09-01，但旧版 `bond_safety_refresh` 读取 PostgreSQL `DATE` 后直接 `toISOString()`，在上海时区把该日写成 2026-08-31，导致计划结果没有形成可确认水位并产生 `late`/`degraded` 告警。版本 `0.7.0.7` 已改为 SQL `trade_date::text` + `normalizeTradeDate`，补跑后水位已确认，相关告警已关闭。剩余3条开放告警均为 IPO/套利历史批次的预算顺延，保留等待后续自动窗口处理。

## 2026-09-02 受限额度专项复盘

生产只读核查显示，主 Tushare 当日 `100/100` 时仅形成 17 个分钟窗口、单窗口最高 16 次，未触及官方分钟速率；打新核心的 `new_share` 请求是在系统内部预算预检阶段被拦截，日报随后因依赖事实未成功而阻断。历史生产日最高实际主 Tushare 请求为 1397 次，说明 100 次内部日线明显过低；巨潮资讯历史最高为 345 次，原 300 次也存在正常增量被误拦截的风险。腾讯、港交所、汇率、上交所/深交所等来源近期未触及现有 2000 次日线。

本地版本 `0.7.0.12` 已将 Node/Python 默认保护线统一为：主、备用 Tushare 均为 450 次/分钟、5000 次/日；巨潮资讯 20 次/分钟、500 次/日；当前实际使用的腾讯行情不设置本系统分钟/日预算，仅保留上游异常处理，汇率、中债、港交所、公告/风控等其他经过 Guard 的来源仍使用通用 60 次/分钟、2000 次/日兜底。主、备 Tushare 的 450 次/分钟按官方 500 次/分钟保留 50 次/分钟余量，5000 次/日是按已观测峰值加两倍以上余量的内部止损线，不是官方日额度。任务单批上限仍按各任务实际批处理边界执行，IPO 核心 1 次、晚间补全 15 次、日报 0 次不变。
