## 打新域（本批最后完成）

`routes/ipo.js` 的 18 处巨型 SELECT（含多段 CTE、窗口函数）与 **9 个 SQL 片段生成器**（`hkOfferPhaseSql`／`hkIpoShortNameJoinSql`／`hkSignalJoinSql`／`hkSignalKindSql`／`hkSignalFreshnessSql`／`hkSignalHistoryJoinSql`／`stockHistoryStageSql`／`stockFieldStatusSql`）整段迁入 `server/repositories/ipoRepository.js`。

做法与收益：SQL 用脚本按括号匹配**逐字搬移**（零抄写风险），位置参数改写为具名对象；仓储返回 pg `result` 以保持 `rows`/`rowCount` 消费方式不变；`hkOfferPhaseSql`、`stockFieldStatusSql` 仍从路由转发导出，外部契约不变。

**过程中暴露并修掉两个真实缺陷**：①片段生成器漏搬导致 `/history` 直接 500（`stockHistoryStageSql is not defined`）——说明"仓储引用未搬的函数"只会在运行时爆；②路由里 `const outcome` 写在 `try` 块内导致块外 `ReferenceError`（账户域净值导入），已提到外层 `let`。

受影响的 6 个测试全部按方案 6.1 改为"路由＋仓储"合并源码检查（`ipo-api`、`ipo-history-sync`、`ipo-instrument-identity`、`convertible-bond-revision-frontend`），断言一条没删。

其余 2 处真实事务（`knowledge.js` 分类移动、文章排序）保留原写法：两者都在 `FOR UPDATE` 锁内做多步校验后提前 `ROLLBACK` 并返回 404/400/409，改成统一封装要把提前返回改为抛错，收益低于改坏排序的风险。已在本卡登记为待评估。

## 已确认事实与顺带修复

- **净值导入事务改造引入过一次真实回归**：`const outcome` 误写在 `try` 块内导致块外 `ReferenceError`，`nav-authority-regression` 首轮失败。已修（提到块外 `let`），复跑通过。教训：块级作用域变量在事务封装改造时必须提到外层。
- 市场周期域原代码用模板字符串拼接表名与列名（`SELECT MAX(${calculatedColumn}) FROM ${metricTable}`），已换成 4 条固定 SQL 常量按 metric 分派，行为等价且不再拼接标识符。
- 账户域 4 处 `pool.connect()` 全部改为 `withTransaction`；净值导入的幂等重试分支改为“返回结果对象→事务外响应”，提交语义与原来一致（原来在幂等分支单独 `COMMIT` 后返回）。
- 知识后台与前台共用同一仓储，避免了文章/评论两套 SQL 各写一遍。
