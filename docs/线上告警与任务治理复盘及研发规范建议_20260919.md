# 告警与任务治理规则比对及门禁补强提案

> 复盘日期：2026-09-19  
> 适用范围：后台任务、外部数据同步、数据分区、告警恢复和生产补跑  
> 文档性质：规则比对与门禁提案；不是新增现役规范
> 当前状态：事实已核验，提案待团队评审；暂不创建 ADR-0003 或修改现役规范

本提案保留本轮复盘事实，但事实详情以 [`INC-0026`](incidents/INC-0026-后台补档任务阻塞与完成判定失真.md) 为唯一权威来源：可转债假缺口见 `INC-0026:125`，生产补跑与依赖阻塞恢复见 `INC-0026:129`。本文只负责把现役规则与实现缺口对照出来，并列出需要新增的自动门禁。

## 评审采纳结论

本次评审意见**有条件采纳**：保留当前文档结构，不直接升级为 `ADR-0003`；新增“契约声明—运行时消费”闭环、原始配置与默认值边界、告警证据注册表、来源告警核对与自动恢复的区分，以及分阶段上线门禁。评审意见中的个别代码定位需按当前仓库校正：当前未找到 `parseDatasetDependencies()`，但 `datasetDependencyState()` 确实没有消费 `partitionDatePolicy`；当前来源告警已有带新探测成功和熔断关闭条件的自动恢复入口，不能表述成“完全没有自动关闭”。

## 一、结论摘要

这几天处理的不是单个 Bug，而是三类边界问题叠加：

1. 任务计算的“目标对象集合”不准确，制造了虚假数据缺口。
2. 任务已经成功，但告警恢复证据链不完整或被错误拦截。
3. 历史公告重建在身份、来源并发、文本分类和断点续跑上缺少统一边界。

本轮最终结果：

- 可转债行情三日分区恢复为 `311/311`、`310/310`、`310/310`，缺口队列归零。
- 下游安全评分和估值任务均成功完成。
- 本链路相关数据质量、依赖阻塞和超时告警均按证据收敛。
- 全量测试 `135` 项通过、`0` 失败。
- 线上版本为 `0.8.1.70`，生产代码提交为 `c46a79b`；其后 `3997b7b`、`ac81467` 是纯文档提交，不代表生产树版本。

## 二、问题复盘

### 2.1 可转债行情虚假缺口

**现象**

2026-09-16 至 2026-09-18 连续出现 `bond_daily` 部分发布，旧记录显示缺少约 140 只可转债行情。

**根因**

- Tushare `cb_basic` 使用 `YYYYMMDD`，调度器目标日使用 `YYYY-MM-DD`，旧代码直接比较字符串。
- 允许上市日期为空，导致没有明确上市事实的债券进入目标集合。
- 历史退市、到期、停止转股的债券未被正确排除。
- 定向/私募债券没有沿用公开发行过滤规则。

**只读核查证据**

- 原缺口中有 130 只历史退市/停止状态债券、7 只定向债、3 只未上市债。
- 公开在市目标集合为 310 只。
- `cb_daily` 对这 310 只全部有有效价格，实际不是行情源缺失。

**修复**

- 统一生命周期日期格式，强制要求目标日前已有上市事实。
- 统一排除退市、到期、停止转股、定向和私募债券。
- `server/services/convertibleBondAnalysis.js` 复用 `bondSafetyTushare.isActiveBond()` / `filterPublicBonds()`；回归覆盖带横线目标日、空上市日和定向债过滤。

### 2.2 任务成功后告警无法自动恢复

**现象**

行情、估值和安全评分已经成功，但历史阻塞告警仍保持活动状态。

**根因**

- 告警作用域曾混用槽位业务日和实际数据分区日。
- 港股 IPO `server/services/hkexIpo.js` 的四个成功收尾分支曾向非空字段 `ops.ingestion_runs.error_message` 写入 `NULL`，导致成功被误判为失败。
- 历史槽位请求模式与实际运行模式不一致，恢复证据因此被拒绝。
- `dependency_blocked` 告警在外层校验中被提前拒绝，未进入已有的严格恢复证据层。

**修复原则**

告警不能只看槽位状态，必须同时核对：

```text
运行结果 → 失败数据集 → 数据分区 → 质量状态 → 水位日期 → 任务依赖
```

只有证据完整时才允许恢复。数据质量告警仍必须由对应数据集分区证据关闭，不能由普通任务成功掩盖。

### 2.3 历史强赎公告重建边界不足

**主要问题**

- 旧档案保存申购简称，和正式债券简称不一致。
- 同一正股存在多只历史转债时，公告无法唯一匹配。
- 纯下修公告被误归类为强赎公告。
- 公告列表和 PDF 正文共用并发槽位，造成批量 `BUDGET_WAIT`。
- 日期排版、重复更正公告、法律意见书等特殊文本导致解析门禁阻断。

**修复方向**

- 按正股、官方债券身份和公告日生命周期做唯一匹配。
- 无法唯一匹配时继续阻断，不默认选择第一条。
- 公告列表和正文使用独立并发额度。
- 保存检查点，失败只续跑未完成对象。
- 只有正文证据和业务字段都完整时，才替换历史投影和推进水位。

## 三、反复出现的共同原因

这些问题表面上分别属于行情、告警和公告解析，实际都属于同一种缺陷：

> 现役规则已经写好，但实现只覆盖了部分分支；同一事实又在多个模块中各自实现了一遍。

具体表现为：

- 规则存在、实现分支漏接：0.8.1.70 的 `dependency_blocked` 先被 `verifyAlertScope()` 外层拒绝，未进入已有的 `verifySlotRecoveryEvidence()`；0.8.1.57 曾把槽位业务日误当数据分区日；0.8.1.58 曾因历史槽位残留 `mode=core` 与实际 `enrichment` 不一致而拒绝恢复。
- 日期在不同模块使用不同格式和不同含义。
- 目标对象集合没有独立的权威口径。
- 任务成功状态和数据真正发布状态没有完全绑定。
- 告警发送逻辑和告警恢复逻辑没有共用同一证据服务。
- 外部接口限制、重试和断点规则散落在任务代码中。
- 回归测试覆盖了正常样例，但没有形成规则条款到全部实现分支的对照审计。

### 4.1 项目实际术语对照

- 统一恢复证据服务：`server/services/jobRecoveryEvidence.js` 的 `verifySlotRecoveryEvidence()`；告警入口是 `server/services/jobAlertMailer.js` 的 `verifyAlertScope()`。
- 日期边界：`expectedDataDate()`、任务结果的 `targetTradeDate`、`ops.dataset_partitions.partition_key`（分区日）与 `scope_key`。
- 告警作用域：`ops.alert_notifications.scope_type/scope_key`；数据质量使用 `data_quality`，依赖阻塞使用 `dependency_blocked`。
- 来源告警：必须按数据库实际关闭的 `source:*` 作用域核对；通配熔断不能自动当作恢复证据（`AGENTS.md:21`）。

### 4.2 新发现：契约字段必须形成运行时消费闭环

评审指出的 `partitionDatePolicy` 缺口与当前代码核对后成立，但准确表述如下：

- `server/services/jobDefinitions.js` 的 `JOB_DEFINITION_SOURCE` 已在部分 `datasetDependencies` 中声明 `partitionDatePolicy: 'business_date'`，最终定义还会与 `JOB_CONTRACTS` 通过 `DEFAULT_JOB_OPTIONS` 合并。
- `server/services/jobScheduleSlots.js` 的 `datasetDependencyState()` 当前始终把 `normalizeBusinessDate(slot.business_date)` 作为分区日查询条件，没有读取 `requirement.partitionDatePolicy`。因此契约表面支持分区日期策略，运行时实际等价于“只按槽位业务日校验”。当前存量声明大多恰好使用业务日，不能据此断言线上已有错误，但属于真实的静默失效风险。
- 当前仓库没有 `parseDatasetDependencies()`、`scopeResolver` 或 `completenessRule` 的现成实现；它们只能作为后续契约设计候选，不能写成已存在能力。
- `server/services/jobScheduleSlots.js` 的 `expectedDataDate()` 对 `dataDatePolicy: 'none'`、`'same_day'`、`'latest_available'`（IPO 特殊任务除外）都会返回规范化后的槽位业务日；`none` 当前更接近“使用槽位业务日、不做交易日偏移”，不是“完全没有日期证据要求”。

因此，契约门禁不能只检查字段是否填写，还必须检查：

1. 字段有合法值校验和唯一的运行时消费入口。
2. 每个字段至少有一个非默认值测试；删除或绕过消费逻辑时测试必须失败。
3. 禁止出现“解析并保存，但运行时从未读取”的字段。
4. `dataDatePolicy`、`partitionDatePolicy`、`producesDatasets`、`datasetDependencies` 首批纳入闭环审计；`scopeResolver`、`completenessRule` 等待正式契约设计后再纳入。

### 4.3 来源告警：核对与自动恢复分开治理

- **收敛结果核对**：必须按数据库实际关闭的 `source:*` 作用域核对；不能用空查询、通配作用域或熔断器总状态替代，并保留仍打开的权限、额度和历史故障告警。
- **当前实现边界**：`verifyAlertScope()` 对来源端点会检查熔断记录全部关闭，并要求 `last_success_at` 晚于告警的 `last_seen_at`；`reconcileRecoveredSourceAlerts()` 会在该证据成立时执行自动收敛。因此不能把当前代码描述为“来源告警完全人工审核”。
- **后续增强条件**：若要提高来源告警自动恢复的稳定性，还需明确身份、权限和请求参数一致性、冷却期、连续成功次数及证据版本；“熔断已关闭”本身不能单独作为恢复证据。

## 五、真正需要补齐的门禁与优先级

### P0：立即补齐

1. **原始任务契约完整性与单一事实来源门禁**：在应用 `DEFAULT_JOB_OPTIONS` 之前检查 `JOB_DEFINITION_SOURCE` 和 `JOB_CONTRACTS`；区分遗漏字段与显式空数组，明确两层配置的权威边界，检查重复、冲突、非法枚举、数据集注册和跨字段不变量。
2. **契约字段运行时消费门禁**：首先修复或明确 `partitionDatePolicy` 的消费路径；每个契约字段都必须有唯一消费者和非默认值测试，“已解析但未读取”直接失败。
3. **告警证据策略注册表**：登记作用域、验证器、是否允许自动收敛、分区/质量/依赖/连续成功要求、来源探测新鲜度和证据版本；未知告警类型不得自动关闭，但必须允许创建并保留。
4. **首批负向测试**：删除原始 `dataDatePolicy` 后，即使有默认值也必须失败；两层契约声明冲突必须失败；非默认 `partitionDatePolicy` 必须选择正确分区日；未知 `alert_type` 不得自动收敛；通配熔断关闭不得恢复具体 `source:*` 告警。

### P1：近期补齐

- 建立机器可读的“规则 ID → 实现符号 → 测试 → 责任人”追踪矩阵；不让脚本直接从 Markdown 自然语言推断实现是否存在。矩阵至少校验实现符号仍存在、测试进入全量入口、例外未过期，以及契约字段确实被消费。
- 明确 `dataDatePolicy: 'none'` 的真实语义；若继续表示槽位业务日，逐步迁移为更明确的 `slot_business_date` 或 `same_business_day`，兼容期保留旧别名，新任务不得继续使用歧义值。
- 增加来源告警的新成功探测、证据新鲜度、身份/参数一致性和连续成功模型；扩展现有任务契约、全局门禁和恢复证据测试，不另建平行测试体系。
- 增加日期策略 × 任务模式 × 告警类型 × 部分发布状态的参数化测试，并覆盖检查点、退避、无进展保护和 `BUDGET_WAIT` 续跑。
- 任务契约门禁分三阶段启用：阶段一只报告缺失、默认兜底、重复和冲突；阶段二只强制新增/修改任务，遗留任务走有责任人和到期日的白名单；阶段三存量补齐后全量阻断，例外到期自动失败。

### P2：持续改进

- 建立生产补跑结果的统一验收报表，把任务、分区、告警和恢复证据串成可查询链路。
- 对重复出现三次以上的事故，把散文规则升级为自动门禁；现有 `check:knowledge` 只负责知识路由和规则同步，不能冒充业务不变量门禁。

## 六、仍未收敛项与遗留风险

“告警收敛”不等于“所有告警清零”。以下状态必须按证据保留：

- CNINFO `topSearch` 历史 403 权限告警。
- Tushare 权限拒绝、额度耗尽或来源熔断告警。
- 任何没有对应数据集分区、来源成功探测或严格槽位证据的历史告警。

这些记录保留是为了区分“仍有外部风险”和“本轮已修复问题”，不是遗漏关闭。`recovery`、`worker_recovered` 等恢复通知保留为 `sent` 历史记录，也不应被误算成待处理告警。
