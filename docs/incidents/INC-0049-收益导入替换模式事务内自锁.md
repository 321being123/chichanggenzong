# INC-0049 收益导入「替换模式」事务内 DELETE 后自锁，请求永久挂起

状态：2026-11-02 本地已修并通过真实入口回归（未部署）。生产未复现记录，因为该路径一旦进请求就会挂到客户端超时，历史上很难拿到服务端证据。

## 1. 现象

`POST /api/nav/import`（`mode='replace'`，即「全量替换导入」）发出后请求不返回：浏览器一直转圈，服务端不报错、日志没有失败行，客户端最后超时。同一份数据用 `mode='merge'`（默认）导入则正常完成。

2026-11-02 N2 补验收证据时，在隔离测试库第一次跑 `replace` 就稳定复现；查 `pg_stat_activity` 能看到两条连接互相等待：

| 连接 | 状态 | 语句 |
|---|---|---|
| A | `idle in transaction` | `DELETE FROM nav_history WHERE username=$1 AND account_name=$2` |
| B | `active`，`wait_event=transactionid`，被 A 阻塞 | `INSERT INTO nav_history … ON CONFLICT … DO UPDATE` |

A 执行完 DELETE 后不在跑语句（在等 JS），B 在等 A 持有的行锁 —— 也就是**同一个进程的两条连接互相等待**，没有任何一方会超时释放。

## 2. 根因

`server/routes/accounts.js` 的导入事务里，`upsertImportedNav` 调用只传了参数数组、**没有传事务连接**，于是它用了仓储的默认参数 `client = pool`：

```js
// 修复前
await navImportRepository.upsertImportedNav(
  [username, ... , inputHash]
);   // ← 少了 client
```

而 `replace` 分支在同一事务里先执行了 `deleteAllNav`（持有 `nav_history` 行锁），紧接着的 INSERT 走另一条池连接，于是自己等自己。

`merge` 模式不执行 DELETE，所以不会卡住 —— 但**同一个漏参数在 merge 下是另一个问题**：nav 行的写入跑在事务之外，后续步骤一旦失败，事务回滚也回滚不掉已经写进去的 nav 行，正是 `accounts.js` 第 216 行注释声称已经修好的「提示失败但导入了一部分」。

## 3. 修复

同一处补上事务连接，两个问题一起消掉：

```js
await navImportRepository.upsertImportedNav(
  [username, ... , inputHash],
  client, // 必须沿用事务连接：走池连接会与本事务已持有的 nav_history 行锁互相等待
);
```

## 4. 同类核查（按 AGENTS 第 4 节）

把导入事务（`server/routes/accounts.js` 约 780—1030 行）与回滚事务里的**全部** `navImportRepository.*` 调用逐条核对：

`findImportBatch`、`listNavHistory`、`listPositionsForImport`、`listTradesForImport`、`readAccountHkRate`、`listFxRatesUntil`、`selectUnreferencedSnapshotBatches`、`insertImportBatch`、`deleteAllNav`、`upsertImportedNav`、`upsertAnchorDailyPrice`、`deletePositionSnapshotsByBatch`、`insertPositionSnapshot`、`deletePositionSnapshotsByIds`、`deleteLegacyNavRows`、`bumpNavVersion`。

除已修的 `upsertImportedNav` 外，其余都显式传了 `client`，**没有第二处同类问题**。事务外的 `accountsRepository.readAccountId`（第 31 行）在 `withTransaction` 之前执行，属只读且不在锁范围内，本次不动。

## 5. 回归证据

新增 `server/test/nav-import-replace.test.js`（真实 express 路由 + 真实隔离库，8 项）：

1. merge 导入两天 → 两行都记在 b1 名下；
2. replace 只导今天 → 昨天的行被删除、今天改为本次值、批次改为 b2（**修复前此步永久挂起**）；
3. replace 后被取代的 b1 快照仍保留（回滚要用）、b2 快照已落；
4. 回滚 b2 → 两行原样恢复且今天那行**重新指回 b1**（不能只恢复行不恢复批次引用）；
5. 回滚后 b2 快照被清、b1 仍可解析；
6. 重复回滚同一批次走幂等，行数不变；
7. 同一天连续 replace 两次不会让 nav 行累积，快照批次数有界；
8. 非法 replace（现金 > 总资产）在校验阶段就被拒绝，**不删除已有 nav 行**（不能先清空再报错）。

同时 `server/test/nav-import-snapshot-cleanup.test.js`（6 项，merge 路径）复跑通过，确认本次改动没有影响孤儿批次清理与基准行保护。

## 6. 未验边界
