## 1. 结论摘要

本次不是单纯的“80 条上限太小”，也不是 Tushare 数据不足，而是四类问题叠加：

1. 可转债任务负责 `2026-09-15`，正股补水却按机器当前日期计算最近 30 个交易日，把尚未收盘的 `2026-09-16` 也纳入校验。
2. 补水对象使用历史可转债档案和未及时收敛的 `listed` 状态，得到 936 只正股，而当前真实在市可转债约 310 只。
3. 单次最多处理 80 只后，任务把“本批未处理完”当成失败；自动重试又继承前一次外部调用数，后续尝试拿不到完整的新预算。
4. 多个任务存在“任务结果、数据分区、水位、待处理队列”互相覆盖的问题，可能出现真失败被标成功，或正常空跑被判失败。

因此，正确整改不是简单调大 80、600 或重试次数，而是同时修正目标日期、对象集合、续批方式、外部调用计数和完成判定。

## 2. 用户看到的两个数字分别代表什么

### 2.1 为什么是“最近 30 个交易日”

`server/services/convertibleBondAnalysis.js` 在按交易日批量补行情后，会再检查每只正股最近 30 个开市日是否仍有缺口。这个窗口用于：

- 防止 Tushare 按交易日批量返回时因行数或个别证券异常漏数；
- 支撑强赎观察、近期估值和短周期计算；
- 避免每次都按 500 个历史交易日逐股重拉。

所以“30 个交易日”本身是一个近期完整性检查窗口，不表示任务失败了 30 天，也不表示要拉 30 次接口。

真正的问题是窗口上界错了。当前 `backfillUnderlyingStockMarket()` 内部自行调用 `getRecentOpenDays(windowDays)`，没有使用编排器已经算好的目标交易日。2026-09-16 08:00 执行时，任务目标应是上一交易日 `2026-09-15`，但补水窗口可能包含 `2026-09-16`。当日尚未收盘，日线天然不存在，于是大量股票都被判为“缺口”。

整改后，30 日窗口仍可保留，但最后一天必须小于等于任务唯一目标交易日，所有子阶段都不得自行改用当前日期。

### 2.2 为什么有 800 多只股票，而上市可转债只有 300 多只

截图中的 `853` 不是完整对象数，而是“本轮先处理 80 只后仍剩余的数量”。生产只读核查结果为：

| 项目 | 数量 | 含义 |
|---|---:|---|
| 补水查询得到的正股集合 | 936 | 被现有 SQL 认定需要参与校验的不同正股 |
| 首次判定存在缺口 | 933 | 因日期和对象集合错误而进入补水队列 |
| 本轮处理上限 | 80 | `CONVERTIBLE_BOND_STOCK_REPAIR_LIMIT` 默认值 |
| 页面显示仍剩余 | 853 | `933 - 80` |
| 当前真实在市可转债 | 约 310 | 正确业务范围，且多只转债可能对应同一正股 |

现有补水 SQL 从 `fundamental.convertible_bond_profiles` 出发，以 `public.bond_unified.status='listed'` 作为主要生命周期条件。历史记录中存在长期未更新的上市状态，729 条历史档案的 `source_updated_at` 为空，旧债对应正股仍进入集合。

因此，936 不是“市场上有 936 只在市可转债正股”，而是历史档案、陈旧生命周期状态和当前对象混在一起后的错误集合。正确的正股集合应从目标交易日的有效可转债事实出发，再去重得到正股，不得只依赖一个可能陈旧的 `listed` 字段。

这说明问题不是所有补档任务都坏了，而是“对象集合大、分阶段、有限批次、可重试”的任务更容易触发同一类编排缺陷。

## 4. 根因链路

### 4.1 数据源到页面的完整链路

```text
任务计划实例给出业务日
  → Runner 启动业务任务
  → 业务子阶段自行重新计算日期/候选对象
  → 外部接口按错误对象集合调用
  → 成功结果部分入库，但剩余对象触发失败
  → result_summary 保存累计 externalCalls
  → 下一次尝试继承累计值，单次预算越来越少
  → 水位、数据分区或旧状态再次参与完成判定
  → 后台显示阻塞、重复失败，或出现未完整却成功的假象
```

### 4.2 直接原因

- `backfillUnderlyingStockMarket()` 没有接收任务目标交易日，内部日期与计划实例脱节。
- 正股集合只依赖档案和 `listed` 状态，没有以目标交易日有效行情事实收敛。
- 固定批次上限只做 `slice(0, 80)`，没有把“还有下一批”作为可续跑状态。
- `jobOrchestrator.js` 将槽位摘要中的累计 `externalCalls` 传入下一次尝试。
- `jobRunnerProcess.js` 用该累计值初始化 Guard；`externalCallGuard.js` 据此提前触发 `JOB_BUDGET_EXCEEDED`。
- 严格数据集发布、业务空跑和水位恢复各有自己的成功语义，缺少一个最终裁决顺序。

### 4.3 根本原因

系统已经具备持久化计划实例、任务定义、外部调用 Guard、数据分区和同步水位，但这些能力的职责没有完全分开：

- 计划实例负责的业务日，没有成为所有子阶段唯一日期；
- 单次尝试预算和同一槽位累计调用量共用一个数字；
- “批次未处理完”被当成业务失败，而不是正常续批；
- 水位只证明某个来源到达某日，却被用来替代整个任务的完整性；
- 历史候选没有明确终态或下次重试时间，会反复占据有限队列。

### 4.4 为什么之前修过仍会再次出现

2026-09-15 的强赎行情缺口修复解决了 SQL 参数错误、停牌重复和个别错误映射，但当时生产补水仍覆盖 936 只正股，说明对象集合过宽没有被根治。随后严格分区、累计预算和自动水位收敛继续叠加，使同一基础问题换成“任务阻塞”“空跑失败”和“假成功”再次出现。

## 5. 架构对齐结论

本次继续复用现有能力，不新增第二套调度器、平行业务表或新的外部数据源：

- 计划实例：`ops.job_schedule_slots`；
- 每次执行审计：`public.job_runs`；
- 数据进度：`ops.sync_cursors`；
- 数据分区：`ops.dataset_partitions`；
- 外部请求保护：`externalCallGuard`；
- 业务事实：现有 `core/market/fundamental/event/analytics/public` 表。

阶段进度和计数可先保存在现有 `result_summary JSONB`，无需为本次问题新增一套队列表。只有实施中确认现有字段无法满足查询性能或审计要求时，才另行提出最小迁移。

## 6. 研发改造方案

### 6.1 目标日期只计算一次

复用 `jobScheduleSlots.expectedDataDate()` 和 `jobRunners.js` 已计算的 `targetTradeDate`，继续传给全部子阶段：

```js
{
  businessDate: '2026-09-16',
  targetDate: '2026-09-15'
}
```

改造要求：

- `backfillUnderlyingStockMarket()` 增加明确的 `targetTradeDate` 参数；
- `getRecentOpenDays()` 查询条件增加 `trade_date <= targetTradeDate`；
- 日线、估值、复权、停牌和分区发布使用同一个 `targetDate`；
- 任务补跑历史业务日时，禁止使用 `new Date()` 或数据库 `CURRENT_DATE` 改变对象集合和窗口上界；
- 后台详情同时展示计划时间、业务日和目标数据日。

> **第三轮定稿（2026-09-16）**：`jobRunners.js` 已把 `expectedDataDate` 结果作为 `targetTradeDate` 传入可转债主任务；本次只补齐生命周期、周期补漏和正股补水的局部透传，并用行为测试禁止这些数据窗口改用当前日，见 §12.6。

### 6.2 以目标交易日事实生成可转债对象集合

新增一个共享的“目标日有效可转债集合”查询能力，供行情补水、公司财务、安全性和相关派生任务复用。它属于现有可转债数据层的一部分，不是新业务链路。

对象必须同时满足：

- 目标日已有上市事实；
- 目标日尚未退市、到期或停止交易；
- 非定向、非私募；
- 在目标日最新 `market.convertible_bond_daily_metrics` 分区中有有效记录，或有可核验的官方生命周期事实；
- 正股身份有效，且同一正股去重。

查询结果必须返回纳入数和排除原因统计，例如：

```json
{
  "targetDate": "2026-09-15",
  "currentBondCount": 310,
  "underlyingStockCount": 307,
  "excluded": {
    "historicalDelisted": 620,
    "expired": 4,
    "privatePlacement": 2,
    "missingTargetDateEvidence": 0
  }
}
```

历史档案继续保留用于追溯，不删除；只是不得再进入当前在市补档队列。

> **补录（2026-09-16）**：本节属现有可转债数据层的查询扩展，不新建链路；落地方式与遗漏项见 §12.6。

### 6.3 区分单次预算和槽位累计量

外部调用计数拆成两个语义：

| 字段 | 用途 | 重试时行为 |
|---|---|---|
| `attemptExternalCalls` | 当前这一次执行的保护上限与审计 | 每次尝试从 0 开始 |
| `slotExternalCallsTotal` | 同一计划实例累计消耗，供后台观察、告警及槽位总止损 | 原子累加，不参与单次 `maxExternalCallsPerRun`，但不得超过独立 `slotExternalCallsLimit` |

具体改造：

- `jobOrchestrator.js` 不再把上次累计数作为下一次 Guard 初始值；
- `jobRunnerProcess.js` 每次进程启动先将本次计数设为 0；
- Node 调用 Python 子进程时，仍可在同一次尝试内合并调用数；
- `public.job_runs.external_call_count` 记录单次尝试值；
- `ops.job_schedule_slots.result_summary.slotExternalCallsTotal` 保存累计值；
- 自动续批必须设置整个槽位的硬上限 `slotExternalCallsLimit`，不能复用 `maxExternalCallsPerRun`；详见 §12.1。

> **补录（2026-09-16）**：本节与技术架构 §518 现有口径（跨次重试沿用累计值）直接冲突，且系统内共有 4 种计数口径。开工前先裁决口径表与 `dailyBudget` 归属，见 §12.1。

### 6.4 把固定批次改成可续跑批次

80 条上限保留为单批止损线，但处理完一批后不再抛出不可恢复失败。

本批完成且仍有剩余时返回：

```json
{
  "ok": true,
  "status": "partial",
  "continuationRequired": true,
  "processed": 80,
  "remaining": 853,
  "failed": 0,
  "nextAttemptAt": "受控的下一批时间"
}
```

编排器把同一槽位重新放回待执行队列，保留本批已入库结果，不把正常续批计入业务失败次数。下一批重新查询真实缺口，只处理剩余对象；不得从最前 80 只重复开始。

阶段摘要建议保存在现有 `result_summary`：

```json
{
  "targetDate": "2026-09-15",
  "stages": {
    "bondMarket": { "status": "succeeded" },
    "stockMarketBackfill": { "status": "partial", "processed": 80, "remaining": 853 },
    "suspension": { "status": "pending" }
  },
  "attemptExternalCalls": 80,
  "slotExternalCallsTotal": 164
}
```

自动重试只运行未完成阶段；已成功的行情、公告或 PDF 不重复下载和计算。

> **补录（2026-09-16）**：示例中的 `partial` 不在现有槽位状态集合内，且 933 只缺口 ÷ 80 需至少 12 批，`maxAttempts: 4` 会在第 4 批后彻底放弃。续批的状态承载与 attempt 语义必须先裁决，见 §12.4。

### 6.5 统一最终完成判定顺序

最终状态按以下顺序裁决：

1. Runner 明确返回 `ok=false`：不得被普通水位改成成功；
2. 必需阶段或必需数据集仍有 `failed/pending`：不得成功；
3. 严格分区未发布或质量未通过：不得成功；
4. 任务明确返回“已核验无变化/有效空结果”：允许发布本业务日的核验分区；
5. 上述均通过后，水位只用于确认数据日期，不再代替完整性。

`reconcileByWatermark` 仅允许恢复“业务已提交成功，但最后写槽位状态失败”的明确场景。恢复前必须同时核对原运行结果、必需阶段和数据集分区，不能只看 `last_success_date`。

> **第三轮定稿（2026-09-16）**：现有 `verifyAlertScope` 只能判断告警是否可关闭，不能直接决定当前失败槽位转成功；应抽取唯一中立的运行、阶段、分区和水位证据服务，供 `reconcileByWatermark`、`degraded` 重验和告警关闭共同调用，见 §12.3。

### 6.6 公司财务正常空跑

队列为 0 代表“已核验没有新增、缺口或到期重试对象”，不是没有执行。

改造方式：

- 返回 `ok=true`、`changed=false`、`verifiedNoChange=true`；
- 外部调用数为 0；
- 为当前业务日发布 `stock_financial_reports` 核验分区；
- `partition_key` 使用本次业务日，`data_as_of` 仍使用最近一份真实财务披露日期；
- diagnostics 记录 `queue_count=0`、有效报告行数和核验依据，不伪造新财报。

这样既满足严格发布，也不会把“没有新财报”伪装成新增数据。

> **第三轮定稿（2026-09-16）**：采用带核验证据的快照分区，但保留真实财务事实总行数和最近披露日；`changed_rows=0` 不等于数据集零行。只有事实表确实为空且目标集合也核验为空时才允许 `allowEmpty`，见 §12.2。

### 6.7 港股 IPO 陈旧候选治理

当前招股书候选条件允许 `listing_at IS NULL AND ipo_status IN ('active','priced','allotted')` 绕过日期窗口，导致 `01355.HK`、`01792.HK`、`01822.HK` 等历史已上市记录长期排在队首。

改造方式：

- 关联 `core.instruments.list_date/status` 形成有效上市日期和生命周期；
- `listing_at` 为空时，必须有近期认购日期、官方公告日期或其他可核验的当期发行证据，才能进入队列；
- 对已确认历史上市但 IPO 字段不全的记录，标记为历史资料缺失终态或低优先级离线补全，不进入日常有限队列；
- 把 `not_found`、`not_applicable`、`terminal_missing`、`next_retry_at` 写入现有 `data_completeness/source_documents` 证据，不反复请求同一无效候选；
- 候选排序优先处理已有官方文件且解析未完成的记录，再处理近期真实发行对象。

### 6.8 套利公告的来源完成与解析完成分开

任务至少展示两个状态：

- 公告来源同步是否完成；
- PDF 解析队列是否完成，以及多少条尚未到重试时间。

尚未到 `next_retry_at` 的 PDF 不应在本轮重复下载，但只要它属于必需解析范围，也不能仅凭公告水位把整个槽位标成成功。可返回 `degraded/partial`，并在最早可重试时间再续跑；若业务允许先发布案件，则必须在结果中明确“来源已完成、解析待补”，页面不能显示全绿成功。

### 6.9 市场波动任务按子数据集判断新鲜度

取消用统一 `freshnessMaxLagDays=45` 代表所有子数据集。分别检查：

- 中国国债收益率；
- 沪深 300 PE；
- 中证全指 PE；
- 恒生指数 PE；
- 美国十年期国债收益率；

## 12. 补录（2026-09-16）：第三轮复核定稿

> 本节保留第 1–11 节作为问题发现过程，并给出可直接开发的最终口径。第三轮复核修正了三处关键误判：① `verifyAlertScope` 是告警关闭判定，不能直接作为失败槽位转成功的判定器；② `expectedDataDate` 已在 `jobRunners.js` 中计算并传入可转债任务，真正缺口是子阶段丢失参数；③公司财务空跑发布的是“核验快照分区”，不是把现有财务事实伪装成零行数据集。除生产数据写入仍需单独授权外，本节不再保留 A/B 双选项。

### 12.1 §6.3 的计数口径与总止损定稿

**冲突事实**：`docs/技术架构.md:518` 现有明文写着「跨次重试沿用计划实例 `result_summary.externalCalls`，Node 与 Python 子进程共享累计值……`JOB_BUDGET_EXCEEDED` 表示本批次边界，按任务结果处理为不可重试的部分完成」，同一段还写着「`maxExternalCallsPerRun` 是单个计划批次的执行上限，`dailyBudget` 是该任务每日预算报表的计入值，**二者不能混为一谈**」。§6.3 要求“不再继承累计值”，与该句直接对立；若不同步修改技术架构，代码落地当天即出现文档与实现不一致。

**现状代码路径（§4.2 的描述准确，行号已核对）**：

- `jobOrchestrator.js:527`：从 `result_summary.externalCalls` 取出累计值放进 `runContext.externalCallCount` → 跨次重试继承；
- `jobRunnerProcess.js:32`：`setExternalCallCount(...)` 用该累计值初始化本次 Guard（`:33` 设 `JOB_EXTERNAL_CALL_LIMIT`，`:28` 通过 `JOB_BUSINESS_DATE` 传业务日）；
- 同一次尝试内 Node→Python 合并计数保留不变（`jobRunnerProcess.js:42-43` 使用 `getExternalCallStats()`）。

**四种计数口径必须先写死（并确认 `dailyBudget` 归属）**：

| 口径 | 承载位置 | 现有取值示例 | 是否参与“本次还能不能继续调用” | 重试时行为 |
|---|---|---|---|---|
| 单次尝试上限 | `jobDefinitions.maxExternalCallsPerRun` + `ops.external_call_budgets` | 可转债 600（`jobDefinitions.js:79`）、公司财务 80（:65）、市场波动 6（:85） | 是 | 每次尝试从零开始 |
| 槽位累计量 | 现有 `result_summary.externalCalls`，拟另设 `slotExternalCallsTotal` | 可转债 600 级、港股 IPO 29 级 | 不参与单次上限；参与独立 `slotExternalCallsLimit` 总止损 | 原子累加 |
| 每日预算计入值 | `jobDefinitions.dailyBudget` | 可转债 7、套利 4、港股 IPO 各段 0 | 否 | 不参与 |
| 来源级 Guard | `ops.external_call_budgets` / `ops.external_circuits`（`docs/技术架构.md:527`） | 主 Tushare 450 次/分、备用 180 次/分 | 是（最终止损） | 按实际请求独立计数 |

**最终口径与前置条件**：

1. `dailyBudget` 归属“每日预算报表计入值”，**不得被新字段替代或改语义**；它不是运行时拦截线。
2. `maxExternalCallsPerRun` 只限制一次进程执行，每次尝试从零开始；`public.job_runs.external_call_count` 记录该次实际值。
3. **续批任务必须同时声明槽位总止损** `slotExternalCallsLimit`，并在每次外部调用前以 `slotExternalCallsTotal + attemptExternalCalls` 校验；未声明总止损的任务不得启用自动续批。来源级 Guard 继续作为账号、接口和速率的最后保护，不能替代槽位总止损。
4. 续批首次形成时记录 `initialRemaining`、`batchSize`、`continuationCount=1`、`lastRemaining`、`noProgressCount=0`，并计算 `continuationMaxBatches=ceil(initialRemaining/batchSize)+1`；连续 2 批剩余量没有下降、达到最大批数、达到槽位总调用上限或超过业务日 24 小时仍未完成时转 `blocked`，停止自动调用并告警。
5. `slotExternalCallsTotal` 通过同一槽位行的原子更新累计，不能由多个进程各自读旧值后覆盖；它同时用于后台展示、总止损和审计，不参与单次 `maxExternalCallsPerRun` 判断。
6. 同步修改项：`docs/技术架构.md:518` 改为四口径与续批停止线，并明确“跨次重试不再继承单次上限，但槽位总止损必须保留”。

### 12.2 §6.6 的公司财务核验快照分区定稿

**冲突事实**：`docs/技术架构.md:510` 写公司财务「无待办时以成功空跑结束且**不发布伪分区**」；§6.6 要求「为当前业务日发布 `stock_financial_reports` 核验分区」。两句互斥，不能同时成立。

**现有数据语义**：公司财务空跑时，`latestFinancialDataAsOf()` 已返回财务事实表中最新真实披露日期和当前有效事实总行数；`queue_count=0` 表示本次没有新增、缺口或到期重试对象，不表示财务事实表为零行。因此不能把本场景写成“零行数据集”，也不能把 `partition_row_count` 写成 0 来代表“本次新增 0 行”。

**最终采用核验快照分区**：

- `partition_key` 使用本次业务日；
- `data_as_of` 使用最近一份真实财务披露日期；
- `row_count` 使用 `report_type='1' AND is_current_version=true` 的当前有效事实总行数；
- diagnostics 至少记录 `coverage_status='verified_no_change'`、`target_count`、`queue_count=0`、`changed_rows=0`、`valid_report_rows` 和核验时间；
- 只有目标公司查询成功、队列构造成功且不存在应重试失败项时才允许发布；查询异常、目标数异常或存在到期失败游标时不得伪装为空跑成功；
- 若系统首次运行且有效事实总行数确实为 0，只有 `target_count=0` 且目标集合核验成功才允许走带证据的 `allowEmpty`；`target_count>0` 但事实为 0 必须失败。

`verified_no_change` 与 `verified_no_suspension` 同属“已核验覆盖状态”，但分别保留业务含义；注册表统一使用允许值集合，不用一个状态冒充另一个状态。`docs/技术架构.md:510` 同步改为「不伪造数据行；允许为业务日发布带核验证据、保留真实 `data_as_of` 和事实总行数的核验快照分区」。

### 12.3 §6.5 的共享恢复证据服务定稿

**2026-09-16 只读核对结果**：

- `jobScheduleSlots.js:232-247`（`reconcileByWatermark`）：查水位 → `isDataAsOfFresh()` → 直接 `UPDATE status='succeeded'`，**未核对** `public.job_runs` 结果、必需阶段与数据集分区；
- `jobScheduleSlots.js:249-262`（`degraded` 重验）：同样只看水位就改成功 → **§6.5 原文漏了这条路径**，必须一并纳入；
- `server/services/jobAlertMailer.js:79` 的 `verifyAlertScope` 已由运行时告警关闭与历史调和共用，但它是**告警关闭判定器**：槽位作用域只有在原槽位已经成功，或后续同业务日、同模式槽位成功时才返回恢复；它不能在状态修改前判断一个当前 `failed/degraded` 槽位是否具备转成功证据。把它直接接入槽位恢复会形成“必须先成功才能证明可以成功”的循环。
- `verifyAlertScope` 当前对普通槽位告警看到 `status='succeeded'` 就返回恢复，没有同步核验严格任务的数据分区；这也没有完整实现 20260915 方案中“严格发布任务还须分区证据”的要求。

**与历史方案的关系（第三轮定稿）**：20260915 方案要求“运行时与历史调和调用同一实现”的方向正确，但现有共享范围仅覆盖告警生命周期，没有形成可供调度器调用的中立槽位证据。INC-0026 的「假成功」既是调度接线缺口，也是现有共享实现没有下沉到运行/阶段/分区证据层的边界缺口。

**最终落地方式**：从 `verifyAlertScope` 中抽出唯一的中立服务 `jobRecoveryEvidence.js`（名称可等价，但只能有一份核心判断），由调度恢复和告警关闭共同调用；`verifyAlertScope` 只保留作用域解析、后续可比槽位和通知层逻辑。中立服务必须返回结构化证据并满足：

1. 原 Runner/`job_runs` 明确成功，`result_json.ok` 不为 `false`；明确失败不得被水位覆盖；
2. 必需阶段无 `failed/pending`，续批任务无 `continuationRequired`；
3. `failedDatasets` 为空；严格发布任务的全部声明分区在精确目标业务日已发布、未过期且质量通过；
4. 任务需要水位时，水位达到 `expectedDataDate(jobCode,businessDate)`；不需要水位的任务明确标记“不适用”；

### 12.4 §6.4 的续批状态承载与 attempt 语义（遗漏四）

**算术与现状**：936 只正股、933 只缺口，单批 80 → 需**至少 12 批**。而 `convertible_bond_universe_refresh`（`jobDefinitions.js:41`）是 `maxAttempts: 4`、`retryDelaysMinutes: [15, 60, 240]`；`jobScheduleSlots.js:452` 在 `attempt_count >= maxAttempts` 时把槽位置为 `failed`，`:492` 之后不再领取。**结论：按 §6.4 现有文字实施，任务仍会在第 4 批后彻底放弃，跑不完。**

**状态语义不匹配**：

- §6.4 示例返回 `status: "partial"`，但槽位允许状态集合是 `succeeded / degraded / failed / blocked / skipped`（`jobScheduleSlots.js:660`），**没有 `partial`**；
- `docs/技术架构.md:518` 限定可执行状态为“到期的 `pending`、带未来 `next_attempt_at` 的 `failed`、外部来源恢复后到期的 `waiting_external`”。

**领取 SQL 现状核对（2026-09-16 二次复核）**：直接「回 `pending` + 设未来 `next_attempt_at`」在现有领取逻辑下**不可行**——`claimJobSlot`（`jobScheduleSlots.js:423-432`）领取时无条件 `attempt_count+1`，且 WHERE 要求 `attempt_count < maxAttempts`；`listDueSlots`（`:484-487`）与 `claimJobSlot`（`:430`）对 `status='pending'` 均短路跳过 `next_attempt_at` 检查，`pending` 槽位会被立即再领取，「15 分钟后继续」无法生效。因此落地必须同时修改这两处领取 WHERE（或引入续批专用状态/领取路径）；§7 的 `jobScheduleSlots.js` 条目（“续批不消耗业务失败次数”）即包含此修改。

**最终口径**：

1. 续批视为**同一业务日的阶段推进**，不是失败重试；新增统一的 `continueSlot()`，把槽位放回 `pending`、写入未来 `next_attempt_at`，并像 `waiting_external` 一样把本次领取时增加的 `attempt_count` 减回去。这样不需要改变所有历史 `attempt_count` 的含义，也不会让正常续批耗尽 `maxAttempts`。
2. `listDueSlots` 与 `claimJobSlot` 对 `pending` 同样必须检查 `next_attempt_at<=now()`；禁止通过 `status='pending'` 短路立即领取。
3. `result_summary` 保存 `continuationRequired`、`continuationCount`、`continuationMaxBatches`、`initialRemaining`、`lastRemaining`、`noProgressCount`、`nextAttemptAt`、`pendingStages`、`slotExternalCallsTotal` 和 `slotExternalCallsLimit`。`partial` 只作为结果/展示态，不新增数据库执行状态。
4. 下一批只执行 `pendingStages`。可转债任务若仅 `stockMarketBackfill` 未完成，不得重新执行 `cb_basic/stock_basic/cb_daily/daily/daily_basic/adj_factor/suspend_d`；进入 Runner 前把阶段摘要传入 context，业务层仍须按数据库真实缺口重新查询，不能仅相信旧的剩余数字。
5. 批次总数不受失败重试 `maxAttempts` 约束，但必须受 §12.1 的动态最大批数、连续 2 批无进展、24 小时槽位年龄和槽位总调用上限约束；触线统一转 `blocked`，不能继续 `pending`。
6. 同步修改 `docs/技术架构.md:518` 的状态白名单和 attempt 说明，并在后台把“续批中”显示为展示态，不污染数据库状态集合。

### 12.6 §6.1 / §6.2 复用已有能力，不新建（遗漏六）

- `expectedDataDate(jobCode, businessDate)` **已经存在**（`jobScheduleSlots.js:68-82`），编排器已用它计算分区日与新鲜度判定（`jobOrchestrator.js:543` 附近的 `fresh` 短路），Runner 也已通过参数和 `process.env.JOB_BUSINESS_DATE`（`jobRunnerProcess.js:28`）拿到业务日；
- `jobRunners.js:54-117` 已经为 `convertible_bond_universe_refresh` 调用 `expectedDataDate()`，并把结果作为 `targetTradeDate` 传给 `syncConvertibleBondUniverseWithBackfill()`；因此本次不需要为了可转债任务再在编排器创建第二个日期入口。
- **真正缺的**是局部透传：`syncConvertibleBondUniverse()` 仍用 `new Date()` 判断生命周期，`backfillCycleGaps()` 和 `backfillUnderlyingStockMarket()` 调用时没有收到已有的 `targetTradeDate`；后者内部又使用 `CURRENT_DATE`。`getRecentOpenDays(days,endDate)` 本身已经支持目标上界，只需正确传参。

§6.2 的对象集合以目标日生命周期/证券主档事实为纳入依据，以目标日日行情作为覆盖率和缺口证据；不得反过来只用“已有目标日日行情”决定谁属于对象集合，否则恰好会把缺行情的新债排除。已有 `listCurrentBondUnderlyingTargets()` 可抽取查询结构，但必须由“最新指标日”改为显式目标日，并返回排除原因统计。

**增加行为门禁（防第 4 次复发）**：在 `convertible_bond_universe_refresh` 的生命周期筛选、周期补漏、正股补水和最近 30 日检查中，统一断言最大日期不超过 `targetTradeDate`。不做全文件粗暴字符串禁用，因为计时、租约和日志时间仍可合法使用 `new Date()`；测试只约束对象集合与数据窗口。

### 12.7 §6.7–§6.9 的终态、新鲜度与可执行口径

#### 12.7.1 港股 IPO 陈旧候选

#### 12.7.2 套利 PDF 解析

- `not_due` 文档不下载，槽位以正常续批方式等待最早 `next_parse_attempt_at`；结果必须返回 `parsePending`、`earliestRetryAt` 和待处理文档 ID。

- 公告来源水位只证明来源同步；只有必需 PDF 已解析、已进入明确等待或有可审计终态时，才能裁决整体状态。等待中的槽位不得显示全绿成功，终态缺失不得被水位改写。
