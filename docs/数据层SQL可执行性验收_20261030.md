# 数据层 SQL 可执行性验收（2026-10-30）

一句话结论：数据层 1064 条写死的 SQL 里，964 条能在真实库结构上被数据库解析，**全部通过（0 失败）**。首次运行时抓到的 18 条问题已全部处理完毕：1 条潜伏类型错配修复，2 条增量水位改接新表，15 条随死代码删除。验收命令 `npm.cmd run acceptance:repo-sql`，测试 `server/test/repository-sql-coverage.test.js`（11 项，连库）。

## 1. 为什么单独做这件事

分层静态门禁回答的是「代码放在哪一层、有没有越界」，回答不了「这条 SQL 数据库能不能执行」。两者可以同时成立与不成立：

- 2026-10-30 发现：补「持仓基准快照」的 INSERT 自 0.9.1.2 上线起从未成功执行——`daily_prices.date` 是 TEXT 列却写成 `d.date::text=$3`，与同一语句里的 `$3::date` 争抢参数类型（PG 报「操作符不存在: text = date」），`round(double precision, int)` 也不存在。当时的分层扫描是 505 文件、越界/待登记/解析失败 0/0/0，全绿。
- 那次只覆盖了一条链路（导入旅程），方案第 5 节留着「更广范围的仓储 SQL 可执行性仍未系统覆盖」。本文件交付的就是这个覆盖。

## 2. 方法

`PREPARE <名称> AS <SQL>` 只让数据库做语法、名称解析和类型推断，**不产生行、不写数据、不需要真实参数值**，因此可以在隔离库上安全地逐条跑。

- 扫描范围：`server/repositories/`（84 个文件）+ `server/db/`（14 个文件），共 86 个文件。
- 提取规则：`.query(` 后面的引号字面量，且内容以 `select/insert/update/delete/with/values` 开头。
  - 还原 JS 转义（`\'` → `'`、`\\` → `\`），否则 PG 会报「语法错误在 "\" 或附近」这类假失败；
  - `query(` 与 SQL 之间夹注释也要能穿透，否则加一行注释就等于这条 SQL 免检（实测踩到过）；
  - 模板插值 `${...}` 与「字面量后紧跟 `+`」的拼接一律记为动态、不参与校验，单独统计。
- 隔离要求：脚本拒绝在库名不含 `test/ci/accept` 的库上运行，避免误连业务库。
- 已知失败清单：`governance/repository-sql-known-failures.json`。规则是**清单必须与事实一致**——出现未登记失败算回归（红），登记了但本次通过算清单过期（也红，要求删登记）。

## 4. 发现与处置

### 4.1 已修：一条潜伏的类型错配

`server/db/accounts.js` 的 `saveAccountData` 里：

```sql
DELETE FROM nav_history WHERE username=$1 AND account_name=$2 AND NOT (date = ANY($3::date[]))
```

`nav_history.date` 是 **TEXT** 列，`date = ANY($3::date[])` 变成 `text = date`，PG 没有这个操作符。它藏在 `if (lockedDates.length)` 分支里——只有存在「锁定净值」记录时才走到。当前生产 `is_locked=true` 记录为 0 条，所以一直没炸，属于「等哪天开始锁净值就炸」。已改为 `$3::text[]`。

### 4.2 已处置：17 条引用已删除旧表的语句（**先证明已被替代，再动手**）

17 条全部 `42P01`，指向 migration008 明确 `DROP` 的 7 张表。处置前先核了「这些功能是否已有别的 SQL 承担」，结论是**都有**：

| 原写入目标 | 现在由谁承担（活路径） |
|---|---|
| `ops.raw_records`（原文/主档） | `financialDataArchitecture.persistCollectedData` → `projection.insertRawRecord`，`stockAnalysis.refreshStockAnalysis` 每轮都调（321 行） |
| `event.company_events` / 公告原文 | `saveCollectedEvents` → `upsertDocument` / `upsertCompanyEvent` |
| `analytics.analysis_snapshots` 与指标 | `saveAnalysisResults` → `syncAnalytics` + `syncQualityIssues`（`stockAnalysis` 228/329 行调用） |
| `market.daily_bars` / `market.daily_valuations` / `fundamental.financial_facts` | `market.daily_valuations` 现由 `convertibleBondAnalysisStore` 等活跃路径写；读取侧 `loadAnalysisInputs` 已全部改用 `core.*` / `fundamental.financial_reports` / `market.daily_valuations` / `market.share_capital_history` / `event.company_events` 等新表 |
| 分红 / 业绩预告 | `fundamental.corporate_actions`（`action_type='dividend'`）、`fundamental.earnings_guidance` |

具体处置：

1. **删除 15 条**：
   - `stockProjectionRepository`：`syncRawRecords`、`syncMarket`、`syncFundamentals`、`syncEvents`、`syncCursors`、`syncReportTable`、`listLegacyStockCodes`、`readLegacySnapshot`（文件 416 → 295 行，导出 26 → 18 项）。它们只在 `financialDataArchitecture.syncStockToArchitecture` 里被调用，而该函数**除测试断言导出名外无任何引用**。
   - `financialDataArchitecture`：删 `syncStockToArchitecture` 与 `backfillLegacyFinancialData`（后者只依赖 `listLegacyStockCodes`），并同步移除 `data-layer-boundary.test.js` 导出清单里的两项。
   - `stockAnalysisRepository`：删 `saveMetadata`、`saveAux`、`saveValuations`、`setSyncState`，以及 `stockAnalysis.js` 里对应的 4 个未导出包装（它们互相只调对方，没有外部入口）。
2. **保留但改写 2 条**（原判断是"死代码"，核查后纠正）：`latestDividendEndDate` / `latestForecastAnnDate` **是被调用的活代码**（`stockAnalysis.js` 220/229 行），只是查已删表必然报错，且被 `try {} catch (_) { return null }` 吞成「没有本地数据」。改接 `fundamental.corporate_actions.fiscal_period_end` 与 `fundamental.earnings_guidance.announced_at`，返回格式不变（YYYYMMDD 或空串），调用方无需改动。

### 4.3 为什么这件事一直没告警（对应用户疑问）

两个原因叠加，都不是"有替代所以不报错"，而是**错了看不见**：

- **大部分函数根本没被调用**：死代码不执行，不执行就不会报错。`syncStockToArchitecture` 整条链就是这样躺了一年多。
- **少数被调用的异常被吞**：两个增量水位在 `try/catch` 里，报错 → 返回 null → 上层理解为"本地没有分红数据，按首发全量拉"。表现是**每次多打上游接口**，而不是报错。所以功能"看起来正常"，只是白白重复外采。

修复后的直接收益：分红/业绩预告有了真实的增量水位，重叠窗口按水位计算，不再无条件全量重拉。

## 5. 覆盖边界（明确没做到的）

- **100 条动态拼接**（模板插值 97、多段拼接 3）无法静态还原，未校验。报告里逐条列出（文件、行、函数、原因），可人工抽查。
- **helper 拼装的 SQL 不在扫描范围**：如 `db/accounts.js` 的 `bulkInsert`、各类 `buildXxxSql()`，SQL 由运行期拼接，静态文本里没有完整语句。
- `scripts/`、`ipo-report/`、迁移文件里的 SQL 未纳入（迁移有独立执行与回滚路径）。
- **PREPARE 只证明「能解析」**：不证明语义正确、索引命中、结果符合业务口径。金融口径正确性仍由各域专项回归负责。

## 6. 怎么用

```bash
# 需要本地 PostgreSQL（用隔离库；不带 test/ci/accept 的库会被拒绝）
PGPREPAREDB=portfolio_test npm.cmd run acceptance:repo-sql
# 机器可读结果
PGPREPAREDB=portfolio_test npm.cmd run acceptance:repo-sql -- --json _probe/repo-sql-report.json
```

- 新增 SQL 写错（列名、类型、表名）→ 命令非零退出，输出 `文件:行 [错误码] 函数`。
- 修好某条已登记失败 → 命令报「已登记但本次通过」，要求同步删登记；测试同样会红。
- 不允许为了让命令变绿往清单里加条目：每条都要写 `status`、`reason`、发现日期。
