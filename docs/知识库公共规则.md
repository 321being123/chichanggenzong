# 知识库公共规则

> 状态：现行公共规则。最后核对：2026-10-26（知识结构、录入与协作流程；不代表业务或生产重新验收）。
> 适用：本仓库全部开发人员与 Agent。新增、修改、引用或归档项目知识前必须遵守；用户最新明确指令及项目授权边界优先。
> 本文是知识治理细则的唯一维护位置。AGENTS保留强制入口，技术架构2.1保留兼容指针；两处不再复制本规则全文。

## 0. 每次任务的最小必读

- 遵守已加载的AGENTS和用户最新指令；先看索引“快速入口”，只提取命中的路由，不默认全文加载索引、路由表和架构。
- 知识写入前读本节，再按本次动作读相关细则：普通录入2—4/9节，新增记录加5节，多Agent协作加6节，替代/归档加7节，调整结构/路由读1/8节。
- read文件必须核对“当前摘要＋相关完整章节/约束及直接依赖”，不默认通读整篇；不能把搜索片段、截断输出或目录当作读完规则。
- 优先修改原权威位置；状态带日期/范围/证据，原文、授权和未完成项保留；正文先于目录/索引，写前重读最新目标段。
- 根因不明、跨模块、数据/权限/安全/任务/部署风险，或发现冲突/引用缺失时扩大阅读，不能为节省Token跳过必要检查。
- 本会话已完整读取且未变化的章节复用；文件或指令变化时只补读受影响部分。压缩后规则缺失则重新读取，不把私有记忆当事实来源。

## 1. 结构设计与权威边界

沿用现有目录，按“公共规则 → 主题索引/机器路由 → 当前说明 → 证据与历史”组织。每个事实只有一个完整维护位置，其他地方写必要摘要和准确链接。

| 内容 | 唯一完整维护位置 | 不应放入 |
|---|---|---|
| 知识如何写、如何核对与协作 | 本文件；AGENTS仅保留强制入口和业务红线 | 技术架构的业务章节、私有记忆 |
| 去哪里找、当前关键边界 | 知识索引；机器匹配由knowledge-map维护 | 大段参数、执行过程和测试流水 |
| 当前技术机制、字段、读写合同 | 技术架构原业务章节 | 发布历史或任务卡作为唯一解释 |
| 功能目标、设计取舍、实施验收清单 | 原专项方案；重要长期技术选择另按ADR体例记录 | 同主题新建第二份方案、将设计直接当实现 |
| 重大或重复故障根因、同类范围及防复发 | 原Incident；没有同根因记录才新建 | 规则文件堆事故全过程 |
| 某次发布的版本、提交、授权、步骤结果 | 生产部署历史记录；功能专项证据回原方案/事故 | 现行部署步骤或全项目架构顶部 |
| 当前部署方法与环境操作边界 | 生产部署流程；本机环境按本地验证交接文档 | 旧安装示例代替现行步骤 |
| 跨会话未完成工作 | 原active任务卡；任务目录只放摘要和链接 | 多份TODO清单、私有记忆独占待办 |
| 用户可见版本、生成资料、分享材料 | 既有变更记录、生成文件、分享原文件 | 当作现役规范或人工修改生成结果 |

这是一套职责划分，不是要求新建上述所有文档。现有路径保持兼容；不为目录整齐批量移动、改名或重写方案。确需拆分大文档时，先明确独立主题与原入口不能承载的原因，再在本次范围内迁移、保留指针并修正路由。

技术架构只保留稳定机制和必要边界；案例计数、逐版本过程回证据正文。专项方案内部把“当前说明”“设计/验收清单”“历史执行记录”分开，已经被实现替代的设计必须标出偏差，不能整份盖章为全部完成。

## 2. 写入前的六项判断

1. **必要性**：是否改变当前行为、长期约束、数据口径、可复用根因或未完成边界？只有成功日志、临时计数或重复验收时，不新增规则或架构正文。
2. **归属**：先按上表及机器路由找到原位置；搜索主题、字段、规则编号和旧结论。没有找到，才判断是否新建。
3. **替代关系**：明确是原位更新、补证、纠错、合并、归档或不写；先修正旧当前结论，不能仅在文首/文末追加一段相反的“最新进度”。
4. **保留边界**：根因、来源原文、用户授权及范围、失败记录、生产验收和真实未完成项必须保留。不能因日期旧、活动告警为0或任务成功就删除。
5. **影响引用**：核对索引、目录、read/update、Markdown链接及证据锚点。历史记录不进入默认read；迁移前先确认消费者。
6. **交付结果**：说明新增为何必要、替代/归并/归档了什么、哪些未验项保留。不为证明做了判断再新建一份流水。

不变结论不反复复制。门禁要求同步核对时，优先复用已有说明；确需记录，局部注明核对范围与结论不变，不用反复改日期、堆回执或虚构实现凑文件差异。若路由持续要求无关文件变更，应核对并局部收窄路由，不能降低真实同步要求；本规则本身不改变检查脚本的判定方式。

## 3. 录入格式与最小信息

新建文档及本次实际修订的当前摘要采用下列信息；旧文档在被修改时逐步补齐，不批量刷头部。没有证据的字段写“待核验”，不能推测填写。

```md
文档职责：当前机制｜专项方案｜决策｜事故｜任务交接｜历史证据
截至日期及范围：YYYY-MM-DD；本次实际核对的章节、对象或环境
当前结论：一句话说明已确认行为或实际达到的阶段
权威与证据：原文档/章节或稳定锚点；涉及发布时附版本与提交
未验证/未完成：具体缺口、下一步；没有则按核对范围说明
```

- “最后修改”不等于“最后核对”。只改一节时写清范围，不把全篇日期刷新成所有事实今天都重新验证。
- 当前摘要控制在5行或一个简短表格单元格；索引同主题只留一行。大段参数、测试数字、槽位、哈希及过程写入唯一证据段。
- 一条机制说明只讲清规则、适用条件、失败边界与对应实现/证据，不把多个无关主题堆在同一段。
- 测试结果写执行日期、对应代码范围、检查名称、结果和未覆盖范围；不是本次执行的，注明“已有回执记载”，不得写成“本次实测”。
- 数量必须写明对象集合、业务日/报告期、统计含义。不同日期、全量/定向、元数据/详情的数量不能直接比较。
- 结论引用仓库内可长期找到的摘要、原文来源或证据锚点。忽略目录中的探针、截图、日志可辅助核对，但不能成为未来无法恢复的唯一结论来源。
- 密码、Token、私钥、个人数据和敏感连接串不进入文档、提交或回复；敏感配置仅使用环境变量名和受控位置说明。

## 4. 状态必须分开表达

文档的生命周期、功能实施和数据结果是不同维度，不能用一个“已完成”概括。

| 维度 | 允许表达 | 判定边界 |
|---|---|---|
| 文档生命周期 | 现行、待评审、历史、已替代（附替代位置） | 历史记录保留当时事实；不能作为今天的操作指令 |
| 功能实施 | 待实施、已本地实现、本地已验证、已提交/推送、已部署、线上专项已验证 | 只写实际达到阶段；代码存在不等于原方案全部通过，已部署不等于真机或专项通过 |
| 任务/数据 | 执行成功、质量恢复、运营确认、正常等待、仍缺失 | 按原槽/日期/对象/字段证据区分；acknowledged不等于数据恢复，NULL不等于零 |

实现与部署按本地代码和生产版本分别描述，不能写模糊的“已修复”却不说明环境。只有部署记录，没有目标接口/任务等专项证据时，只能写已部署。

“待核验”必须附不确定点、已有证据和下一步。旧授权不会因换Agent自动失效，也不能被扩大；记录授权日期/指令摘要、对象、模式和生产写入边界，禁止从一处修复推断获得全量授权。

原文证据、当前实现与生产回执各自证明不同问题：来源证明字段含义，代码证明实现机制，运行回执证明某版本在某范围的实际结果。不能靠提交说明、文档修改时间、私有记忆或测试绿灯跨维度裁决。证据矛盾时在原位置标待核验，保留双方证据，不按“最后写入者”定论。

## 5. 各类记录怎样写

| 类型 | 必须有 | 不应有 |
|---|---|---|
| 当前机制 | 适用条件、数据/调用边界、失败处理、实现位置 | 连续版本叙事和单次任务计数 |
| 专项方案 | 已有/复用/缺口、用户范围、架构对齐、分项实施与验收状态、未闭环 | 未实施设计冒充现役；重新写一份替代用户原方案 |
| ADR | 背景、决策、取舍、影响、重评条件、状态 | 顶部不断新增某次发布日志 |
| Incident | 根因链、同类核查、修复/回归证据、防复发与遗留 | 只有症状或一次成功就称根治 |
| 发布回执 | 版本/提交、实际授权与范围、执行结果、专项证据、剩余项 | “本次”不带日期；本地测试冒充生产验收 |
| 活动任务卡 | 当前目标、授权边界、阻塞、证据位置、下一步 | 将旧阶段待办长期当今天待办；复制完整实施过程 |

ADR、Incident、任务卡沿各目录README原模板；本文件规定共同字段，不另建第二套模板。短任务不强制建卡，普通修复不强制新建ADR/事故；同根因问题优先补原记录。新编号先检查全部文件名，既有INC-0002/0003同号异题按完整文件链接引用，不自动重编号。

## 6. 多Agent写入与整合顺序

1. 开始确认仓库、Git HEAD、已有未提交文件和本任务目标章节。只处理实际负责的段落，不回退、不覆盖或顺手提交他人改动。
2. 同一任务多人协作，指定一个整合负责人处理公共规则、索引及路由；其余人员先完善负责正文，再提供“文件/章节、原结论→新结论、证据、未验范围”。这不授权向其他聊天发消息，也不代表未协调的会话已经停笔。
3. 写前重读最新目标段；若与已读基线不同，保留双方有效增量后局部合并。无法裁决的内容留待核验，不能用旧快照整文件覆盖。
4. 固定顺序：**原正文和当前摘要 → 事故/任务目录 → 知识索引 → 必要的路由更新 → 检查及交付前差异复核**。
5. 交付时再次核对磁盘和Git差异。并发改变同一段时重新核对；未解决冲突不能宣称知识闭环。

上述是所有人员的协作约束，目前没有自动文档锁或语义合并功能。平台私有Memory只能作既有规则允许的接续指针，不得独占项目事实；本次结构优化不改变平台记忆权限。

## 7. 证据引用、替代与归档

- 同一实测段只维护一份完整原文。优先留在原专项/事故；当前合同需要放架构时，架构保留机制，事故保留案例证据。其他位置用摘要和精确链接，不复制整份回执。
- 已引用的evidence锚点保持稳定。发现证据记录错误时，注明更正原因、原结论及替代证据，不能静默改写成原先就成功；新的一次执行建立新的证据段，不覆盖旧执行。
- 当前事实改变时先更新原段落，再同步摘要；旧过程有审计价值则标历史或归档，没有独立价值的重复描述合并为引用。没有最终证据的旧待办继续跟踪。
- 历史文件写明覆盖日期、职责和当前入口。不要把新日期内容继续塞入标题“截至旧日期”的归档；需要续档时建立下一期归档并保留旧文件和链接，不为升级日期批量改名。
- 任务结束前先把结论回写权威位置，未完成项明确去向，再按tasks流程压缩归档；移动/删除仍遵守项目授权要求，不自动清场。
- 文件移动、合并或拆分必须同时核对链接、锚点、目录和read/update。附件不存在时保留原路径并标缺失，不留下假装可用的链接，不编造恢复结果。

## 8. 阅读与路由管理

### 8.1 三层读取

| 层级 | 读取范围 | 何时需要 |
|---|---|---|
| 短入口 | 已加载AGENTS、本规则0节、索引快速入口、匹配路由 | 每次任务；已在有效上下文中的内容不重复全文读 |
| 主题正文 | read文件当前摘要、本次完整相关章节、直接依赖；按readSections定位 | 已明确目标后，执行前读；多个路由的重叠章节合并一次 |
| 扩展证据 | 原方案验收、事故根因、指定历史/代码/运行回执 | 根因或边界不清、跨模块/高风险、摘要冲突、证据不足时；按问题扩展而非全库扫读 |

read表示必须查阅该文件的相关当前依据，不等于每篇必须从头到尾读取。AGENTS或用户明确要求全文/指定章节时照做；readSections只提供候选起点，不是阅读白名单，不降低强制约束。

先按任务描述匹配主题，再按实际变更路径补匹配；合并read和checks，避免同一文件被多个路由重复加载。不要仅因“接口/服务/任务”等泛词就加载全部模块，也不能只凭短描述漏掉真实影响。

### 8.2 如何定位与停止

1. 先查当前摘要与标题；用rg在相关文件内定位字段、错误、路由或实现符号，再读取命中的完整章节及必要上下文。不要默认用Get-Content -Raw输出几十万字符。
2. knowledge-map优先通过JSON解析筛选命中路由，输出该路由的read/readSections/update/checks/expandOn，不把整个JSON塞入上下文。只调整规则/路由或匹配不明时扩大到相关定义。
3. readSections是Agent使用的章节定位元数据，当前check:knowledge不自动执行章节读取或检查语义。标题不存在、同号多标题、命中范围太大时，先查实际标题并按主题消歧，不凭章节号猜内容。
4. 读取到足以确认“适用规则、当前链路、修改位置、验收与未闭环边界”即可停止。只有缺口、引用或风险触发下一层；不为证明认真默认遍历历史。
5. 截断表示读取未完成；缩小输出范围并补读缺失内容，不能不断重发同一大文件。相关必读与高风险核查没有固定字数上限，不能为了省Token跳过。

### 8.3 增量复用与交接

本会话维护简短已读指针：文件＋章节/主题、适用结论、核对时的Git或文件变更标识。无需为每次阅读新建仓库日志、缓存表或平台Memory；指针不是独立事实副本。

相同版本的同一章节不重复读取；本地未提交文件还须核对磁盘变更，不能仅凭HEAD未变判断内容未变。指令变化、目标扩展或有并发修改时补读对应章节；写入前仍必须重读最新目标段。

压缩或跨Agent交接仅保留目标/授权边界、当前进度、已确认结论及准确指针、未知项和下一步。接手者重读必要规则和将修改的段落，不默认重读全部历史；上下文未保留的强制规则不能仅靠“前面读过”略过。

### 8.4 路由维护与写入配合

公共规则正文变更由knowledge-common-rules路由要求同步核对AGENTS入口、索引、架构2.1和路由；普通业务/文档更新不强制改公共规则。read列必要当前依据，readSections列候选章节，update列必须同步核对的位置，checks按实际风险配置；生成矩阵仍由现有生成器维护。

默认阅读不包括历史、生成报告、审查清单和分享材料；需要证明具体结论时再沿证据指针读取。共享代码命中多模块时，各模块只写自身变化/不变边界与源证据链接，不复制同一回执。

读取定位优先使用专题路由：notification-center承载通知身份、事务和投递；feedback承载反馈与附件；market-cycle承载市场周期账户就绪及日期/数据边界。通用前端默认读共享控件、移动端公共规则和权限，模块适配记录按主题回查；生产部署必须补齐其完整流程，不因读取量较大省略。

本次优化了主题路由和章节边界，没有新增自动检索、缓存、文件锁或语义检查程序。未来标题/职责改变时同步维护readSections；定位优化复用既有问题及冻结检查点对照，并另核对权限、阶段和授权边界，不改样本去凑通过。不要另建与机器路由重复的完整手工目录。

## 9. 收尾核对清单

- 已找到原权威位置，并完成必要性、归属、替代关系和保留边界判断。
