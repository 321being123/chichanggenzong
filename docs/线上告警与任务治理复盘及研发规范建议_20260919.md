# 告警与任务治理规则比对及门禁补强提案

> 复盘日期：2026-09-19  
> 适用范围：后台任务、外部数据同步、数据分区、告警恢复和生产补跑  
> 文档性质：规则比对与门禁提案；不是新增现役规范
> 当前状态：事实已核验，提案待团队评审；暂不创建 ADR-0003 或修改现役规范

本提案保留本轮复盘事实，但事实详情以 [`INC-0026`](incidents/INC-0026-后台补档任务阻塞与完成判定失真.md) 为唯一权威来源：可转债假缺口见 `INC-0026:125`，生产补跑与依赖阻塞恢复见 `INC-0026:129`。本文只负责把现役规则与实现缺口对照出来，并列出需要新增的自动门禁。

## 一、结论摘要

这几天处理的不是单个 Bug，而是三类边界问题叠加：

1. 任务计算的“目标对象集合”不准确，制造了虚假数据缺口。
2. 任务已经成功，但告警恢复证据链不完整或被错误拦截。
3. 历史公告重建在身份、来源并发、文本分类和断点续跑上缺少统一边界。

本轮最终结果：

- 可转债行情三日分区恢复为 `311/311`、`310/310`、`310/310`，缺口队列归零。
- 下游安全评分和估值任务均成功完成。
- 本链路相关数据质量、依赖阻塞和超时告警均按证据收敛。
- 全量测试 `135` 项通过、`0` 失败。
- 线上版本为 `0.8.1.70`，生产代码提交为 `c46a79b`；其后 `3997b7b`、`ac81467` 是纯文档提交，不代表生产树版本。

## 二、问题复盘

### 2.1 可转债行情虚假缺口

**现象**

2026-09-16 至 2026-09-18 连续出现 `bond_daily` 部分发布，旧记录显示缺少约 140 只可转债行情。

**根因**

- Tushare `cb_basic` 使用 `YYYYMMDD`，调度器目标日使用 `YYYY-MM-DD`，旧代码直接比较字符串。
- 允许上市日期为空，导致没有明确上市事实的债券进入目标集合。
- 历史退市、到期、停止转股的债券未被正确排除。
- 定向/私募债券没有沿用公开发行过滤规则。

**只读核查证据**

- 原缺口中有 130 只历史退市/停止状态债券、7 只定向债、3 只未上市债。
- 公开在市目标集合为 310 只。
- `cb_daily` 对这 310 只全部有有效价格，实际不是行情源缺失。

**修复**

- 统一生命周期日期格式，强制要求目标日前已有上市事实。
- 统一排除退市、到期、停止转股、定向和私募债券。
- `server/services/convertibleBondAnalysis.js` 复用 `bondSafetyTushare.isActiveBond()` / `filterPublicBonds()`；回归覆盖带横线目标日、空上市日和定向债过滤。

### 2.2 任务成功后告警无法自动恢复

**现象**

行情、估值和安全评分已经成功，但历史阻塞告警仍保持活动状态。

**根因**

- 告警作用域曾混用槽位业务日和实际数据分区日。
- 港股 IPO `server/services/hkexIpo.js` 的四个成功收尾分支曾向非空字段 `ops.ingestion_runs.error_message` 写入 `NULL`，导致成功被误判为失败。
- 历史槽位请求模式与实际运行模式不一致，恢复证据因此被拒绝。
- `dependency_blocked` 告警在外层校验中被提前拒绝，未进入已有的严格恢复证据层。

**修复原则**

告警不能只看槽位状态，必须同时核对：

```text
运行结果 → 失败数据集 → 数据分区 → 质量状态 → 水位日期 → 任务依赖
```

只有证据完整时才允许恢复。数据质量告警仍必须由对应数据集分区证据关闭，不能由普通任务成功掩盖。

### 2.3 历史强赎公告重建边界不足

**主要问题**

- 旧档案保存申购简称，和正式债券简称不一致。
- 同一正股存在多只历史转债时，公告无法唯一匹配。
- 纯下修公告被误归类为强赎公告。
- 公告列表和 PDF 正文共用并发槽位，造成批量 `BUDGET_WAIT`。
- 日期排版、重复更正公告、法律意见书等特殊文本导致解析门禁阻断。

**修复方向**

- 按正股、官方债券身份和公告日生命周期做唯一匹配。
- 无法唯一匹配时继续阻断，不默认选择第一条。
- 公告列表和正文使用独立并发额度。
- 保存检查点，失败只续跑未完成对象。
- 只有正文证据和业务字段都完整时，才替换历史投影和推进水位。

## 三、反复出现的共同原因

这些问题表面上分别属于行情、告警和公告解析，实际都属于同一种缺陷：

> 现役规则已经写好，但实现只覆盖了部分分支；同一事实又在多个模块中各自实现了一遍。

具体表现为：

- 规则存在、实现分支漏接：0.8.1.70 的 `dependency_blocked` 先被 `verifyAlertScope()` 外层拒绝，未进入已有的 `verifySlotRecoveryEvidence()`；0.8.1.57 曾把槽位业务日误当数据分区日；0.8.1.58 曾因历史槽位残留 `mode=core` 与实际 `enrichment` 不一致而拒绝恢复。
- 日期在不同模块使用不同格式和不同含义。
- 目标对象集合没有独立的权威口径。
- 任务成功状态和数据真正发布状态没有完全绑定。
- 告警发送逻辑和告警恢复逻辑没有共用同一证据服务。
- 外部接口限制、重试和断点规则散落在任务代码中。
- 回归测试覆盖了正常样例，但没有形成规则条款到全部实现分支的对照审计。

## 四、现役规则对照与实现缺口

本章不再重复写一套“建议规范”。日期、目标集合、告警恢复、外部接口、测试和发布要求已经固化在 `AGENTS.md`、`ADR-0002` 和 `docs/技术架构.md`；本章只列“既有条款 → 本轮暴露的实现缺口 → 需要新增的门禁”。

| 既有条款（权威来源） | 本轮暴露的实现缺口 | 需要新增的门禁 |
| --- | --- | --- |
| 日期、游标和目标对象：`AGENTS.md` 1.6；`docs/技术架构.md` 的 `normalizeBusinessDate()`、`targetTradeDate`、数据集分区规则 | 规则已存在，但 0.8.1.57 的分支仍把槽位业务日当作分区日；旧 `activeProfile()` 还直接比较 `YYYYMMDD` 与 `YYYY-MM-DD` | 静态检查禁止裸日期字符串比较和 UTC 截断；回归测试必须同时断言槽位业务日、目标数据日、`ops.dataset_partitions.partition_key`（分区日）与 `scope_key` 一致 |
| 目标集合：`AGENTS.md` 1.6、1.1；可转债目标集合复用 `bondSafetyTushare.isActiveBond()` / `filterPublicBonds()` | 行情入口曾自行实现生命周期和公开发行过滤，造成 140 条假缺口 | 任务注册时必须声明目标集合规则/过滤器；同类任务不得复制生命周期过滤；测试必须输出理论集合、来源集合和差集 |
| 告警恢复：`AGENTS.md` 1.7；`ADR-0002` 决策第 6 条；`docs/技术架构.md` 298、328 | `server/services/jobAlertMailer.js` 的 `verifyAlertScope()` 曾在外层提前拒绝 `dependency_blocked`，未进入 `server/services/jobRecoveryEvidence.js` 的 `verifySlotRecoveryEvidence()`；0.8.1.58 还暴露了历史 `mode` 分支不一致 | 新增 `alert_type` 证据注册表；未声明证据类型的告警不得进入收敛路径。`data_quality`、`dependency_blocked`、来源告警必须分别绑定数据集分区、槽位成功证据、实际关闭的 `source:*` 作用域 |
| 外部接口与重试：`AGENTS.md` 1.2、1.3；`ADR-0002` 决策第 1、2 条 | 统一 Guard、检查点和续跑能力已经存在，但公告列表/PDF 正文并发边界等实现分支仍可能各自解释预算 | 静态检查禁止业务模块直连外部接口或自建预算；集成测试验证失败分类、`BUDGET_WAIT`、检查点、剩余队列和恢复时间均可续跑 |
| 测试与自动门禁：`AGENTS.md` 第 6 节；`ADR-0002` 影响范围 | 本轮有专项回归，但没有“规则条款 → 全部代码分支”的通用对照审计 | 每次新增任务、告警类型或状态分支必须通过契约矩阵测试；审计脚本输出“有规则无实现”清单，不能只依赖文字规范 |
| 生产补跑和发布验收：`AGENTS.md` 生产部署铁律、`docs/生产部署流程.md` | 现行流程要求预览和明确 ID，但“告警收敛”容易被误读成“告警清零” | 补跑验收必须同时保留目标对象、运行、分区、质量和恢复证据；来源告警按数据库实际关闭的 `source:*` 作用域核对，不得用通配熔断或空查询代替 |

### 4.1 项目实际术语对照

- 统一恢复证据服务：`server/services/jobRecoveryEvidence.js` 的 `verifySlotRecoveryEvidence()`；告警入口是 `server/services/jobAlertMailer.js` 的 `verifyAlertScope()`。
- 日期边界：`expectedDataDate()`、任务结果的 `targetTradeDate`、`ops.dataset_partitions.partition_key`（分区日）与 `scope_key`。
- 告警作用域：`ops.alert_notifications.scope_type/scope_key`；数据质量使用 `data_quality`，依赖阻塞使用 `dependency_blocked`。
- 来源告警：必须按数据库实际关闭的 `source:*` 作用域核对；通配熔断不能自动当作恢复证据（`AGENTS.md:21`）。

## 五、真正需要补齐的门禁与优先级

### P0：立即补齐

1. **任务定义门禁**：任务契约必须显式声明 `dataDatePolicy`、`producesDatasets`、`datasetDependencies`；允许业务上确实为空，但必须写出空数组，缺字段时任务注册直接失败，不能依赖 `DEFAULT_JOB_OPTIONS` 的默认值。
2. **告警类型门禁**：新增 `alert_type` 必须登记证据类型、作用域类型和验证入口；未登记的告警不得进入自动收敛路径。这正是本轮 `dependency_blocked` 外层分流缺口的通用解法。
3. **规则—实现对照审计**：逐条扫描 `AGENTS.md`、`ADR-0002` 和技术架构条款，对照代码分支并输出“有规则无实现”清单；首批固定核查 0.8.1.70 的 `dependency_blocked` 分流、0.8.1.57 的分区日期作用域、0.8.1.58 的任务模式继承。

### P1：近期补齐

- 增加“日期边界 + 生命周期 + 依赖恢复 + `source:*` 作用域”的公共回归测试模板。
- 为任务契约、告警类型和数据集注册表生成可审计矩阵，检查缺字段、重复实现和未覆盖分支。
- 把外部任务的检查点、退避、无进展保护和 `BUDGET_WAIT` 续跑纳入集成测试，不再只测单个正常样例。

### P2：持续改进

- 建立生产补跑结果的统一验收报表，把任务、分区、告警和恢复证据串成可查询链路。
- 对重复出现三次以上的事故，把散文规则升级为自动门禁；现有 `check:knowledge` 只负责知识路由和规则同步，不能冒充业务不变量门禁。

## 六、仍未收敛项与遗留风险

“告警收敛”不等于“所有告警清零”。以下状态必须按证据保留：

- CNINFO `topSearch` 历史 403 权限告警。
- Tushare 权限拒绝、额度耗尽或来源熔断告警。
- 任何没有对应数据集分区、来源成功探测或严格槽位证据的历史告警。

这些记录保留是为了区分“仍有外部风险”和“本轮已修复问题”，不是遗漏关闭。`recovery`、`worker_recovered` 等恢复通知保留为 `sent` 历史记录，也不应被误算成待处理告警。
