# 总资产“今日涨跌 / 历史快照校准差额”整改方案

- 日期：2026-08-15
- 状态：已实施“权威导入锚点/总资产续算”核心链路；在线归因、港股历史币种迁移、完整重算闭环仍按阶段任务待继续实施
- 范围：涨跌归因、权威收益历史导入、交易币种、净值快照、历史重算
- 不包含：本方案不直接修改生产数据，不执行生产同步

## 1. 确定结论

针对截图对应的实际情况，前天、昨天、今天均无交易，因此 `+¥7,661.86` 的**直接来源不是交易现金端**，而是上一日总资产快照与系统后来用于重建上一日资产的价格、汇率不一致。

无交易、无现金流水、持仓数量不变时，现有代码中的校准差额可以严格化简为：

```text
历史快照校准差额
= 使用“previousPrices + prevNav.hkRate”重建的上一日总资产
- 上一日 nav_history.total_asset
```

所以 `+¥7,661.86` 的确定含义是：系统用后来读取到的“上一日价格/汇率”重建出的上一日资产，比当时保存的总资产快照高 7,661.86 元。它不是收益、不是入金，也不是漏记交易。

同时，现有公式**另行确定存在“交易只计算现金端、没有同时计算持仓端”**的问题。该问题会在发生交易时制造另一类残差，但不是本次三天无交易场景的直接原因。

买入时，当前代码把 `成交额 + 费用` 作为现金流出计入“其他变动”，但股价影响仍使用“当前持仓数量 × 当前价与昨价之差”，没有把本次新增数量对应的持仓市值计入。卖出时同理。因此只要统计区间内发生买卖，就会产生接近成交本金的伪“历史快照校准差额”。

最小复现：账户原有现金 10,000 元，当日以 10 元买入 100 股，股价未变、无费用。

```text
真实结果：现金 -1,000，持仓市值 +1,000，总资产变化 0
现有归因：股价影响 0，其他变动 -1,000
现有校准差额：0 - 0 - (-1,000) = +1,000
```

也就是说，校准差额并不是一类真实资产变动，而是“当前总资产变化”减去若干口径不一致或不完整的归因项后得到的兜底残差。

截图中的 `+¥7,661.86` 不能直接认定为某一笔交易，因为截图展示的三项 `-10,779.47 - 27.71 + 0` 合计为 `-10,807.18`，与画面总涨跌 `-3,145.32` 相差正好 `+7,661.86`；但页面底部公式又没有把这项校准差额列入等式。该数值的直接含义只是：**系统少解释了 7,661.86 元**，并不代表账户真实增加了这笔钱。

## 2. 核查证据

| 问题 | 代码位置 | 已确认事实 | 影响 |
|---|---|---|---|
| 交易只算现金端 | `public/shared/core-tables.js` 的 `bindChangeTip()` | 买入按 `-amount-fee`、卖出按 `+amount-fee` 计入 `ledgerChange`；`priceImpact` 只按当前数量计算价格差 | 买卖本金被制造成校准差额 |
| 归因公式漏项 | `public/shared/core-tables.js` | 页面底部等式只展示“股价 + 汇率 + 其他”，未加 `snapshotDrift` | 展示等式与总涨跌不成立 |

### 2.1 本地业务库实测

2026-08-14 对本地业务库只读核查结果：

- `nav_history` 共 218 条，216 条缺少 `snapshot_at`。
- 港股交易共 38 条，其中 22 条的 `amount` 等于 `price × quantity`，说明至少这部分记录按港币成交额保存，却被现有现金账直接当人民币使用。
- 38 条港股交易中，35 条缺少可用于自动判定结算口径的对应历史汇率；因此不能直接批量乘汇率修数据，必须先分级审计。

以上是本地库证据，不等同于生产库数量；生产实施前必须运行同一只读审计。

### 2.2 本次无交易场景定责

本地业务库与实际代码联合核查已确认：

- 2026-08-13 至 2026-08-14，华泰账户和招商证券账户均为 0 笔交易、0 笔现金流水，交易因素已排除。
- `saveDailyPricesToDB()` 只判断 `isMarketOpen()`。午间休市时该函数也会认为“市场已关闭”，从而可能把午间价格写成当日 `daily_prices`；写入后又通过 `localStorage` 当日只保存一次，真正收盘后不再覆盖。
- `recordNav()` 会在之后的每次刷新继续用最新行情覆盖同日 `nav_history.total_asset`。于是同一天可能出现“午间价格基准 + 收盘总资产快照”的组合。
- `server/routes/accounts.js` 查询 `previousPrices` 时按每只证券分别取“今天之前最新一条”，不要求与基准快照为同一天。当前本地华泰账户的基准价实际同时包含 2026-08-12 和 2026-08-13 两个日期。
- `server/db/accounts.js` 读取历史快照汇率时使用 `COALESCE(fx.rate, nh.hk_rate)`，优先用汇率表覆盖快照原值，但不重算同一行的 `total_asset`。本地 2026-08-12 快照原始汇率为 `0.861377`，接口读取值被覆盖为 `0.873`；按相同持仓重建后，华泰账户与快照相差约 4,592.07 元，招商证券账户相差约 9,519.26 元。
- `snapshot_at` 大量为空，无法追溯同日快照究竟对应午间、收盘还是盘后行情；同日快照又会被覆盖，因此截图时刻的逐证券旧输入已不可恢复。

定责结论：本次差额属于**历史估值基准漂移**。确定的代码责任是日价格保存时点错误、价格日期混用、历史汇率读取时覆盖原快照汇率；不是用户漏录交易。

### 2.3 收益历史导入是否影响本次问题

对本次截图，导入不是直接原因：本地账户的导入前备份时间停留在 2026-08-03，截图涉及的 2026-08-12 至 2026-08-14 快照是在导入之后自动生成的。

但产品规则现调整为：**用户确认导入的数据是最高权威来源，必须覆盖相同日期的系统快照，并能替换当前总资产及其对应口径。**

现有实现不能满足该规则，原因是首页总资产由 `持仓实时市值 + 现金` 重新计算；只覆盖 `nav_history.total_asset`，刷新页面后仍会回到持仓和现金计算值。因此不能只修改历史表，必须同时建立可结转的导入对账口径。

新的来源优先级：

| 来源 | 优先级 | 同日覆盖规则 |
|---|---:|---|
| 用户确认导入 `imported` | 100 | 无条件覆盖同日自动/手工快照；后导入批次覆盖前导入批次 |
| 用户手工确认 `manual` | 80 | 可覆盖系统快照，不覆盖导入快照 |
| 系统收盘快照 `system_close` | 50 | 只覆盖较低级系统/遗留记录 |
| 系统盘中快照 `system_intraday` | 20 | 不覆盖收盘、手工或导入快照 |
| 遗留数据 `legacy` | 10 | 可被以上任一来源替换 |

导入后的硬规则：

1. 权威导入模式必须包含 `date + nav + totalAsset + invested + cash`，分别对应日期、净值、券商总资产、累计投入资金、券商现金余额；缺少任一项均不能执行“权威替换”。
2. 同日现有 `nav`、`total_asset`、`invested`、`cash_cny`、估值时点均以导入批次为准；持仓数量继续使用系统现有持仓，不由收益历史导入覆盖。
3. 导入后以券商现金替换系统现金锚点，以 `券商总资产 - 券商现金` 作为券商持仓总值锚点；它与系统同一时点持仓估值的差值只保存在导入批次审计信息中，不进入现金、持仓、总资产或收益归因，也不在页面长期展示。
4. 导入日总资产直接等于券商总资产，状态为 `broker_exact`；导入日之后采用“券商锚点 + 本系统新增变化”续算，状态为 `system_delta_estimate`，不得冒充券商实时精确值，也不携带任何长期差额项。
5. 自动行情刷新和历史重算不得覆盖导入快照，但必须在其后按导入锚点继续计算。
6. 每次导入先保存完整批次备份；重新导入同一日期时新批次生效，旧批次保留版本并可整批回滚。

## 3. 正确业务口径

### 3.1 统一基准

每次归因只允许使用一个明确区间：

- 基准：估值时刻之前最近一条有效快照 `baseSnapshot`。
- 当前：同一次估值生成的持仓、现金、价格和汇率 `currentValuation`。
- 交易与现金流水：严格按 `(baseSnapshot.snapshot_at, currentValuation.snapshot_at]` 取数。
- 如果旧快照没有 `snapshot_at`，标记为 `legacy_incomplete`，不能假装有精确的同日边界。

禁止继续混用“倒数第二条快照日期”“昨天最新价”“当前实时总资产”三个不同时点。

### 3.2 完整恒等式

先用交易账本重建基准时点的现金和持仓，得到 `baseLedgerTotal`。完整归因必须满足：

```text
当前总资产 - 基准快照总资产
= 价格影响
+ 汇率影响
+ 外部资金流
+ 交易及持仓变动影响
+ 基准快照校准
```

各项定义：

- 价格影响：基准和当前共同持有数量 × 价格变化 × 基准汇率。
- 汇率影响：港股共同持有数量 × 当前港币价格 × 汇率变化。
- 外部资金流：入金、出金、分红、利息等真正改变账户外部资金的流水。
- 交易及持仓变动影响：买卖现金结算与对应数量市值变化的净额；正常买卖本金应互相抵消，只留下费用、滑点和真实盈亏。
- 基准快照校准：`baseLedgerTotal - baseSnapshot.totalAsset`，仅用于标识遗留快照本身与账本不一致；使用权威导入锚点时该项固定为 0。

“交易及持仓变动影响”不得再只取现金结算额。任何一项无法计算时，接口返回 `data_incomplete` 和缺失原因，禁止用一个无来源残差凑平等式。

### 3.3 币种口径

- `price`、`amount`：证券报价币种金额；A 股/可转债为 CNY，港股为 HKD。
- `fx_rate_to_cny`：成交时锁定的报价币种兑人民币汇率；CNY 固定为 1。
- `amount_cny`：人民币结算本金，计算式为 `amount × fx_rate_to_cny`。
- 手续费字段统一存人民币。
- 现金账只允许使用 `amount_cny` 和人民币费用。
- 市值和现金必须使用同一汇率口径；不得一边乘汇率、一边不乘。

### 3.4 权威导入总资产口径

导入确认时建立“券商现金锚点 + 券商持仓总值锚点”。持仓数量继续使用本系统数据，并保存同一时点的系统持仓估值，用于计算导入之后的持仓增量：

```text
anchorBrokerTotal = 导入的券商总资产
anchorBrokerCash = 导入的券商现金
anchorBrokerPositionValue = anchorBrokerTotal - anchorBrokerCash
anchorSystemPositionValue = 导入时按本系统行情和汇率计算的持仓市值

导入当时：effectiveTotal = anchorBrokerTotal
导入之后：
effectivePositionValue(t)
  = anchorBrokerPositionValue
  + [systemPositionValue(t) - anchorSystemPositionValue]

effectiveCash(t)
  = anchorBrokerCash
  + 锚点后的外部资金流
  + 锚点后的交易现金结算

effectiveTotal(t) = effectivePositionValue(t) + effectiveCash(t)
```

例如，券商导入总资产为 1,000,000 元、现金为 200,000 元，则券商权威持仓总值为 800,000 元。本系统同一时点持仓估值为 795,000 元，不创建 5,000 元差额项。次日本系统持仓估值变为 797,000 元、现金无变化，说明持仓新增变化为 +2,000 元，因此当前续算总资产为 1,002,000 元。

准确性边界：

- 导入记录中的总资产、现金、持仓总值、净值、累计投入资金是券商精确值。
- 同一批导入之间的总资产和净值变化也是券商精确值。
- 没有新导入的盘中或后续日期，只能按本系统行情和汇率计算增量，属于续算估值；系统无法凭空知道券商当时使用的汇率和价格。
- 下一次导入到达后，直接以新券商总资产替换续算估值，并重建新的锚点；替换差异不记为收益、现金或历史校准差额。
- 如果要求逐只持仓市值也与券商完全一致，导入文件必须额外提供逐证券市值，或者券商实际成交/估值价格及汇率；仅凭总资产和现金无法唯一反推出每只证券的券商市值。

券商持仓总值与本系统同一时点持仓估值的差值可能来自港币汇率、行情时点、价格精度和费用入账时点不同。该差值只写入 `nav_import_batches.diagnostics.position_source_gap_cny` 供排查；导入现金与原系统现金的替换差值另存 `cash_replacement_delta_cny`：

- 不创建长期资产项。
- 不加到现金或持仓。
- 不计入收益或今日涨跌。
- 不要求以后一直保持相同差值。
- 下一次导入直接建立新的券商锚点，旧锚点停止生效。

- 导入现金为券商权威现金余额，必须满足 `0 <= cash <= totalAsset`；导入当日权威持仓总值固定为 `totalAsset - cash`。
- 持仓代码和数量始终使用本系统持仓；收益历史导入不新增、删除或修改持仓。
- 导入历史日期且本地账本可完整回放时，保存该日 `system_market_value_at_snapshot`，用于从最后一条导入记录向后续算。
- 券商只提供持仓总值、未提供逐证券市值时，不把券商与系统的估值差按比例硬摊到每只证券。页面分为两层：账户总览显示“券商持仓总值”，持仓明细显示“系统参考估值”；两者口径不同，不要求逐证券行之和等于券商持仓总值。
- 导入历史日期但本地账本无法完整回放时，总资产和净值仍以导入为准；该行标记 `total_authoritative`，收益总额准确，但价格/汇率细分显示“导入数据未提供明细”，不得制造伪分解。
- 最新导入日期无法取得同一时点系统持仓估值时，不允许伪造实时续算，状态标记 `anchor_incomplete`；页面保持显示最新券商总资产和现金，直到补齐锚点或导入更新日期的数据。
- 券商采用的港股汇率允许未知。`broker_fx_rate` 为可选字段；未提供时不得用系统汇率反向篡改券商总资产，完整价格/汇率细分状态标记为 `broker_fx_unknown`。
- 导入的 `invested` 是累计净投入资金的权威值，用于计算累计盈亏 `totalAsset - invested`，并用于校验相邻导入日的资金变化；不得再用本地现金流水覆盖导入值。
- 导入日之后的累计投入资金按 `导入 invested + 锚点之后本地净入金` 续算；现金按 `导入 cash + 锚点之后资金流和交易结算` 续算；下一次导入再次以券商投入资金和现金为准重置锚点。

## 4. 目标实现

### 4.1 后端成为唯一计算源

新增 `server/services/navAttribution.js`，集中完成：

1. 选择唯一基准快照。
2. 按 `snapshot_at` 读取区间交易和现金流水。
3. 重建基准及当前持仓、现金。
4. 计算全部归因项并做分级精度校验。
5. 返回 `status`、`reasonCodes`、输入时点和计算版本。

前端 `public/shared/core-tables.js` 只负责展示后端结果，删除现有本地拼接 `priceImpact / ledgerChange / snapshotDrift` 的计算。不得在前后端保留两套公式。

建议接口：

```http
GET /api/accounts/:name/nav-attribution?as_of=2026-08-14
```

返回结构：

```json
{
  "status": "complete",
  "calcVersion": "nav-attribution-v2",
  "baseSnapshotAt": "2026-08-13T15:00:00+08:00",
```

### 4.2 数据库变更

新增迁移，不修改旧迁移文件。

`trades` 增加：

```sql
quote_currency  text
fx_rate_to_cny  numeric
amount_cny      numeric
currency_status text not null default 'legacy_unresolved'
```

`nav_history` 增加：

```sql

source_priority  integer not null default 10
import_batch_id  text
market_value_cny numeric
cash_cny         numeric
broker_fx_rate  numeric
system_market_value_at_snapshot numeric
anchor_import_batch_id text
calc_version    text
calc_status     text not null default 'complete'
diagnostics     jsonb not null default '{}'::jsonb
is_locked       boolean not null default false
input_hash      text
```

沿用现有 `snapshot_at`，但改为服务端生成并强制写入；客户端不再提供可信时间。

`account_data` 增加：

```sql
nav_dirty_from date
```

用于记录最早待重算日期。多次修改使用 `LEAST(旧值, 新值)` 合并，成功重算后清空；失败必须保留并返回 `recompute_pending`。

新增 `nav_import_batches`：

```sql
id             text primary key
username       text not null
account_name   text not null
imported_at    timestamptz not null
range_start    date not null
range_end      date not null
row_count      integer not null
input_hash     text not null
status         text not null
backup_payload jsonb not null
```

新增 `nav_position_snapshots`，保存可用于精确归因的逐证券基准：`snapshot_id / instrument_id / quantity / price / quote_currency / fx_rate_to_cny / market_value_cny / source`。只有具备该明细或可由完整账本回放时，才返回完整价格、汇率归因。

`nav_history.calc_status` 增加明确状态：

- `broker_exact`：该日期总资产、现金、净值、投入资金直接来自券商导入。
- `system_delta_estimate`：以最近券商锚点叠加本系统行情、汇率和账本增量得到。
- `broker_fx_unknown`：券商未提供汇率或逐证券市值，不能精确拆分券商口径下的股价与汇率影响。
- `anchor_incomplete`：缺少同一时点系统持仓估值，不能继续向后续算。

约束：权威导入行 `snapshot_source='imported' AND source_priority=100 AND is_locked=true AND import_batch_id IS NOT NULL AND total_asset IS NOT NULL AND invested IS NOT NULL AND cash_cny IS NOT NULL AND system_market_value_at_snapshot IS NOT NULL`，并满足 `market_value_cny = total_asset - cash_cny`、`0 <= cash_cny <= total_asset`。

### 4.3 历史港股交易迁移规则

先执行 dry-run，只输出分类，不写库：

1. CNY 交易：`fx_rate_to_cny=1`，`amount_cny=amount`。
2. 港股且 `amount ≈ price × quantity`：只有在存在可靠成交日汇率时，才可认定 `amount` 为 HKD 并计算 `amount_cny`。
3. 港股且 `amount ≈ price × quantity × 历史汇率`：认定旧 `amount` 已是 CNY，同时补存报价币种金额和汇率。
4. 缺汇率、差额超容差或语义冲突：标记 `legacy_unresolved`，禁止自动修正现金和历史快照。
5. dry-run 报告经人工确认后才允许 `--apply`；应用前备份相关账户的 `trades`、`account_data`、`nav_history`。

不得根据证券市场直接无条件重算全部旧交易，本地库已有 35 条港股记录缺少足够历史汇率证据。

### 4.4 快照和重算闭环

- 交易、持仓事件、现金流水的新增、编辑、删除，必须在同一事务内更新 `nav_dirty_from`。
- 路由不能再吞掉重算异常后返回“全部成功”；应返回业务操作结果以及 `navRecompute: complete|pending|blocked`。
- `server/jobs/replayNav.js` 必须先把 PostgreSQL `Date` 统一转换为 `YYYY-MM-DD`，再建立汇率 Map。
- 重算前执行完整性闸门：期初持仓/现金、交易、每日价格、汇率、无重复、无非法超卖全部通过才可写快照。
- 缺数据时保留原快照，记录 `calc_status=incomplete` 和明确 `reasonCodes`。
- `snapshot_source=manual/imported` 或 `is_locked=true` 的快照不得被自动覆盖。
- 自动生成导入日期之后的快照时，分别使用最近一条权威导入的 `market_value_cny / system_market_value_at_snapshot / cash_cny` 作为持仓与现金锚点，只累计锚点之后的持仓市值变化、资金流和交易结算；不得携带固定差额资产项。
- 重算必须幂等：相同输入重复执行，金额、状态和版本完全一致。

### 4.5 权威导入事务流程

`POST /api/nav/import` 调整为服务端一次事务完成：

1. 解析到临时 staging，不直接写 `nav_history`。
2. 校验日期、重复行、数值，以及净值、总资产、累计投入资金、现金必填，确认估值时点及人民币单位；校验现金不得小于 0 或大于总资产。
3. 按日期读取本地持仓、现金、价格、汇率；能回放则生成资产拆分及逐证券快照，不能回放则明确标记 `total_authoritative`。
4. 返回预览：每个冲突日期展示“原/新总资产、原/新累计投入、原/新现金、券商持仓总值、同一时点系统持仓估值、审计差值、将被覆盖的字段”；审计差值明确标记为“不进入资产与收益”。
5. 用户确认后，在事务内写导入批次备份、以优先级 100 UPSERT 同日快照、重建最新导入日期之后的非导入快照。
6. 更新当前账户数据版本并返回新的总资产、收益历史和归因状态；任一步失败整体回滚。

前端不再先修改内存 `navHistory` 再请求后端。前端只上传映射结果、展示服务端预览，并使用提交成功后的服务端完整结果刷新页面。

本次已落地的核心范围：迁移 072/073/074 已增加导入来源锁定、券商现金/持仓锚点、交易币种结算、历史港股人民币结算回填、归因快照和 `nav_dirty_from`；`/api/nav/import` 已强制五字段、原子批次写入、同日覆盖、输入哈希幂等，并按导入日真实收盘价/历史汇率建立系统锚点；读取汇总已按最新导入锚点续算；普通净值写入、删除和全量保存不会覆盖锁定导入行；后端统一归因结果已接入页面；批次回滚已提供接口。数据库不可用时不得宣称接口回归通过，必须在 PostgreSQL 可连接环境执行第 6 节验收。

## 6. 必须通过的验收用例

金额恒等式容差统一为人民币 `0.01` 元。

| 场景 | 预期 |
|---|---|
| CNY 买入，价格不变，无费用 | 现金与新增持仓市值抵消，总资产变化 0，校准 0 |
| CNY 卖出，价格不变，无费用 | 现金与减少持仓市值抵消，总资产变化 0，校准 0 |
| CNY 买卖有费用 | 交易及持仓变动只体现真实费用，不出现成交本金残差 |
| HKD 10 元买 100 股，汇率 0.9 | 人民币现金 -900、持仓 +900，总资产变化 0 |
| 仅股价变化 | 变化全部进入价格影响 |
| 仅港币汇率变化 | 变化全部进入汇率影响 |
| 仅入金/出金 | 变化全部进入外部资金流 |
| 同日先快照后交易/流水 | 依靠 `snapshot_at` 正确纳入区间，不漏不重 |
| 今天无快照、跨周末 | 使用最近有效快照作为唯一基准，各项日期一致 |
| 午间打开并刷新、收盘后再次刷新 | 午间价不得保存为日收盘价；收盘价与净值快照使用同一批估值输入 |
| 历史汇率表后来补写或修改 | 已保存快照的 `hk_rate` 与 `total_asset` 不被静默拆成两个口径 |
| 某只证券基准日无价格 | 返回 `data_incomplete`，不得回退到另一日期后继续凑差额 |
| 权威导入缺少日期、净值、总资产、累计投入资金或现金任一项 | 拒绝提交并明确提示缺少的必填列 |
| 权威导入覆盖最近两条快照 | 导入值覆盖线上值，立即成为今日涨跌基准；自动刷新不能覆盖回来 |
| 券商总资产与本地持仓市值+现金不同 | 券商总资产立即生效；差值仅进入批次审计，不产生长期资产项或收益项 |
| 导入现金大于总资产或小于 0 | 拒绝导入，不修改任何数据 |
| 导入前后持仓 | 持仓代码和数量完全不变 |
| 导入文件提供完整现金/持仓拆分 | 使用导入拆分并逐项校验，总资产差额必须不超过 0.01 元 |
| 历史导入缺少持仓明细且账本不可回放 | 总资产和收益准确；归因状态为 `total_authoritative`，不展示虚构的价格/汇率拆分 |
| 导入后刷新行情 | 当前总资产 = 券商持仓锚点 + 本系统持仓增量 + 券商现金锚点 + 后续现金变化，不出现固定差额项 |
| 券商未提供港股汇率 | 券商总资产仍为权威值，标记 `broker_fx_unknown`，不伪造精确汇率归因 |
| 同一持仓因汇率不同导致券商持仓总值与系统明细合计不同 | 保留两层口径并清晰标注，不建立差额资产、不按比例摊到证券 |
| 导入日查看总资产 | 显示券商导入值，状态为 `broker_exact` |
| 导入后尚未再次导入 | 显示券商锚点续算值，状态为 `system_delta_estimate`，不标成券商实时值 |
| 再次导入券商数据 | 新券商值无条件替换续算估值并建立新锚点，替换差异不进入收益归因 |
| 相邻导入日累计投入发生变化 | 以导入投入资金差额识别资金变化，不被本地现金流水反向覆盖 |
| 同日重复导入 | 后确认批次生效，前批次保留版本，可整批回滚 |
| 同一文件重复提交 | 输入哈希命中，返回原批次结果，不重复写入 |
| PostgreSQL 返回 `Date` 类型汇率日期 | 历史重算可以按字符串日期命中汇率 |
| 缺历史价格/汇率/期初仓位 | 返回 `data_incomplete`，不覆盖旧快照，不生成伪校准 |
| 手工/导入锁定快照 | 自动重算不覆盖 |
| 同一输入重复重算 | 输出完全一致 |
| 任意完整数据场景 | 全部归因项之和与总资产变化误差不超过 0.01 元 |

数据库验收：

- 新生成快照的 `snapshot_at` 缺失数必须为 0。
- 权威导入行的 `source_priority`、`import_batch_id`、`is_locked`、`input_hash` 缺失数必须为 0。
- 任意权威导入行的 `total_asset`、`invested`、`cash_cny`、`system_market_value_at_snapshot` 均不为空，且 `total_asset = market_value_cny + cash_cny`；券商与系统持仓估值差只存在批次审计信息中。
- 新港股交易的 `quote_currency`、`fx_rate_to_cny`、`amount_cny` 缺失数必须为 0。
- `currency_status=legacy_unresolved` 的记录必须有原因，且不会被自动历史修复。
- 所有 `nav_dirty_from` 要么已成功清空，要么有可见的 pending/blocked 原因，不能静默滞留。
