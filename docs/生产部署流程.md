6. **回读与异常接续**：逐条回读确认状态、关联版本和处理历史，记录已更新、待核查、冲突和失败项；零条匹配须与读取失败明确区分。部署失败或验收未通过时不写“已实施”；明确失败的回写不改变原状态，列入同一发布记录待续办，超时等结果未知时先回读再决定是否重试。代码发布成功但反馈未回写时，分别记录两者结果，不能宣称反馈闭环完成。

### 测试分级与全量结果复用

本节是测试执行时机、范围与结果复用的权威规则（2026-11-04 用户批准）。替代此前「任何代码交付均全量」的统一要求，适用于各开发者、Agent、路由 checks 及交接/发布 Skill；各专项中「每期/每次代码交付须全量」等旧频次表述统一按本节执行。原专项的业务断言、必需环境与发布验收条件继续保留，历史实测结果不回改。

| 阶段/变更 | 必须验证的范围 |
|---|---|
| 纯文档、规则说明、知识路由或 Skill 文本 | `npm.cmd run check:knowledge`，复核引用、状态、格式与 Git 差异；不启动服务或执行全量业务测试。修改检查器、测试运行器或 CI 行为属于代码/配置变更，不能按纯文档处理 |

| 共享基础能力、鉴权/会话、迁移、调度、依赖、部署配置或跨模块重构 | 扩大到消费者、权限/失败/兼容及相关集成回归，执行原架构/日期/SQL/任务矩阵等适用门禁；影响边界不清、无法列清消费者或存在未定位回归时，开发交接前提前全量。选测不足或关键专项未执行时保持待验收 |
| 整合并准备发布 | 完成合并、冲突处理、版本记录及专项验证后，对最终应用/测试代码树运行一次 `npm.cmd run test:all`，或核对下列条件全部满足的已有全量证据。各任务的专项通过不等于整合树全量通过 |
| 部署之后 | 核对版本/提交、服务、静态资源及本次接口/页面/任务的实际结果，按第5节完成验收；不在生产运行写库测试 |

**全量证据与复用条件**：

- 原任务卡或发布回执保存执行日期、命令、runId（入口提供时）、完整 SHA；未提交时保存基线及可还原的精确差异/代码树标识，提交后补对应关系。记录 Node/Python/PostgreSQL、测试库/迁移与夹具、相关配置/模型等实际环境依据，结果须含通过/失败/跳过、耗时及日志位置，不保存密钥。
- 复用前逐项比对目标树与已测树。仅提交号不同、分支包含旧提交或聊天说「已测过」均不足以复用；多任务合并、冲突解决只要改变应用代码、测试/辅助工具、依赖及锁文件、模型/夹具、数据库迁移、运行配置或部署文件，原发布全量即失效。相关运行环境、测试库 schema/样本或模型变化也须重新全量。
- 已测应用/测试树和相关环境均未变，只有文档、规范说明或发布元数据变化时，可沿用已有全量；仍对变动内容做知识/引用/格式检查，版本元数据另做版本一致性及对应本地运行验收。变更夹带在 `package.json`/锁文件中的依赖、脚本或配置时不属于元数据例外。
- 证据须无失败且必需项未跳过；环境缺失、超时、中断、未定位失败不能视为通过或用旧绿结果覆盖。按原规则或用户明确批准的例外单列跳过及未验范围，不写成全部通过。证据缺失、差异或环境无法核实时，由发布负责人补跑，不能仅因任务卡写「完成」跳过。
- 开发交接允许写「专项通过，发布全量待整合后执行」，它是阶段安排，不是虚报全量通过；选测理由、必需专项、文档和固定提交齐全即可交接。运行器尚未自动选择测试或缓存证据，以上比对由负责人执行。GitHub Actions 的 Linux/PostgreSQL 全量保留，当前不作为省略本地最终全量的替代。

    ```bash
    actual=$(sha256sum <组>.sql.gz.gpg | awk '{print $1}')

    ```

涉及网站性能优化时，必须额外验收：

- `curl -sI --http2 https://<域名>/` 确认 HTTP/2；对 JSON、JS、CSS 请求确认 `Content-Encoding: gzip`、单一 `Cache-Control`，公共接口第二次带 `If-None-Match` 返回 304。静态 location 必须保留 `proxy_hide_header Cache-Control`，避免 Node `express.static` 的默认 `max-age=0` 与 Nginx 缓存头重复。
- 并发请求超过 30 个首页静态资源时不得出现 429；`limit_conn` 只能位于动态 `location /` 内，不能配置在 `server` 级影响 HTTP/2 静态资源并发流。
- Nginx 日志包含 `request_time`、`upstream_connect_time`、`upstream_response_time`；必要时用 `curl -w` 记录 `time_connect`、`time_appconnect`、`time_starttransfer`、`time_total`。
- 首页冷启动与回访分别记录 LCP/CLS；首页卡片保持固定最小高度。账户接口确认摘要请求不返回交易/净值历史，进入持仓页仍能加载完整数据。
- 修改 Nginx 前备份实际生效的 `/etc/nginx/nginx.conf`、`/etc/nginx/conf.d/portfolio.conf`；模板仓库文件不包含生产 `http` 块时，回滚必须同时恢复服务器备份，不能只回滚 Git 模板。

涉及统一任务调度、任务依赖或数据集发布门禁变更时，还必须确认 Worker 已加载新任务定义，并核对受影响任务的计划时刻、上游任务依赖、目标业务日分区及质量状态。IPO链路变更重点检查：`ipo_history_sync` 的18:00核心、19:30核心和19:35补全阶段均已生成计划实例，`ipo_calendar_refresh` 为18:05/19:45且只在对应时段的 `ipo_history` 基础分区质量通过后执行；19:30核心槽位使用方案声明的 `freshnessGate=false`，避免晚间公告被前一轮水位短路。代码部署本身不等同于人工补数，不得顺带手工触发生产采集。

### 独立远程验收命令（Windows/Codex）

- 通过 Paramiko 执行多行远程脚本时，优先复用 `deploy/deploy_password.py` 的 `run_sudo`（内部使用 `shlex.quote`），或使用 `exec_command('sudo bash -s')`，通过标准输入写入脚本后调用 `shutdown_write`。
