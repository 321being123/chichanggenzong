# 持仓管理架构与交易数据整改方案

> 文档日期：2026-08-03  
> 核查范围：持仓管理总览、持仓明细、交易管理、现金流、历史净值、账户保存与后台净值任务  
> 文档性质：代码与本地数据只读核查后的整改方案；不包含代码修改、生产数据修改或部署操作

## 一、结论

持仓管理当前的主要问题不在总览页面的加总公式，而在总览依赖的持仓、交易、现金和净值没有形成统一账本。

目前系统同时允许：

- 录入交易并自动修改持仓；
- 直接编辑、导入或删除持仓；
- 单独删除或清空交易；
- 单独增删现金流；
- 前台和后台分别生成历史净值。

这些入口没有使用同一套业务规则。任意一边发生修改，都可能造成持仓数量、交易净数量、现金余额和历史净值互相不一致，最终表现为持仓总览、交易管理页和收益页数据对不上。

近期完成的结构化数据源整改已经解决旧 JSON 数据“还魂”、账户删除残留和部分并发覆盖问题，但持仓业务账本仍未完成收口。

## 二、本地实测结果

本次仅核查本地数据库，未连接或修改生产数据库。

### 2.1 结构完整性

- 未发现没有账户主记录的持仓、交易、净值、现金流、每日价格或指数历史。
- 旧 `account_data.data` 中仍有 8 组业务数组残留，但当前仅作为归档，不参与日常读取。
- 6 个只有账户元数据、尚未产生业务数据的账户属于正常空账户提示。
- 项目自带的账户数据源、版本保护、零持仓和净值备份测试均通过。

### 2.2 业务一致性

| 账户 | 持仓数 | 交易数 | 核查结果 |
|---|---:|---:|---|
| 华泰账户 | 43 | 49 | `160719` 持仓数量为 40，但交易净数量为 120 |
| 招商证券账户 | 32 | 34 | 32 笔交易的 `amount` 不等于 `price × quantity` |

华泰账户的 `160719` 存在三条内容完全相同、ID 不同的买入记录：

- 日期：2026-06-26；
- 方向：买入；
- 单价：2.4528；
- 数量：40；
- 金额：98.11；
- 实际只应保留一条，当前多出两条；
- 重复记录使现金额外减少约 196.22 元。

招商证券账户的交易记录存在“交易价、持仓成本价、成交金额”混用。例如部分记录的成交金额等于持仓成本价乘数量，而交易价格保存的是另一价格。交易管理页同时展示这两个字段时，会形成自相矛盾的成交记录。

以上说明现有结构审计只能证明数据库没有孤立记录，不能证明持仓、交易、现金和净值在业务上相互一致。

## 三、问题明细

### 3.1 持仓与交易没有统一事实来源

当前交易录入会同时写入交易和修改持仓，但后续操作不是对称的：

- 删除交易只删除交易记录，不恢复对应持仓；
- 清空交易不会调整持仓；
- 直接修改持仓数量不会生成资金或交易调整；
- 删除持仓不会处理交易历史和现金；
- 删除现金流后不会立即重算前端现金。

结果是：持仓数量来自 `positions`，现金来自 `cash_base + cash_flows + trades`，两者却可以分别修改。总览把二者直接相加，因此任意单边修改都可能制造虚假的资产增加或减少。

### 3.2 两条交易录入路径算法不一致

手工录入交易与智能导入分别实现了一套持仓更新逻辑：

- 手工买入使用持仓当前市价参与加权，却没有正确更新持仓成本；
- 手工卖出把卖出价反向加入市价计算，所得价格没有金融含义；
- 智能导入直接把持仓现价改成交易价格；
- 两条路径对成本、现价和数量的处理规则不同。

这会导致交易保存后、下一次行情刷新前，总览市值使用错误的持仓价格。行情刷新虽然可能重新覆盖现价，但不能修复已经错误的成本和历史交易字段。

### 3.3 允许无持仓卖出和超量卖出

系统没有统一校验“卖出数量不得超过当前可用数量”。当卖出不存在的持仓或卖出数量超过持仓时：

- 卖出交易仍会保存；
- 现金仍按全部卖出金额增加；
- 持仓可能保持不变或直接删除；
- 不生成负持仓，也没有错误提示。

该问题可以直接制造虚假现金和虚假总资产，属于最高优先级风险。

### 3.4 交易字段定义不清

当前 `trades` 同时保存 `price`、`quantity`、`amount` 和费用，但没有强制以下关系：

```text
amount = price × quantity
```

历史导入中又把成本金额、现价和模拟建仓交易混在同一结构内。系统后续使用 `amount` 计算现金，却在交易管理页把 `price` 当成交价展示，导致展示含义和现金计算依据不一致。

需要明确区分：

- 真实成交交易；
- 期初持仓导入；
- 持仓数量校正；
- 成本校正；
- 仅更新当前行情价格。

不能继续用一条普通“买入交易”同时模拟以上多种业务。

### 3.5 历史净值重放缺少可靠起点

后台净值任务通过交易流水从零重建历史持仓，但系统允许直接导入和编辑持仓，交易历史不一定完整。

如果账户只导入当前持仓、遗漏历史交易，或交易存在重复，后台重放得到的历史持仓和现金必然错误。当前代码却把这种重放称为“精确回填”，与实际数据条件不符。

正确重放至少需要：

- 明确的期初日期；
- 期初持仓数量和成本；
- 期初现金；
- 期初日期之后完整且去重的交易；
- 完整的入金、出金和费用；
- 可追溯的历史收盘价和汇率。

缺少任一条件时，应停止精确重放并提示数据不完整，不能静默生成净值。

### 3.6 交易日期格式导致当天交易漏算

前端手工交易日期可能保存为 `YYYY-MM-DD HH:MM`，后台净值任务使用 `YYYY-MM-DD` 纯日期，并直接进行字符串比较。

例如：

```text
2026-08-03 10:00 > 2026-08-03
```

因此当天交易可能被判定为“晚于当天”，不会进入当天持仓和现金计算。

交易日期应拆成明确的交易日和成交时间，所有按日计算统一使用交易日字段。

### 3.7 同日现金流会污染收益率

当天已经存在净值记录后，再录入当天入金或出金，前端更新当天净值时可能没有识别这笔同日现金流，从而把入金误算成盈利、把出金误算成亏损。

根因是净值只使用日期，没有保存快照时间或已结算现金流边界。

### 3.8 前端仍然整包保存账户数据

前端每次修改都会提交完整账户对象。后端在一个保存请求内删除并重建：

- `positions`；
- `trades`；
- `nav_history`；
- `cash_flows`。

当前数据集版本号可以阻止部分旧页面覆盖后台新净值，但没有真正实现按数据集独立保存：

- 修改持仓仍会重写交易、净值和现金流；
- 每次保存都会提升四个数据集版本；
- 两个页面修改不同数据集时仍容易冲突；
- 新增后台写入者若忘记同步版本，旧快照仍可能覆盖新数据。

### 3.9 缺少不可变账户主键外键

持仓、交易、净值和现金流仍主要使用 `username + account_name` 文本关联。虽然当前删除和重命名代码已通过事务同步多个表，但数据库没有使用统一不可变 `account_id` 对所有子表建立外键。

每新增一张账户业务表，都必须人工加入删除、重命名和审计清单，容易遗漏。

### 3.10 现有测试缺少业务账本场景

现有测试主要覆盖：

- JSON 旧数据不再恢复；
- 数据集版本保护；
- 账户删除和重命名；
- 历史净值备份、还原和清理。

尚未覆盖：

- 买入后持仓、现金和总资产联动；
- 部分卖出后的数量和成本；
- 删除或修改交易后的回滚；
- 无持仓卖出和超量卖出；
- 重复交易导入；
- 期初持仓加后续交易；
- 当天交易参与当天净值；
- 当天入金不影响投资收益率；
- 持仓与交易净数量一致性。

## 四、目标架构

### 4.1 基本原则

1. 每类数据只能有一个权威来源。
2. 交易、持仓和现金的关联修改必须在服务端同一事务完成。
3. 前端不再自行实现持仓和现金计算规则。
4. 当前行情价格与历史成交价格严格分开。
5. 期初持仓不是普通买入交易，必须使用独立业务类型。
6. 历史净值只能基于可证明完整的数据生成。
7. 所有数据修正必须可追溯、可审计、可回滚。

### 4.2 建议的数据职责

| 数据 | 权威来源 | 说明 |
|---|---|---|
| 账户身份 | `accounts` | 使用不可变 `account_id` |
| 真实交易 | `trades` | 只保存真实成交，不保存当前行情 |
| 期初持仓 | 独立期初持仓表或账本事件 | 保存起始日期、数量、成本 |
| 持仓数量 | 服务端账本计算结果或事务内维护的物化结果 | 不允许前端任意双写 |
| 持仓成本 | 服务端统一成本算法 | 明确移动加权、先进先出等规则 |
| 当前价格 | 行情表/行情缓存 | 不因录入历史交易被覆盖 |
| 现金 | 期初现金、现金流、交易和费用计算 | 不长期保存第二份可编辑现金 |
| 历史净值 | 每日快照表 | 由统一服务生成并记录计算版本 |
| 手工校正 | 独立调整事件 | 必须有原因、操作者和时间 |

### 4.3 推荐账本关系

```text
账户
  ├─ 期初现金
  ├─ 期初持仓
  ├─ 真实交易
  ├─ 入金/出金
  └─ 明确的校正事件
          ↓
统一账户账本服务
  ├─ 当前持仓数量与成本
  ├─ 当前现金
  ├─ 当前总资产
  └─ 每日历史净值
```

## 五、整改方案

### 阶段一：立即阻断新增错误

1. 增加卖出校验：不存在持仓或卖出数量超过持仓时拒绝保存。
2. 统一手工录入和智能导入的交易处理函数。
3. 禁止交易录入直接修改持仓当前价格。
4. 交易金额统一由服务端按成交价和数量计算；导入金额不一致时拒绝或进入待确认状态。
5. 删除交易、删除现金流后立即重新加载服务端结果，不继续使用旧内存现金。
6. 对智能导入增加业务去重，不能只按随机 ID 去重。

阶段一不处理历史数据，只阻止继续产生新错账。

### 阶段二：建立服务端统一交易事务

新增正式交易服务，负责一次性完成：

1. 校验账户、证券、方向、数量、成交价和费用；
2. 锁定账户或对应持仓；
3. 校验可卖数量；
4. 写入交易；
5. 更新或重算持仓数量和成本；
6. 更新账户修订号；
7. 标记受影响日期之后的净值需要重算；
8. 提交事务后返回服务端最新持仓、现金和总资产。

交易删除和修改也必须走服务端事务：

- 没有后续相关交易时，可以反向撤销并重算；
- 存在后续交易时，必须从该交易日起重放该证券和账户现金；
- 无法安全重放时拒绝直接删除，改用明确的冲正交易。

### 阶段三：拆分保存接口

逐步退出 `PUT /api/data/:name` 整包保存，改为局部接口：

```text
POST   /api/accounts/:id/trades
PUT    /api/accounts/:id/trades/:tradeId
DELETE /api/accounts/:id/trades/:tradeId

POST   /api/accounts/:id/cash-flows
DELETE /api/accounts/:id/cash-flows/:flowId

POST   /api/accounts/:id/opening-balances
POST   /api/accounts/:id/adjustments

PUT    /api/accounts/:id/preferences
```

持仓读取使用只读接口，普通用户操作不再提交整张持仓表。

### 阶段四：重构历史净值

1. 交易保存独立 `trade_date` 和 `executed_at`。
2. 明确定义上海时区日界线。
3. 保存账户期初日期、期初现金和期初持仓。
4. 净值重放先检查账本完整性，通过后才执行。
5. 同日现金流使用事件时间或快照结算边界计算。
6. 每条净值保存计算版本、数据截止时间和是否完整。
7. 重算失败时保留上一份有效净值，不写入半成品。

### 阶段五：账户主键和数据库约束

1. 所有账户子表新增 `account_id`。
2. 建立指向 `accounts.id` 的外键。
3. 账户重命名只修改名称，不更新子表关联键。
4. 明确 `ON DELETE CASCADE` 或受控软删除策略。
5. 为交易增加必要约束：

```text
direction ∈ {buy, sell}
quantity > 0
price > 0
amount >= 0
各费用 >= 0
trade_date 非空
```

6. 导入批次保存 `import_batch_id`、源文件摘要和原始行号，用于去重和追溯。

### 阶段六：历史数据只读审计与人工确认

在获得用户明确授权前，只生成报告，不修改生产数据。

审计至少输出：

- 重复交易组；
- 持仓数量与交易净数量差异；
- 无持仓卖出和累计超卖；
- `amount` 与 `price × quantity` 差异；
- 期初持仓和交易历史缺口；
- 当前现金重算差异；
- 历史净值异常跳变；
- 同日现金流导致的收益异常；
- 账户子表孤立记录。

华泰账户 `160719` 的重复交易和招商证券账户的交易字段混用必须进入人工确认清单，不能直接自动删除或覆盖。

## 六、测试要求

### 6.1 交易与持仓

- 首次买入生成正确持仓数量和成本。
- 多次买入按选定成本算法计算。
- 部分卖出不改变剩余持仓单位成本，或严格按既定算法处理。
- 全部卖出后持仓归零。
- 无持仓卖出被拒绝。
- 超量卖出被拒绝。
- 重复导入同一批交易不会新增记录。
- 撤销交易后持仓和现金恢复一致。

### 6.2 现金和总资产

- 买入按成交金额和费用减少现金。
- 卖出按成交金额扣除费用后增加现金。
- 入金和出金立即反映到总览。
- 删除现金流后现金立即恢复。
- 直接持仓校正不会无原因增加总资产。
- 行情刷新只更新市值，不改交易价格和持仓成本。

### 6.3 历史净值

- 当天带时间的交易能进入当天净值。
- 当天入金和出金不计入投资收益。
- 期初持仓账户可以正确续算。
- 交易不完整时拒绝标记为精确重放。
- 缺少历史价格时保留原有效快照并记录失败原因。

### 6.4 并发与数据边界

- 修改交易不会重写持仓以外的无关数据集。
- 修改账户偏好不会重写交易、持仓、现金流和净值。
- 后台生成净值时，前台录入交易不会互相覆盖。
- 同一交易并发修改时明确返回冲突。

## 七、验收标准

整改完成必须同时满足：

1. 新增、修改、撤销交易后，持仓和现金始终由服务端返回一致结果。
2. 系统无法保存无持仓卖出或超量卖出。
3. 当前行情价格、成交价格和持仓成本不再混用。
4. 持仓总览、持仓明细、交易管理和现金流页面使用同一账户结果。
5. 任何局部修改不再提交或覆盖完整账户快照。
6. 历史净值可以追溯到期初状态、交易、现金流、行情和计算版本。
7. 业务一致性审计中重复交易、超卖、金额关系异常和持仓数量差异均为零，或全部有明确的人工豁免记录。
8. 所有相关自动化测试通过。
9. 生产数据整改前完成全量备份，整改后逐账户核对数量、现金、总资产和最新净值。

## 八、建议实施顺序

| 优先级 | 整改项 | 原因 |
|---|---|---|
| P0 | 阻止超卖、统一交易录入逻辑、禁止交易覆盖当前价格 | 直接阻止新增错账和虚假资产 |
| P0 | 服务端交易事务与业务去重 | 保证交易、持仓、现金原子一致 |
| P0 | 修复交易日期和同日现金流净值计算 | 防止收益率继续失真 |
| P1 | 拆分整包保存接口 | 缩小覆盖和并发冲突范围 |
| P1 | 建立期初持仓和账本完整性检查 | 让历史净值具备可靠起点 |
| P1 | 输出生产只读差异报告 | 确定真实历史数据整改范围 |
| P2 | 迁移不可变 `account_id` 和外键 | 完成长期架构收口 |
| P2 | 经确认后修正历史数据 | 避免自动处理造成二次数据损失 |

## 九、安全边界

- 未获得明确同意，不连接生产数据库执行数据修改。
- 未获得明确同意，不生成可直接修改生产数据的 SQL。
- 历史重复交易、字段错位和持仓差异先输出只读报告，由用户逐账户确认处理口径。
- 数据修正必须先备份，按单账户事务执行，失败完整回滚。
- 不通过修改当前持仓或当前现金来掩盖历史账本错误。

本次整改的最终目标不是让总览页面暂时显示一个看似正确的数字，而是让持仓、交易、现金和净值都能从同一套可追溯业务账本得到一致结果。
