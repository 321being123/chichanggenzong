# ADR-0001：公告数据源优先级与统一采集

状态：已采纳
日期：2026-09-16

## 背景

公告相关能力由可转债、套利、A 股 IPO 和港股 IPO 等任务共同使用。近期核查发现，页面读取已经主要依赖本地数据库，但公告发现、定向资料补全、PDF 下载和重解析仍存在业务链路各自处理的情况，容易造成重复请求、来源口径不一致、缓存无法复用和失败后重复犯错。

## 决策

采用“统一公告采集层、独立业务投影”的架构，并固化以下优先级：

1. 本地完整事实优先；本地只有原始响应、PDF 或正文时，先本地重解析。
2. 公告发现先检查来源/接口/业务日的游标和覆盖水位，只查询未覆盖窗口。
3. 外部来源按“官方交易所 → 任务契约允许的巨潮资讯 → 明确登记的 Tushare 末级备源”执行。官方主链禁止回退时，不得自行切换巨潮。
4. 外部结果统一写入 `ops.raw_records`、`event.documents`，完成来源编号/URL/内容哈希去重后，才交给可转债、套利、IPO 等业务投影。
5. 业务任务可以因业务时点不同保留独立槽位，但不得复制公告查询、下载、游标、去重和缓存逻辑；页面、API 和计算不得直接访问公告外部源。
6. 新增公告需求必须登记来源、接口、市场范围、筛选条件、主备顺序、覆盖水位、唯一键、缓存周期、补漏方式、失败保留策略和下游消费者。

## 备选方案与取舍

- **每个业务继续独立采集**：改动最少，但会重复调用、重复下载，且同一公告可能出现不同来源和解析结果，否决。
- **把所有业务合并成一个巨型定时任务**：表面上只有一个入口，但会耦合业务时点和失败重试，单一业务故障可能阻塞全部公告，否决。
- **统一采集层 + 独立业务投影（采纳）**：共享外部调用和缓存，保留各业务的时点与状态边界，改造范围可控。

## 影响范围

- `ops.sync_cursors`、`ops.raw_records`、`event.documents` 成为公告采集的公共基础设施；解析版本、原文哈希、质量状态和失败重试必须可追溯。
- 可转债公告、套利公告继续使用官方交易所主源；IPO 招股书和上市流通等定向资料按各自契约执行交易所优先、允许时巨潮兜底。
- IPO 招股书、港股配发/取消上市资料、可转债上市流通/发行结果资料已接入统一持久化 PDF 缓存：Node 与 Python 共用 `data/document_pdf_cache`，使用 URL 哈希键、原子写入、30 天 TTL 和 5 GiB 总量清理；命中缓存时不重复联网，业务事实仍写入 `ops.raw_records`/`event.documents`。
- 本 ADR 只固化架构和研发约束，不代表本地代码变更已经完成生产发布；实际发布状态以代码、任务记录和生产验收为准。

## 何时重新评估

出现新的官方公告接口、来源授权口径变化、统一文档库无法满足某类业务的时效/质量要求，或发现同类重复采集问题时重新评估，并同步更新 `AGENTS.md`、`docs/技术架构.md` 和 `docs/知识索引.md`。
