# 线上后台告警与任务失败专项整改研发方案

> 状态：待开发、待生产授权  
> 编写日期：2026-09-14  
> 适用范围：后台定时任务、数据集发布、外部接口保护、告警生命周期  
> 当前生产版本：`0.8.1.22`，提交 `6d01b2e`

## 1. 背景与结论

2026-09-14 对生产后台进行只读核查。Web、Worker 和健康检查定时器均正常运行，`/health` 返回正常，当前问题不是系统整体宕机。

核查时共有 15 条活动告警，其中只有 2 条在最近 24 小时内发生；其余 13 条为 9 月 6 日至 11 日的历史遗留。大量失败记录主要由错误重试和告警未自动收敛放大，同时存在港股交易日历分区错误、巨潮旧接口 403、IPO 资料真实缺口和节假日文件权限错误。

本方案不引入新的调度器、数据源或告警系统，继续复用现有 Worker、API Guard、`ops.job_schedule_slots`、`ops.job_runs`、`ops.dataset_partitions`、`ops.job_alerts` 和质量问题表，只修正现有链路中的语义与状态流转。

## 2. 整改目标

1. 等待外部接口恢复时只保留一个等待状态，不重复制造失败运行记录。
2. 数据集分区日期与数据覆盖截止日期分开保存，保证下游依赖可以识别当天数据。
3. 外部接口故障按具体接口隔离，单接口 403 不得关闭整个数据源。
4. 真实数据缺口继续失败闭合，不允许通过清告警伪装任务成功。
5. 已恢复的历史告警自动关闭，但完整运行历史继续保留。
6. 修复 Worker 启动时节假日配置文件无写权限的问题。

## 3. 不在本次范围

- 不降低现有 API 每分钟、每日或最小调用间隔保护线。
- 不删除 `ops.job_runs`、外部调用审计或历史告警记录。
- 不伪造 IPO 行业、主营业务、行业市盈率等事实。
- 不重构 Worker 主架构，不新增另一套任务队列。
- 不在未授权情况下修改生产数据、清除熔断或手工重跑任务。
- 不把已知接口权限不足、额度限制直接当作程序故障修复。

## 5. 根因一：港币汇率等待被错误改成高频重试

### 5.1 现象

- `exchange-rate` 策略为每分钟 1 次、每日 24 次、最小间隔 24 小时。
- 最近一次真实调用为 2026-09-13 22:39，下一次允许调用时间为 2026-09-14 22:39。
- 当天固定任务在 16:15 到达，Guard 正确返回 `BUDGET_WAIT`，且外部调用次数为 0。
- 任务随后约每 2 分钟再次执行，累计产生 44 条失败运行记录。

### 5.2 根因

`server/jobs/hkRate.js` 捕获 Guard 错误后只返回 `errorCode`、`errorType` 和 `source`，丢失了 `recoverAt`、`apiName`、凭据和预算窗口等信息。

`jobOrchestrator.failOrRetry()` 无法取得准确恢复时间，只能使用默认的短间隔重试时间，导致同一等待状态反复写入运行历史和告警计数。

同时，`/api/hkrate` 和 `server/routes/positionComparison.js` 的持仓对比接口仍可能在页面请求时调用 `ensureHkRate()`。Guard 虽能阻止实际外部请求，但页面访问会继续制造无意义的刷新尝试，并可能改变下一次调用时间的口径。

### 5.3 修改方案

1. `runHkRateJob()` 必须原样抛出或完整传递结构化 Guard 错误，至少保留：
   - `errorCode`
   - `errorType`
   - `source`
   - `apiName`
   - `recoverAt`
   - `tokenFingerprint`
   - `credentialProfile`
   - `budgetWindow`
2. Worker 执行前先读取数据库中的 `hk_rate_updated_at`。最近一次有效汇率未超过 24 小时时，复用现有 `freshnessGate` 直接返回 `status=fresh` 并完成槽位，不进入 Guard、不产生外部调用；只有没有有效值或已过期时才进入 Guard。
3. `BUDGET_WAIT` 和带明确恢复时间的熔断不得登记为普通失败；任务槽位进入 `waiting_external`，`next_attempt_at` 直接使用 `recoverAt`。
4. `recoverAt` 已在过去时必须立即重试，不得再次等待 60 秒。`recoverAt` 缺失时不得退化为 `now + 60 seconds` 的高频重试：首次兜底等待 30 分钟，按退避递增，最长封顶 2 小时；连续 3 次仍缺失恢复时间后转为 `blocked` 并记录需要人工处理的原因。同一槽位在 `next_attempt_at` 前不得重复领取。
5. `/api/hkrate` 和持仓对比接口默认只读取数据库中的最后一条有效汇率。外部刷新只允许由 Worker 发起。
6. `hkRate.js` 对无 `code` 的网络异常、响应解析异常等错误不得返回 `{ok:false, rate:null}` 作为普通结果，必须统一转换成带 `errorCode/errorType/recoverAt`（如可计算）的结构化失败。
7. 保留当前 24 小时最小调用间隔，不通过放宽额度掩盖问题；现有 `waiting_external` 状态、`next_attempt_at` 字段和 `failOrRetry` 流程直接复用，不新增状态或字段。

### 5.4 验收

- 恢复时间在数小时后时，只生成一条等待记录，不新增重复失败运行记录。
- 数据库中的有效汇率未超过 24 小时时，现有 `freshnessGate` 直接返回 `status=fresh`，且外部调用次数为 0。
- `next_attempt_at` 与 Guard 返回的 `recoverAt` 一致。
- 已过期的 `recoverAt` 会立即进入一次重试，不再等待 60 秒。
- `recoverAt` 缺失时首次等待 30 分钟、最长封顶 2 小时，连续 3 次后进入 `blocked`，不会无限重试。
- 到期前执行器轮询不重复领取同一槽位，也不增加告警次数。
- 页面连续请求汇率和持仓对比接口时外部调用计数保持为 0。
- 到达恢复时间后任务只执行一次，成功后槽位和告警正常收敛。

## 6. 根因二：港股交易日历发布到错误分区

### 6.1 现象

2026-09-14 港股交易日历任务成功写入 347 条记录，实际覆盖 2026-01-01 至 2026-12-13，其中有 234 个开市日。数据本身存在，但港股 IPO 盘前任务仍提示当天日历缺失。

生产分区记录显示：

| 任务业务日 | 当前错误 `partition_key` | `data_as_of` | 正确 `partition_key` |
|---|---|---|---|
| 2026-09-10 | 2026-12-09 | 2026-12-09 | 2026-09-10 |
| 2026-09-11 | 2026-12-10 | 2026-12-10 | 2026-09-11 |
| 2026-09-14 | 2026-12-13 | 2026-12-13 | 2026-09-14 |

### 6.2 根因

`server/services/jobRunnerProcess.js` 将任务返回的 `result.dataAsOf` 优先作为 `partitionDate`。港股交易日历会一次写入未来约三个月的数据，因此覆盖截止日被错误当成任务业务分区。

下游 `datasetDependencyState()` 按 `slot.business_date` 查询 `partition_key`，最终出现“数据已经存在，但当天分区不存在”的矛盾状态。

该回归由 2026-09-09 的提交 `762f403` 引入。

### 6.3 修改方案

1. 明确两个字段语义：
   - `partition_key`：本次任务对应的业务日期或任务策略声明的分区日期。
   - `data_as_of`：本次结果实际覆盖到的最后日期。
2. `publishJobDatasets()` 默认使用任务 `businessDate` 或任务策略明确声明的期望分区，不再用 `result.dataAsOf` 覆盖。
3. 港股交易日历在 2026-09-14 运行时应发布：
   - `partition_key=2026-09-14`
   - `data_as_of=2026-12-13`
4. 上线前只读审计近期所有数据集，列出 `partition_key` 与任务业务日异常不一致的记录，确认是否还有同类受影响数据集。
5. 部署后定向补正 9 月 10、11、14 日分区元数据，再重排或重跑被阻塞的港股 IPO 槽位。

### 6.4 验收

- 港股日历任务可继续保存未来日期数据。
- 当天 `hk_trade_calendar` 分区存在并为 `published`、质量通过。
- `hk_ipo_preopen` 可读取当天分区，不再错误提示 `missing`。
- 对未来覆盖型数据集增加回归测试，确保 `data_as_of` 不会改变业务分区。
- 修复脚本可重复执行，重复执行不产生重复分区。

## 7. 根因三：巨潮旧 HTTP 接口触发来源级永久熔断

### 7.1 现象

17:30 的可转债公告历史任务总体显示成功，但上市流动性补充阶段有 2 个标的失败：

- `127115`：无法取得股票 `001202` 的巨潮 `orgId`。
- `123284`：无法取得股票 `301628` 的巨潮 `orgId`。

同一时间出现巨潮资讯 `api_name=*`、`PERMISSION_DENIED`、`recover_at=NULL` 的永久熔断，错误为 `HTTP Error 403: Forbidden`。由于探测条件要求 `recover_at IS NOT NULL AND recover_at <= now()`，该熔断不会自动进入探测状态，只能人工解除或由明确的恢复流程处理。

### 7.2 根因

1. `ipo-report/ipo_lib_fetch.py` 的 `_get_org_id()` 仍调用 `http://www.cninfo.com.cn/new/information/topSearch/query`，而现有 Node 适配器已使用 HTTPS。
2. Python Guard 对非 Tushare 数据源统一返回 `api_name=*`，导致一个旧接口的 403 关闭整个巨潮来源。
3. `_get_org_id()` 捕获所有异常，重试后只返回空值，丢失结构化 Guard 信息。
4. `sync_bond_listing_liquidity.py` 即使候选全部失败仍返回 `ok=true`，父任务因而显示成功，质量诊断也错误显示 `passed`。
5. `server/services/cninfoAnnouncement.js` 在 Node 侧遇到 429/额度错误时同样可能写入 `apiName='*'`，存在同类“单接口影响整来源”风险。
5. `server/services/cninfoAnnouncement.js` 在 Node 侧遇到 429/额度错误时同样可能写入 `apiName='*'`，存在同类“单接口影响整来源”风险。

### 7.3 修改方案

1. 统一使用现有 HTTPS 巨潮适配能力和一致的请求头，不继续维护 HTTP 分支。
2. 为 Python 侧巨潮调用设置稳定的接口名，例如 `topSearch`、`hisAnnouncement`，禁止使用通配 `*`。
3. 公共匿名接口的 403 先按限时退避处理，并记录明确 `recoverAt`；不得直接判定为永久凭据无权限。连续 5 次退避到期后仍返回 403 时，任务转为 `blocked`，并发送人工处理告警，不再无限退避循环。
4. `_get_org_id()` 继续允许有限次数网络重试，但必须向上返回结构化失败原因。
5. 上市流动性有失败候选时返回 `partial` 或 `stale`，记录独立质量问题；不得标记为 `passed`。
6. 主公告任务可以只按其已声明的核心数据集决定成功，但运行摘要和后台必须明确展示流动性子阶段部分失败。
7. Node 和 Python 两侧都必须为巨潮调用设置具体接口名，禁止使用 `*` 作为正常接口标识。
8. 对 `recover_at=NULL` 的历史永久熔断增加受控处理：代码提供人工解除或一次性成功探测后的定向关闭入口，关闭操作写入审计；不得依赖自动半开探测。
9. 代码修复并完成成功探测后，才允许关闭当前错误的巨潮来源级熔断。

### 7.4 验收

- `topSearch` 使用 HTTPS，目标股票可以正确取得 `orgId`。
- 单接口故障只影响该接口，不影响巨潮其他公告接口。
- 403 有明确的重试时间和上限，不形成永久来源级熔断。
- 连续 5 次退避到期仍为 403 时进入 `blocked` 并产生人工处理告警。
- 历史 `recover_at=NULL` 熔断具备可审计的人工解除或定向恢复路径，不会永久卡死在开放状态。
- 2 个候选失败时，流动性结果不得为 `passed`。
- 父任务摘要能够区分核心公告成功与流动性补充失败。

## 8. 根因四：凯达重工 IPO 资料存在真实缺口

### 8.1 现状

`920025` 凯达重工当前缺少：

- 所属行业；
- 主营业务；
- 业务赛道；
- 行业市盈率来源暂不可用，重试日期为 2026-09-18。

9 月 11 日的 `ipo_history_sync` 连续 3 次未通过质量门禁，属于真实数据不完整，不应通过关闭告警或放宽质量门槛处理。

### 8.2 修改方案

1. 优先复用已入库的官方招股书、发行公告或巨潮原始记录。
2. 若现有事实不足，定向读取该标的官方文件，只补缺失字段，不全量重抓 IPO 历史。
3. 主营业务必须保留官方原意；业务赛道由现有标准规则派生，并保存证据和可信度。
4. 行业市盈率在来源不可用期间保留缺失和下次重试时间，不构造替代数值。
5. 对同一标的、同一来源结果未变化的重试，复用已经保存的检查状态，避免一次任务内连续下载相同资料。
6. 字段补齐并通过质量检查后，重新发布对应业务日分区，再运行依赖的 IPO 日历任务。

### 8.3 验收

- 行业、主营业务和业务赛道均有官方事实或可追溯派生依据。
- 行业市盈率缺失时明确显示缺失，不阻止其他已具备官方依据的字段保存。
- 同一轮任务不会重复下载完全相同的文件。
- `ipo_history` 分区质量通过后，依赖任务才允许执行。

## 9. 根因五：告警生命周期只能按原槽位关闭

### 9.1 现象

- 9 月 8 日 `arbitrage_reparse` 曾产生 96 条失败运行，后续修复和任务成功后旧告警仍为活动状态。
- 9 月 8 日套利 `duplicate_success` 告警没有 `slot_id`，当前逻辑永远无法自动关闭。
- 9 月 6 日可转债公告失败后，后续已有 9 次成功，旧告警仍未关闭。
- 港股 IPO 的旧阻塞告警仍对应真实分区缺口，暂时不应关闭。

### 9.2 根因

`resolveJobSlotAlerts()` 仅按同一个 `slot_id` 关闭告警。后续业务日成功无法关闭历史任务级告警；没有 `slot_id` 的告警更无法进入自动关闭流程。

### 9.3 修改方案

为告警增加明确作用域和关闭条件。当前 `ops.alert_notifications` 只有 `slot_id`/`job_code`，因此需要新增数据库迁移 `151`，补充作用域字段、约束和历史回填规则；不改变既有通知审计记录。

建议迁移内容：

- `scope_type`：`slot`、`job`、`dataset`、`source_endpoint`。
- `scope_key`：与作用域对应的稳定键，例如槽位 ID、任务代码、数据集加分区或来源加接口。
- `alertKey` 与 `scope_key` 分工固定：`alertKey` 继续用于通知去重和同类告警合并，`scope_key` 只用于告警关闭判定、历史对账和作用域唯一性；两者不互相替代，必要时由 `alertKey` 映射到规范化的 `scope_key`。
- `slot` 告警继续关联 `slot_id`；任务级、数据集级和来源接口级告警使用 `scope_key`，并增加必要的非空/唯一约束。
- 历史记录按已有 `slot_id`、`job_code`、告警代码和消息内容回填；无法安全判断作用域的记录保留为历史待人工对账，不强行关闭。
- 迁移必须幂等，执行前备份，支持只读预览和回滚。

告警作用域与关闭条件如下：

| 告警类型 | 作用域 | 自动关闭条件 |
|---|---|---|
| 单次运行失败 | `slot` | 原槽位成功、跳过或被明确替代 |
| 重复成功、Worker 异常 | `job` | 同任务连续 3 次运行正常，且异常条件消失 |
| 数据缺口、分区缺失 | `dataset` | 对应分区或数据水位恢复并通过质量检查 |
| 权限/额度限制 | `source_endpoint` | 成功探测，或配置明确标记为已知禁用 |

同时调整后台默认展示：

- 默认只显示当前可操作告警。
- 历史告警和运行记录保留在历史视图。
- 同一槽位的重复 `BUDGET_WAIT` 合并为一条等待状态和一条告警，只更新发生次数。
- 当前仅允许单条告警确认；后续不得新增无审计、无筛选条件的批量确认接口。历史告警只能根据后续成功、数据分区恢复或成功探测进行对账。

### 9.4 一次性历史对账

部署新规则后执行只读预览，输出每条拟关闭告警及其证据。经确认后再定向关闭：

- 9 月 6 日且已有后续成功证据的可转债公告失败。
- 9 月 8 日且已完成修复、后续运行成功的套利重复和补解析告警。
- 不关闭仍受 IPO 数据缺口或港股日历错误分区影响的告警。

### 9.5 验收

- 后续成功可以关闭符合规则的任务级旧告警。
- 无 `slot_id` 的任务级告警具备明确关闭路径。
- 真实数据缺口未恢复前保持活动状态。
- 历史运行记录、错误详情和通知记录不被删除。

## 10. 根因六：节假日配置文件无写权限

### 10.1 现象与根因

Worker 启动时出现：

```text
EACCES: permission denied, open '/opt/portfolio/server/config/holidays.json'
```

文件当前为 `root:root 0644`，Worker 使用 `portfolio-app` 账户运行。systemd 的 `ReadWritePaths` 只允许路径进入可写范围，不会绕过 Linux 文件属主权限。

### 10.2 修改方案

1. Git 追踪的 `/opt/portfolio/server/config/holidays.json` 只作为初始种子，不再作为运行时写入目标。
2. 运行时可写副本固定放在非 Git 追踪目录 `/opt/portfolio/data/holidays.json`；代码加载时优先读取该副本，副本不存在时才读取 Git 种子并初始化副本。
3. 将运行时副本及其目录的属主/权限交给 `portfolio-app`，权限控制到专用目录，不给整个项目目录宽泛写权限。
4. 节假日保存继续使用原子替换或临时文件落盘，避免写入中断造成 JSON 损坏。
5. 部署流程禁止用 `git reset --hard` 覆盖运行时数据目录；代码更新和运行时数据更新必须分离。
6. 启动加载失败必须进入可见告警，不能只写日志。

### 10.3 验收

- 使用 `portfolio-app` 身份可完成一次节假日文件写入和重新读取。
- Worker 重启不再出现 `EACCES`。
- 部署后运行时副本不会被 Git 同步或重置覆盖。
- 文件内容无变化时不重复写入。
- 月度节假日任务能成功更新并保留上一份有效配置。

## 11. 完整数据链路与影响面

```text
外部数据源
  ├─ 汇率 / 巨潮 / Tushare / 港股交易日历
  ↓ API Guard：额度、间隔、熔断、恢复时间
Worker 定时槽位
  ↓ job_runs：一次真实执行对应一次记录
业务数据表 + 原始响应审计
  ↓ dataset_partitions：业务分区、数据覆盖日、质量状态
下游任务依赖检查
  ↓ 服务层 / 后台 API
后台任务、告警、数据质量页面
```

本次修改的核心约束：

- Guard 返回的结构化错误必须完整传递到槽位调度层。
- `partition_key` 表示任务业务分区，`data_as_of` 表示数据覆盖水位，两者不得混用。
- 子阶段失败必须在运行摘要和质量状态中如实表达。
- 页面接口只读已入库数据，不成为隐式外部采集入口。
- 告警关闭必须有运行成功、数据恢复或接口探测成功的证据。
