# INC-0016：页面读取绕过数据层导致行情页面慢加载

状态：已部署生产
日期：2026-09-10

## 现象与影响

“可转债 → 上市可转债”首开明显慢，线上同一接口在 2026-09-10 多次耗时约 4.7–5.3 秒；普通数据库快照读取约 0.4–0.5 秒。用户看到的是本应只读数据层的页面，却被隐式实时行情刷新阻塞。

## 根因链路

数据源 → 数据库 → 服务 → 接口 → 页面/任务 → 运行环境：

1. `public/js/bond-list.js` 首次加载把 `forceRefresh` 设为真，并请求 `refresh=1`；15 分钟定时器也重复传入该参数。
2. `server/routes/bondAnalysis.js` 将该参数传给 `getBondList({ refreshQuotes: true })`。
3. `server/services/convertibleBondListService.js` 强制绕过腾讯行情缓存，批量处理约 311 只转债及其正股；随后查询每只正股最多251条历史，用于重新计算波动率和理论指标。
4. 同时，导航入口先加载完整安全性列表，再初始化当前子页；持仓刷新在批量行情失败后逐只回退；收益图在缺指数快照时从浏览器直接调用 `/api/kline` 并写回数据库。

## 直接原因、根本原因与保护机制失效原因

- 直接原因：只读列表的首开路径误用了“强制实时刷新”路径。
- 根本原因：页面读取路径与后台采集/计算边界未严格执行，多个页面把补数逻辑放在浏览器生命周期内。
- 保护机制失效：已有架构文档要求页面只读数据库或服务端缓存，但前端测试反而固定要求上市列表首开带 `refresh=1`，没有保护“首开不得外部调用”的契约。

## 同类范围与核查结果

- 完全同类的“首开强制刷新全市场行情”只发现上市可转债列表。
- 持仓页保留明确的实时行情业务，但已限制为一次批量请求加一次整批重试。
- 持仓收益图的指数数据已统一改为读取账户 `index_history`；外部采集由 `index_baseline/index_recent` Worker 任务负责。
- 可转债安全性、周期、估值、强赎、下修及个股分析读取数据库快照；仓位对比只在用户点击后计算；套利实时行情仍走共享腾讯缓存，不存在上市列表的强制刷新定时器。

## 修复与回归证据

- 上市列表首开和定时器改为只读数据库快照；用户主动点击仍保留显式行情刷新。
- 可转债导航只初始化当前子页，删除安全性整表重复加载和 URL 恢复二次加载。
- 持仓行情刷新删除逐只回退，最多执行两次批量请求。
- 指数图表删除浏览器侧外部 K 线回源；正股历史 SQL 用窗口函数限制每只证券最多251条，避免加载11万余条后再由 JavaScript 截断。
- 定向回归：上市列表 10 项通过、导航 78 项通过、持仓刷新通过、周期前端 20 项通过；5 个修改 JavaScript 文件均通过 `node --check`。
- 全量回归：`npm run test:all` 在本地测试库通过，128 个数据库/单元测试、2 个安全与 IPO 测试、4 个 Python 测试全部通过。
- 生产验收：提交 `2f59f6d` 已发布；Web、Worker、健康检查定时器均为 `active/enabled`，`/health` 返回 `0.8.1.11`，上市可转债接口返回 200，更新后的 4 个静态资源版本均命中；本次不涉及数据库结构、历史数据或生产数据同步。

## 防复发措施与遗留风险

- 保持“页面只读库/缓存、Worker 负责外部采集和计算”的架构门禁，并保留首开不带 `refresh=1` 的静态回归断言。
- `refresh=1` 仍是用户主动操作，线上发布后需核对手动刷新耗时、腾讯批次数和失败时旧快照保留情况。
- 部署后需继续观察上市列表首开只产生无 `refresh` 参数的接口请求，并观察同一时段外部腾讯调用数；用户主动点击“刷新行情”仍会按设计触发实时行情刷新。
