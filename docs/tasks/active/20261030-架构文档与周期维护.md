### S4 数据恢复试点：已完成，途中发现并修复一个 P1

按方案「先通过一个旅程再扩域」，选定「导入 → 行情 → 持仓基准 → 净值」。做法是先建可复现样本再改代码，样本为 `server/test/account-recovery-journey.test.js`（隔离临时库、只建本次用到的最小表、5 个场景，不碰生产库、不访问外部行情）。

**发现（P1）**：补「持仓基准快照」的写入 SQL 自 0.9.1.2 上线起有两处确定性解析错误，用真实库结构 `PREPARE` 直接报错：

1. `daily_prices.date` 是 TEXT 列，SQL 写成 `d.date::text=$3`，与同一语句里的 `$3::date` 争抢参数类型 → PG 报「操作符不存在: text = date」；
2. `round(p.quantity * px.price …, 2)` 的参数是 double precision，PG 只有 `round(numeric, int)`。

两处都会让整条 INSERT 解析失败，而 `routes/accounts.doImportSnapshot` 用 try/catch 把错误吞成一行 console.error，于是**这个功能从上线起从未真正写入成功**。生产上 guoyanchaocn / being 两个账户「0 条快照」由此得到解释——不是账户本来没有，而是写入一直失败。

**修复**：`d.date=$3::text`、`round((…)::numeric, 2)`；缺口可解释性上补 `selectUncoveredPositionCodes`（查出被过滤掉的持仓，随返回值带 `skipped` / `reason`），路由把基准未覆盖与补价 `failed` 都落 warn 日志。补价 `need_dates` 由「已有 nav_history 日期」改为「已有日期 ∪ 目标业务日」，解决新导入账户空表时一只都选不出来、当天行情永远补不到的问题。

**验证**：5 个场景全通过；两处 SQL 修复分别做破坏性验证（改回旧写法后场景 1、场景 3 各失败 1 项，恢复后全绿）；全量 `run-all.js` 275 通过 / 1 失败，唯一失败是基线既有的 `ops-alert-remediation-regression`。同类核查：全仓 SQL 内 `round(` 仅此一处，同一参数既 `::date` 又 `::text` 的混用未发现第二处；**更广范围的仓储 SQL 可执行性仍未系统覆盖**，按方案不扩域。

核查把它列为「仍缺证据」，本次补上可执行样本 `server/test/nav-journey-regression.test.js`（9 项，真库）。按真实时序逐日推进，不用「先做完所有交易再回头补净值」那种倒序构造（倒序会让基准快照用当前持仓倒推历史，本身就构造出错误事实）。

| 日 | 动作 | 断言的可手算数值 |
|---|---|---|
| 第 1 天 | 期初建仓 601995 1000 股 @10，收盘价 11 | 持仓 1000 股 / 单位成本 10；净值总资产 111000（10 万现金 + 1000×11），累计净值 1 |
| 第 2 天 | 卖出 400 股 @12，佣金 5 + 印花税 4.8 + 过户费 0.048，收盘价 12 | 剩余 600 股、单位成本不变；现金 104790.152（4800 − 9.848）；总资产 111990.152；累计净值 1.0089203 |
| 第 3 天 | 换股 601995 → 002091 比例 1:0.5，收盘价 22 | 计划 600×0.5 向下取整 = 300 股、成本平移为每股 20；源持仓清零、目标持仓 300 股 @20；不产生现金流；总资产 111390.152；累计净值 0.944055 |

链路走的是真实入口：`tradeLedger.applyTrade`（持仓/成本/现金/费用真库落库）、`stockSwapSettlement.buildPlan` + `buildLedgerEvents`（真实计划与账本事件）、`accountPositionBasis.ensurePositionBasis`（净值续链必需的持仓基准）、`navSnapshot.recordNavSnapshots`（含首页基准重算与链式净值）。

**破坏性验证**：把 `public/shared/nav-math.js` 里卖出费用的扣减临时去掉，第 2 天现金（实际 104800 vs 期望 104790.152）与第 2、3 天总资产三项断言同时变红；恢复后 9/9 全绿。说明这套断言真的卡住了金额正确性，不是自证。

**边界（不冒充完整结算）**：换股段没走 `settleOne` 的结算单写入、案件筛选（`findSettleableCases`）与事务外壳，也没构造 `event.arbitrage_cases` / `core.instruments` 的真实案件记录；只验证了「真实计划 + 真实账本事件 + 真实账本应用 + 真实净值」这条主链。结算单与案件层仍由原套利模块的测试覆盖，本文件不声称覆盖它。

**排查中确认的一个时序规则**（值得记住，不是缺陷）：净值写入按快照时刻过滤未来交易。若把「今天 23:59」的账本事件喂给今天的净值，盘中运行时它会被正确排除，看起来像「持仓市值丢了」。构造样本必须用过去日期，或用早于快照时刻的时间。
