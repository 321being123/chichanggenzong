**CI 第二轮反例与修正（2026-11-06 追加，同版本 0.9.2.23）**：提交 `a015c32e` 的 CI 剩 3 条失败，均已定位到根因。①僵尸进程被当成存活：Linux 上子进程被 SIGKILL 后要等父进程回收，期间 `kill(pid,0)` 仍成功，于是"确认已退出"的终止循环等不到结果、锁释放判据认为还有人活着而保留锁。`testRunControl` 新增 `/proc` 状态读取（`processStateOnLinux`）与进程组成员扫描（`groupHasLiveMembers`），僵尸按已退出处理。②`stock-selection-pipeline` 的确定性缺口不够确定：缺口证券只写了净资产事实、没有归母净利，R01 落进"一条财报都没有 → 不可评估"（不产生缺口）；补上净利事实后空库实测 `gapCount=1 / pending=1 / partial / 未发布`。同时它的公司名必须落在清理前缀内，否则行业归属残留会让下一次清理撞外键。③`feedback-gap-recheck` 偶发崩溃：删临时库前会 `pg_terminate_backend`，被切断的连接向 pool 抛 `error` 事件，无监听器时进程直接退出（用例其实全过）。按既有惯例给 admin 与 pool 挂空错误监听。

**第三轮 CI 修正（2026-11-06，同版本 0.9.2.23）**：超时收尾在"整组已确认退出"时直接强制释放测试资源（不再依赖登记注销的时间差，确认不了仍保留锁）；`feedback-module` / `feedback-gap-recheck` 的 admin 与 pool 补空 `error` 监听，避免删临时库切断连接时进程以未捕获异常退出。详见[生产部署流程](生产部署流程.md)与[意见反馈方案](意见反馈与版本发布闭环研发方案_20261023.md)的对应补记。

**共享连接池的错误监听（2026-11-06 第四轮追加，同版本 0.9.2.23）**：`server/db/connection.js` 给共享 `pool` 挂上 `'error'` 监听。空闲连接被服务端单方面断开（PG 重启、网络抖动、`pg_terminate_backend`、临时测试库被删）时，pg 会向进程抛 `'error'` 事件；此前没有监听器，Node 按未捕获异常处理，**整个进程直接退出**。生产含义是"数据库抖一下服务就挂"，测试里表现为"用例全过但进程崩了、退出码 1"（CI 实测 `feedback-module`、`feedback-gap-recheck`、`nav-basis-migration` 三个文件）。现在只记录并继续，坏连接由池丢弃、下一次取连接自动重连。
