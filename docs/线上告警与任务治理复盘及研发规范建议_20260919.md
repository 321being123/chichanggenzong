# 线上告警与任务治理复盘及研发规范建议

> 复盘日期：2026-09-19  
> 适用范围：后台任务、外部数据同步、数据分区、告警恢复和生产补跑  
> 当前状态：本轮可转债行情链已完成修复、补跑和告警收敛

## 一、结论摘要

这几天处理的不是单个 Bug，而是三类边界问题叠加：

1. 任务计算的“目标对象集合”不准确，制造了虚假数据缺口。
2. 任务已经成功，但告警恢复证据链不完整或被错误拦截。
3. 历史公告重建在身份、来源并发、文本分类和断点续跑上缺少统一边界。

本轮最终结果：

- 可转债行情三日分区恢复为 `311/311`、`310/310`、`310/310`，缺口队列归零。
- 下游安全评分和估值任务均成功完成。
- 本链路相关数据质量、依赖阻塞和超时告警均按证据收敛。
- 全量测试 `135` 项通过、`0` 失败。
- 线上版本为 `0.8.1.70`，生产提交 `c46a79b`。

## 二、问题复盘

### 2.1 可转债行情虚假缺口

**现象**

2026-09-16 至 2026-09-18 连续出现 `bond_daily` 部分发布，旧记录显示缺少约 140 只可转债行情。

**根因**

- Tushare `cb_basic` 使用 `YYYYMMDD`，调度器目标日使用 `YYYY-MM-DD`，旧代码直接比较字符串。
- 允许上市日期为空，导致没有明确上市事实的债券进入目标集合。
- 历史退市、到期、停止转股的债券未被正确排除。
- 定向/私募债券没有沿用公开发行过滤规则。

**只读核查证据**

- 原缺口中有 130 只历史退市/停止状态债券、7 只定向债、3 只未上市债。
- 公开在市目标集合为 310 只。
- `cb_daily` 对这 310 只全部有有效价格，实际不是行情源缺失。

**修复**

- 统一生命周期日期格式。
- 强制要求目标日前已有上市事实。
- 统一排除退市、到期、停止转股、定向和私募债券。
- 复用安全评分模块已有的活跃债券和公开发行过滤逻辑。

### 2.2 任务成功后告警无法自动恢复

**现象**

行情、估值和安全评分已经成功，但历史阻塞告警仍保持活动状态。

**根因**

- 告警作用域曾混用槽位业务日和实际数据分区日。
- 某些成功分支向非空字段写入 `NULL`，导致成功被误判为失败。
- 历史槽位请求模式与实际运行模式不一致，恢复证据因此被拒绝。
- `dependency_blocked` 告警在外层校验中被提前拒绝，未进入已有的严格恢复证据层。

**修复原则**

告警不能只看槽位状态，必须同时核对：

```text
运行结果 → 失败数据集 → 数据分区 → 质量状态 → 水位日期 → 任务依赖
```

只有证据完整时才允许恢复。数据质量告警仍必须由对应数据集分区证据关闭，不能由普通任务成功掩盖。

### 2.3 历史强赎公告重建边界不足

**主要问题**

- 旧档案保存申购简称，和正式债券简称不一致。
- 同一正股存在多只历史转债时，公告无法唯一匹配。
- 纯下修公告被误归类为强赎公告。
- 公告列表和 PDF 正文共用并发槽位，造成批量 `BUDGET_WAIT`。
- 日期排版、重复更正公告、法律意见书等特殊文本导致解析门禁阻断。

**修复方向**

- 按正股、官方债券身份和公告日生命周期做唯一匹配。
- 无法唯一匹配时继续阻断，不默认选择第一条。
- 公告列表和正文使用独立并发额度。
- 保存检查点，失败只续跑未完成对象。
- 只有正文证据和业务字段都完整时，才替换历史投影和推进水位。

## 三、反复出现的共同原因

这些问题表面上分别属于行情、告警和公告解析，实际都属于同一种缺陷：

> 系统边界没有被统一定义，并且同一事实在多个模块中各自实现了一遍。

具体表现为：

- 日期在不同模块使用不同格式和不同含义。
- 目标对象集合没有独立的权威口径。
- 任务成功状态和数据真正发布状态没有完全绑定。
- 告警发送逻辑和告警恢复逻辑没有共用同一证据服务。
- 外部接口限制、重试和断点规则散落在任务代码中。
- 回归测试覆盖了正常样例，但没有覆盖边界组合。

## 四、建议形成的研发规范

建议形成一份简短、可执行的《线上任务与告警研发规范》，不建议写成大而全的制度文件。

### 4.1 日期与分区规范

- 所有外部日期进入系统后立即标准化为统一格式。
- 明确区分：槽位业务日、目标数据日、数据分区日、运行时间。
- 告警作用域必须使用实际目标分区日，不得默认使用槽位业务日。
- PostgreSQL `DATE` 转业务日时统一使用上海时区。
- 每个任务定义必须声明 `dataDatePolicy`。

### 4.2 目标集合规范

每个数据同步任务必须先回答两件事：

1. 目标集合理论上应该包含哪些对象？
2. 当前来源实际返回了哪些对象？

两者必须分别记录并计算差集。生命周期、上市状态、发行类型、市场范围等过滤条件必须在任务入口统一处理，不能由下游页面或告警逻辑临时补过滤。

### 4.3 任务完成与告警恢复规范

任务成功至少需要同时满足：

- 运行记录成功。
- `failedDatasets` 为空。
- 必要数据分区已发布。
- 分区质量状态通过。
- 数据水位达到任务期望日期。
- 上游依赖满足要求。

告警关闭只能通过统一恢复证据服务完成，禁止直接修改状态或批量清零。不同告警类型必须绑定不同证据：

| 告警类型 | 必要证据 |
| --- | --- |
| 数据质量 | 对应数据集、市场范围、分区日和质量状态 |
| 依赖阻塞 | 原槽位成功、运行记录、依赖分区和水位 |
| 外部来源 | 熔断关闭且有新的成功探测 |
| 普通任务失败 | 后续同模式成功运行，历史告警还需满足连续成功要求 |

### 4.4 外部接口与重试规范

- 不在业务代码中写死没有官方依据的调用次数上限。
- 区分权限错误、限流、网络失败、参数错误和合法空结果。
- 长任务必须支持检查点和断点续跑。
- 重试必须有上限、有恢复时间、有无进展保护。
- 已成功的对象不能因为批次重跑而重复请求。
- 对外部来源的调用次数、来源、失败类型和恢复时间必须留痕。

### 4.5 代码测试规范

每个线上 Bug 至少补三层验证：

1. **最小回归测试**：直接锁定本次根因。
2. **数据库/任务集成测试**：验证状态、分区、依赖和恢复证据。
3. **全量测试**：确认没有破坏其他任务和页面。

日期类问题必须覆盖紧凑日期、带横线日期、时区转换和空日期；告警类问题必须覆盖成功、失败、部分发布、依赖阻塞和历史告警。

### 4.6 生产操作规范

生产补跑统一遵循：

```text
只读核查 → 明确授权 → 标准重试入口 → 观察运行结果
→ 核对数据分区 → 告警恢复预览 → 按明确 ID 收敛
```

禁止：

- 未确认目标对象就补跑全量任务。
- 用手工改状态代替数据修复。
- 在没有恢复证据时关闭告警。
- 为了让告警变少而降低质量门禁。

### 4.7 发布与知识同步规范

涉及任务、告警、数据口径的代码变更必须同步：

- 版本记录。
- 技术架构中的现役规则。
- 事故文档中的最终结论。
- 专项回归测试。
- 发布后的线上版本和服务验收结果。

## 五、建议的落地优先级

### P0：立即固化

- 统一业务日、目标日、分区日的字段命名和传递规则。
- 所有告警恢复统一调用中立证据服务。
- 禁止生产脚本直接改告警状态。
- 为任务契约增加目标集合和数据分区声明。

### P1：近期补齐

- 增加“日期边界 + 生命周期 + 依赖恢复”的公共回归测试模板。
- 为外部任务统一检查点、退避和无进展保护。
- 在知识门禁中增加告警作用域和硬编码调用上限检查。

### P2：持续改进

- 建立生产补跑结果的统一验收报表。
- 将任务、分区、告警和恢复证据串成可查询链路。
- 对重复出现三次以上的事故，把散文规则升级为自动门禁。

## 六、当前结论

本轮问题已经修复并完成生产验证，但规范化工作还没有正式合并到整体研发规范中。建议先让相关人员评审本文，确认术语、责任边界和验收口径后，再将最终版本合并到项目的统一研发规范和知识索引中。
