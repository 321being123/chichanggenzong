# Skill 宿主发现与行为验收（2026-10-30）

一句话结论：**显式调用这一层验证通过了**——WorkBuddy 在本会话能发现并加载三个 Skill 的工作区级薄入口，且薄入口只指路、正文关键契约由自动化测试守住（8 项）；**自动触发与负例仍未实测**，不能宣称"Skill 行为已验证"。

## 1. 为什么单独验这件事

Skill 是给 Agent 读的流程文本，不是代码约束。它可能以三种方式失效，而且都不会报错：

- **发现不了**：宿主只扫自己的目录，仓库里 `.agents/skills/` 那份永远没人读——文件写了等于没写；
- **该触发不触发**：用户说"发布"，Agent 没加载发布 Skill，又回到凭记忆拼命令（历史上正是这么出过部署事故）；
- **不该触发却触发**：只是查数据、改文档，却走了发布流程甚至动了生产。

所以「文件存在」「格式校验通过」都不够。方案第 5 节 S2 的退出条件写的是"目标宿主能发现并正确使用 Skill，代表性场景有结果，错误场景不误执行"。

## 2. 当前结构（两层，避免两套事实）

| 层 | 位置 | 作用 | 是否入 Git |
|---|---|---|---|
| 权威层 | `portfolio-server/.agents/skills/{site-doc-handoff,site-release-closeout,site-monthly-review}/SKILL.md` | 唯一流程定义，只引用仓库权威文档，不复制字段/架构/生产状态 | 是 |
| 薄入口层 | `D:/Users/存在小站/.codebuddy/skills/<同名>/SKILL.md` | 只做三件事：切到仓库目录、读权威文件、提醒按现行文档执行 | 否（工作区级，不入库） |

薄入口存在的原因：WorkBuddy 只扫工作区级 Skill 目录，不扫仓库子目录。

## 3. 已实测：显式调用（WorkBuddy，2026-10-30 本会话）

逐个显式调用，三个都成功返回薄入口内容，且都指向仓库权威文件：

| Skill | 显式调用结果 | 薄入口指向 |
|---|---|---|
| `site-release-closeout` | 成功加载 | `.agents/skills/site-release-closeout/SKILL.md` + `docs/生产部署流程.md` + 反馈方案 |
| `site-doc-handoff` | 成功加载 | `.agents/skills/site-doc-handoff/SKILL.md` + `AGENTS.md`/`docs/知识索引.md`/`governance/knowledge-map.json` |

这说明：**WorkBuddy 的发现链路（工作区级目录 → 薄入口 → 仓库权威文件）是通的**，不是"写了但没人读"。

## 4. 已自动化：内容契约（8 项）

`server/test/skill-host-contract.test.js`（随 `test:all` 自动执行）：

1. 三个 Skill 存在、frontmatter 的 `name` 与目录同名、`description` 不为空（兼容 CRLF 与 LF）；
2. 描述里既有触发场景、也有排除语（"不适用/不要用"）——这是负例不误触发的文本前提；
3. 发布 Skill 保留「A 新发布」与「B 只补回写」两支，且写明 B 不许改版本、不许重新部署；
4. 发布 Skill 的「反馈核对准备」必须排在「部署」之前，并含 `--feedback-none-evidence`；
5. 发布 Skill 写明三个完成态（`applied_verified`/`applied_verified_no_implementation`/`crosschecked_no_related_feedback`），其余算未闭环；
6. 文档 Skill 要求同步摘要/索引与"旧结论要被替代"；
7. 月度 Skill 要求复查上月行动是否有效；
8. 薄入口存在、只指路（必须含 `.agents/skills/<名称>/SKILL.md`）、长度受限（<1200 字符，防止复制成第二份事实）、指向的仓库文件真实存在；没有该目录的机器打印 `[SKIP]`。

**破坏性验证（已执行）**：把发布 Skill 里的「只补回写」改名后，第 3 项立即红；恢复后 8/8 通过。

## 5. 仍未验（不冒充通过）

| 项 | 为什么没验 | 怎么补 |
|---|---|---|
| 自然语言自动触发 | 需要新会话，看用户说"发布 0.9.x"时宿主是否自动加载发布 Skill，而不是等用户点名 | 新开会话只发一句发布口令，看它是否先读 `docs/生产部署流程.md` 与反馈批次 |
| 负例不误触发 | 同上，需观察"帮我查下某个数据/改个文档"时是否误走发布流程 | 新开会话发一个只读请求，看它是否调用了 site-release-closeout |
| 加载后是否真按流程执行 | 属行为验收，需要真实任务样本；本会话不便用生产验证 | 用离线样本（假 feedback-run-id、无证据文件）看它是否在**生产变更前**停手 |
| Codex 侧 | 本轮没有在 Codex 上实测发现方式；不同宿主机制不同，不能按 WorkBuddy 推定 | 在 Codex 会话里显式要求使用该 Skill，记录是否能读到仓库文件 |
| 薄入口的跨机器可复现 | 薄入口在工作区级目录、不入 Git，换机/新工作区需要重建 | 已知限制：重建方式写在 `docs/知识索引.md` 的"文档更新、发布收尾、月度复盘流程"行与本节 |

## 6. 已知限制（写在前面，避免过度承诺）

- Skill 是**流程指导**，不是权限控制，也无法阻止 Agent 不读它。要"防止不按流程"，靠的是脚本闸门与测试（如发布脚本缺核对依据直接拦、SQL 可执行性验收），不是 Skill 文本。
- 薄入口是"工作区级副本"，一旦有人往里写流程细节，就会出现第二套事实。第 8 项的长度上限与路径断言就是防这个。
- 显式调用通过，只说明"能读到"；本次没有做"读完之后动作对不对"的端到端验证。

## 7. 后续（认领后做）

1. 新会话做自然语言触发与负例各一次，把结果补进第 5 节表格（这是本文件唯一还空着的硬证据）。
2. Codex 侧同样做一次显式调用。
3. 如果多个宿主都只认用户级目录，考虑把薄入口生成做成脚本（避免手写漂移），但不要复制流程正文。
