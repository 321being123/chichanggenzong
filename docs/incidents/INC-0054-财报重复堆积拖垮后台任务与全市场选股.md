# INC-0054：财报重复堆积拖垮后台任务与全市场选股

状态：已关闭（0.9.5.10 已发布并完成生产清理与端到端验收）
日期：2026-11-26

## 现象与影响

后台任务出现整点齐次超时：`company_financial_incremental_sync` 在 08:40、09:25、10:55、15:25 连续四次跑到 **1800 秒**（任务默认 30 分钟预算）被杀，落库错误为「job child process exited null without result」，`timed_out` 为真且外部调用计数为 0——不是在等外部接口，是自己算不完。

`stock_analysis_refresh` 同一时段也贴边：00:45 用时 1709 秒、01:44 用时 1667 秒，02:42 那次直接超时失败。同期正常值只有 42～148 秒。

影响面：财报增量同步与个股分析刷新无法完成，选股与个股页面数据停留在旧日期。

## 根因链路

数据源 → 数据库 → 服务 → 接口 → 页面/任务 → 运行环境：

1. **版本键口径错误（主因）**：`stockProjectionRepository.syncReportRows` 用整条 payload 的 sha256 当 `source_version`。同一份财报每次采集的字段形态并不相同（实测同一家同一期出现 51 键/1647 字节、12 键/322 字节、16 键/22680 字节三种 payload），内容一变就算「新版本」，于是唯一约束 `(company_id, report_kind, period_end, source_id, source_version)` 形同虚设，重复采集必然新增行。
2. **`update_flag` 空值与 `'0'` 未归一**：同一份报告因空字符串与 `'0'` 两种写法被当成两份不同报告，形成约 89.7 万对「假重复」。
3. **采集频次放大**：当日 `stock_analysis_direct` 触发 8504 次采集运行（00:37–10:36），每次都重采该公司全部历史财报。`fundamental.financial_reports` 从 108 万行涨到 **2,164,411 行 / 9,420MB**，仅 2026-11-26 一天就写入 107.9 万行。
4. **选股被连带拖慢**：全市场选股 `loadUniverse` 用 LATERAL 按 `instrument_id` 反查 `core.company_instruments`，该表仅 8748 行却没有 `instrument_id` 前导索引，导致 5000+ 次全表扫；叠加大表后实测 **494 秒**（100 只 7.8 秒 × 5582 只）。
5. **交互放大**：财报越大 → 选股越慢 → 30 分钟预算被吃光，形成「越写越慢、越慢越重试、重试又写更多」的正反馈。

## 修复范围

- 版本键改为**业务身份哈希** `reportIdentityVersion`：公司、报告种类、报告期、来源、`ts_code`、报告类型、公司类型、`update_flag`、公告日、`f_ann_date`、币种、合并口径。采集形态变化不再产生新版本。
- 新增 `normalizeUpdateFlag`：空、null、空白统一归一为 `'0'`；`sameIdentity` 查询、原始留证键、INSERT 参数同步改用归一值。
- 删除「沿用旧 `source_version`」的兜底写回，避免版本键被历史脏值污染（保留 coverage 合并逻辑）。
- 迁移 213：新增 `ix_core_company_instruments_instrument (instrument_id, relation_type, valid_from DESC NULLS LAST)`，消除选股逐只全表扫。
- 新增存量清理脚本 `server/scripts/dedupeFinancialReports.js`：默认 dry-run，`--apply` 才改数据；按身份分组建计划，保留「最完整 / 已是 current / payload 最大 / 最新入库」的那一行，删除前先把 `financial_facts` 与 6 张 `statement_*` 宽表数据合并到保留行，再归一 `update_flag`、重算版本键、同步宽表版本、重算 `is_current_version`。
- 新增回归 `server/test/financial-report-identity.test.js`：断言归一与身份键口径，并以真实事务验证同一报告三种形态（极简 → 完整 → 改值）只落 1 行、宽表与 facts 值正确，不同公告日必须落 2 行。

## 清理与验收证据

生产部署 `0.9.5.10` / 提交 `fb8646cc` / 迁移 213 已应用。存量清理在生产实跑（脚本按保守批大小分事务）：

| 阶段 | 结果 |
|---|---|
| 删除重复行 | **983,410 行**（首轮 119,854 + 次轮 863,556，791,201 组） |
| `update_flag` 归一 | 1,075,272 行 |
| 版本键重算 | 1,181,001 行 |
| 宽表版本同步 | 876,400 行（balance_cas 230,009 / income_cas 230,004 / cashflow_cas 229,931 / balance_hkfrs 64,102 / income_hkfrs 64,123 / cashflow_hkfrs 58,231） |
| `is_current_version` 重算 | 0 行改动（保留行本就是正确的那份） |
| 最终规模 | **1,181,001 行 / 9,445MB**（原 2,164,411 行 / 9,420MB） |

清理后校验：

- 剩余重复身份组 **0**、冗余行 **0**；按 `sameIdentity` 最严口径（含 `ts_code` 与币种）复核同样 0。
- `update_flag` 只剩 `0`（1,169,911）与 `1`（11,090），无空值。
- 无「同一公司同一报告期出现多个 current」的分组。
- `loadUniverse` 实测 **494 秒 → 185 秒**。
- 端到端复跑：`company_financial_incremental_sync` 手动触发 **142 秒成功**（`remaining:0`、`failures:[]`），过程中真实重采 2 家公司、新增 52 行，与既有行身份碰撞 **0** —— 证明修复后再采集不再产生重复。
- 顺带手工清理两张行情表死元组：`market.daily_valuations` 219,265 → 0、`market.daily_bars` 193,667 → 0（二者此前 `last_vacuum` 为空，从未被回收）。

## 遗留风险与后续

- **物理空间未归还**：`financial_reports` 仍占 9,445MB。普通 `VACUUM` 只把空间标记为可复用，要真正缩容必须 `VACUUM (FULL)`，会持 ACCESS EXCLUSIVE 锁并需空闲磁盘不少于新表大小（约 5GB，当前可用 12GB），须在低峰单独执行。
- **`shared_buffers` 仅 128MB**：实例内存 3.7GB、`effective_cache_size` 却设为 4GB，超出实存；大表扫描几乎全走磁盘。调整需重启实例，未在本批处理。
- **自动清理被大表挤占**：`autovacuum_max_workers = 3`，长期被 `financial_reports` 占用，导致 `daily_valuations`、`daily_bars` 长期未被回收。本次为手工 `VACUUM (ANALYZE)` 补救，长期需调参或对大表降低触发频率。
- **统计值口径提醒**：`daily_valuations` 清理前 `n_live_tup = 75,916` 是过期统计值，`ANALYZE` 后真实活行 **12,846,015**；据此误判「73% 死元组膨胀」是不成立的，该表实际死元组仅占 1.7%。排查此类问题必须先 `ANALYZE` 或按真实 count 判断。
