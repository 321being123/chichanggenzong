## 1. 问题背景、最新基线（0.9.5.12）与止血边界

### 1.1 生产现象与已记录容量/性能事实

据 [INC-0054](incidents/INC-0054-财报重复堆积拖垮后台任务与全市场选股.md) 2026-11-26 生产只读快照，服务器根盘 58.9 GiB 已用 44.6 GiB（利用率 80%，剩余 11.8 GiB），PostgreSQL 16 数据目录占 34.0 GiB（76%）。与股票筛选及财报采集直接相关的对象物理占用如下：

| 数据库对象 | 2026-11-26 物理占用 | 构成与现象 |
|---|---:|---|
| `ops.raw_records` | **13.27 GiB** | 堆表 0.84 + 索引 0.50 + TOAST 11.93 GiB；当日仅 `lixinger_response` 写入 108,629 行（1.456 GiB 压缩 payload），四类适配转换报文写入 9.52 GiB |
| `fundamental.financial_reports` | **9.22 GiB** | 清理 983,410 重复行后仍存 1,181,053 行，其中 TOAST 占 7.28 GiB（`raw_payload` 含比较值与大数组覆盖清单） |
| `market.daily_valuations` | **2.65 GiB** | 约 1,285 万活行，全市场 10 年 PB 窗口查询单次排序耗时 60+ 秒（原方案 27.28 实测 60.7s） |
| `fundamental.financial_facts` | **2.45 GiB** | 约 537 万活行，索引 1.43 GiB |
| `analytics.stock_selection_candidates` | **1.40 GiB** | 上线约三周即达 1.40 GiB，其中 TOAST 占 **1.14 GiB**；抽样最大字段为每只股复制的 11 年年度数组与计算证据 |

同步暴露的任务运行问题：
- `company_financial_incremental_sync`（`selection_inputs`）与 `stock_analysis_refresh`（`selection_daily`）多次触达 **1,800 秒（30 分钟）** 超时，其中包含**外部调用次数为 0 仍跑满 30 分钟**的事故记录；
- 单日出现 8,504 个 `stock_analysis_direct` 采集批次，大量历史财报反复重拉；
- 日/周选股槽在数据未齐时段反复重算并产出 `partial` 试算批次与告警。

## 3. 根因链路与现状分析

全链路：`理杏仁官方 API` → `lixingerOfficial / lixingerDatasetAdapter` → `ops.raw_records / market.daily_valuations / fundamental.financial_reports` → `stockSelectionRepository / stockSelectionService / stockSelectionInputsSync` → `analytics.stock_selection_runs / candidates / members` → `stock_analysis_refresh / company_financial_incremental_sync / storage_retention`。

1. **批前批后双重全市场审计（超时首因）**
   - [stockSelectionInputsSync.js](../server/services/stockSelectionInputsSync.js) 每次 `syncSelectionInputs` 在批前与批后各执行一遍全市场 `service.auditInputs()`（两遍完整 `computeSelection`）。即便 `0.9.5.12` 将单次审计从 ~880s 降到 ~197s，每批仅补 20 只股仍要固定耗费约 6—7 分钟审计时间，续批多轮后仍极易积压或超时。
2. **日/周选股槽缺少前置就绪检查（无效空算与 `partial` 垃圾批次来源）**
   - [stockAnalysisRefresh.js](../server/jobs/stockAnalysisRefresh.js) `enqueueDueSelectionPeriods` 负责发现到期目标并入队，真正执行计算的是 `selection_daily` / `selection_weekly` 槽位。当前 A 股估值在 T+1 08:00、港股估值在 T+1 08:45 才齐，但日/周槽在数据未齐时段每次唤醒都跑完整全市场 `computeSelection` 并落库 `partial` 试算运行。
3. **硬过滤未按原因码短路 + 对淘汰股补行业（无效补数与误阻断放大器）**
   - [stockSelectionRulesV2.js](../server/domain/stockSelectionRulesV2.js) 与 [stockSelectionRules.js](../server/domain/stockSelectionRules.js) 的 `worstStatus` 将 `PENDING` 置于 `FAIL` 之前；同时 [stockSelectionService.js](../server/services/stockSelectionService.js) `auditInputs` 对所有 `!item.industry` 标的均入队补行业。
   - 需特别注意：`NOT_APPLICABLE` 并非全部等价于「客观淘汰」——如 [stockSelectionRulesV2.js](../server/domain/stockSelectionRulesV2.js) 中 `history_calendar_unverified`、`history_coverage_unknown` 也返回 `NOT_APPLICABLE`，因此只能按明确原因码区分，不能粗暴全局提升 `NOT_APPLICABLE` 优先级。
4. **选股补财报走「全量三表 + 原生比较值」请求模式（外采与 `raw_records` 最大放大器）**
   - [stockSelectionInputsSync.js](../server/services/stockSelectionInputsSync.js) `collectOne` → [lixingerDatasetAdapter.js](../server/dataAccess/adapters/lixingerDatasetAdapter.js) `resolveFinancialReports` 默认请求全套三表字典与原生同比/环比/单季。经仓库 `lixingerReportMetrics.js` 实算：A 股非金融四表为 `1(核心) + 3(三表全量) + 10(原生比较) = 14 批`，12 年跨度拆 2 段 = **28 次财报请求/股**（加档案与分红共 31 次/股）；港股非金融为 `(1 + 2 + 5) × 2 = 16 次`财报请求/股。每次响应均经 [lixingerOfficial.js](../server/services/lixingerOfficial.js) 整包写入 `ops.raw_records`。
5. **港股估值未按适用端点分组批量更新，历史缺口整段重拉且写库无守卫**
   - `collectHkMarketData` 每次固定拉 11 年估值 + 1 年日线，且 [stockSelectionRepository.js](../server/repositories/stockSelectionRepository.js) `upsertDailyValuationRows` / `upsertDailyBarRows` 无 `IS DISTINCT FROM` 守卫，无变化行也重写 `ingested_at=now()`。
   - 现有 `resolveValuationRowsDetailed` 将全部港股统一发往 `hk/company/fundamental/non_financial`，而理杏仁对港股银行等金融企业另设独立端点（如 `hk/company/fundamental/bank`），不可把全部港股不加分组发往单一非金融端点。
6. **个人测算物理复制全市场候选 + `candidates.detail` 冗余 + 原始报文历史回放边界**
   - `createSimulation` 调用 `copyCandidates` 将源批次 5,600 行含巨型 `detail` JSONB 的候选全表复制；`detail` 内含 11 年 `annual.years` 全量数组及重复的 `ttmEvidenceRef`。
   - **关键约束（原方案第 8 节）**：原分红事实表为可变当前投影，历史计算依赖 `ops.raw_records` 中的分红原文版本还原当时修订；因此 `dividends` 原始报文**不得**简单划入 7–14 天常规清理。
7. **周度未复用同日计算 + `loadUniverse` 冗余 `LATERAL` + `loadPbWindow` 全表排序**
   - `loadUniverse` 对全市场 5,600 只无条件执行 `np`（`pe_static` 已不参与排名）与 `eq`（仅 < 2% `v.pb IS NULL` 需回退）两个财报 `LATERAL`；周度未接入 `computation_input_hash` 受控复用；`loadPbWindow` 在原方案 27.28 实测耗时 60.7s。

## 4. 分批研发设计合同

按「**第一批：先去重复审计与未就绪重算 → 第二批：缩小外采范围与数据合同 → 第三批：存储零复制与受控留存 → 第四批：周度复用与实测驱动的 PB 优化**」四批推进。

---

### 第一批（Batch 1，最优先）：消除重复全市场审计与未就绪重算

#### B1-1：更新基线耗时剖析 + 缺口队列增量化与续批定点复核

1. **先量后改（`0.9.5.12` 新基线剖析）**：
   - 在隔离环境/只读基线上分别量出单次 `selection_inputs` 中「`auditInputs`（按 7 条查询拆解）」「外部采集（按接口分类）」「数据库落库」三段实际耗时，作为第一批改造前基线。
2. **缺口队列身份绑定**（[stockSelectionRepository.js](../server/repositories/stockSelectionRepository.js) / [stockSelectionInputsSync.js](../server/services/stockSelectionInputsSync.js)）：
   - 沿用 `ops.sync_cursors` 的 `selection_inputs:{market}`（`dataset_code='gap_queue'`），队列载荷显式冻结并校验四维身份键：
     `queueIdentity = { market, asOfDate, strategyCode, inputVersion }`（其中 `inputVersion` 纳入 `universeArtifact.contentHash`、策略/公式版本与港股 `targetSetHash`）。
   - 仅当「无现有队列 / 四维身份键任一变化 / 队列已被标为需重审 / 显式强制全审」时，才在批前执行全市场 `auditInputs` 重建冻结队列；否则续批直接消费现有冻结队列。
   - **完整保留既有轮转语义**：沿用跨批 `attempts` 计数、`failedCodes` 与 `deferredCodes` 轮转排序，不丢失任何失败重试公平性。
3. **续批定点复核 + 清零前全市场终审**：
   - 本批实际处理的 ≤ `limit` 只股票，批后仅对这批对象（按其 `instrument_id` / `company_id` 集合）执行**定点重读与规则重算**，原地更新冻结队列中的对应缺口项与 `remaining*` 计数，**不触发全市场 `auditInputs`**。

   - 强制回归反例：「同证券数量但 PB、年度利润/分红或行业版本改变 → `computation_input_hash` 变化 → 拒绝复用并完整重算」。
2. **清理 `loadUniverse` 冗余财报 `LATERAL`**（[stockSelectionRepository.js](../server/repositories/stockSelectionRepository.js)）：
   - 移除不再参与选股排名的 `np`（`pe_static`）全市场逐股 `LATERAL`；
   - `eq`（`pb` 空值回退）改为复用紧随其后的 `loadEquityFacts` 批量结果在内存完成等价同币种闭合回退（注意保留 `0.9.5.12` 撤销 `report_kind='balance'` 限制后的完整净资产语义，不漏非 `balance` 净资产事实）。

#### B4-2：PB 10 年预聚合（先量后定，条件触发）

1. **触发前置条件**：仅在 `0.9.5.12`（迁移 214）与 Batch 1（缺口队列增量化 + 前置就绪检查）落地并完成隔离/线上真实耗时剖析后，若 `loadPbWindow`（原方案 [27.28 节](投资策略选股中心研发方案_20261102.md#2728-性能四方案实测与预聚合结论2026-11-07)实测 60.7s）仍为全链路主要墙钟瓶颈，才启动本项。
2. **先定义失效与重算合同，再选粒度**：
   - 在建表前必须冻结四类变更的失效与精确重算规则：**① 交易日历变更、② 停牌日历补录/更正、③ 多来源优先级变化、④ 历史估值行补采或数值更正**；
   - 使用同一批真实数据对比「按年预聚合（首尾残段查原表）」与「按月预聚合」在查询耗时、维护复杂度与表体积上的差异后定型；
   - 逐证券严格对账 5 项输出：`max_pb` / `max_positive_pb` / `min_positive_pb`、**极值同值取最早日期（`min_pb_date` / `max_pb_date`）**、各类覆盖天数（`positive_days` / `observed_days` / `non_positive_days` / `invalid_days` / `exempt_days`）、`effective_start` 及内容摘要 `series_digest`（diff = 0）。

## 8. 风险、回滚策略与未验证边界

### 8.1 主要风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 续批定点复核与全市场状态漂移，导致漏补对象 | 队列绑定四维身份键；任何身份变化立即重审；队列清零前强制跑一次全市场 `auditInputs` 终审；港股独立核对冻结目标池 |
| 按原因码短路误放行未核实的日历/覆盖缺口 | 禁止全局提升 `NOT_APPLICABLE`；仅白名单内确定性原因码可短路，且由单测锁定白名单与反例；上线前做同冻结输入影子对比 |
| 轻量财报误影响单股三表展示或覆盖已有全量三表 | 显式拆分 `core_complete` 与 `full_statements_complete`；合并层严格保护旧全量行不被轻量行降级；单股刷新继续默认 `'full'` |
| 港股批量估值端点错配或漏码 | 先按 `fsTableType` 分组对应端点（非金融/银行分流），逐证券核对返回日期与必需字段，漏码与未核实类型均留缺口不硬发 |
| 清理原始报文破坏历史分红时点回放 | 明确排除 `dividends` 不进 7–14 天清理；先完成全引用盘点再启用其余数据集清理；淘汰详情保留当时判定依据快照 |
