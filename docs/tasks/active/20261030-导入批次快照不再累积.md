## 1. 问题与证据

### 1.1 现象

生产 `nav_position_snapshots` 在清理前 246 行，其中 75 组「同账户 + 同业务日 + 同证券」重复，多出 139 行：

| 账户 | 业务日 | 行数 / 证券数 | 批次数 |
|---|---|---|---|
| daicunzai / 投资实验账户 | 2026-08-16 | 128 / 32 | 4 |
| daicunzai / 本人账户 | 2026-08-16 | 86 / 43 | 2 |
| being / 默认账户 | 2026-10-29 | 28 / 28 | 1（基准行，非导入） |
| guoyanchaocn@gmail.com / 默认账户 | 2026-10-26 | 3 / 3 | 1（基准行，非导入） |

38 个快照批次里只有 2 个仍被 `nav_history.import_batch_id` 引用，**171 行属于不再被任何导航历史引用的孤儿批次**。

### 1.2 根因（代码位置）

1. 每次导入生成新的 `importBatchId`，并把它当作快照的 `snapshot_id` 写入（`server/routes/accounts.js` 第 939-946 行，`insertPositionSnapshot`）。
2. `upsertImportedNav` 在 `(username, account_name, date)` 冲突时 **`import_batch_id=EXCLUDED.import_batch_id`**（`server/repositories/navImportRepository.js` 第 150-155 行）——同一个 CSV 再导入一次，历史 nav 行被改指向新批次。
3. 导入前只调 `deletePositionSnapshotsByBatch({ snapshotId: importBatchId })`（`server/routes/accounts.js` 第 933 行；仓储 `navImportRepository.js` 第 170 行），**只删"本次批次"的行**，上一次批次的行原地留下。
4. 结果：每重复导入一次，就多留下前一整套快照，没有任何一方引用它。

### 1.3 当前影响（已核对，不是"看起来重复"）

- 读取侧（`server/services/navAttribution.js:77-79`、`server/jobs/navSnapshot.js:104-108`）都按 `nav_history.import_batch_id` 过滤到单一批次，再按证券用 `Map.set` 覆盖写入，**不会重复计数**。
- 风险在两处：①「引用批次缺失时按最新日期兜底」（`navAttribution.js:85`）会把同一天的多批次行全部取出，取值顺序由 `ORDER BY snapshot_date, snapshot_id` 决定，等于**任取一条**；②表持续膨胀、口径不可解释。

### 1.4 存量清理（2026-10-30 已执行）

- 备份：`/var/backups/portfolio/manual/nav_position_snapshots_before_cleanup_20261030.sql.gz`（246 行全量 `--inserts`，sha256 `f6d5ffe6…84bd4`，本地另存一份）。
- 删除孤儿批次 171 行 → 246 → 107 行。
- **清理时踩过的错（必须记住）**：第一版规则写成「删掉不被 `nav_history.import_batch_id` 引用的行」，把 **32 行 `manual_reconciliation` 基准快照一起删了**——基准行的 `snapshot_id` 是 `basis-…`/随机 UUID，天生不会被 `import_batch_id` 引用，但它们是净值续链的锚点。已按备份还原（逐列比对样本行一致、32 行 `sum(quantity)=124514.0000`、`sum(market_value_cny)=468950.37` 与备份重算完全一致）。
- **正确的清理规则**：孤儿判定必须排除基准行

  ```sql
  DELETE FROM nav_position_snapshots s
   WHERE s.source <> 'manual_reconciliation'
     AND NOT EXISTS (SELECT 1 FROM nav_history h WHERE h.import_batch_id = s.snapshot_id);
  ```

- 清理后状态：107 行（导入批次 75 行 + 基准 32 行），重复组 0；两个被引用的批次 32/43 行完整。

## 2. 目标

1. 同一账户反复导入同一份文件，快照行数**不随导入次数增长**。
2. 任何仍被 `nav_history` 引用的历史批次**不得删除**（历史锚点是净值续链的事实）。
3. 导入批次回滚（`POST /nav/import/:batchId/rollback`）后，回滚前那套锚点仍可用，不能出现"回滚成功但净值算不出来"。
4. `manual_reconciliation` 基准行永不参与此类清理。

## 3. 方案对比

| 方案 | 做法 | 优点 | 主要问题 |
|---|---|---|---|
| A1 导入尾部立即清孤儿 | 导入事务末尾执行 1.4 的删除 SQL | 最简单，表永不留垃圾 | **破坏回滚语义**：本次导入刚刚取代的上一批次会被立刻删掉，而回滚要按 `backup_payload` 恢复 nav 行（含旧 `importBatchId`），那时锚点已不存在 |
| **A2 只清"本次导入之前就已孤儿"的批次**（推荐） | 导入开始时先记下当时的孤儿集合，事务末尾只删这一批 | 回滚安全（本次被取代的批次保留）；垃圾最多残留一个批次，下次导入清掉 | 表可能短暂多一套快照（一次导入的量） |
| B 快照改为单一事实（按账户+业务日+证券 upsert） | 与 migration 179 同思路，`ON CONFLICT` 覆盖 | 语义最干净，行数与导入次数无关 | 需要改读取侧"按批次取锚点"的模型、历史数据要迁移；且回滚仍需旧值快照，风险面大 |
| C 定时清理任务 | 每天/每周跑一次孤儿清理 | 实现最省事 | 滞后一天到一周；仍要单独解决回滚窗口 |

**推荐 A2**：改动集中在导入事务内的两条查询，不动读取模型，不动历史数据；回滚窗口的语义保持与今天一致。

### 3.1 A2 的实施要点（给实现者）

1. `server/repositories/navImportRepository.js` 新增两个函数：
   - `selectUnreferencedSnapshotBatches({ username, accountName }, client)` → 返回当前已孤儿且非基准的 `snapshot_id` 列表；
   - `deletePositionSnapshotsByIds({ snapshotIds }, client)` → 按 id 删除（走 `snapshot_id = ANY($2)`，不用字符串拼接）。
2. `server/routes/accounts.js` 的导入事务里，在 `insertImportBatch` **之前**取第 1 步的名单（此时新批次还没写，名单天然不含"本次被取代的批次"），在 `insertPositionSnapshot` 循环**之后**执行删除；两者同一事务，失败一起回滚。
3. 删除条件里必须写死 `source <> 'manual_reconciliation'`，并在注释里说明原因（见 1.4）。
4. 记一条日志：删了几个批次、几行，便于对账。

## 4. 验收标准

| 编号 | 验收项 | 判定方式 |
|---|---|---|
| IMP-1 | 同一 CSV 连续导入 3 次后，快照总行数不增长（只保留最新批次 + 基准行） | 隔离库测试：每次导入后 `count(*)` 相同，且只剩 1 个 `system_*` 批次 |
| IMP-2 | 被 `nav_history` 引用的历史批次不被删除 | 构造两次不同日期导入，第二次后查旧批次仍有行 |
| IMP-3 | 导入后回滚，回滚前的锚点仍存在且净值链可算 | 真库旅程：导入 → 回滚 → 断言旧批次快照仍在、`navSnapshot.recordNavSnapshots` 能算出对应日期 |
| IMP-4 | `manual_reconciliation` 基准行从不清除 | 测试里插入基准行 + 孤儿批次，跑清理后基准行仍在（**这条就是 1.4 事故的回归**） |
| IMP-5 | 清理与导入同事务：任一步失败不留下半套数据 | 注入失败后断言行数回到导入前 |
| IMP-6 | 破坏性验证 | 去掉清理调用后 IMP-1 必红 |

## 5. 风险与边界

- 不要用"按账户全删"代替孤儿判定：多个导入日期共存时，旧批次可能是更早日期的锚点。
- 不要顺手把基准行纳入清理（1.4 已付出一次代价）。
- 本次只清理存量，不改变导入行为——**在这条立项实施前，重复导入仍会继续产生孤儿批次**。
- 若将来引入"多版本锚点对比"需求，A2 需要重新评估（当前读取侧只认单一批次）。
