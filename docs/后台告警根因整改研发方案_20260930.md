## 二、架构对齐与修改边界

| 分类 | 内容 |
|---|---|
| 已有能力 | 休市页面及编辑接口、年度同步、共享交易日历、统一Guard、任务Runner、分区注册表、公告/PDF缓存、告警恢复验证器 |
| 可复用能力 | `holiday_sync`、`ipo_history_sync`、可转债公告任务、`nav_snapshot`、`hk_ipo_enrichment`、`stock_analysis_refresh`及现有历史告警对账 |
| 真正缺口 | SSE未来日历持久化及覆盖检查、模式内完成证据、历史缺口与当前产出的分别验收、未恢复数据的定点补齐 |

沿用既有数据源、事实表和调度器，不新增平行任务或日历库。只修改命中问题的函数及相关回归。保持已有页面、权限、行情计算、预测模型和强赎业务规则；不开展全文件重构。

总体影响链路：来源或本地原文 → 现有事实/日历/快照表 → 对应服务与Runner → 分区发布和质量校验 → 既有业务接口、页面、日报与后台告警。

## 三、R1 接通已有日历并恢复今日任务

### 3.1 现有实现中的缺口

- `server/jobs/holidaySync.js` 请求年度 `trade_cal` 后只提取休市日期写JSON；判断配置新鲜后直接返回，未检查共享日历是否缺失。
- `server/services/jobRunners.js` 的 `holiday_sync` 将结果统一包装为 `{ ok: true }`；同步取数失败只打印警告并返回时，存在被报成功的风险。
- `server/services/convertibleBondAnalysis.js` 的 `getRecentOpenDays()` 只保存截至目标日的历史窗口；个券分析请求未来日历仅供内存计算，没有补共享未来日期。
- `server/services/datasetPartitionRegistry.js` 的 `trade_calendar/GLOBAL` 行数与日期查询未过滤交易所，HKEX全年覆盖可能掩盖SSE断档。此项为代码核查发现，尚未单独实测生产误发布过程。

### 3.2 实施内容

1. 扩展现有 `holiday_sync` 同步入口。保留现有休市页面，将核验后的交易日历先幂等保存到 `market.trade_calendar`，再从同一批事实生成JSON兼容配置；页面保持原接口与外观。
2. 首次检查目标年度全日期差集，补齐当前年度缺口，重点恢复09-30之后的覆盖。不要只查最大日期；中间缺日同样失败。保留 `exchange + trade_date` 唯一键及 `source_code/raw_payload/ingested_at` 来源证据。
3. 继续使用现有Tushare客户端与Guard，接口 `trade_cal`，字段至少为 `cal_date,is_open`，交易所明确为SSE。请求当前年度缺失区间；不额外拉行情或其他接口。接口依据见 [Tushare官方文档](https://tushare.pro/document/1?doc_id=26)。
4. 日常复用既有每日覆盖检查与月度刷新入口。全年连续覆盖且配置一致时不联网；缺口按日期差集补取，来源更正沿用月度核对。下一年度沿用既有年末预拉入口，仅保存上游已公布并通过覆盖核验的日期；未公布时保持未知，不猜开市日。
5. 完成条件同时包含：SSE日期连续、开休市标记合法、所需下一交易日存在、落库及兼容配置成功。失败或可疑空响应保留旧数据，返回明确失败/部分完成；Runner原样传递结果，不能统一包装成功。
6. 沿用已有 `trade_calendar/GLOBAL` 数据集代码和scope，针对 `holiday_sync` 的注册查询与质量诊断明确SSE范围；不以HKEX的最大日期替代SSE覆盖证据。日历覆盖截止日与任务目标业务日分别记录，不混用分区键。
7. 启动、定时和管理员同步复用同一入口及现有锁/审计。IPO与可转债消费者只查本地日历，缺覆盖时返回可诊断错误，不能各自联网补一套日历。

### 3.3 管理员维护兼容

现有 `server/routes/admin.js` 的休市编辑只写JSON。该入口也要接入统一保存服务，使明确维护年度内的页面配置与共享日历保持一致；只读GET不得触发补库或联网。

自动刷新不能悄悄覆盖已有人工维护差异。实施前核对编辑审计及来源；人工覆盖的取舍沿用可追溯配置记录。未能区分官方和人工值时先保留并报告冲突，不将其当作已验证来源发布。保存失败不能返回成功；数据库与文件更新之间失败时记录不一致并修复，不能宣称二者天然具备跨存储事务。

### 3.4 恢复顺序与验收

代码上线且取得对应生产数据写入授权后：日历同步 → 重试同业务日IPO与新债检查 → 两个精确分区质量通过 → 重试日报。使用既有Runner，保留业务日期，不能用运行当天替换原任务日期。

验收：年度中间缺日可发现；国庆长假后下一交易日来自落库事实；跨年未知不伪造；只有HKEX全年数据时SSE检查仍失败；上游空/失败不产生成功分区；重复执行无缺口时外部调用为0；页面与任务对同日开休市判断一致。

## 四、R2 修复IPO阶段完成判定及超时续跑

`JOB_CONTRACTS` 已声明 `targeted` 不发布全局数据集且要求 `stageComplete`。Python定向出口返回目标代码、质量和阶段完成结果，但不返回全局日期。本轮看到多个定向槽位degraded；具体水位短路与完成检查分支需按对应运行复现后局部修复，不预设所有degraded都是误报。

- 将 `prediction_ready/core/enrichment/targeted` 分别按已有阶段契约验收，不把任务级日期检查无差别套到所有模式。
- 定向成功必须同时具备：请求代码全部处理、请求字段有落库/核验依据、`stageComplete=true`、无失败对象和待续跑阶段。缺字段、Guard停止、目标遗漏均不得通过。
- `targeted` 不发布全局IPO分区；以目标范围的完成证据替代不适用的全局水位要求，不能简单关闭整个任务的质量门禁或填今天日期。
- 核对既有11项补全缺口，区分未披露、原文缺失、解析失败及请求失败。优先本地事实和缓存原文，补取只限剩余目标与字段。
- 09-29运行3396已确认超时。核对超时前已保存进度、剩余队列及下一次时间；复用现有游标/续跑机制，下一轮只处理剩余项。未完成仍为partial/等待，不只扩大超时时间。

影响文件候选：`server/jobs/ipoHistorySync.js`、`ipo-report/ipo_history_sync.py`、`server/services/jobDefinitions.js`、`jobScheduleSlots.js`、`jobOrchestrator.js`、`jobRecoveryEvidence.js`。仅修改实测命中的分支。

验收：完整定向任务正常结束；漏目标、缺指定字段、阶段未完继续失败；核心分区仍严格校验；超时后续跑不重复处理已完成原文，不丢进度。

## 七、R5 有证据地收敛告警

复用 `jobAlertMailer.verifyAlertScope()`、`jobRecoveryEvidence` 和 `server/scripts/reconcileAlertHistory.js`，先只读预览，再按获准范围处理。生产写入前列出精确告警ID、scope、恢复证据及预计操作。

| 告警作用域 | 允许关闭的证据 |
|---|---|
| 原槽位/任务模式 | 对应模式完成且质量/阶段符合契约，后续证据须通过现有可比规则 |
| 数据集 | 精确 `dataset_code + scope_key + partition_key` 已发布，质量通过且未过期 |
| 来源接口 | 同来源、同接口及凭据范围的相关熔断已关闭，并有新的成功时间 |
| 旧误报/不适用条件 | 可查原规则与事实依据，人工确认并留审计，不伪造恢复 |

空查询、仅有最大日期、普通任务done、其他日期成功均不能关闭历史数据质量告警。通配来源只核对实际 `source:*` 作用域，不能代替具体接口恢复。恢复通知按告警键去重，不删除运行记录、不批量清零，也不要求42条全部消失才算代码正确。
