# INC-0029：IPO补全空候选误报成功

状态：0.8.1.85 本地修复与全量测试、知识门禁通过；待标准生产发布及资料缺口处置
日期：2026-09-23

## 现象与影响

2026-09-23 生产 `ipo_history_sync/enrichment` 首轮运行 `3230`（19:35）因剩余 16 个资料字段未补齐而失败；重试运行 `3238`（19:52）仍有 18 项缺口，分布为行业 3、行业 PE 9、主营业务 4、业务赛道 2。该范围涉及 `301718、301569、920162、920157、001246、301716、920202、301686、920229、920298、920258`。

20:53 的运行 `3242` 实际没有尝试对象，外部调用数为 0，却报告 `remaining=0` 并成功；计划槽位 `994124` 因此成功，告警 `21480` 被自动标记为已解决。生产记录仍显示此前存在的 18 项资料缺口，空跑没有形成数据恢复证据。

## 根因链路

同日尝试标记排除候选 → `ipo_history_sync.py` 候选查询为空 → 快捷返回 `remaining=0` → Worker 将阶段判为成功 → 槽位成功证据收敛失败告警。

## 直接原因、根本原因与保护机制失效原因

- 直接原因：`enrich_stock_missing_details()` 在 `if not candidates` 分支立即返回零剩余，没有运行后面的真实缺口统计。已经尝试过、但字段仍为空的证券因此在同日后续空跑中被伪装成“没有剩余资料”。
- 根本原因：把“没有符合本轮重试条件的候选”与“阶段范围内没有未完成数据”视作同一事实。
- 保护机制失效：Worker 和告警恢复器按任务返回值消费了这个虚假的成功；恢复链没有机会发现该成功运行实际尝试数为 0，且阶段仍有已知字段缺口。这违反空查询不能作为恢复证据的现行规则。

## 同类范围与核查结果

- 影响同一个 `enrich_stock_missing_details()` 的目标代码补全、全量 `enrichment` 和定向补全调用；当已有同日尝试记录使候选集合为空、但字段仍缺失时会触发。
- 生产剩余字段中，9 项为行业、主营业务或业务赛道资料缺口；9 项为行业 PE 缺口，现存来源诊断包括官方文件未找到/解析未命中、样本不足或不匹配、来源暂不可用。不能靠手工关闭告警或单纯空跑证明这些字段已恢复。
- 只读查询确认核心 `ipo_history` 分区仍按其独立质量状态发布；本事故是 enrichment 阶段完成标记及告警恢复证据错误，不是核心事实分区被回滚。

## 修复与回归证据

- 本地修复删除“候选为空就返回零剩余”的快捷分支，让函数无论本轮是否有可尝试对象，都统计所声明代码范围内真实缺失的字段。
- 增加回归样例：目标证券仍缺四项资料、但 `attempted_on` 已是当天；断言本轮 `attempted=0` 时仍返回四项剩余字段。
- `npm.cmd run test:all`：142 项通过、0 失败、0 跳过；`npm.cmd run check:knowledge` 通过。生产代码、生产数据和告警状态未由本次操作修改。

## 防复发措施与遗留风险

- 任务返回成功必须由实际阶段状态及真实剩余进度决定；“没有候选”只说明本轮没有可尝试对象，不能覆盖已知缺口。
- 修复发布后，需在获得生产发布及资料补跑授权后，经现有 `ipo_history_sync` Runner 重试；只有字段更新或可信终态证据形成后，才能按现有告警证据链恢复告警。
- 在生产修复发布并完成受控重试前，告警 `21480` 已处于 `resolved`，因此生产告警界面无法可靠表达当前资料缺口；不得将这条 resolved 状态作为数据完整性凭证。
