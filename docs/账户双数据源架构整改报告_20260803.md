# 账户双数据源架构整改报告

**报告日期：** 2026-08-03  
**核查范围：** 账户、持仓、交易、历史净值、现金流、指数历史、账户元数据及相关前后台读写链路  
**报告性质：** 架构整改方案，本文不包含生产数据修改或部署操作

## 一、问题结论

近期历史净值“清空后恢复”、数据源错乱、还原无效等问题，不是单个按钮或单条 SQL 的偶发错误，而是账户数据长期存在两套事实来源造成的系统性缺陷：

1. 结构化业务表：`accounts`、`positions`、`trades`、`nav_history`、`cash_flows`、`index_history` 等；
2. 兼容 JSON：`account_data.data` 中仍保存 `positions`、`trades`、`navHistory`、`cashFlows`、`cashBase`、`hkRate` 等字段。

当前代码同时存在双写、双读、空表回退、查询时自动迁移和整包覆盖。任何一条链路漏写、写入失败或执行顺序不同，都会导致两份数据不一致。之后再遇到“结构化表为空”等条件时，旧 JSON 会重新参与业务读取，使已经清空的数据再次出现。

最近增加的“表与 JSON 同时写入”只能避免特定按钮立即出错，不能消除根因，反而扩大了后续所有功能都必须正确维护双写的范围。

## 二、实测证据

本地数据库只读核查结果：

| 核查项 | 结果 |
|---|---:|
| `account_data` 账户记录 | 3 个 |
| 持仓表与 JSON 数量不一致 | 1 个账户 |
| 交易表与 JSON 数量不一致 | 1 个账户 |
| 历史净值表与 JSON 数量不一致 | 1 个账户 |
| 现金流表与 JSON 数量不一致 | 1 个账户 |
| “结构化表为空、JSON 仍有数据”的还魂候选 | 四类数据各 1 个账户 |
| 不属于任何 `accounts` 账户的孤立 `account_data` | 1 个账户 |

以上结果证明该风险已经形成真实数据残留，并非理论推测。该结果仅代表本地数据库，生产数据库必须在获得明确授权后单独执行只读差异核查。

## 三、当前主要缺陷

### 3.1 结构化表为空时读取旧 JSON

`loadAccountData()` 在持仓、交易、净值和现金流四张表同时为空时，会把 `account_data.data` 中的旧数组重新作为页面数据返回。

该判断无法区分以下两种情况：

- 账户尚未迁移，需要从 JSON 补数据；
- 用户已经主动清空数据，结构化表为空是正确结果。

因此，“表为空”不能作为迁移或恢复条件。

### 3.2 历史净值继续双写

当前历史净值备份、还原和清理同时修改 `nav_history` 与 JSON。任何新增净值写入者只要漏掉其中一边，两份数据就会再次分叉。

后台 `navSnapshot`、`replayNav` 等任务直接写 `nav_history`，并不维护 JSON 中的完整镜像，因此双写一致性无法长期保证。

### 3.3 查询过程带有自动写入

`index_history` 为空时，读取链路会从旧 JSON 取数据并自动写回结构化表。读取接口因此具备恢复旧数据的副作用，也无法判断空表是否来自用户主动删除。

### 3.4 管理员迁移接口可重复回灌旧数据

现有 `/migrate-json` 可以再次把 `account_data` 中的持仓、交易、净值和现金流合并进结构化表。只要旧 JSON 未清理，已经删除的数据仍可能被重新导入。

### 3.5 前端整包保存可能覆盖后台新数据

前端每次保存都会发送完整账户对象；服务端删除并重建持仓、交易、净值和现金流四张表。后台任务新增净值后，如果旧浏览器继续用内存中的旧快照保存其他内容，就可能把后台新增净值整表覆盖。

现有乐观锁只绑定 `account_data.version`，而部分后台结构化表写入不提升该版本，因此不能完整拦截这种覆盖。

### 3.6 账户删除没有删除业务数据

页面提示“删除账户及其所有持仓数据”，实际主要删除账户列表或 `accounts` 元数据，持仓、交易、净值、现金流、价格和 `account_data` 可能继续保留。重新创建同名账户后，旧数据可能再次出现。

### 3.7 账户重命名不是原子操作

当前重命名采用“读取旧账户数据、修改账户列表、再保存到新名称”的方式：

- 中间任一步失败会形成半完成状态；
- 旧账户业务数据没有被可靠删除；
- 新账户保存可能受版本号和权限同步顺序影响；
- 重新添加旧名称时可能重新看到旧数据。

### 3.8 账户列表也存在双来源

页面账户列表优先读取 `accounts` 表，部分权限校验仍读取 `users.accounts` JSON。两者分步更新，任一步失败都可能产生页面与权限不一致。

### 3.9 缺少账户级外键和级联删除

持仓、交易、净值、现金流等表主要依靠 `username + account_name` 文本关联，没有统一不可变的账户主键和完整外键约束，因此数据库允许孤立数据长期存在。

### 3.10 错误被静默吞掉

多处 JSON 解析、迁移和兼容读取使用空 `catch`，数据损坏、迁移失败或回退发生时缺少明确日志和质量告警，问题通常直到页面数据异常才被发现。

## 四、整改目标

整改后的基本规则：

1. 每类业务数据只能有一个权威来源；
2. JSON 兼容数据不得参与日常业务读取；
3. 空表代表真实的空数据，不触发自动恢复；
4. 所有写入者走统一服务和事务；
5. 前端不再整包覆盖互不相关的数据集；
6. 删除、重命名和后台任务必须纳入版本控制；
7. 数据迁移只能执行一次，并有账户级迁移状态和审计记录；
8. 数据库用不可变 `account_id`、外键和级联规则保证完整性。

## 五、目标数据源矩阵

| 数据集 | 唯一权威来源 | 处理方式 |
|---|---|---|
| 账户身份、名称、券商、可见性 | `accounts` | 使用不可变 `account_id` |
| 期初本金、账户汇率 | `accounts` | 删除 JSON 回退 |
| 持仓 | `positions` | 只读写结构化表 |
| 交易 | `trades` | 只读写结构化表 |
| 历史净值 | `nav_history` | 只读写结构化表 |
| 现金流 | `cash_flows` | 只读写结构化表 |
| 指数历史 | `index_history` | 只读写结构化表 |
| 每日价格 | `daily_prices` | 只读写结构化表 |
| 税费设置等账户偏好 | 新建 `account_preferences`，或 `accounts` 的明确 JSONB 字段 | 仅保存设置，不保存业务事实数组 |
| 净值备份 | 独立 `nav_history_backups` | 保存快照时间、账户、记录和操作人 |
| 当前现金、总资产 | 按持仓、现金流、交易和行情计算 | 不作为第二份业务事实长期保存 |
| 旧 `account_data.data` | 只读迁移档案 | 迁移完成后退出运行时链路 |

## 六、分阶段整改方案

### 阶段一：建立数据源边界并停止继续扩散

1. 明确上述唯一数据源矩阵；
2. 禁止新增任何 `account_data.data` 业务数组读写；
3. 增加静态测试，发现业务代码读取 `data.positions`、`data.trades`、`data.navHistory`、`data.cashFlows`、`data.indexHistory` 的服务端 JSON 兼容链路时直接失败；
4. 增加账户数据一致性只读审计，列出表与 JSON 差异、孤立账户和重复账户；
5. 暂停使用可重复执行的 `/migrate-json`，避免继续回灌旧数据。

### 阶段二：一次性迁移与冲突处理

1. 对每个账户生成结构化表与 JSON 的差异报告；
2. 默认以结构化表为权威来源；
3. 对“表为空、JSON 有数据”的账户单独列出，禁止自动迁入；
4. 经确认后，只对确属未迁移的数据执行一次性补录；
5. 设置 `data_source_version=2` 或 `structured_migrated_at`；
6. 将原 JSON 完整归档并记录校验值；
7. 从运行时 JSON 中移除持仓、交易、净值、现金流和指数历史数组；
8. 迁移完成后，即使结构化表为空，也不得再读取归档 JSON。

### 阶段三：改造运行时读写

1. `loadAccountData()` 永远从结构化表组装结果；
2. 读取接口不得执行迁移或写库；
3. 拆分整包保存接口：
   - 持仓增删改只影响 `positions`；
   - 交易录入只影响 `trades` 及明确关联的持仓；
   - 净值导入和管理只影响 `nav_history`；
   - 现金流操作只影响 `cash_flows`；
   - 设置修改只影响账户偏好；
4. 所有前台与后台写入调用统一的数据服务；
5. 每个数据集使用独立版本号，或所有写入共同提升统一账户修订号；
6. 禁止旧浏览器用整包数据覆盖后台新记录。

### 阶段四：账户生命周期整改

1. 为账户建立不可变 `account_id`；
2. 持仓、交易、净值、现金流、价格和指数历史全部关联 `account_id`；
3. 账户重命名只修改 `accounts.account_name`，不搬运业务数据；
4. 新增正式账户删除 API，在单个事务内处理账户和所有子数据；
5. 配置外键和明确的 `ON DELETE CASCADE` 或受控软删除；
6. 账户列表只读取 `accounts`，退出 `users.accounts` JSON；
7. 删除、重命名、恢复均记录审计日志。

### 阶段五：退出 `account_data`

1. 将净值备份迁入独立备份表；
2. 将账户设置迁入正式设置表；
3. 将版本号和更新时间迁到权威账户或数据集；
4. 核实 `fundRecord` 等遗留字段是否仍有业务用途，无用途则废弃；
5. 所有调用方完成切换并连续通过数据一致性检查后，删除或永久只读封存 `account_data`。

## 七、迁移安全要求

1. 生产操作前必须先做数据库全量备份；
2. 先执行只读差异核查，不得直接自动合并；
3. 结构化表为空但 JSON 有数据时，必须人工确认数据含义；
4. 每个账户迁移前后记录各表数量、日期范围、金额汇总和校验值；
5. 迁移使用单账户事务，失败时完整回滚；
6. 迁移脚本必须幂等，但已完成账户不得再次读取旧 JSON；
7. 迁移后先保留只读归档，确认稳定后再决定物理删除；
8. 未获得用户明确同意，禁止执行生产数据同步或生成直接修改生产数据的 SQL。

## 八、防复发验收标准

### 8.1 数据源验收

- 结构化表为空、JSON 有旧数据时，页面必须显示为空；
- 清空净值后刷新、重新登录、重启服务，数据仍为空；
- 管理员迁移接口不能再次恢复已迁移账户的旧数据；
- 读取任何账户接口不会产生数据库写入；
- 运行时代码不再读取 JSON 中的五类业务数组。

### 8.2 并发验收

- 后台新增净值后，旧浏览器保存持仓不会删除新净值；
- 两个浏览器同时修改不同数据集互不覆盖；
- 同一数据集发生并发冲突时明确返回冲突，不静默覆盖；
- 后台任务、导入、还原和手工编辑使用相同版本机制。

### 8.3 账户生命周期验收

- 删除账户后，所有关联数据按设计删除或进入明确的软删除状态；
- 重新创建同名账户不会出现旧数据；
- 重命名账户不会复制、遗漏或遗留孤立数据；
- `users.accounts` 与 `accounts` 不再形成两套账户列表；
- 数据库不存在没有账户主记录的持仓、交易、净值、现金流和兼容 JSON。

### 8.4 自动化测试

至少覆盖以下场景：

1. 表空、JSON 非空时禁止还魂；
2. 主动清空后刷新和重启仍为空；
3. 后台净值写入与前端持仓保存并发；
4. 删除账户后重新创建同名账户；
5. 账户重命名成功与中途失败回滚；
6. 一次性迁移只执行一次；
7. 迁移冲突账户不会自动选择 JSON；
8. 孤立数据审计结果为零；
9. 所有写入失败时保留上一份有效数据；
10. 全量测试、安全测试和迁移回归测试全部通过。

## 九、优先级建议

| 优先级 | 整改项 | 原因 |
|---|---|---|
| P0 | 取消运行时 JSON 兜底和自动回迁 | 直接阻断数据还魂 |
| P0 | 停止整包保存覆盖、统一版本控制 | 防止后台新数据被旧页面删除 |
| P0 | 修复账户删除和重命名 | 防止孤立数据和同名账户复活 |
| P1 | 执行生产差异核查和一次性迁移 | 清理已经形成的双源不一致 |
| P1 | 统一账户列表来源和不可变 `account_id` | 消除权限、名称和子表关联错乱 |
| P1 | 拆分净值备份和账户偏好 | 为退出 `account_data` 做准备 |
| P2 | 删除或永久封存 `account_data` | 完成架构收口 |

## 十、建议实施顺序

建议不要继续增加新的“双写修补”。正式整改顺序如下：

1. 先增加只读审计和防还魂测试；
2. 取消运行时 JSON 回退与可重复回迁；
3. 改造整包保存、版本控制、账户删除和重命名；
4. 输出生产数据库差异报告；
5. 经用户确认后执行一次性数据迁移；
6. 观察一段时间并持续核对一致性；
7. 最后拆分剩余设置和备份字段，退出 `account_data`。

整改完成的判断标准不是“当前按钮能用”，而是系统中每类账户数据都只有一个权威来源，任何空表、删除、重命名、后台任务或旧浏览器保存都不会再触发旧数据恢复或覆盖新数据。
