# 交付核查与复验

目标是首轮集中找齐问题，第二轮集中复验。“轮”指交给用户的验收结论，同一轮可以多次读取、探查、补跑和复核。两轮是组织目标，验收结论以实际证据为准。

按用户限定的范围验收当前交付。验收默认只读；测试数据写入须遵守项目的资源归属和隔离规则。修复、提交、部署和生产写入按用户授权及项目规则处理。

## 首轮：按交付合同覆盖全链路

1. **锁定验收对象。** 找到用户要求、权威方案和约定的验收条件。区分方案定稿、功能实现、本地验收和发布验收。记录分支与提交 SHA；如果验的是未提交版本，附上工作树差异、未跟踪交付文件或能定位受验内容的其他标识。
2. **先列矩阵，再跑测试。** 从正常入口追到实际结果，每个关键验收条件一行。按影响纳入人工和自动入口、旧入口和回退路径、数据来源与依赖、权限与状态、UI 和 API 契约及既有调用方。纯文档验收核对需求覆盖、事实依据、交叉引用和状态一致性。
3. **一处反例，查完整组。** 先识别被违反的约束，再按相关维度核查同类场景：

   - **输入**：从实际读取、关联、筛选和计算代码反查参与结果的全部输入，与方案逐项核对。
   - **入口**：核查触发同一逻辑的调用方，包括适用的旧入口、批量操作和自动任务。
   - **时序**：核查读取与确认之间的更新、重试、并发、迟到响应和中断后恢复。
   - **变化形态**：核查新增、删除、原地更正及总数不变的更正。

4. **取得能证明结果的证据。** 按项目入口运行适用测试，再补关键反例。结果依赖实际数据时，首轮同时核对来源是否提供关键证据、现役采集与仓储是否传到计算、代表性样本是否具备该证据。构造样本可验证成功和拒绝分支，真实覆盖按实际样本判定。高风险路径尽量覆盖成功、拒绝和运行失败，核对最终状态、写入次数、金额、资格或用户实际看到的内容。现有测试覆盖不到时，可在授权范围内用可清理的最小探针。发现第一处阻断后，继续完成可安全进行的其他检查。确需先修复才能继续验证的场景，记为待验并写明复验条件。
5. **交付前自检。** 每个已确认问题是否已查相关的整组场景？正常入口是否实际经过本次改动的各层，替身是否只用于需要隔离的边界？是否核对了最终落库和重试结果？矩阵每行是否都有结论，或注明待验原因及复验条件？
6. **集中交付并保留接续材料。** 同因问题合并，保留关联矩阵行、受影响入口和代表性证据。把报告和完整矩阵写入本任务既有、可跨会话查阅的验收记录或任务卡，并在回复里给出可定位的链接。没有合适记录、无写入授权或用户要求仅在聊天交付时，在首轮报告直接附完整矩阵。

### 涉及共享数据写入、外部依赖或重试时

首轮根据实际调用链在矩阵中展开适用的反例。单个用例可以覆盖多项，避免仅因代码里存在某个名字就追加场景。

| 风险 | 验证场景和证据 |
|---|---|
| 测试绕过入口 | 至少走一次正常入口，实际经过变更涉及的查询、模型和持久化，使用与目标版本一致的隔离库结构。需要替换上游时，把替身放在外部适配器边界。直接注入业务结果的测试只证明注入点之后的行为。 |
| 多入口写同一事实 | 从最终写入位置反查仍可写入的入口，包括定时、手动、历史补数和重算。按实际业务身份核对所有权范围、旧代码和规范代码。若同一对象有多种表示，验证同一账户与不同账户，以及两种表示先后互换。检查最终读取消费的值及冲突状态。 |
| 并发或重试打破唯一性 | 顺序重跑与真正交错分别验证。可暂停一个入口于最后一次判定可写之后、持久化之前，让另一入口提交，再恢复第一个。若使用锁，验证需要共享业务身份的入口确实等待同一把锁，并在获得锁后读取已提交的值。最终核对全部写入行和下游结果。 |
| 部分到齐或上游异常 | 同批组合已有本地有效值、首批拿到的有效值和仍缺失的数据，分别验证真正相关的空响应、报错或限流。核对前两类是否按合同保留、失败是否只落在未完成对象、上游恢复后是否只处理剩余缺口。同时确认已在本地解决的单项是否仍发起不必要的外部请求。 |
| 时点决定准入 | 固定业务日期和运行时钟，按合同测试阈值前、恰在阈值、刚过阈值、晚于运行时刻及跨日。核对写入资格与下游能否使用，避免仅断言解析函数的返回值。 |

汇报首个反例前，沿同一业务约束完成可以独立验证的相关场景。测试失败若阻断另一条链路，应记录具体的待验入口和解阻条件。隔离库、上游替身和生产实测各自标明证据范围。

## 复验启动与收口

- 收到“已修改，再核查”时，先对比上次受验版本、工作树、验收标准及相关数据、环境和新证据。验收标准、相关行为或运行条件变化，或有可能改变结论的新证据时，只复验受影响的矩阵行。用户明确指定重测或项目门禁另有要求时，按其要求执行。
- 仅改任务卡、文档或交接状态，且功能验收条件和证据保持有效时，核对差异、引用及适用门禁，标注为交接核对，复用原功能结论和轮次。交付对象本身是文档时，按文档的验收条件复验。没有相关变化或新证据时，简报核对结果。
- 缺少真实样本、权限或前置修复时，完成当轮其他可验证项，记录具体缺口、能解阻的证据及取得后要跑的入口。有新证据或前置条件满足后再复验该项，避免每次交接重复查询同一缺口。属于必验项的，保持待验。

## 按矩阵集中复验

1. 从任务记录或首轮报告取回矩阵，按实际差异确定范围。首轮材料暂不可得时，先依据权威方案、当前差异和可取得的历史证据重建矩阵，标出无法核实的旧项并复验可验证的范围。只有缺失材料确实阻断关键验收时才向用户索取。
2. 复跑已报告的失败项及同类反例，核对首轮已通过但受差异影响的行，补跑相关旧流程和必要门禁。达到复发阈值时，执行下节的整组验收。其他结论仅在项目规则允许且原证据对当前版本仍适用时复用，并注明来源。修复触及矩阵外的行为时补行。
3. 问题关闭需要原反例与修复边界的相邻反例均通过。比如补上跨账户加锁后，同组还要复验会使用另一种对象身份的入口。若修复改变了共享写入点，先重查写入者和下游消费者，再给出整组结论。复用可重复的交错与故障注入场景，并核对恢复后的实际结果。
4. 沿用首轮场景和问题编号，标注已关闭、仍阻断、新发现或待验。新发现说明它属于新增差异、首轮覆盖缺口，还是首轮无法取证。只记录证据支持的原因。

## 同类问题反复出现时

- **触发升级。** 按被违反的业务约束归类，重计、漏计和字段串写可能是同一事件身份规则的不同表现。先核对项目规定的复发阈值。达到阈值必须升级为整组验收。项目未规定阈值时，同一约束经整改后再次失败即升级，覆盖原入口和出现同类问题的其他入口、旧数据或时序。
- **先冻结同组矩阵。** 围绕同一业务约束，顺着输入、共享事实、写入和最终用途追踪，再从最终结果反查同组的生产者、写入者及直接消费者。纳入绕过改动函数却读写或消费同一事实的旧入口、回退和自动任务。每行记录入口、初始状态、操作顺序、可观察的断言和证据。按影响组合单条与批量、修订、重放和必要的并发。需修复或补证后才可执行的行标待验，并注明解阻条件。同组已通过的相关行随共享逻辑变化复跑，测试规模按项目规则选择。
- **覆盖会相互顶替的对象。** 同一批次内有多个对象可能因代码、别名、缓存键或回退而串用结果时，至少覆盖全部到齐、每一方分别缺失、全部缺失、顺逆序和缺失恢复后重跑。逐个断言结果归属，并回读哪些记录新写、保留或仍待处理。先验证可独立执行的组合，再集中报告。
- **核实夹具初始状态。** 对复用旧事实的路径，执行前在隔离环境查询并记录会影响结果的记录、状态和业务日期。分别构造首次写入、已有正确记录和已有错误记录，按既有合同核对复用、拒绝或允许更正的行为。复用旧夹具时核对前轮数据和缓存。记录初始状态无法证明的场景为待验，使用已验证初始状态的样本取证。
- **下一版整改逐项交付证据。** 整组矩阵逐行关联项目内可重复执行的测试入口、场景、断言和受验版本上的结果。优先复用项目已有测试和夹具，能参数化时复用断言。至少从受影响的正常入口运行代表性场景，实际验证持久化和下游回读或页面结果。多个入口写同一事实时，分别核对首次写入、重试、必要的并发及入口间一致性。临时探针可证明当轮功能，交接时记录仍缺少的正式回归及复验条件。验收默认只读。
- **按整组结果关单。** 关闭前核对受验版本、可重复回归与矩阵各必验行的结果。沿用原问题 ID 和同一矩阵，分别记录本地功能结果、回归交接缺口和现场待验事项。必需的整组回归或关键证据缺失时保持待验，已实证通过的功能行保留通过结论。

例如，同一业务事件补齐日期或修订金额后只应计一次，独立事件应各自保留，已确认字段应归原事件。即使合计正确，也要检查逐笔字段归属。跳过写入的候选不能被当成已写入，影响同批后续记录。

## 超过 3 轮时沉淀经验到本 Skill

任一任务或同一问题的核查超过 **3 轮**（即进入第 4 轮及以上）时，关单前必须复盘原因，把导致多轮往返的**漏查规律与可复用必查动作**直接提炼写入本 `SKILL.md`（补充到对应的风险表、维度或检查条目），避免下次再经历多轮核查：

- **写清首轮漏查原因**：漏了哪类入口、消费者、回退路径、时序或数据组合，为何首轮矩阵没有覆盖到。
- **固化首轮必查动作**：提炼成可直接执行的核查条件或反例类型，不写空泛口号，且与现有条目合并去重。
- **随仓库同步生效**：更新本 `SKILL.md` 后按仓库门禁检查并提交，确保所有协作 Agent 共享最新核查基线。

## 判定与报告

- **阻断**：核心结果错误，或出现误放行、数据错写、权限越界、不可恢复的失败。
- **非阻断**：可延后处理且不影响本次验收标准的问题。
- **待验**：证据不足或受环境、权限、前置问题限制。必验项待验时，总体结论保持待验；存在已确认阻断时为不通过。

### 验收矩阵

| 场景 ID | 场景及入口 | 预期 | 验证方式与证据 | 结果 |
|---|---|---|---|---|
| A-01 | 验收条件 | 可观察的结果 | 测试命令、证据类型与定位 | 通过 / 失败 / 待验及原因 |

场景用稳定 ID（如 `A-01`）；问题单独编号（如 `F-01`），并关联受影响的场景 ID。同一问题跨轮次沿用原编号。

### 报告模板

- **结论** · 通过 / 不通过 / 待验。附验收阶段和受验版本，功能验收或复验注明轮次，交接核对注明沿用的证据与结论。
- **阻断与非阻断** · 问题 ID、关联场景 ID、实际与预期、定位、同类覆盖范围和复验条件。复验时注明关闭、仍存在或新发现。
- **已通过与证据边界** · 测试入口、关键结果及证据类型。区分代码检查、自动测试、浏览器、真机和生产实测。
- **待验** · 场景 ID、原因、复验所需条件。
- **完整矩阵** · 附在报告内，或链接到已同步的任务记录。
