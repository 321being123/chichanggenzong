## 3. 服务器整改项

以下各项的“证据”和“方案”保留首次审计时的基线快照；是否已执行，以第 8 节的生产验收记录为准。

优先级 P1 表示应优先处理，P2 表示随后安排。优先级是本项目的整改顺序，不等于漏洞数据库的 CVSS 等级。

### S1｜P1：备份尚未形成自动、异地、可恢复的闭环

**证据：** `/opt/portfolio/backups` 没有备份文件；检查常用 cron 位置及 systemd 单元，未找到业务备份或异地上传任务。`/var/backups` 有 14 个项目 `.dump` 文件，其中 12 个可被应用账号直接读取；最新发现的项目备份时间为 2026-09-02 13:36 左右。数据库约 1,670 MB，`archive_mode=off`。仓库已有 `scripts/backup_db.sh`，支持加密、校验与保留组数，但不能以脚本存在代替生产已启用。

**影响：** 本机损坏或被控制时，数据库和同机备份可能同时丢失；备份可被应用账号读取，也会扩大单个应用漏洞的泄露范围。云快照是否另有配置尚未核实。

**方案：** 复用现有备份脚本，先建立每日加密备份、独立备份账号、异地对象存储及失败告警；目录使用 0700、文件使用 0600，备份口令从受保护的环境配置读取，解密密钥保留独立恢复副本。先以“最多丢失 24 小时数据、4 小时内恢复”为建议目标，实际恢复耗时必须演练确认；若需要恢复到任意分钟，再增加 WAL 归档，不直接上复杂集群。

**验收：** 连续 7 天自动成功；异地备份有时间、大小、校验值和保留记录；应用账号无法读写备份；在隔离数据库完成解密、恢复，并对账户/交易/净值、核心行情和任务游标做数量及抽样对账。日常备份和迁移前备份都必须受控。

### S2｜P1：应用能改写发布目录，存在扩大入侵影响的条件

**证据：** 以 `portfolio-app` 身份只读检查写权限，`/opt/portfolio`、`server`、`deploy`、`.git` 和 `.git/hooks` 均可写。虽然部分文件归 root 所有，但可写父目录仍允许替换目录项。应用没有 sudo 权限；部署脚本却会以 root 在该目录执行 Git 操作和 `npm ci`。

**影响：** 一旦攻击者先取得应用进程权限，就可能持久化篡改代码，并利用后续高权限发布扩大影响。这里确认的是权限链条危险，**未实际执行提权或篡改**。

**方案：** 发布代码和 `.git` 改由独立部署账号持有，应用仅能读取；运行数据、报告、上传、模型产物迁到明确的可写目录。部署中的安装/构建使用低权限账号，仅固定的配置安装和服务操作保留 sudo。调整 ubuntu 的 `NOPASSWD: ALL` 时须保留独立维护入口，避免锁死运维。停止依靠整仓 `chown -R portfolio-app` 修复权限的做法，先列明真正需要写入的路径。

**验收：** 应用账号对代码、发布配置和 `.git` 的创建、替换、删除权限均被拒绝；正常报告、模型和缓存写入仍成功；完成一次标准发布和回滚演练。

### S3｜P1/P2：数据库与文件解析进程权限还可收窄

**证据：** 数据库账号 `portfolio_user` 不是超级用户，也不能建库/建角色，但拥有 117 张业务表。Web 与 Worker 都会在启动时调用 `initSchema()`，运行账号因此兼任表结构维护。Excel/DOCX 子进程继承完整 `process.env`，与 Web 使用相同系统账号。

**方案：** 优先拆开迁移账号与日常运行账号；迁移作为发布中的一次性步骤，Web 仅校验版本、执行必要读写。随后按现有业务边界给 Worker 与 Web 分配最小权限。文件解析器用最小环境变量和独立受限账号，限制对数据库凭据、SMTP 凭据和代码目录的访问。这里不要求立刻重构全部 SQL，也不把“没有 RLS”直接等同于越权漏洞；多租户 RLS 可在账号隔离测试成熟后再评估。

**验收：** Web 账号无法 DROP/ALTER 业务表；只读分析不需表结构权限；隔离环境中验证迁移失败不会启动不兼容应用；文件解析进程无法读取业务秘密。

### S4｜P2：主机纵深保护与补丁闭环不足

**证据：** Web/Worker 的 `NoNewPrivileges`、`ProtectSystem`、`ProtectHome`、`PrivateTmp` 均未启用，MemoryMax 无上限。主机 IPv4 INPUT 默认 ACCEPT，现有规则主要是恶意 IP 黑名单；IPv6 单独拦截 SSH，未形成统一端口白名单。自动更新服务已启用，但当前 APT 索引仍列出 121 个可更新包，其中包含标记为 security 的更新；这不等于 121 个漏洞。

**方案：** 在验证数据目录和临时文件兼容后逐项启用 systemd 隔离及合理资源上限，为数据库留出余量；主机和云安全组共同限制入站端口，SSH 尽可能限制维护来源，同时覆盖 IPv4/IPv6。根据 Ubuntu 包版本和安全公告处理实际安全更新，记录升级、重启需求和回滚结果。资源上限先测量高峰再定，不能机械套用固定内存数值。

**验收：** 从维护入口和外网分别检查端口；正常任务在资源限制内运行；异常任务不会拖垮 Web/数据库；未处理安全更新有明确原因和期限。

## 4. 网站整改项

### W1｜P1：知识列表遗漏会话吊销检查（本地已复现）

**证据：** `server/routes/knowledge.js` 的 `GET /articles` 直接以 `req.session.user` 判断登录，调用 `getUserKsInfo()` 时只读取角色和权限，不检查用户状态或 `auth_version`；详情接口已经使用 `optionalLogin`。本地模拟“管理员禁用/会话版本过期”，列表处理器仍返回测试草稿元信息，且未查询会话版本。

**影响：** 持有旧会话的人仍可能读取草稿标题、摘要、作者等信息。此次确认范围是列表元信息，不能扩大成已能读取草稿全文或修改文章。

**方案与验收：** 列表及同类按会话改变返回内容的公开接口统一复用 `optionalLogin`，只信任 `req.authUser`。覆盖改密、禁用、删除、降权、无会话和正常会话六类真实路由用例；失效会话只能得到游客可见内容，其他用户草稿元信息不得出现。检查范围同时包含知识分类和市场周期等直接读取 session 的公开入口。

### W2｜P1：静态缓存匹配会覆盖 API 的私有缓存与限流

**证据：** `deploy/nginx-portfolio.conf:69` 起按 URL 后缀匹配 `.js/.css` 等，隐藏上游 `Cache-Control` 并强制七天 public 缓存。公网 `HEAD /api/data/audit-placeholder.js` 返回的是 API 的 401 JSON，却携带 `Cache-Control: public, max-age=604800`。本地模板和生产 Nginx 文件哈希一致。

**影响：** 只要参数路径带静态后缀，就会落入静态 location，绕过动态 location 的连接/请求限制；若该路径返回用户私有数据，上游 private 缓存头也会被覆盖。尚未测试真实账户的 200 响应或证实共享缓存泄露。

**方案与验收：** 为 `/api/` 设置优先于静态正则的专用 location，保留动态限流和上游缓存头；静态规则限定真正静态资源路径。私有接口按敏感程度使用 `private, no-cache` 或 `no-store`，公共金融快照继续保留短缓存。覆盖带各种文件后缀的 API 参数，确认 200/401/403 均不会被强制 public；同时保留既有 HTTP/2 静态资源并发加载验收，避免再次引入 429 事故。

### W3｜P2：PATCH 未进入来源检查，来源匹配也不够严格

**证据：** `server/middleware/security.js:21` 仅检查 POST/PUT/DELETE；实际存在 `PATCH /api/admin/arbitrage/:caseId`。本地模拟恶意 Origin：POST 被拦截，PATCH 被放行。当前来源白名单按主机/可选端口匹配，未完整约束 scheme。

**限制：** SameSite=Lax、浏览器跨域预检和后台权限会阻挡多种跨站攻击；此次证明来源检查遗漏，不等于已完成外站攻击。

**方案与验收：** 对所有非 GET/HEAD/OPTIONS 请求统一保护，精确匹配 scheme、host、port，并按实际移动上传流程处理合法来源。覆盖 PATCH、同站不同来源、缺失 Origin/Referer 和正常操作；现有权限校验继续保留。

### W4｜P1/P2：恢复邮箱、旧密码与登录抗滥用需要补齐

**证据：** `PUT /api/profile` 可凭现有会话直接更改邮箱，未要求旧密码或验证新邮箱；找回密码随后依据这个邮箱发送验证码。密码最低仅 6 位；生产 8 个用户中有 1 个旧截断 SHA256 哈希、2 个旧 PBKDF2 哈希、5 个 scrypt。本人改密接口没有独立限流且未统一新密码上限。密码校验仍使用同步 `scryptSync`。

**影响：** 被盗会话可能通过改邮箱变成持久账号接管；历史弱哈希在备份泄露后更容易被离线破解。同步计算和不一致限流还会放大登录/改密对 Web 的阻塞。

**方案与验收：** 更换恢复邮箱要求近期重新验证身份及新邮箱验证码；敏感变更吊销旧会话并通知原邮箱。三个历史账号通过受控重设完成升级，不能把旧哈希再哈希来假装完成迁移。统一登录、注册、本人改密、后台重置的长度策略和账号/IP 双维限流；高权限账号优先增加第二因素。改为异步密码计算并限制并发，参数在现有机器上测量后确定。验收须证明被盗旧会话不能独自更换恢复渠道，旧哈希数量清零，合法用户操作不被误拦。

### W5｜P1：AI 密钥的存储方式与已有加密能力不一致

**证据：** `server/services/aiModels.js:20` 将带 `apiKey` 的模型列表直接 JSON 写入 `platform_config`；生产汇总确认有 1 项配置带密钥。相邻的 `externalApiConfig.js` 已有 AES-256-GCM 凭据保护能力。接口显示掩码只保护页面展示，并不保护数据库备份。

**方案与验收：** 优先把密钥放入 `.env`，数据库只保存引用；如必须保留后台改密钥能力，则复用现有加密实现，主密钥放受保护的环境配置，保留版本和轮换兼容。处理存量密钥后轮换受影响凭据，检查日志和历史备份；不能仅清空界面显示。验证数据库导出不含明文 API Key，应用仍能正常调用，错误信息与审计记录均不泄露凭据。加密数据和解密密钥的异地恢复要分别保管。

### W6｜P2：依赖存在已知告警，需升级并验证可达性

**实测：** npm 生产依赖审计为 **4 个中危包告警，0 高危、0 严重**；4 个包由 3 份上游公告关联产生，不应写成 4 条独立可利用攻击链。生产实际版本与锁文件一致：

| 依赖 | 当前状态 | 处理 |
|---|---|---|
| qs 6.15.3 | 两份拒绝服务相关公告；Express 4.22.2 与 body-parser 1.20.6 受依赖关系连带标记 | 更新到含 qs ≥6.16.0 的兼容依赖树，重新核对锁文件和接口参数解析。 |
| @xmldom/xmldom 0.8.13 | XML 序列化注入公告 | 更新至 0.8.15 或兼容修复版本，并验证 DOCX 转换。 |
| Requests 2.32.3（IPO venv） | 命中 `<2.32.4` 的 `.netrc` 凭据泄露公告范围 | 更新到受支持的修复版本，补入 Python 审计。检查的三个系统账号主目录均未发现 `.netrc`，没有证据表明当前已触发该泄露。 |

qs 的公告需要特定解析选项或 parse→stringify 路径；xmldom 公告涉及攻击者可控的 EntityReference 序列化。本次业务代码检索未发现这些直接调用，因此优先做兼容升级，不能据此宣称公网必然可利用。升级只修依赖，不改变业务数据口径。

### W7｜P2：内容与外部请求保护尚有收口空间

- CSP 已移除 `script-src`/`style-src` 的整体 `unsafe-inline`，静态内联块改用 SHA-256 哈希；动态 `onclick` 与 `style` 属性暂由 `script-src-attr`/`style-src-attr` 单独放行，后续迁移属性后再关闭。本次没有确认新的可执行 XSS。
- AI 请求已通过 `fetchSafeAi` 逐跳解析全部 DNS 地址并拒绝私网/回环结果，连接固定到已验证公网 IP；只允许同源、最多 3 跳的手动重定向，不向新来源转发授权头。需要模型配置权限或被控制的受信上游才可能触发此类风险。

### 5.2 优先修正的架构问题

1. **统一 Python 运行环境（已实现，待本轮版本部署复核）。** 生产四个覆盖变量统一指向受控 `ipo-report/venv`，并已通过依赖检查；部署后继续核对任务实际解释器和模型加载结果。
2. **模型与生成报告脱离 Git 发布树（已实现两阶段入口）。** `model_runtime.py` 支持 `IPO_MODEL_DIR`，迁移脚本将现役模型以临时文件原子安装到 `/var/lib/portfolio/models/ipo`；先部署支持版本并验收，再删除 Git 中旧模型 JSON，避免回滚覆盖运行产物；不新建第二套行情事实库。
3. **分离发布迁移与启动（已实现入口）。** Web/Worker 设置 `DISABLE_RUNTIME_MIGRATIONS=1` 后只检查最新迁移；`runMigrations.js` 使用 `MIGRATION_DATABASE_URL` 和 `portfolio_owner` 执行版本化迁移，`split_database_roles.sql` 撤销 `portfolio_user` 的 schema CREATE 权限。数据库结构变化仍采用向前兼容步骤并提供匹配的回滚策略，不能以代码回滚代替数据恢复。
4. **按业务逐步拆分大文件。** `db/migrations.js` 6,184 行、`convertibleBondAnalysis.js` 3,203 行、`routes/accounts.js` 1,136 行、`routes/knowledge.js` 1,112 行。先在后续实际改动中分离纯计算、查询、外部适配及 HTTP 处理，保留现有接口和测试；冻结已执行迁移，新增迁移按编号独立组织。文件大本身不是漏洞，也不是一次性重构全仓的理由。
5. **健康检查与超时反映真实依赖。** `/ready` 的 HTTP 状态目前只依赖数据库，Redis 状态也没有完整的断连/重连更新；生产又要求 Redis 必须可用。改为反映实际数据库、会话存储和业务角色状态，保留 `/health` 的轻量存活语义。为 Web 查询设置合理等待/执行超时，后台长任务另设边界；当前数据库全局 `statement_timeout=0`，连接池也未统一设置查询超时。
6. **把门禁从“代码里有关键词”补到“真实行为正确”。** 本次现有安全测试 59 项全通过，但仍可复现 W1/W3；部分安全回归只检查源码字符串。保留现有测试，补真实路由、完整中间件顺序、失效会话、多用户隔离和 Nginx 匹配测试；CI 增加 Python 依赖审计，固定 `trufflehog@main` 为已审核提交，给中危告警设置处理期限。依赖审计还需定期运行，不能只依赖有人提交代码。

目前 8 个用户、单机轻负载的事实不支持为解决上述问题拆微服务、引入 Kubernetes 或更换数据库。先建立高峰监测，只有资源长期紧张、恢复目标提高或团队需要独立发布时，才评估独立数据库/多实例。

### 5.3 对原数据链路的影响

目标链路继续保持：

`外部数据源 → 现有 Guard/增量采集 → ops 原始记录与游标 → core/market/fundamental/event → analytics 快照 → 服务 → API → 页面`

`现有 JOB_DEFINITIONS → 独立 Worker → 同一批服务和数据表`

| 整改批次 | 影响链路 | 不改变的业务口径 | 验收重点 |
|---|---|---|---|
| 认证/缓存修复 | 会话与 users → 中间件 → API → 页面 | 行情、持仓、净值、评分公式 | 吊销及时生效、跨用户拒绝、公开内容仍可读、API 缓存正确。 |
