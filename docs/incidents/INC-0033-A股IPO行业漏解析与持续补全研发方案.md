## 根因及反复原因

1. **直接原因：解析格式遗漏。** `ipo_lib_fetch.py` 主要识别“行业名称（代码）”，本次为“发行人所属行业为‘（C39）行业名称’”，代码在前，现有规则漏识别。
2. **提前结束条件错误。** `_fetch_exchange_ipo_issuance_detail` 拿到行业 PE 就退出候选及主备遍历，即使调用方只缺行业，也会过早停止。
3. **补全路径缺联动。** `fetch_stock_historical_detail` 只在缺主营时调用主营/招股书路径；已有主营、缺行业时，不能因此独立重解析招股书行业。
4. **行业诊断太粗。** 只有 `value/retryable`，不能区分文档未找到、下载失败、未披露与漏解析。多份公告的字段合并后共用一组来源信息，也不利于逐字段追溯。
5. **完整度定义不一致。** 基础完整与增强完整容易混淆；赛道候选及剩余统计只检查 `exposures` 键，实际字段状态要求数组非空，存在空数组漏计风险。

评审补充的缺口（按下文两步交付）：

- **无新值时证据可能不落库。** `fetch_stock_historical_detail` 在只缺行业时不生成主营及 PE 诊断；`enrich_stock_missing_details` 的无值变化分支仅接受主营来源、主营诊断或 PE 诊断，忽略行业证据及已有的 `industry_pe_source`。因此即使本轮读到公告，也可能只记 `no_new_value`。这是代码可达缺陷；由于当次证据未保存，不能据此断言 9 月 24 日实际抓到了哪份文件或把它认定为唯一原因。
- **兜底值阻挡权威值。** 当前候选以空值为主，解析后的 `resolved_industry` 和 SQL 都优先已有行业。本地主档/Tushare 先填入后，既不会因来源质量不足自然进入候选，也无法被公告行业升级。
- **分类体系和 PE 口径混用。** 同一 `industry` 保存公告标准长名和 Tushare 短名，PE 映射直接按名称查 Tushare 行业样本，存在不匹配及同名异义风险；不能把不同体系一律认定为必然匹配失败。本地主档是存储来源，不是分类体系，公告也必须按原文区分分类标准及版本，不能全部标成“证监会”。

历史修复分别解决了未上线/旧报告（INC-0017）、条数上限（0018）、交易所主源（0025）、风险公告及 PE 解析（0028）、空候选误报（0029），但未共同覆盖“本次所需字段齐全才结束”和真实行业格式回放。

## 架构对齐

已有能力：交易所优先、巨潮备源、Tushare 末级补充、统一 Guard、PDF 缓存、`ipo_history`、字段状态、补全 Runner、只读详情。

真正缺口是字段级解析、继续查找条件和证据/状态一致性。扩展现有链路，不新增来源、任务、调度器或事实表；优先用现有 JSONB，不预设结构迁移。

影响链路：公告/缓存原文 → 分字段解析 → `ipo_history` 与质量/来源 → 现有补全阶段 → 详情及历史接口/日报 → 打新日历。页面仍只读库。

## 开发方案

### 交付安排与完成条件

采纳两步交付：P0-A 修复空行业的解析、补全和证据链；P0-B 单独处理已有值升级及分类/PE 语义。每一步独立完成相关测试与 P2 发布验收，第二步未完成不阻塞第一步。P1 的缓存/哈希、状态一致、并发幂等与任务诊断是第一步的配套要求，不能全部拖到第二步。

| 交付项 | 完成条件（DoD，均待实施） |
|---|---|
| P0-A 取证 | 当日缺口逐只留下已核验证据或明确阻塞原因、尝试范围及下次处理时间；未取到全文不能记作未披露 |
| P0-A 解析与补全 | 鸿富诚及已取得原文的样本通过；不因 PE 提前退出，行业可独立重解析；存量回放无未经核验的变更或丢值 |
| P0-A 证据与运行 | 值未变也保存诊断，字段来源不串；原因摘要可见，缓存、并发和升级续跑测试通过 |
| P0-B 升级与隔离 | 权威升级可回溯，分类及 PE 口径明确，下游预测输入差异通过专项回归；长期语义改变实施前补 ADR |

第一步不批量替换已有行业，不改变 `industry` 的兼容语义或重算历史预测，但须保存新证据的分类标签，禁止为新补行业生成口径不明的派生 PE；已核实的公告 PE 保留。第二步才启用展示投影及存量来源升级。第一步能解决已复现问题，不能预先承诺四只均有可补出的值。

### P0-A：解析与补全（第一步）

- **取证与已复现修复并行推进**：只读核验 920196、301718、301716、920162 的已落库来源与缓存；鸿富诚已有证据直接复用。缺缓存再经既有来源/Guard 取必要文件。其他三只首轮单只设 30 分钟人工排查时间盒（工程安排，不是接口额度或永久放弃条件），遇 Guard 等待即记恢复时间并转下一只。鸿富诚修复和通用规范化无需等待全部取证成功；新原文持续补入测试矩阵，发布前冻结本轮语料。按句式漏识别、仅招股书披露、文档未发现、下载受限、已核验文档未披露归类；未取得全文不得记作未披露。受限对象保留待办，不阻塞其他已验证对象交付，此项仍待实施。
- **首个实现项：行业证据必须落库。** 在 `need_industry` 分支形成 `industry_diagnostic`，行业状态复用 `_detail_field_state`；无字段值变化但产生诊断或证据时仍写入现有 JSONB。按字段合并证据，不整体覆盖已有有效来源；区分“没有新值”和“没有新证据”，相同证据幂等，新诊断保留。网络/Guard 异常也须保存已完成字段及未完成原因。

- 在现有解析函数统一换行、空白、引号、全半角括号，覆盖“名称（代码）”“（代码）名称”“代码＋名称”和表格标签。必须绑定发行人上下文，避免抓取同行公司行业。
- 标准行业、分类代码、分类依据按原文存证；业务赛道独立，不把“新材料”等宽泛标签当标准行业，不靠公司名猜行业。
- 发行资料函数接收本次 `required_fields`，只在目标字段齐全时允许成功提前结束。仍缺字段且来源可用时，遍历当前业务范围内去重后的交易所候选及允许备源候选（含分页），每份原文每个解析版本只解析一次；最终逐文档记录解析结果、字段缺口及候选发现是否完整。Guard、超时、无进展或权限阻塞可以中止，但必须返回未完成、保留剩余进度并续跑，不能为了“遍历全部”绕过保护或无限循环。
- 行业缺失可独立重解析缓存招股书，无需主营也缺失。先复用本地事实、公告地址和 PDF，缺缓存才进入现有增量发现及主备链。
- 首期保存文档 URL、证据片段及其在抽取全文中的字符区间 `[start,end)`（Python Unicode 字符索引，基于规范化前全文），不承诺页码，不为页码改造下载层。各字段绑定自己的证据与哈希，不能被另一份文件的元数据覆盖。
- 同字段取值与候选顺序无关：先限制目标发行人、发行事件、分类体系和可用披露时点；明确更正关系优先，其次取同口径最新有效披露，同日优先该字段的专门披露文件（PE 为定价/发行及风险公告，行业为明确分类段落），同等级冲突保留候选并标记冲突，不用遍历先后裁决。镜像同文档按哈希去重；跨文件允许分别补行业和 PE，但必须各自存证且口径匹配。尚未遍历到的官方更正通过既有增量发现后触发重核，不能把首次字段齐全视为永久完成。

### P0-B：权威升级与分类隔离（第二步，独立验收）

- **权威值升级**：候选除空值外，还要包含已知兜底值且未完成官方核验、或本地解析版本落后的记录。公告明确且身份/业务时点一致时可替换兜底展示值，保存旧值、旧来源和替换理由供回退；低优先级及空值不得反向覆盖。读取优先复用本地主档，但权威性依据其原始来源，不让同一 Tushare 值因入主档而自动升级。来源未知的旧值先核验证据，不批量自动覆盖。
- **分类与 PE 隔离**：现有 JSONB 分别记录 `classification_system`、`classification_version`、`classification_code`、名称、`source`、基准日；未知代码/版本留空，不编造。公告行业与 Tushare 行业各保留自身事实，`industry` 仅作为兼容展示投影。派生 PE 只能使用与样本同体系的分类值，不能拿公告长名硬匹配或模糊映射 Tushare 短名。公告静态 PE 与 Tushare 样本中位数分别标记来源、算法、分类和日期，不能冒充同口径；缺少匹配分类时明确不可计算。行业升级时同时复核 PE 来源与适用性，保留旧 PE 证据但不得继续以不匹配口径参与计算；涉及现有预测输入的调整需专项回归，不能隐式重写历史预测。

### P1：持续补全与状态

- 复用字段状态，区分未找到、下载失败、漏解析、未披露、权限阻塞，保留尝试时间、下次重试和待办字段。
- 缓存分层：进程内缓存仅去重单次运行，键至少包含代码、解析版本、规范化 required_fields 和已发现文档指纹集合；跨进程复用依靠落库证据/版本、`enrichment.attempted_on`、重试状态与持久化 PDF 缓存。`attempted_on` 只能限重复尝试，不能证明资料完整或从未出现新公告。已知同版本原文有效时重解析不联网；新公告发现按既有未覆盖窗口执行，跨日不作绝对零联网承诺。缓存过期/损坏按现有规则补取；解析版本升级可绕过同日尝试短路，但不重拉仍有效 PDF。
- 哈希口径固定：现有 `ipo_announcement_content_hash` 是抽取全文 UTF-8 的 SHA-256，保留原语义，不改名义后塞 PDF 哈希。文本身份使用“文本哈希＋文本抽取版本”，解析结果身份再加业务解析版本；不能把文本哈希改变直接解释为 PDF 更新。原始字节哈希仅在现有缓存/采集层实际可取得时另记 `document_sha256`，不得猜造；下载缓存的 URL 哈希只是定位键，不是内容哈希。
- 统一候选、剩余统计、字段状态的缺失定义，包含空白和空赛道数组。基础完整与增强完整明确分开，增强失败不回滚合格基础分区。
- 空值不覆盖有效旧值，权威值替换兜底值在第二步按 P0-B 的来源升级规则执行，未决冲突保留证据；取得行业后复用现有赛道规则，不保证必有赛道，不为消除待补状态伪造分类。
- 接口对缺行业展示“待补全”并复用原因说明，不改布局。当前详情读最新事实，历史日报保留历史属性。

- 原有每日增强任务输出原因分布摘要，按“证券＋字段”的当前缺口去重，展示各原因数量、本轮尝试/补齐/剩余、最早未解决时间及可定位代码；不能以文档尝试次数充当缺口数。摘要由最终落库状态生成，并带查询成功标志；查询失败不能报零。沿用任务详情及现有告警，不新增任务、看板或通知渠道。
- 并发：当前 `runIpoHistorySync` 先执行 `tryClaimJob(JOB)`，未取得锁返回 `locked`；手工入队还有事务锁及活动槽位去重。继续统一经 Runner 进入，禁止直接 Python 写库绕开领取；实施时验证锁租约、续期、释放及异常恢复，不能仅因入口相同就认定绝对串行。新增定时/手动同时触发测试；字段证据按证券、字段、文档指纹和解析版本幂等合并，重试不重复覆盖或新增相同历史。
- 升级负载：先统计受影响旧版本证券数、原文数量/字节数、缓存命中数并小样本计时，再决定原任务内批次。缺口及当前发行优先，完整记录先离线回放，不因版本升级全市场联网；超过任务时间或无进展保护时保存游标、剩余数和下次时间再续跑。304 条记录不等于 304 份 PDF，不能预设单次可跑完；暂停不是完成。

### P2：存量与发布

- 根据 P0 取证结果生成存量变更预览，并按实施时全量 CN IPO 重统计；扫描已有行业的异常标签及兜底来源，列出权威升级前后值、PE 口径变化与未决项。不得把首次 304/4 快照当固定清单或扩大为无证据批量改值。
- 生产补全另取数据写入授权，经现有 Runner 定向执行；优先缓存重解析，不硬编码鸿富诚行业。只刷新相关当前派生结果，历史预测重算另定范围。
- 标准发布后核对提交、服务版本、接口字段、任务与质量状态、同类清单；健康检查或单次任务成功不能单独证明修复。

## 防复发验收

1. 鸿富诚真实公告同时解析 C39 行业、73.89 及基准日，保留证据，禁止代码特判。
2. 覆盖只缺行业/只缺 PE/两者皆缺、第一份仅有 PE 第二份有行业、主源部分成功备源补全；不得因 PE 成功提前停止。
3. 覆盖下载失败、漏解析、未披露、权限阻塞、空候选、同日尝试、版本升级、空赛道数组；真实增强缺口存在时不得完整成功。
4. 缓存可用外部请求为零；重复执行不重复写值，空结果保留旧值，字段证据不串文件，页面刷新不联网取源。
5. 以实施当日全量 CN IPO 重统计为准（首次取证快照 304 条、4 个行业缺口），逐一形成“有证据补齐”或“明确原因及后续处理”，有效旧值不得倒退。包括北交所样本在内，允许行业补齐而同体系样本不足导致派生 PE 不可计算：行业缺口可关闭，PE 保留具体原因和复查安排；是否允许阶段完成按已声明的字段契约判断，不能直接标全部资料完整。已核实的官方 PE 不因 Tushare 无匹配被清空。

取证逐文档记录分类标准、版本和代码，不能按北交所/创业板或 C39 代码预设体系，也不能未经核验就认定 Tushare 样本属于同一证监会口径。分类未知即标未知，禁止猜测转换。
