## 阅读与写入边界

- 日常发布按第 1—5 节执行。专题检查只在本批触发时读取对应专项。待发布范围以任务卡、固定交接提交和实际运行基线为依据。

- 发布前计划写到本批任务卡，发布结果写入[生产部署历史记录](知识索引.md#历史记录)中覆盖本批日期的文件。当前流程和执行条件有变化时更新原步骤。专项验收写回原方案或事故，逐项保留尚缺的证据。

- 每次发布后的文档状态对齐按[公共规则第11节](知识库公共规则.md#11-持续更新与周期复核)执行：先回执与原正文，再任务/索引，开发、部署与专项验证分别记载。
- 已授权操作沿原范围执行，新增生产写入按AGENTS单独确认；纯文档整理不触发部署。

- 用户另开对话要求“部署所有最近改动”时，先执行[公共规则第6.4节](知识库公共规则.md#64-新发布对话的固定动作)，从任务卡、可见worktree/分支及实际部署/回滚基线确定范围并整合验证，再进入本文第1—5节；不得直接提交主目录全部差异。开发中的任务继续独立工作，发布仅处理已固定的交接提交；记录原任务提交与最终运行SHA的对应关系，未纳入、无归属或待验内容必须说明，不冒充全部部署。

## 前端移动端变更的验收要求

前端版本除原业务检查外，还应按《技术架构》第 5.3 节检查手机布局、触控、键盘及桌面回归；共享静态资源更新后，各 HTML 入口的资源版本必须一致。内联脚本/样式的 CSP 哈希在 Web 启动时收集，包含独立 HTML 样式变化的版本必须由标准部署重启 Web 加载，不能只覆盖静态文件。用户限制浏览器或服务启动时，应明确区分自动检查、运行检查和真机验证的结果，不得将未做的验收标为通过。本条是后续发布标准，不表示移动端目标版本已经生产发布。

## 1. 先更新版本记录

必须先执行版本记录更新，未完成不得部署。

```powershell
.\venv\Scripts\python.exe add_changelog.py --version <新版本号> --date <YYYY-MM-DD> --item "<更新说明>" --bump-package
```

该命令同步维护 `public/changelog.json`、`CHANGELOG.md`、`package.json` 和 `package-lock.json`。
部署前以 `package.json` 的 `appVersion` 作为唯一版本号，并核对 `package-lock.json` 根包版本与两份变更记录同步；本文不固定写入某个当前版本。
提交和部署前必须以待推送 `master` 的版本记录为准，确保本地 `package.json.appVersion`、`package-lock.json` 根包版本、`CHANGELOG.md` 首个版本和 `public/changelog.json` 首条版本完全一致；部署脚本不接受未提交的代码或版本记录。
任务、接口、数据集或预算定义发生变化时，版本记录校验后还必须确认自动生成的任务矩阵与 `JOB_DEFINITIONS` 一致，并通过 `npm.cmd run check:knowledge`。
涉及公告解析或公告任务时点的发布，部署后还须核对 Worker 已加载新任务定义、来源游标按上海自然日推进、目标案件及同类案件的公告链和解析状态已更新；补发/更正公告只在用户明确授权后定向重解析或补同步。
涉及后台任务外部调用边界的发布，还须同时核对任务契约与任务定义中的 `externalApis`、`maxExternalCallsPerRun`、`mayConsumeQuota` 和实现行为一致；部署后确认 Worker 已加载这份新定义。

统一调度器相关发布还须核对：同一计划槽位处于 `manual_retry`/`auto_retry` 的执行或待执行状态时，不能覆盖其请求参数；管理员强制补跑必须能将 `force=true` 传递到实际 Worker。
涉及外部接口保护的发布，须核对Node/Python使用同一接口策略、凭据作用域与恢复记录；仅采用已核验的官方限制，不自行设置来源级或Token级内部额度。当前规范见AGENTS 1.2和技术架构8.2.2。
前端页面修改还需同步递增对应静态资源查询参数，并在部署后确认详情页加载的 CSS/JavaScript 版本与提交一致，避免浏览器继续使用旧缓存。主站 vendor 的 Chart.js、Vditor、marked、DOMPurify 也必须带版本参数；生产 Nginx 对带版本参数的 JS/CSS 返回 `public, max-age=604800, immutable`，图片/字体等其他静态资源返回 7 天公共缓存。
共享证券代码分类规则变更时，还必须联动核对行情供应商代码、标准主档后缀、收盘任务筛选和历史回补路由，并补齐对应代码段回归测试。

前端 API、Presenter 与 View 沿用静态资源发布。验证 HTML 加载顺序、懒加载契约及新增脚本的 `__APP_VERSION__` 引用。

### 版本文案格式（强制）

- 每条版本说明必须以 `新增：`、`优化：` 或 `修复：` 开头，不能使用无分类前缀的文案。
- 同一版本内的条目固定按 `新增 → 优化 → 修复` 排序；`add_changelog.py` 会校验前缀并自动排序。
- 历史版本记录也必须遵守同一格式；发现旧记录缺少前缀时，先统一修订后再发布。

接入后的操作入口（2026-10-23 验收整改后）：
- `server/scripts/reconcileFeedbackRelease.js --mode read|detail|prepare|conclusions|freeze|verify|apply|rollback|status`；read 走只读事务与编号游标分页，清单经标准输入传递，不接受用户提供的 SQL。
- `prepare/verify/apply/rollback` 必须带 `--operator <内容管理员账号>`：服务端查库校验该账号真实存在、状态正常且有 `content_manage`（或管理员）权限，伪造/无权限账号一律拒绝。`--owner` 同理。
- `apply` 的 `--deployment-id` **必填**（缺失直接失败）；实际运行提交与版本由服务端在发布锁内自行读取，`--current-sha`/`--current-version` 只做交叉核对，与实际不符即拒绝，无法伪造；旧清单不能套到新代码上。
- `rollback` 只恢复「本批次关闭、且之后没有被任何人再修改」的反馈；被后续版本或人工处理改过的记录保留现状并单独列出，不批量覆盖。
- `--mode hold-lock --hold-seconds <秒> --ready-file <路径> --token <令牌>`：给部署脚本用的目标级发布锁，与回写共用同一把 advisory lock。持有时间单位是**秒**（上限 21600），不再接受 `--hold-ms`（历史单位事故：5400 被当毫秒只持有 5.4 秒）；`deploy_password.py` 传 `--hold-seconds 5400`（90 分钟，覆盖部署 3600 秒 + 反馈回写 600 秒）。ready 文件为 JSON（token/pid/acquiredAt/expiresAt），拿不到锁即中止部署（首次发布因服务器尚无该脚本会降级提示“本次代码部署未参与串行边界”）。**凭证文件按部署批次隔离（D-01）**：路径为 `/tmp/portfolio-release-lock.<令牌>.ready`，启动清理、等待确认、反馈第二段与释放四处均用本批次路径——等待中的第二发布者只清理自己的文件，删不到持有者的凭证；CLI 收尾只删令牌仍属于自己的文件。迁移账号权限实录与部署前自查（0.8.4.17）：生产迁移账号无库级 CREATE，`CREATE SCHEMA IF NOT EXISTS` 在模式已存在时仍会报权限错误并触发回滚；**每次部署前自查新增迁移**——禁止无条件 `CREATE SCHEMA`，一律先查 `information_schema.schemata`、缺模式才建（样板 `era07Feedback.ensureSchema`；静态守卫测试自动扫描；见技术架构第 7 节与部署说明零节第 2 条），本次部署实录：0.8.4.16 首次发布即因此回滚，0.8.4.17 修复后重发。本次部署实录：0.8.4.17 已生产发布成功（迁移 170/171 执行、反馈接口上线、sharp 实测可用），部署验收登记「反馈核对：未接入，未自动更新状态」；发布锁本次因服务器旧版无脚本按设计降级，下次部署起强制持锁。0.8.4.18 端到端实录：发版锁全程持锁并在反馈第二段之后释放；回写因服务器 git dubious ownership 读不到运行版本被 fail-closed 拒绝（符合设计），补 `safe.directory` 后重试成功，反馈 #1 标记已实施（0.8.4.18）；0.8.4.19 起读取运行版本自带该声明，不再依赖服务器 git 配置；0.8.4.19 批次 2 的第二段回写一次成功（feedback_applied=true）。
- `--mode release-lock --ready-file <路径> --token <令牌>`：部署收尾统一释放（幂等）。锁的释放顺序（2026-10-23 三次复验 C-03）：失败路径由回滚 trap 在恢复完成后释放；成功路径由 `setsid` 持锁进程跨 SSH 会话存活，Python 在反馈第二段之后 `finally` 释放——回滚期间与回写期间都持锁。
- 第二段回写携带 `--held-lock-token <令牌> --held-lock-ready-file <路径>` 走「部署已持锁」通道，不再重复抢同一把 advisory lock；凭证不符、ready 文件缺失或持锁进程已死一律拒绝（失锁失败关闭）。
- `deploy/deploy_password.py ... --confirm-production [--feedback-run-id <编号> | --feedback-none-evidence <证据文件>] --deployment-id <UUID> --deploy-operator <内容管理员账号>`；代码部署成功（`deploy_complete=1`）后独立执行回写并把 `deployment_id`/当前提交/版本一并传入，最终输出 `DEPLOY_RESULT={code_deployed, feedback_applied, feedback_status, feedback_reason, feedback_pending}`。
- **核对依据现在是必填（2026-10-30 复查后实现）**：`--feedback-run-id` 与 `--feedback-none-evidence` 二选一，两个都不给时脚本在本地前置校验阶段就退出，**连服务器都不连**，不再出现「先完成生产变更、事后记 not_crosschecked」。给批次编号时，连上 SSH 后、任何生产变更之前先只读执行 `--mode status` 核查：批次已冻结（`prepareStatus=frozen`）、专项验收通过（`verifyStatus=passed`）、明细读取完整且非空、批次目标提交与本次发布一致、且该批次没有被应用过；任一项不符即中止，不动服务器。
- `--feedback-none-evidence` 用于「查过了、确实没有相关反馈」的批次，指向一个 JSON 证据文件，字段要求：`complete`（必须 `true`，分页没读完不算）、`candidates`（必须是数组；为空表示没有候选，非空时每条要有 `conclusion: "unrelated"` 且写明 `reason`）、`queriedAt`（查询时间，超过 48 小时作废）、`releaseSha`（与本次发布提交一致）、`operator`（实际核对人）。示例：`{"complete": true, "queriedAt": "2026-10-30T06:00:00Z", "releaseSha": "<本次提交>", "operator": "<账号>", "candidates": []}`。证据不合格同样在本地被拒。
- `feedback_status` 为机器可判定处置结论：`not_crosschecked`（历史记录专用，新版本不会再产出：缺依据已被前置拦下）、`crosschecked_no_related_feedback`（已完整查询并确认本批无相关反馈，闭环成立、`feedback_applied=true`，与「没核对」严格区分）、`skipped_missing_operator`、`skipped_missing_deployment_id`、`read_failed`（调用失败或超时）、`apply_failed`（退出码非 0 或被拒绝）、`apply_status_rejected`（服务端整体应用状态不是 applied）、`no_items`（没有返回任何明细）、`readback_mismatch`（真实回读与预期不符，原因含具体条目）、`applied_with_pending`（已应用但仍有待续办编号）、`applied_verified`（确有实施且真实回读逐条对上）、`applied_verified_no_implementation`（本批全为不相关项，闭环成立但没有实施任何反馈）。**只有 `applied_verified` 能作为「本批反馈已核验实施」的依据**；`applied_verified_no_implementation` 与 `crosschecked_no_related_feedback` 只表示核对完毕、无待实施项。缺少 `--deploy-operator` 或 `--deployment-id` 时反馈闭环直接记为未执行（代码部署不受影响）；新增字段不改变退出码，也不改变“反馈失败不回滚已成功代码”的语义。`DEPLOY_RESULT` 另带 `feedback_evidence`（本次使用的证据文件路径，便于审计）。

   - **用户可见的「处理记录」只写大白话**：回写时传给反馈事件的 `evidenceSummary`（页面上紧跟在「随版本 X 发布，专项验收通过」后面的那句话）限定一两句，只讲用户能感知到的结果，参考版本记录的写法（如「已到期退市的可转债不再出现在上市列表里，被剔除的债券后台留有记录可查」）。禁止写函数名、文件名、字段名、根因链路、接口路径和回归数字；这些技术证据只能写进本节发布记录、事故文档或任务卡。2026-11-01 已按此口径把线上历史 16 条发布回写说明统一改写（原文备份在本地 `_local_backup/feedback_note_backup_20261101.csv`，不入库）。
3. **汇总最终发布范围**：发布负责人按反馈编号去重，以最终待发布提交核实各项改动及验证结果，合并冲突后形成同一份清单。清单关联目标 `appVersion`，提交推送后补充最终发布 SHA；代码合并、范围或反馈内容发生变化时重新核对受影响项。未纳入最终发布树、只在其他分支或开发者本机完成的反馈不能列为本次已解决。
4. **上线后逐项验证**：完成本文第 5 节通用验收，再验证清单中每条反馈的原问题或验收条件。只有完整解决、相关验证通过且线上提交及版本一致的反馈，才能标记“已实施”；部分解决保持“进行中”并补充进度，未涉及及证据不足项保持原状态。“重复”“不采纳”等决定继续由有权限的管理员处理。
5. **统一回写及防冲突**：由发布负责人通过统一、鉴权的反馈服务入口提交确认清单，服务器按清单更新状态和实施版本，保留操作者、时间、前后状态、发布 SHA 和验证依据。回写前重读当前反馈，并按核对时的内容版本/更新时间及原状态做数据库条件更新，状态与处理历史在同一事务中保存；条件不符时拒绝覆盖并重新核对。按目标环境、部署批次 `deployment_id` 与反馈编号去重，中断重试沿用批次，回滚后重发相同 SHA 使用新批次重新验收；不能仅按 SHA 唯一限制再次发布。每条核对结果持久化，完整读取轻量编号/revision清单，只增量获取变化项正文。
6. **回读与异常接续**：逐条回读确认状态、关联版本和处理历史，记录已更新、待核查、冲突和失败项；零条匹配须与读取失败明确区分。部署失败或验收未通过时不写“已实施”；明确失败的回写不改变原状态，列入同一发布记录待续办，超时等结果未知时先回读再决定是否重试。代码发布成功但反馈未回写时，分别记录两者结果，不能宣称反馈闭环完成。
7. **回滚核对**：回滚时复核由该版本关闭的反馈；仅当解决该问题的改动已撤回，且没有后续有效处理时，才按当前记录校验后恢复未完成状态并留痕，不批量覆盖其他版本或管理员的处理结果。

接入时保持代码部署与反馈回写的失败边界：现有脚本的 `deploy_complete`/退出 trap 管理代码回滚，反馈回写在代码部署成功后独立执行并报告结果，回写失败不触发代码回滚或迁移重跑。标准部署和回滚在同一生产目标串行执行，锁覆盖版本核验及反馈应用，防止多人发布切换版本后旧清单仍被应用。清单绑定环境与部署批次、确认后冻结；变更项旧验收失效，已成功项不能覆盖。

实施落点：部署脚本新增反馈记录/批次参数解析，代码成功后以第二次受控调用执行反馈回写；反馈失败被单独捕获，代码部署退出语义保持成功，同时明确报告反馈未完成。开发Agent经现有SSH在服务器以应用账号调用固定只读入口，连接配置沿用应用.env，不借迁移账号。附件使用现有DATA_DIR写路径，前后端压缩后仅保存WebP；请求≤7MiB适配现有Nginx10m。备份、异地同步及恢复演练三个脚本已按整组契约扩展（同一时间戳的数据库密文 + 附件密文 + `.manifest.sha256` 清单；缺清单或清单声明的附件密文即视为组不完整并拒绝同步/恢复；恢复演练解密到隔离目录后按恢复库 `storage_key/sha256/size_bytes` 逐项核对，含已移除的历史附件）。真实异地配置缺失时继续标记未启用；生产首次迁移、目录权限与整组恢复演练仍需在取得授权后执行，具体上限、字段和27项验收见研发方案。

每次发布在既有记录中使用以下最小清单；未接入、无反馈、查询失败或无本次相关反馈均应明确填写原因，不伪造反馈编号：

| 反馈编号及核对版本/时间 | 处理人及实现提交 | 处理结论与验证依据 | 目标应用版本及最终发布 SHA | 原状态 → 目标状态 | 线上验收及回写结果 |
|---|---|---|---|---|---|
| 按本次实际情况填写 | 同一反馈合并记录 | 完整解决/部分解决/未涉及/待核查 | 推送后核对最终 SHA | 验收前不标已实施 | 成功/待核查/冲突/失败/未接入 |

自动化接入时必须验证：相关与无关反馈、部分解决、未上线、查询失败、反馈被并发修改、重复执行、回写超时后的回读及版本回滚。生产执行仍遵守原有部署与数据写入授权范围。新增自动化须复用现有发版和反馈服务入口，并同步本文、技术架构及知识路由中的实际实施状态。

### 测试分级与全量结果复用

本节是测试执行时机、范围与结果复用的权威规则。自 2026-11-24 起，功能开发、修复及开发交接只做与改动相关的专项和关联回归，全量测试统一由发布负责人在部署前对最终整合树执行。开发期间只有用户明确指示才可提前运行全量。各开发者、Agent、专项文档、路由 checks 及交接/发布 Skill 均按本节执行。原专项的业务断言、必需环境和发布验收条件继续有效。

| 阶段/变更 | 必须验证的范围 |
|---|---|
| 纯文档、规则说明、知识路由或 Skill 文本 | `npm.cmd run check:knowledge`，复核引用、状态、格式与 Git 差异；不启动服务或执行全量业务测试。修改检查器、测试运行器或 CI 行为属于代码/配置变更，不能按纯文档处理 |
| 日常局部开发、修复及开发交接 | 相关语法/静态检查、原问题及失败反例、受影响模块和直接调用方回归，加知识门禁。按数据源→数据库→服务→接口→页面/任务的实际影响链选测，交接记录文件、依据及未覆盖项；每项开发交接仅要求完成本阶段相关验证 |
| 共享基础能力、鉴权/会话、迁移、调度、依赖、部署配置或跨模块重构 | 扩大到消费者、权限/失败/兼容及相关集成回归，执行原架构/日期/SQL/任务矩阵等适用门禁；影响边界不清时继续梳理依赖与调用方，扩大相关回归并记录未覆盖范围。关键专项或必要覆盖缺失时保持待验收 |
| 整合并准备发布 | 完成合并、冲突处理、版本记录及专项验证后，对最终应用/测试代码树运行一次 `npm.cmd run test:all`，或核对下列条件全部满足的已有全量证据。各任务的专项通过不等于整合树全量通过 |
| 部署之后 | 核对版本/提交、服务、静态资源及本次接口/页面/任务的实际结果，按第5节完成验收；不在生产运行写库测试 |

**全量证据与复用条件**：

- 原任务卡或发布回执保存执行日期、命令、runId（入口提供时）、完整 SHA；未提交时保存基线及可还原的精确差异/代码树标识，提交后补对应关系。记录 Node/Python/PostgreSQL、测试库/迁移与夹具、相关配置/模型等实际环境依据，结果须含通过/失败/跳过、耗时及日志位置，不保存密钥。
- 全量入口写入的 `data/test-evidence/last-run.json` 使用工作区代码树指纹：覆盖 `HEAD` 文件集合与当前工作区（含未跟踪代码文件）的实际内容；发布脚本用同一算法复核。这样未提交开发树的证据不会误绑到旧 `HEAD`，提交后工作区内容不变时指纹可直接对应最终提交树。
- 复用前逐项比对目标树与已测树。仅提交号不同、分支包含旧提交或聊天说「已测过」均不足以复用；多任务合并、冲突解决只要改变应用代码、测试/辅助工具、依赖及锁文件、模型/夹具、数据库迁移、运行配置或部署文件，原发布全量即失效。相关运行环境、测试库 schema/样本或模型变化也须重新全量。
- 已测应用/测试树和相关环境均未变，只有文档、规范说明或发布元数据变化时，可沿用已有全量；仍对变动内容做知识/引用/格式检查，版本元数据另做版本一致性及对应本地运行验收。变更夹带在 `package.json`/锁文件中的依赖、脚本或配置时不属于元数据例外。
- 证据须无失败且必需项未跳过；环境缺失、超时、中断、未定位失败不能视为通过或用旧绿结果覆盖。按原规则或用户明确批准的例外单列跳过及未验范围，不写成全部通过。证据缺失、差异或环境无法核实时，由发布负责人补跑，不能仅因任务卡写「完成」跳过。
- 开发交接允许写「专项通过，发布全量待整合后执行」，它是阶段安排，不是虚报全量通过；选测理由、必需专项、文档和固定提交齐全即可交接。运行器尚未自动选择测试或缓存证据，以上比对由负责人执行。GitHub Actions 的 Linux/PostgreSQL 全量保留，当前不作为省略本地最终全量的替代。

涉及网站性能优化时，必须额外验收：

- `curl -sI --http2 https://<域名>/` 确认 HTTP/2；对 JSON、JS、CSS 请求确认 `Content-Encoding: gzip`、单一 `Cache-Control`，公共接口第二次带 `If-None-Match` 返回 304。静态 location 必须保留 `proxy_hide_header Cache-Control`，避免 Node `express.static` 的默认 `max-age=0` 与 Nginx 缓存头重复。
- 并发请求超过 30 个首页静态资源时不得出现 429；`limit_conn` 只能位于动态 `location /` 内，不能配置在 `server` 级影响 HTTP/2 静态资源并发流。
- Nginx 日志包含 `request_time`、`upstream_connect_time`、`upstream_response_time`；必要时用 `curl -w` 记录 `time_connect`、`time_appconnect`、`time_starttransfer`、`time_total`。
- 首页冷启动与回访分别记录 LCP/CLS；首页卡片保持固定最小高度。账户接口确认摘要请求不返回交易/净值历史，进入持仓页仍能加载完整数据。
- 修改 Nginx 前备份实际生效的 `/etc/nginx/nginx.conf`、`/etc/nginx/conf.d/portfolio.conf`；模板仓库文件不包含生产 `http` 块时，回滚必须同时恢复服务器备份，不能只回滚 Git 模板。

涉及统一任务调度、任务依赖或数据集发布门禁变更时，还必须确认 Worker 已加载新任务定义，并核对受影响任务的计划时刻、上游任务依赖、目标业务日分区及质量状态。IPO链路变更重点检查：`ipo_history_sync` 的18:00核心、19:30核心和19:35补全阶段均已生成计划实例，`ipo_calendar_refresh` 为18:05/19:45且只在对应时段的 `ipo_history` 基础分区质量通过后执行；19:30核心槽位使用方案声明的 `freshnessGate=false`，避免晚间公告被前一轮水位短路。代码部署本身不等同于人工补数，不得顺带手工触发生产采集。

### 独立远程验收命令（Windows/Codex）

- 通过 Paramiko 执行多行远程脚本时，优先复用 `deploy/deploy_password.py` 的 `run_sudo`（内部使用 `shlex.quote`），或使用 `exec_command('sudo bash -s')`，通过标准输入写入脚本后调用 `shutdown_write`。

- 远程 Shell 解析失败时，先确认实际验收命令是否执行；如果未执行，明确记录“未执行验收命令、未影响服务”，再改用上述安全方式重试。

核心验收有失败时，保留实际失败与回滚结果，发布验收不得标记通过。身份未知、业务未验和反馈未闭环分别记录。

| 目标提交/版本 | 本地干净master及origin一致性前检、appVersion/变更记录；服务器Git更新 | 固定最终被测/推送的完整SHA及appVersion；锁内重核远端与目标，不能让远端主线后来前进使验收换目标 |
| Web实际运行 | systemd重启、MainPID、/health版本与buildIdentity自述 | 绑定该次发布SHA、实际unit PID/启动时刻/启动目录；已有采集不能替代关联核验，磁盘HEAD或版本相同不证明内存代码一致 |
| Worker实际运行 | 心跳SHA/PID/版本与unit进程绑定、epoch/UTC时间语义；本地复验证据见原整改清单 | 真实发布必须抄录与目标SHA绑定的身份行；本地场景不代替生产运行/分区质量或真实双Worker验收，见清单第14节 |
| 迁移就绪 | 独立迁移入口、schema_migrations及Web/Worker启动检查 | 与该固定提交的迁移集合逐项比对，保留执行/校验结果；存在某个最大版本或schema已就绪不能反证旧Worker代码已更新 |
| 专项与回执 | 目标接口、数据分区/质量、静态资源及反馈闭环 | 同一部署ID/目标SHA/版本下记录实际范围、结果与未验项，先原回执/专项正文，再架构/索引；代码部署、业务验收、反馈回写分开表达 |

维护身份探针时，先核对进程身份采集的权限、启动时刻与版本覆盖规则（包括`APP_VERSION`环境变量），禁止输出凭据/完整环境。单元active、当前目录Git HEAD、health版本和心跳版本各证明一个方面，任何一项都不能独立给出Web/Worker完整同版同提交证明。

涉及S-005停机整改的发布另核对[安全方案11节](项目与服务器安全架构审计及整改方案_20260905.md#11-web停机与worker恢复s-005待实施)：先在隔离环境通过在途请求/Session写回、Worker取消/接管与退出码测试，再核对服务器有效KillMode/TimeoutStopSec。Web与Worker分别核验，不把Web3秒兜底套用于Worker，不因停机整改手工清租约或改任务成功状态。
