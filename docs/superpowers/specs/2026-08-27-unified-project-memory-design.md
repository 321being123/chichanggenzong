# 存在小站统一项目记忆系统设计

> 状态：待用户审阅
> 设计日期：2026-08-27
> 适用范围：仅 `D:\Users\存在小站\portfolio-server`
> 不适用范围：其他 Codex 项目、全局 Codex 配置、生产部署与业务功能

## 1. 背景

当前项目已经具备 `AGENTS.md`、`docs/技术架构.md`、`CHANGELOG.md`、大量专项方案和部分 Agent 平台记忆，但仍存在以下问题：

1. 架构文档依赖人工记得更新，CI 没有阻止遗漏。
2. 当前事实、历史过程、技术决策和故障经验混在多种文档中，缺少统一入口。
3. 已说明的问题仍可能复发，文字规则没有稳定转化成回归测试和机械门禁。
4. Bug 修复容易停留在当前现象，没有固定的数据、研发、产品、运维影响分析。
5. Codex、WorkBuddy、CodeBuddy 等平台各自保存记忆，已经出现内容分叉和过期。
6. 全量加载全部文档会显著增加 Token，并可能让真正重要的约束被噪音淹没。
7. 限制读取范围又可能误判任务类型，导致遗漏相关知识。

本设计把“记忆”从某个平台的私有能力，改造成存放在 Git 仓库中的项目知识治理系统。

## 2. 设计目标

### 2.1 必须实现

- 让所有 Agent 平台读取同一套项目事实。
- 让 Codex 在本项目中不读取、不生成原生项目记忆，改用仓库记忆库。
- 每次任务都能稳定读取最小入口，并按任务自动扩大到相关知识。
- 架构、数据、接口、任务、配置和部署变化必须触发知识检查。
- Bug 必须形成可核验的根因、同类范围和防复发证据。
- 控制 Token，禁止无目的全量加载，但不得以预算为理由跳过必要证据。
- 所有检查都能在本地和 CI 中机械执行。
- 保留现有文档，不推倒重写，不触碰无关业务逻辑。

### 2.2 明确不做

- 不建设向量数据库、RAG 服务或独立知识平台。
- 不在不同 Agent 的私有 Memory 之间做双向同步。
- 不把所有历史聊天保存进项目。
- 不自动相信文档；当前代码、数据库 Schema、测试和已验证运行态仍是事实证据。
- 不修改 `C:\Users\戴存在\.codex\config.toml` 等全局 Codex 配置。
- 不清理旧文档、旧记忆或工作区残留；后续清理必须单独审计并取得用户确认。

## 3. 核心原则

1. **仓库是唯一项目记忆库**：项目事实进入 Git，平台私有 Memory 不具有项目事实权威。
2. **同一事实一个权威位置**：规则进 `AGENTS.md`，现状进架构文档，原因进决策，故障进事故记录，历史进 Git/CHANGELOG。
3. **入口小、正文按需读**：每次只自动加载规则和索引，相关正文按任务读取。
4. **预算可扩容**：上下文预算是初始范围，不是硬上限；风险、不确定和跨模块信号必须扩大读取。
5. **双向路由**：开始前用任务描述选知识，结束前用实际改动反查遗漏。
6. **证据高于声明**：不能以“已阅读”“已修复”作为完成证据，必须给出文件、测试、数量或运行结果。
7. **防复发优先使用可执行记忆**：稳定规则优先落实为测试、检查脚本或 Hook，而不是继续追加提醒文字。

## 4. 权威知识结构

### 4.1 L0：每次任务自动加载的入口

| 文件 | 职责 | 内容边界 |
|---|---|---|
| `AGENTS.md` | 项目强制规则 | 红线、启动流程、完成标准、知识入口；不复制完整架构 |
| `docs/知识索引.md` | 人和 Agent 的导航 | 任务类型、关键词、改动路径到权威文档的映射 |
| `governance/knowledge-map.json` | 机器路由 | 路径、风险等级、必读知识、必更文档和必跑检查 |

L0 的目标是保证“知道去哪里找”，不是把所有知识预先塞进上下文。Codex 自动加载的项目指令总量应保留在官方默认 32 KiB 上限以内，并为未来嵌套规则预留空间。

### 4.2 L1：当前项目事实

继续使用并就地维护现有文件：

- `docs/技术架构.md`：当前技术栈、目录、请求链路、数据、任务、外部源、配置和部署边界。
- `docs/生产部署流程.md`：当前发布、部署、回滚和生产验收流程。
- 现有产品、数据模型及专项文档：只在确实承担现役职责时保留为权威说明。

`docs/技术架构.md` 保留现有权威地位。实现时只调整索引、状态和重复边界，不推倒重写。

### 4.3 L2：决策与故障知识

新增：

```text
docs/decisions/
  README.md
  ADR-0001-<主题>.md

docs/incidents/
  README.md
  INC-0001-<主题>.md
```

ADR 只记录会长期影响后续开发的重要决定：最终选择、备选方案、取舍、适用范围和替代条件。

Incident 只记录重大问题、重复问题或暴露系统性缺口的问题：现象、根因、影响范围、为何未被发现、修复、防复发测试和遗留风险。普通小错误不强制建立事故文档。

### 4.4 L3：活动任务交接

新增：

```text
docs/tasks/active/<任务编号>.md
docs/tasks/closed/<任务编号>.md
docs/tasks/README.md
```

任务卡仅用于跨会话、跨 Agent 或长任务，记录：

- 目标和边界；
- 当前 Git 基线；
- 已读取知识；
- 已确认事实与证据；
- 已排除原因；
- 当前修改及风险；
- 未解决问题；
- 下一步。

任务完成后不长期堆积过程流水账。仍有效的内容分别沉淀到架构、ADR、Incident、测试或 CHANGELOG；任务卡压缩为目标、结论、证据和知识去向后移入 `docs/tasks/closed/`。

### 4.5 历史层

| 载体 | 只回答什么 |
|---|---|
| Git 提交 | 具体代码在何时如何变化 |
| `CHANGELOG.md` | 用户可感知的版本变化 |
| ADR | 为什么选择当前方案 |
| Incident | 为什么发生故障、以后如何阻止 |
| 历史专项文档 | 当时的范围、证据和实施过程；必须标明状态 |

## 5. 知识路由设计

`governance/knowledge-map.json` 使用简单 JSON，不增加第三方依赖。每条规则包含：

- `paths`：命中的代码或配置路径；
- `keywords`：任务描述关键词；
- `risk`：`low`、`medium`、`high`；
- `read`：开始前必须读取的文档或章节；
- `update`：发生实质变化时必须核对的文档；
- `checks`：必须执行的测试或检查；
- `expand_on`：必须扩大上下文的信号。

首版至少覆盖：

| 改动域 | 必读/必核对知识 |
|---|---|
| `server/db/**` | 数据架构、Schema、迁移、单位、唯一约束、回滚、历史数据 |
| `server/jobs/**`、调度定义 | 后台任务、幂等、补偿、锁、告警、失败保留 |
| `server/routes/**` | API、鉴权、调用方、兼容性、错误格式 |
| `server/services/**` | 数据源、缓存、计算口径、数据库读写、失败策略 |
| `public/**` | 产品流程、权限、同类页面、共享组件、用户可见变化 |
| `deploy/**`、环境变量 | 部署流程、服务、配置、回滚、生产验收 |
| `package*.json` | 技术栈、版本、依赖、CHANGELOG 一致性 |

### 5.1 防止初始误判

任务开始时按描述进行第一次路由；修改结束时按 `git diff --name-only` 进行第二次路由。以下任一情况必须扩大读取范围：

- 根因尚不确定；
- 文档、代码、数据库或运行态冲突；
- 改动跨越两个以上业务层；
- 涉及历史数据、单位、时间口径、缓存、并发、任务调度、权限、安全或部署；
- 发现同类问题或历史事故；
- 实际修改文件超出最初声明范围。

高风险任务不设相关知识硬上限。

## 6. 跨 Agent 平台适配

### 6.1 共享方式

所有平台共享 Git 仓库中的权威文件，不同步各自私有 Memory。平台适配文件只做三件事：

1. 指向 `AGENTS.md` 和 `docs/知识索引.md`；
2. 声明平台私有记忆不具有项目事实权威；
3. 要求执行统一的开始、诊断、收尾和门禁流程。

### 6.2 适配策略

| 平台 | 适配原则 |
|---|---|
| Codex | 原生读取根目录 `AGENTS.md`，项目配置放在 `.codex/` |
| WorkBuddy | 使用其实际支持的项目规则入口指向统一入口；现有 `.workbuddy/memory` 只读迁移，不继续保存项目事实 |
| CodeBuddy | 使用其实际支持的项目规则入口指向统一入口；工作区内通用 Agent/Skill 集合不作为项目事实 |
| 其他平台 | 先验证官方加载机制，再选择原生引用、短指针或生成镜像，禁止猜测文件名 |

如果平台支持原生引用，适配器直接引用统一入口。如果不支持引用，则由脚本生成不超过必要内容的短镜像，并在 CI 中校验镜像来源和内容。Windows 环境不强制使用软链接。

### 6.3 冲突裁决顺序

同一事实发生冲突时按以下顺序裁决：

1. 当前代码、Schema、配置和相关测试；
2. 当前已验证运行态；
3. 仓库权威文档；
4. Git、ADR、Incident 和历史文档；
5. 平台私有 Memory。

无法裁决时标记 `pending`，不得将猜测写回权威文档。

## 7. Codex 项目级替换原生记忆

### 7.1 范围

只新增：

```text
D:\Users\存在小站\portfolio-server\.codex\config.toml
```

不修改：

```text
C:\Users\戴存在\.codex\config.toml
C:\Users\戴存在\.codex\memories\
```

其他 Codex 项目继续使用原有设置。

### 7.2 项目配置目标

项目配置采用以下意图：

```toml
[features]
memories = false

[memories]
use_memories = false
generate_memories = false
```

正式实施前必须使用当前 Codex 版本验证这些键能从受信任项目的 `.codex/config.toml` 生效；验证失败时不得改全局配置绕过，而应停止并报告项目级限制。

### 7.3 生效条件

- Codex 必须以 `D:\Users\存在小站\portfolio-server` 或其子目录作为当前项目打开。
- 该目录必须被 Codex 识别为受信任项目。
- 从上级 `D:\Users\存在小站` 启动时，不得假设子项目配置已经加载。
- 新开 Codex 任务时必须验证项目根、实际加载的规则链和 Memory 状态。

### 7.4 官方机制依据

- Codex 在开始工作前读取 `AGENTS.md`，并从项目根到当前目录合并规则：<https://learn.chatgpt.com/docs/agent-configuration/agents-md>
- Codex 官方建议把必须遵守的团队指导放入 `AGENTS.md` 或仓库文档，Memory 只作为辅助召回层：<https://learn.chatgpt.com/docs/customization/memories>
- 项目 `.codex/config.toml` 和项目 Hook 仅在受信任项目中加载：<https://learn.chatgpt.com/docs/config-file/config-advanced#hooks>

## 8. 统一任务工作流

### 8.1 开始阶段

1. 确认项目根、分支、提交和未提交修改。
2. 自动加载 `AGENTS.md`。
3. 读取 `docs/知识索引.md`。
4. 根据任务描述匹配 `knowledge-map.json`。
5. 读取命中的文档章节、历史事故和必要代码。
6. 输出简短“知识读取凭证”：读了什么、当前基线、发现何种冲突。

### 8.2 诊断阶段

Bug、数据异常和生产故障必须形成根因证明：

1. 现象与正确结果；
2. 稳定复现条件；
3. 从数据源、数据库、服务、接口到页面的完整链路；
4. 最早出现错误的状态；
5. 直接原因、根本原因和保护机制失效原因；
6. 已排除的其他合理假设；
7. 数据、研发、产品、运维四个影响面；
8. 同类对象和同类功能范围；
9. 修复前失败、修复后通过的测试；
10. 本地或生产验收证据。

紧急故障可以先做明确标注的临时止损，但永久修复仍必须补齐根因证明。

### 8.3 修改阶段

- 先建立复现或最小失败测试；不可自动化时记录可重复的人工证据。
- 只修改根因相关局部，不扩大无关重构。
- 改动扩大时重新执行知识路由。
- 涉及外部 API 时遵守首次入库、后续增量、失败保留和去重要求。
- 涉及数据库结构和生产数据时继续执行现有用户确认规则。

### 8.4 收尾阶段

1. 根据实际变更文件反向匹配知识路由。
2. 就地更新现有权威文档，不另建重复架构文档。
3. 重要决策写 ADR，重大或重复故障写 Incident。
4. 用户可见变化进入 CHANGELOG；全部技术细节留在 Git。
5. 记录测试、同类扫描范围、通过数量和遗留异常。
6. 运行知识治理检查。
7. 未闭合事项标记 `pending`，不得用“基本完成”替代。

## 9. 自动门禁

新增 `scripts/check-knowledge.js`，使用 Node.js 标准库实现，不增加依赖。

首版检查：

1. `knowledge-map.json` 格式和引用路径有效。
2. 架构相关路径变化时，相关文档已更新或存在明确的不更新理由。
3. 不能只修改“最后核对日期”而不修改相关正文。
4. `package.json`、`package-lock.json`、`CHANGELOG.md`、`public/changelog.json` 的版本一致。
5. 重要 Bug 的任务卡包含根因、同类范围和回归证据。
6. 需要 ADR/Incident 的任务已建立对应记录。
7. 平台适配器只包含允许的入口信息，未复制项目事实。
8. 活动任务卡没有把已完成事项继续标为开放。
9. 文档内部路径和索引有效。

门禁接入：

- `package.json` 增加 `check:knowledge`；
- GitHub CI 新增独立知识治理任务；
- 部署流程在版本更新和部署前执行；
- 是否增加本地 Hook，以当前 Codex 支持事件和项目实际工作流为准，不依赖 Hook 作为唯一防线。

CI 失败必须给出明确的文件、触发规则和修复动作，不能只输出“文档未更新”。

## 10. Token 控制

### 10.1 默认读取策略

| 风险 | 默认范围 |
|---|---|
| 低 | L0 + 当前文件/功能说明 |
| 中 | L0 + 相关架构章节 + 相关测试/历史事故 |
| 高 | L0 + 完整相关领域知识 + 运行态/数据证据 |

### 10.2 控制规则

- 不读取全部 89 份 Markdown。
- 文档按章节读取，历史先搜索关键词再读取命中片段。
- 同一任务中，文件未变化且摘要仍完整时不重复读取。
- 规则只写一次，平台适配器不复制正文。
- 低风险任务不运行完整根因协议。
- 高风险和不确定任务允许自动扩大上下文，Token 预算不得阻止必要证据。

### 10.3 防遗漏

- 任务描述路由和实际改动路由必须同时通过。
- 无匹配规则、冲突或原因不确定时默认扩大，而不是默认忽略。
- 交付凭证必须列出读取内容和未读取原因。
- 定期审计用于发现绕过 Git 的生产、数据库和平台记忆漂移。

## 11. 错误处理

- 路由表命中多个领域：合并必读项并按最高风险执行。
- 路由表无匹配：读取 L0、技术架构相关索引并标记缺失路由，任务收尾时补规则。
- 平台适配器无法验证加载：该平台标记 `pending`，不得宣称已接入。
- Codex 项目级 Memory 设置不生效：停止实施并报告，不修改全局设置。
- 文档与代码冲突：以代码、Schema、测试和验证运行态裁决；无法裁决则保留冲突。
- CI 因既有问题失败：区分既有失败和本次新增失败，不通过删除检查或降低门禁解决。

## 12. 安全与权限

- 记忆库禁止保存密码、Token、授权码、Cookie、完整环境变量或私钥内容。
- 允许记录环境变量名、密钥存放规则和脱敏连接方式。
- 平台旧 Memory 和同步临时目录先只读审计，未确认前不删除。
- 项目配置不得修改认证提供方、全局通知、全局 Memory 或其他项目设置。
- 生产写入、数据回填、部署、删除和清场继续遵守现有用户确认规则。

## 13. 实施范围

### 阶段一：建立骨架

- 新建知识索引、机器路由、模板目录和项目 Codex 配置。
- 调整现有 `AGENTS.md` 的入口和工作流，不删除原有有效约束。
- 建立 `check:knowledge`，接入 CI，但先只覆盖确定性规则。

### 阶段二：迁移现有知识

- 给现有专项文档标记当前、历史、待决或被替代状态。
- 只提炼重要历史决策和重复故障，不回填每个小版本。
- 审计 WorkBuddy/CodeBuddy 现有项目记忆，权威事实迁回仓库；旧内容不自动删除。

### 阶段三：验证和收紧

- 选择至少一个普通 Bug、一个数据问题、一个跨模块问题做回放。
- 验证必读知识是否召回、Token 是否受控、遗漏能否被反向路由发现。
- 根据真实误报和漏报调整路由，再决定是否增加 Hook 或更严格 CI。

## 14. 验收标准

1. 新 Codex 任务在本项目中能证明加载项目 `AGENTS.md`，且不使用、不生成原生 Memory。
2. 其他 Codex 项目的 Memory 行为不受影响。
3. 至少 Codex、WorkBuddy、CodeBuddy 均能通过已验证入口读取相同权威知识；无法验证的平台明确标记 `pending`。
4. 修改数据库、任务、路由、数据服务或部署文件时，门禁能指出应核对的知识面。
5. 初始任务分类遗漏时，实际文件反向路由能补充必读和必更项。
6. 重大或重复 Bug 没有根因、同类范围和回归证据时不能通过治理检查。
7. 简单任务不会加载全部项目文档，高风险任务不会因 Token 预算停止必要调查。
8. 现有业务测试、部署流程和敏感信息规则不被破坏。
9. 未提交的既有用户修改没有被覆盖、提交或清理。

## 15. 设计决策摘要

- 选择 Git 仓库作为共享记忆，而不是同步平台私有 Memory。
- 选择小入口加按需路由，而不是每次全量加载。
- 选择软预算加自动扩容，而不是固定 Token 硬上限。
- 选择任务前后双向路由，而不是只依赖任务描述分类。
- 选择测试和门禁作为可执行记忆，而不是继续增加提醒文字。
- 选择项目级关闭 Codex Memory，不改变全局 Codex 行为。
- 选择增量整理现有文档，不推倒重写或一次性大清理。
