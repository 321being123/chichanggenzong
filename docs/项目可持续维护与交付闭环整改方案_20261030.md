## 1. 整改目标与问题范围

整改目标是让项目事实持续准确，开发与发布可交接、可验证，关键数据缺口可解释、可恢复，需求增长后仍能维护。验收关注结果，不以规则数量、文件拆分、提交数或测试条数作为成功标准。

| 本次确认的问题 | 根因或待核验边界 | 整改目标 |
|---|---|---|
| 0.9大改后文档新旧状态混杂 | 当前说明与阶段流水并列；只更新文首未修正文，深层仍有旧“未接入” | 当前正文、摘要、索引、路由与实际实现一致，历史和未验边界可追溯 |
| 其他Agent反复不按文档规范写 | 用户明确报告；现有检查主要验证入口、修改清单及部分符号，不能证明语义正确；新规则分支也未自动传播给旧工作区 | 权威规则统一、任务按流程执行、交接能核查实际文档差异；不宣称Skill能保证所有Agent服从 |
| 上次部署未更新后台反馈状态 | 用户明确报告；已有回写服务，但脚本允许省略批次而跳过第二段，代码部署成功与完整交付容易混淆；具体批次原因未读生产核实 | 先补办真实漏项，再阻止“没核对”冒充“没反馈”，逐条验收/回写/回读 |
| 反复补修数据与业务链路 | 交易/换股、行情、持仓基准、净值之间存在多步骤合同；本地无记录不等于上游无数据 | 从发现缺口到补取、质量发布、重读形成闭环，保留官方等待与权限阻塞 |
| 分层清零后仍有运行缺陷 | 返回形态、变量作用域和SQL污染并非全部属于静态越界；混合编排和共享前端尚有验收债务 | 把位置合规、职责清晰和行为正确分别验证，逐域处理真实热点 |
| 定期维护缺少持续执行和效果验证 | 已写策略但未安装定时任务；首次月报没有可比上月指标 | 按任务/发布/周/月更新，每月复查上次措施是否有效，并记录用户价值、成本和维护风险 |

## 4. 总体实施原则与职责

执行链保持“**仓库规则/合同 → Skill组织步骤 → 脚本与测试验证 → 人工复核语义/效果 → 原任务和发布回执留证**”。Skill读取权威文档，不复制字段、架构和生产状态；脚本不能自动证明全部语义；发布负责人不能仅凭Agent说完成就关单。

| 角色 | 责任与交付 |
|---|---|
| 开发任务负责人 | 在自己的分支交付代码、原文档、实际验证、反馈候选与未验项；每文档写清已更新/无需改/待补的依据 |
| 文档整合负责人 | 复核实际差异、旧结论替代、证据、摘要/索引及交接基线；不以改过文件或检查通过替代内容判断 |
| 发布负责人 | 固定整合提交、运行版本和反馈批次，完成专项、回写与回读；分别报告代码与反馈结果，留下失败/剩余去向 |
| 月度维护负责人 | 执行公共规则11.4—11.6、对比同口径证据及上月行动效果，认领/转交下月少量重点 |

角色是责任分工，当前人员/对话未认领的阶段保持待认领，不能虚构排期。跨对话继续沿既有任务卡和Git提交，不另建任务系统、全局资源锁或私有事实库。

## 5. 分阶段实施与退出条件

### S0：统一知识入口和整改基线（先行，P1）

1. 统一整合本分支已交付的文档与本方案，核对共享正文、索引、read/update/readSections及历史链接，记录任务提交→整合提交映射。
2. 确认Codex的实际项目入口为portfolio-server。当前保存的父目录不应被误当成仓库；仅在命令参数中换目录不能证明宿主已发现嵌套仓库Skill。
3. 核对其他Agent实际读取的入口、规则版本与工作目录；已有旧工作区按原协作规则接续，不自动覆盖其改动。WorkBuddy是否原生发现Skill须实测，不能按Codex行为推定。

**退出条件**：新任务能从现行入口定位正确权威章节，真实任务验证在正确仓库操作；另一工作区接手能找到固定交接提交。没有发现或加载证据时只写待接入。

### S1：补办实际反馈漏项并固定当前结果（最高优先，P1）

1. 只读核对用户所指发布的实际版本/SHA、原部署回执、DEPLOY_RESULT、feedback_run_id与批次状态；完整读取当前反馈及revision，不能按旧开发记录猜编号或状态。
2. 以实际部署代码和线上专项证据分别判断完整解决、部分解决、未涉及和待核验。未验项保留，#7/#8等原遗留不能随版本批量关闭。
3. 若原批次可安全接续，沿原幂等入口补办；内容/范围或验收已变化则按原流程重新核对、冻结和验证。不直接SQL改状态，不为了漏回写重复部署代码或重跑迁移。
4. 在既有授权范围内应用满足条件的反馈，逐条回读状态、实施版本和历史；超时先读实际结果，再决定重试。通知仍由原事务产生，不单独补造成功通知。

**退出条件**：本次相关项都有“已回读确认/部分未完成/待核验/冲突失败”及原因、版本和下一步；正确完成者才标已实施。仅生成计划不算反馈已处理。生产执行沿原授权，缺少必要范围时登记具体待确认对象。

### S2：把高频流程做成三个专项Skill（P1，前两个优先）

拟在实际仓库 `.agents/skills/` 下版本化维护；若特定宿主需用户级分发，只保留加载仓库权威流程的薄入口，不维护独占项目事实。创建位置和其他Agent的支持方式按实际发现机制核实。

| 拟定Skill | 触发任务/输入 | 核心流程 | 必须输出与边界 |
|---|---|---|---|
| site-doc-handoff | 文档更新、任务收尾/交接；输入任务范围、Git差异及原证据 | 根目录/基线→知识路由→原位修改→旧结论及摘要复核→已有门禁→语义交接复核 | 文档章节/实际变更/证据/未验项/检查；普通答疑不制造文档或假变更 |
| site-release-closeout | 用户授权的统一发布或发布反馈接续；输入固定任务提交/环境/反馈批次 | 核对授权与发布范围→现行发布流程→实际专项→反馈应用/回读→分别报告结果 | 代码状态、运行SHA、反馈核对和回读结果；不能由调用Skill扩大部署/生产写入权限，不能强制关闭未验反馈 |
| site-monthly-review | 月度项目复盘/健康检查；输入月份、截止时间、业务与文档基线 | Git/原事故及回执→架构/数据及维护审查→上月行动效果→同口径摘要与优先项→原位同步 | 月报、证据/未知、优化与验收及原任务去向；没有数据不编趋势，不自动执行所有建议 |

每个Skill保持单一职责，用清晰描述支持正常自动匹配，也可显式调用。正文只保留关键决策和流程，详细约束链接仓库；不把AGENTS/公共规则全文复制到Skill，不硬编码私密账号、路径或生产状态。

**行为验收**：逐个验证显式调用、自然语言匹配和不应触发的邻近任务。使用离线/隔离样本验证：文档旧结论未替换、源码变更漏专项、缺反馈批次、无相关反馈有读取证据、revision变化、部分解决、回写失败/未知、月报无上月数据。检查实际动作与产物，不只匹配Skill文字；验证不触发真实生产写入。Skill格式校验通过不等于行为通过。

**退出条件**：目标宿主能发现并正确使用Skill，代表性场景有结果，错误/不适用场景不误执行。Skill不会强制所有Agent服从，下一阶段仍需确定性检查。

### S3：补强现有文档检查和发布完成判据（P1）

**文档执行**：扩展check:knowledge及原任务卡交接，检查权威位置、必要章节/链接、状态/证据字段和可确定的结构错误。对“旧当前结论未替换”“重复现状”“已部署与未部署矛盾”等需语义判断的内容，列为人工审查事项，不用宽泛正则自动删除历史。无需改正文时给出可复核理由，避免仅改日期/凑文件差异过门禁；具体接受合同在原公共规则/检查任务明确。

**发布收尾**：扩展原deploy/reconcile入口，设计明确的反馈处置与证据：未核对、读取失败、完整读取后无相关反馈、已有核对批次、已应用待回读、已回读、冲突/失败等；这些是待设计合同，不冒充当前枚举。没有本批核对依据不能默认为无反馈；发布前必要检查缺失应在生产变更前被发现。

代码成功和整体收尾分别报告：可以代码已部署、反馈待续办；不得只打印“部署完成”掩盖未闭环。若调整退出码或外层自动化，必须确认不会让反馈失败触发旧trap回滚已成功代码、重跑迁移或重复发布。保留DEPLOY_RESULT并增强可消费性，复用既有发布批次与任务记录；没有证明现有结构不能承载前不新增数据表。

**退出条件/反例**：缺核对依据不冒充完成；真实无反馈可凭读取证据完成；相关反馈必须专项通过后应用/回读；超时、权限、错版本、revision冲突、部分完成、重复执行及回滚均保持正确边界。脚本能拦截的遗漏有失败用例，语义复核有责任记录。涉及代码/配置/部署行为时完成原要求的全量验收。

### S4：关键业务合同与数据恢复试点（P1，可在S0后独立推进）

范围先限定导入/保存→交易/换股→行情→持仓基准→净值，并为跨层调用与失败结果建立可复现样本。重点覆盖已有主档后的重复启动、返回形态、变量/SQL有效性，以及记账日、同日顺序、失败保留、幂等与并发。

数据恢复先验证[月报第6节](项目月度复盘_202610.md#6-数据获取优先做可解释可续跑的恢复闭环)的候选：空nav_history、超过80只/部分失败、缺价格或汇率导致部分基准，以及补取后是否完整重读。候选未经复现不能当生产故障。

**链路设计**：页面/任务提出证券、字段与目标日需求→业务/原网关分类缺口→标准表/原文优先→已获准的短时适配或原Runner去重/续跑→Guard约束下的已准入来源→标准化及质量发布→业务重算/快照更新→接口/页面重读。仓储不隐式联网；不把本地空值直接标上游未披露；不改变默认只读策略而不说明影响。

官方未披露按证据等待复查，权限/来源不支持明确阻塞或进入合法备源，临时失败按原机制恢复；补取成功必须是目标数据可用，不能只看API 200。现有估值适配器默认未接线、理杏仁业务回退未全闭环，先核对真实能力，不新造平行数据源。

**退出条件**：固定样本覆盖命中/缺失/过期/等待/权限/异常/并发/续跑/补后重读；不伪造历史持仓、合法零值或未披露事实；剩余工作和失败原因可追踪。金融口径不借重构改变，数据/回放与生产写入按原范围授权。先通过一个旅程再扩域。

### S5：逐域优化架构热点并补齐可维护性证据（P2）

依据月报热点和原分层方案，先选转债资料输入判定/文档处理，再选持仓共享前端；任务配置文件变动多不自动当作架构错误。先固定已提交源码、可复现样本和工具，再提取确有独立变化压力的职责。

数据层保持访问/适配，domain保持纯规则，application保持业务及事务编排，路由/任务保持入口合同，Presenter与View分开验证。每域成功和失败路径都回归；不将金融公式、字段含义、权限或事务语义改动混在机械拆分中。

**退出条件**：固定前后数据与行为对比、返回/事务/身份合同及原强制测试通过；原9项数据/4项服务性能等证据只在自身范围使用，完整HTTP、前端/真机仍按实际执行记录。源文件变短或静态0越界不能单独宣称完成，不做新一轮全站搬家。

### S6：持续维护、运行恢复与成本基线（P2，按风险提前）

执行公共规则11节：任务交付时更新、发布后对齐、每周增量复核、每月项目总结/架构与数据审查/上月行动复查。月报采用约一页健康摘要、重点分析和下月3—5项优先行动，其余待办留原任务。

周/月自动化仅在用户明确安排后配置；先证明人工执行流程有效。自动任务负责读取、复盘和准备文档，不能凭定时触发取得生产写入或大范围重构权限；异常/缺证据保持待办。当前没有创建自动任务。

先核对备份及异地真实恢复证据、任务业务进展与质量可用性，再从现有数据建立交付、API/AI调用、数据/日志增长及成本基线。无法确认独立可恢复副本等高风险项升级P1。没有费用、使用量或同口径上月数据就标未知；不为月报擅自开展生产演练或高负载测试。

**退出条件**：下一次月报能说明上次措施未实施/待验证/有效/无效复发/条件变化；选定指标可复核且口径一致，规则有执行证据、未验项有责任与下一步，不月月复制同一建议。

## 6. 批次顺序、依赖与发布安排

| 批次 | 建议纳入 | 依赖与交接 | 负责角色 |
|---|---|---|---|
| B0 基线与接续 | S0知识入口＋S1原发布只读核对 | 文档先统一整合；真实反馈写入范围、环境与版本单独按原流程确定 | 文档整合/发布负责人 |
| B1 防漏收尾 | S2前两个Skill＋S3文档/反馈检查 | 读取已整合规则；Skill可先离线开发，依赖新增检查的部分不能标终态完成 | 工作流开发/发布负责人 |
| B2 业务恢复 | S4单旅程试点＋相关真实回归 | 独立库/数据与固定代码；不等待月报自动化，接口和调用方合同须同批兼容 | 数据/业务/测试负责人 |
| B3 热点与持续性 | S5小批次＋S2月度Skill＋S6 | 业务先有基线；先验证人工复盘和技能，再决定自动日程 | 相关域/维护负责人 |

不按未经确认的日历承诺完成日期；认领后在原任务卡明确检查点。开发沿独立worktree、固定交接提交和现有共享资源约束；用户仍可另开对话统一整合发布。各批保存回滚边界，不能通过删除事实/重置生产数据来回退。代码/依赖/配置/部署行为改动按AGENTS执行相关专项、test:all及运行验收；纯文档执行知识/引用/差异检查。

## 7. 总体验收与成功指标

| 目标 | 可接受的证据 | 不足以通过的替代物 |
|---|---|---|
| 文档规范真正执行 | 代表任务的正文/摘要/索引同口径，旧结论有明确替代，原证据可定位，整合检查缺陷已消化 | 文档改过、只刷新日期、门禁绿色或Agent口头承诺 |
| 反馈处理完整 | 原运行版本/批次、当前revision、逐项线上证据及回写回读；无相关反馈有完整查询证明 | 代码部署成功、pending空数组、标题相似或直接批量关单 |
| Skill可用 | 宿主实际发现、显式/隐式/负例行为结果，权限与适用范围保持 | 文件存在、格式校验通过、假定所有Agent已加载 |
| 数据恢复有效 | 可补缺口的实际补齐、质量与重读，剩余/等待/阻塞各自可追踪 | 上游请求成功、样本外推全量或把未知填零 |
| 架构优化有效 | 固定样本前后等价、职责及失败合同清晰、变更压力降低有观察 | 行数下降、搬目录或越界归零 |
| 持续维护有效 | 同口径趋势和上月行动效果，未知项、负责人和下一步明确 | 新增更多规则、提交/测试数量增加或一次月报 |

本方案不预设百分比目标或把未知成本写成已节省。实施时按真实范围建立基线及可接受阈值；是否降低复发、等待和重复外采需后续观察证明。

## 8. 权威落点与同步清单

- 执行/知识细则：公共规则6/9/11节；AGENTS只留入口与必要红线。
- 当前机制、层次和实际接线：技术架构原章节；设计/候选风险不冒充当前实现。
- Skill：仓库中三个工作流入口，引用上述权威原文；实际创建后再维护精确路径、发现方式和验证记录。
- 反馈发布合同与代码/反馈结果：原反馈方案、生产部署流程、原批次/任务回执；漏项不另建第二套反馈清单。
- 数据恢复/金融口径：原现金收益、数据/任务和分层专项；技术架构同步实际变动，任务定义/运行规则变更才按原要求更新追踪矩阵。
- 月度发现与改进证据：[项目月度复盘_202610.md](项目月度复盘_202610.md)及后续对应月份；本方案只维护依赖、批次与退出标准。
- 后续任务路由命中本方案；实现时按实际差异补匹配原业务路由，不用本方案免除专项必读与验收。

## 9. 参考与当前未决事项

Skill设计依据已核对的[官方技能文档](https://learn.chatgpt.com/docs/build-skills)和[行为评估实践](https://developers.openai.com/blog/eval-skills)：描述匹配可触发，目录/名称/范围影响发现；需验证实际行为。仓库事实优先，其他Agent支持与本机宿主发现仍待实测。Skill是流程指导，不是不可绕过的权限或代码检查。

GitHub维护实践与本项目取舍统一见[公共规则11.6](知识库公共规则.md#116-可持续维护健康趋势与行动效果)，此处不复制清单。当前最先需要确认的事实是用户所指发布批次/反馈范围、现行规则与Skill的实际加载路径、关键旅程样本及恢复证据。未取得这些信息不影响文档方案交付，但相应执行阶段不能标已完成。
