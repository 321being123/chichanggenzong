# INC-0009：个股分析任务成功误报失败

状态：跟踪中（本地已修复，待生产发布）
日期：2026-09-05

## 现象与影响

后台“个股分析刷新”每日 20:30 的第一次运行显示“失败/任务执行失败”，约 5 分钟后的自动重试显示成功。生产核查发现，第一次运行实际已经完成个股分析和数据集发布，只是任务状态被错误写成失败，造成无效重试和后台告警噪声。

2026-08-20 至 2026-09-04 共核查 12 个计划槽位，12 个全部出现两次运行；9 月 4 日第一次运行已完成 12 只股票分析，发布 `stock_analysis_snapshot` 分区 462 行，第二次运行没有外部调用，仅返回 `fresh`。

## 根因链路

数据源 → 数据库 → 服务 → 接口 → 页面/任务 → 运行环境

个股分析服务正常读取已发布的行情和财务标准层，并成功写入分析结果和数据集分区；统一任务执行器随后读取结果对象。个股分析成功结果包含 `skipped: []`，而 JavaScript 空数组是真值，执行器误把它当作“任务被跳过”，进入通用跳过处理分支，使用空的原因生成 `JOB_FAILED/unknown` 并顺延 5 分钟。自动重试只命中新鲜度门禁，所以表现为第二次成功。

## 直接原因、根本原因与保护机制失效原因

- 直接原因：执行器用 `result.skipped` 的真值判断跳过状态，没有区分空数组和非空跳过列表。
- 根本原因：任务结果契约允许用数组保留跳过明细，但编排层只按布尔信号设计，空列表的“无跳过项”语义没有被统一定义。
- 保护机制失效：既有测试覆盖了成功水位和重试流程，但没有覆盖 `skipped: []` 与 `skipped: true` 的区别；第一次业务写入成功后也没有阻止执行器把结果改写为失败。

## 同类范围与核查结果

已检索统一执行器的所有 `result.skipped` 分支。修复后统一使用“非空跳过信号”判断：真实的 `true`、`fresh`、`not_configured`、错误跳过以及非空数组仍保持原行为，空数组按正常业务结果继续判定。生产历史核查未发现个股分析数据写入失败，问题属于任务状态误报和无效重试。

## 修复与回归证据

已修改 `server/services/jobOrchestrator.js`：新增统一的空列表判定，并覆盖新鲜度、失败、未配置和通用跳过分支；已在 `server/test/job-execution-protection.test.js` 增加回归断言，防止空跳过列表再次触发失败分支。

`npm.cmd run check:knowledge` 已通过；`npm.cmd run test:all` 使用隔离测试库完成 116 项测试，0 失败、0 跳过。本次未执行生产部署，故生产修复状态仍为待发布。

## 防复发措施与遗留风险

- 任务结果中的 `skipped` 语义已写入 `docs/技术架构.md`，后续新增任务必须保持空列表不表示跳过。
- 发布后需观察个股分析连续两个计划日：首次运行应直接为成功，`attempt_count` 不应因该原因变为 2，且不应再出现 `JOB_FAILED/unknown`。
- 现有历史失败记录不回写，避免篡改审计；发布后的新运行记录作为验收依据。
