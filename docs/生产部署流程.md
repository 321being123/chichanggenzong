# 生产部署流程（铁律）

适用范围：任何生产服务器部署、热修复、数据同步、模型更新。无例外。

> 最后核对日期：2026-08-29。

## 1. 先更新版本记录

必须先执行版本记录更新，未完成不得部署。

```powershell
.\venv\Scripts\python.exe add_changelog.py --version <新版本号> --date <YYYY-MM-DD> --item "<更新说明>" --bump-package
```

该命令同步维护 `public/changelog.json`、`CHANGELOG.md`、`package.json` 和 `package-lock.json`。
部署前以 `package.json` 的 `appVersion` 作为唯一版本号，并核对 `package-lock.json` 根包版本与两份变更记录同步；本文不固定写入某个当前版本。

### 版本文案格式（强制）

- 每条版本说明必须以 `新增：`、`优化：` 或 `修复：` 开头，不能使用无分类前缀的文案。
- 同一版本内的条目固定按 `新增 → 优化 → 修复` 排序；`add_changelog.py` 会校验前缀并自动排序。
- 历史版本记录也必须遵守同一格式；发现旧记录缺少前缀时，先统一修订后再发布。

### Windows Python（固定方式）

- Windows 部署前更新版本记录时，固定使用项目根目录 `.\venv\Scripts\python.exe`。
- 不使用 `WindowsApps\python.exe`，它只是应用商店占位程序，可能无输出直接退出。
- 不再猜测 `ipo-report\venv` 等虚拟环境路径；先用 `Test-Path .\venv\Scripts\python.exe` 确认固定路径存在。
- 可转债公告默认以上交所/深交所批量接口为主、巨潮为备；只有确认 Tushare `anns_d` 已开通权限后，才在生产环境配置 `ANNOUNCEMENT_TUSHARE_FALLBACK=true` 启用最后备源，禁止把 Token 写入代码或文档。

## 2. 本地验证

1. 运行本次改动相关测试。
2. 涉及模型时，确认模型可训练、可加载并能产出有效预测。
3. 检查 `git diff` 与 `git status`，确认没有无关改动进入发布范围。
4. 涉及架构、数据、接口、任务、配置、依赖、CI 或部署时，运行 `npm.cmd run check:knowledge`，并处理路由指出的文档更新。

### Windows 全量测试（固定方式）

- 固定使用 `npm.cmd run test:all`，不要使用会触发 PowerShell 执行策略限制的 `npm`。
- 全量测试的外层命令超时至少设置为 240 秒；120 秒可能在测试正常运行时将其提前终止。
- 同一条“修改并部署”链路中，开发阶段先跑本次改动相关测试；完成版本记录并形成最终发布树后，只执行一次最终全量测试。
- 如果最终全量测试通过后只变更版本号、`CHANGELOG.md` 或 `public/changelog.json`，属于发布元数据变更，只需重跑版本一致性、知识门禁和本地 `/health`；代码、依赖、数据库、配置或部署文件发生变化时，必须重新执行发布前全量测试。

## 3. Git 正式发布

所有代码、版本记录、模型文件和同步 SQL 都必须提交并推送到 `master`。不允许只改本地或只改服务器。

```powershell
git add <本次发布文件>
git commit -m "<发布说明>"
git -c core.sshCommand=C:/Windows/System32/OpenSSH/ssh.exe push origin master
```

### Windows GitHub SSH（固定方式）

- Windows 上 Git 自带 SSH 在中文用户名目录下可能找不到 `.ssh/known_hosts` 和私钥。推送**固定**使用上面的系统 OpenSSH 命令，不再使用裸 `git push origin master`、临时关闭主机校验或改用其他推送方式。
- 首次或连接异常时，先执行 `C:\Windows\System32\OpenSSH\ssh.exe -o BatchMode=yes -T git@github.com`；只有认证成功后才推送。
- GitHub 主机指纹异常时，必须以 GitHub 官方文档为准核对后再更新 `known_hosts`，不得直接信任 `ssh-keyscan` 返回值。

## 4. 服务器标准部署

只允许通过以下标准发布流程更新生产代码：

部署脚本必须从干净的 `master` 执行，且本地 `HEAD` 已与 `origin/master` 完全一致；它会在建立 SSH 连接前运行知识与版本检查。没有用户明确的线上部署授权时，不得执行。实际执行必须显式确认：

```powershell
.\venv\Scripts\python.exe deploy\deploy_password.py --confirm-production
```

检查失败时不得连接生产服务器；远端重置后的完整提交 SHA 必须与本地已推送 SHA 一致。
本地前置校验中的 `git fetch origin` 固定使用 `C:/Windows/System32/OpenSSH/ssh.exe`，不得回退到 Git 自带 SSH；本地检查输出按 UTF-8 读取。

1. 只使用项目 `AGENTS.md` 指定的 SSH 私钥登录生产服务器；服务器已关闭密码登录，不得再尝试密码或读取旧的 `DEPLOY_SSH_PASSWORD`。
2. 登录后以 `sudo` 身份在 `/opt/portfolio` 执行以下命令；不要用 SFTP/SSH 直接覆盖代码，也不要用 `git pull`。

```text
sudo git fetch origin
sudo git reset --hard origin/master
sudo npm ci --omit=dev
sudo systemctl restart portfolio-server
```

- 服务由 systemd 管理（`portfolio-server.service`），**pm2 已过时，禁止 `pm2 restart`**。重启后验收 `curl -s http://127.0.0.1:3000/health`。
- **后台任务拆分（WORKER-01，生产现役）**：任务调度注册表收敛在 `server/scheduler.js`，Web（`server/app.js`）与独立 Worker（`server/worker.js`）共用同一清单。Web 通过 `DISABLE_SCHEDULER=1` 固定关闭调度，全部后台任务由 `portfolio-worker.service` 承担，`portfolio-worker-health.timer` 定时检查心跳。`deploy/ecosystem.config.js` 仅作历史参考，生产不再使用。PG 任务锁保证任务不会重复执行；`/health` 只表示 Web 存活。
- 如果本次没有修改 `package.json` 或 `package-lock.json`，可跳过 `npm ci`；不得因此跳过 Git 拉取、重启和验收。
- ⚠️ **服务以 `portfolio-app` 用户运行**。git fetch/reset 用 `sudo` 执行即可；**禁止对 `/opt/portfolio` 执行 `chown -R`**（2026-08-04 事故：误 chown 给 ubuntu 后 `data/.secret` 无法写入，服务 EACCES 启动失败）。确需恢复属主时用 `sudo chown -R portfolio-app:portfolio-app /opt/portfolio`。
- 若服务器 `git fetch origin` 报 `Host key verification failed`，只为 `root` 的 GitHub SSH 配置官方已核对的主机指纹后重试；若报 `Permission denied (publickey)`，必须通过 `sudo` 使用 root 的 GitHub 部署密钥拉取。
- Python 旧版 `.xls` 解析依赖 `xlrd`。服务器为 PEP 668 受管环境，缺少时固定使用 `sudo apt-get install -y python3-xlrd`，随后运行 `python3 -c "import xlrd"` 验证；禁止使用 `pip --break-system-packages`。
- 日常打新发布应随统一数据层版本发布；旧的 `deploy_server.py`/`server_bond_sync.sql` 仅作历史参考，不得再执行旧债表同步。

### 统一数据层直接切换（维护窗口专用）

涉及本方案的发布必须按以下顺序执行：备份数据库与离线旧表快照 → 停止 Web/worker → 发布同一版本代码 → 运行迁移 058 → 执行迁移覆盖率与 `bond_unified` 验收 SQL → 启动 Web/worker → 验收 `/health`、打新日历、债券详情和预测链路。任一验收失败，必须同时回滚应用版本和数据库快照；禁止只回滚代码。生产同步或迁移前必须取得用户明确同意。

涉及数据库迁移或特殊数据处理的版本，在 `CHANGELOG.md` 或任务记录中写明迁移编号和影响范围；本文只维护通用部署流程，不记录某个版本的临时发布说明。生产公告补发/更正只在用户明确同意生产数据同步后执行。

下修监控迁移须兼容旧生产库：迁移 092 在重建视图前先幂等补齐 `analytics.convertible_bond_trigger_daily.minimum_future_days`，迁移 100 发布滚动剩余天数，迁移 101/102 对齐集思录状态有效期并设置公告解析质量门槛，迁移 103 放行有正文证据但未承诺期限的明确“不下修”公告，迁移 104 放行已实施公告正文锁定期证据；下修计算不得把上市前正股行情计入观察窗口。部署后必须检查 Web/Worker 均能完成迁移并通过下修接口验收，确认 `stale=false`、`pending_no_revision_parse=0`，并核对 terminal 异常数是否可解释。

### 数据同步：按需且必须先询问

数据同步不属于每次部署的固定步骤。仅当本次变更涉及数据库结构、历史数据、日报、模型产物或其他生产数据写入时，先向用户说明同步内容和影响，并询问是否执行。只有得到明确同意后，才生成同步 SQL 或执行数据同步。

禁止事项：

- 禁止 SFTP 或 SSH 直接覆盖生产代码、模型文件或配置文件；
- 禁止未更新版本记录就部署；
- 禁止跳过本地验证、Git 提交或部署后验收；
- 禁止以“紧急修复”为由省略流程。紧急修复可先恢复服务，但必须立即补齐完整发布流程。

## 5. 部署后验收

依次确认：

1. 服务器提交版本与 GitHub `master` 一致；
2. `portfolio-server.service`、`portfolio-worker.service` 和 `portfolio-worker-health.timer` 状态正常；
3. `http://127.0.0.1:3000/health` 返回预期版本；
4. 本次相关接口和页面正常；
5. 如用户已同意执行数据同步，确认相关数据、日报或模型结果已写入 PostgreSQL；
6. 前端版本记录可见且与本次更新一致。

### 独立远程验收命令（Windows/Codex）

- 通过 Paramiko 执行多行远程脚本时，优先复用 `deploy/deploy_password.py` 的 `run_sudo`（内部使用 `shlex.quote`），或使用 `exec_command('sudo bash -s')`，通过标准输入写入脚本后调用 `shutdown_write`。
- 禁止把 Python `repr()` 的结果直接拼入 `bash -c`；`repr()` 生成的是 Python 字面量，不是 Shell 安全引用，会导致远程解析失败。
- 远程 Shell 解析失败时，先确认实际验收命令是否执行；如果未执行，明确记录“未执行验收命令、未影响服务”，再改用上述安全方式重试。

任一项不通过，部署状态为失败，不得宣称已上线。
