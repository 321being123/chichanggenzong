## 根因链路与生产证据

汇率来源 → `market.fx_rates.rate_date`（DATE）→ node-postgres 返回本地午夜 Date → `navSnapshot.cnDate` 错误换算 → 汇率按错误日期建 Map → 开市日精确取值失败 → 净值任务 blocked → 归因中间断档 → 卡片显示“—”。

1. 生产应用版本 `0.8.2.2`，部署提交 `837ee09322e703c275ac454d6a6ac680ebdcbedc`；本地审计基线 `be10ef98212c44e6854be40975acd90e49c76376`，两提交之间只涉及三份文档。线上与本地 `server/jobs/navSnapshot.js` SHA256 相同：`9acc4280c9c530cf2552e8970a3e180b8961b542fca2dac71120accecdf7434f`。
2. 生产 Node 的时区和 PostgreSQL `SHOW TimeZone` 均为 `Asia/Shanghai`。因此不是主机忘设北京时间。
3. 9 月 25 日港股收盘任务 16:30 成功；汇率任务 16:35 成功。当天汇率行存在且有效，`fetched_at=2026-09-25T08:35:41.495Z`，早于快照最后失败时间。不能把这次问题归因于上游没有汇率。
4. 9 月 25 日净值槽位尝试 3 次后 blocked，最后完成于北京时间 17:02:41，返回 partial；目标账户诊断中有 17 个港股的 HKD 汇率缺失。

6. `navSnapshot.js:188–200` 读取未转文本的 `rate_date`，用上述函数建键；港股开市日按日期精确查找，因此查不到当天值。重复运行同一代码不会消除这个错误。

目标账户任务还报告过 7—8 月持仓基准、行情、汇率等历史缺口；本次未逐个重算，不能全部归因于同一缺陷。错误映射还有把后一天汇率配给前一天的可能，需核对快照生成时的输入和历史汇率，不能仅凭今天数据库状态认定历史快照错了。

## 直接原因、根本原因与保护机制失效原因

### 1. 把三种不同含义都当成 Date 或随意截取字符串

- **业务日期**：如交易日、汇率日、报告期，只有年月日，不是某个时刻。
- **真实时刻**：如采集时间、成交时刻、任务开始时间，需要时区或 UTC 偏移。
- **任务目标日**：调度槽位要处理哪一天，不必等于执行当天，也不必等于最新数据日。

生产 schema 只读检查发现：标准层有 210 个 DATE 列、186 个 TIMESTAMPTZ 列；所查 schema 无 timestamp without time zone 列。旧账本 `daily_prices.date`、`nav_history.date/snapshot_at`、`trades.date/trade_date/executed_at/created_at`、`cash_flows.date/created_at` 仍为 TEXT。字段类型和驱动返回形态不同，但业务消费代码常按“看起来像日期”统一处理。

`server/db/connection.js` 未统一 DATE 类型解析；只有 `server/scripts/repairFxRateHistory.js` 单独设置了 OID 1082 文本解析。同一份数据通过不同入口可变成不同 JS 类型。

### 2. 公共规则已有，公共实现没有贯穿所有入口

`jobScheduleSlots.normalizeBusinessDate`、`marketState`、`navAttribution.dateKey`、`replayNav.cnDate` 已有正确的上海日期处理。但其他模块仍保留独立 `cnDate/todayCN/nowStr`，修调度或重放不等于修日常快照。

历史证据：INC-0026 记录恢复证据 UTC 截日错误和可转债 `YYYYMMDD`/`YYYY-MM-DD` 生命周期比较错误；技术架构记录收盘价旧格式清理与安全评分 DATE 修复；INC-0031 记录申购时刻被 `String(Date).slice(0,10)` 错误比较。它们是不同入口暴露同一种类型/语义边界缺失，不能只再加一个特例。

### 3. 已有测试没有覆盖这条真实类型链路

- `nav-snapshot-regression.test.js` 主要是正则检查源码包含某些保护逻辑，没有执行“真实 PG DATE → 汇率 Map → 快照”。
- `cross-market-calendar-nav.test.js` 有交易日、半日市等行为回归，但日历 mock 返回的是字符串日期，不能揭露本次 DATE 类型变化。
- `server/test/run-all.js` 继承当前环境，没有为日期测试建立 UTC/上海/纽约时区矩阵。
- AGENTS 已要求阻止 UTC 截断业务日期，但目前全局门禁并未阻止 `stockAnalysisRefresh` 等现存 UTC 截日写法；`check:knowledge` 主要核查规则、知识和指定实现，不是日期计算正确性的证明。
- `/health` 正常只说明服务存活；本次 blocked 与页面留空保护实际生效，但缺少能提前阻断上线的通用日期验证。

### C. 无副作用复现

使用本仓库原函数源码在 VM 中执行；用已安装 `pg.types.getTypeParser(1082)` 解析 `2026-09-25`，未连数据库写数据。测试固定时刻为 `2026-09-27T17:00:00Z`（上海 9 月 28 日 01:00）；区间为结束日 2026-09-28 往前一年。组件回调使用最小 DOM 替身，未启动浏览器。

| 进程时区 | todayCN（应 09-28） | nowStr（应 09-28 01:00） | 快照汇率键（应 09-25） | 区间起点（应 2025-09-28） |
|---|---|---|---|---|
| UTC | 09-28 | 09-28 01:00 | 09-25 | 2025-09-28 |
| Asia/Shanghai | **09-27** | **09-27 17:00** | **09-24** | **2025-09-27** |
| America/New_York | 09-28 | **09-28 05:00** | 09-25 | 2025-09-28 |

这些结果说明测试环境不同会掩盖错误，修改服务器 TZ 为 UTC 只能掩盖部分代码问题，还会改变其他依赖本地时间的实现。

## 解决方案与架构对齐

### 已有能力、可复用能力、真正缺口

- 已有：统一任务槽位、目标分区解析、marketState 市场日历、汇率事实表、快照 Runner、归因完整性保护、分区与告警恢复证据。
- 复用：从现有正确实现中收敛日期工具；沿用原任务和原表补缺，沿用现有恢复证据关闭告警。
- 缺口：日期与时刻的明确输入合同、数据库读出边界、端到端目标日传递、跨时区真实类型测试、可执行的通用日期门禁。
- 不新增平行调度器、行情来源或事实表，不重构整个账本。以下均为待实施方案。

### 第一批：修复确定缺陷，控制修改范围

1. 快照读取汇率时将 `rate_date::text AS rate_date` 固定为业务日期字符串，移除对这类纯日期的 Date 换算；复核同任务其他 DATE 入口。
2. 统一修正上述 6 文件 7 处错误公式。真实时刻转上海显示使用显式 `Intl` 时区；业务日期保持严格 `YYYY-MM-DD`，不走 Date。前后端复用可共享纯函数，避免再复制一组同名实现。
3. 修正两个图表区间入口：使用纯日期的日历运算，明确闰日取值，不混合 local setter 与 UTC 输出。
4. 保留行情/汇率缺失时拒绝计算的机制；接口可透传现有 reason、缺失日期帮助定位，不用 0 或昨日涨跌掩盖断档。

### 第二批：收敛边界和任务日期

1. 建立三类接口约定：业务日期为经过校验的字符串；时刻为含偏移的 ISO/TIMESTAMPTZ；任务使用现有 context 的业务日/目标数据日并携带市场。非法或混合输入失败关闭，不猜测。
2. 优先在 SQL/适配器边界显式输出 DATE 文本；TIMESTAMPTZ 先按字段定义的市场时区转日期，不能直接文本截断。暂不全局改 pg OID 1082：全局修改前先盘点依赖 Date 的消费者、测试与 JSON 输出兼容性；不得连带修改 1184 的时刻语义。
3. 水位/dataAsOf 使用实际处理的数据日期，不以执行时的 today 代替。历史补跑贯穿所有子阶段；实时汇率不伪装成旧日数据。Python 复用 `--today`，真实“现在”显式使用 ZoneInfo；UTC 时刻与市场日期分开。
4. 按 B 类清单逐个确认上游类型，再局部修复；不得把所有导入 Date 当成同一时区。旧 TEXT 字段先约束读写格式，本轮不要求全库迁移。

### 第三批：核对线上历史并恢复本次故障

1. 修复先通过本地验证和标准发布。对目标账户/日期只读列出缺失快照、使用汇率与生成时间，区分缺失与已存在但可能错误的记录。
