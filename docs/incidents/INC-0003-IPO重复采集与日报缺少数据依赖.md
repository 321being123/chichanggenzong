# INC-0003：IPO重复采集与日报缺少数据依赖

状态：已关闭（代码与知识库本地完成，待部署观察）
日期：2026-09-01

## 现象与影响

`ipo_calendar_refresh` 18:00和`ipo_history_sync` 19:30分别调用`new_share`，两者没有依赖；日报声明不依赖数据集。`ipo_history`又只按最后更新时间判断新鲜，无法识别“记录更新过但上市日仍缺失”的内容缺口，可能发布与日历证券集合不一致的日报。

## 根因链路

`new_share`重复采集 → `ipo_history`事实写入缺少内容门禁 → 日报脚本自行取数 → 日历/日报各自形成集合 → 发布只看更新时间。

## 直接原因、根本原因与保护机制失效原因

- 直接原因：两个现有任务都承担了同一接口采集，且执行时间倒置。
- 根本原因：IPO部分只登记了统一任务和调用预算，没有落实接口唯一采集者、数据集发布和下游分区依赖。
- 保护失效：新鲜度只验证更新时间，不验证目标日期、证券集合、采集批次和字段内容；发布前没有集合对账。

## 同类范围与核查结果

已扫描`ipo-report`和任务契约；`new_share`只保留在`ipo_history_sync`核心阶段。日报、新股日历刷新和旧上限回填入口均不再调用该接口。可转债日期继续读取现有标准事件表，没有新增平行任务。

## 修复与回归证据

- `ipo_history_sync`：18:00核心事实，19:30非紧急补全；核心阶段发布`ipo_history`业务日分区并输出质量诊断。
- `ipo_calendar_refresh`：18:05，只在同业务日上游成功且分区质量通过后运行，外部调用预算为0。
- 日报：申购/上市事实只读数据库，发布前对四组证券集合逐项对账，失败不覆盖旧结果。
- 回归入口：`server/test/ipo-history-sync.test.js`、`server/test/ipo-calendar-schedule.test.js`、`ipo-report/test_ipo_unit.py`、`server/test/job-execution-protection.test.js`、全量`test:all`和`check:knowledge`。

## 防复发措施与遗留风险

任务契约测试固定检查`new_share`唯一归属、日报零外部调用和数据集依赖；生成矩阵由知识校验防漂移。当前本地`market.trade_calendar`没有2026-09-01之后的开市日，真实核心同步会按门禁拒绝发布，需由既有`holiday_sync`先补齐；生产部署和数据同步需另行授权。
