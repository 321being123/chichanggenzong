## 2. 背景与目标

2026-09-15 后台出现 4 条新增告警。表面上是不同任务，实际集中暴露了四类共性问题：

1. 任务已经成功，但告警无法按证据自动关闭；
2. 不同任务使用了不一致的数据新鲜度口径；
3. IPO 的基础事实、资料补全和日报发布被绑在同一成功条件中，外部接口异常会放大为多条任务失败。
4. 告警关闭、历史调和与熔断恢复各自维护判断，失败又被静默吞掉，导致运行状态和告警状态长期不一致。

目标是让“任务状态、数据质量、告警状态”三者一致：真实失败必须保留，真实恢复必须收敛，外部暂不可用必须等待而不是重复失败，基础事实不能因低优先级补全失败而丢失。

## 4. 根因分析

### 4.1 告警关闭参数类型错误

`resolveJobSlotAlerts` 同一参数同时用于 `scope_key=$1::text` 和 `slot_id=$1`。PostgreSQL 在第二个比较中推导为 `bigint = text`，更新语句失败；异常被告警处理层捕获后只写日志，原告警保持未解决。

### 4.2 汇率新鲜度口径冲突

`hk_rate` 的业务逻辑使用 `fetched_at` 的 24 小时有效期；统一调度器的 `queryDataAsOf` 只查询 `MAX(rate_date)`，再按日历日期零延迟校验。一个任务因此同时存在“业务上新鲜”和“调度器判定过期”两种结果。

### 4.3 IPO 事务边界和质量门禁错误耦合

`ipo_history_sync` 先取得 `new_share`，随后在同一事务中执行资料补全和 `publication_quality`。CNINFO 403 使资料补全中止，质量门禁抛错后整笔事务回滚；代码 920202 因而没有留下基础发行事实。质量门禁还把行业、主营、业务赛道等增强字段当成 IPO 基础事实发布的必要条件。

### 4.4 外部异常被降级为普通任务失败

资料补全函数捕获 `ExternalCallGuardError` 后只返回 `stopped` 信息，外层仍继续执行质量门禁，最终抛出普通 `RuntimeError`。Worker 收到的错误缺少 `source/apiName/recoverAt`，只能按普通失败重试，不能进入 `waiting_external`。

### 4.5 水位恢复缺少数据质量证据

`reconcileSlot` 对部分失败槽位只检查日期水位是否新鲜，没有同时验证后续成功运行、数据集发布状态、质量状态和同范围未解决的数据质量问题，造成“槽位成功但结果摘要仍失败”的假恢复。

### 4.6 恢复规则和关闭执行分散

运行时 `resolveJobSlotAlerts` 主要按状态关闭，历史脚本 `reconcileAlertHistory.js` 另有 `verifyScope` 证据规则，两套判断未共用。`datasetPartitions.js`、`externalCallGuard.js` 等调用点还存在关闭失败后仅记录普通日志或静默吞掉的路径；Python Guard 直接更新告警，手工关闭熔断也可能被误当成上游已恢复。`sendRecoveryAlert` 强制发送则会绕过稳定键去重。上述问题共同造成“该关的关不上、不该关的可能被关、恢复通知可能重复”。

## 5. 设计原则

- 不删除历史运行记录和告警记录，不用“清零告警数量”代替恢复证明。
- 不伪造行业、主营、赛道或任何上游缺失字段。
- 继续复用现有 Worker、API Guard、数据集分区、`ipo_history` 事实表和告警体系，不新建平行业务链路。
- 外部接口问题按接口级保护；数据事实、资料增强和页面发布按阶段分别判断。
- 恢复证据按告警作用域分别判断；没有产出数据集的任务不能被强制要求提供分区证据。
- 所有自动关闭、自动恢复都必须能指向与该告警作用域匹配的运行、分区、质量检查或接口成功证据；空查询、手工关熔断和单纯日期水位都不算恢复。

## 6. 开发内容

### 6.1 修复告警生命周期

1. 将槽位作用域查询改为两个显式参数：`scope_key=$1::text`、`slot_id=$2::bigint`，禁止同一占位参数跨 `text`、`bigint` 复用；已完成的同类 SQL 扫描确认目前仅 `resolveJobSlotAlerts` 命中。
2. 把 `reconcileAlertHistory.js` 现有 `verifyScope` 规则抽为共享恢复证据服务，运行时自动关闭与历史调和必须调用同一实现；脚本不得再维护第二份判断。
3. `resolveJobSlotAlerts` 仅保留为槽位/任务作用域的关闭入口；数据集、数据质量和接口作用域也必须先通过共享证据服务，再走统一的 Node 告警关闭入口。Python Guard 只维护熔断状态并输出结构化结果，不再直接把手工关熔断等同于告警恢复。
4. 所有关闭调用点移除 `.catch(() => {})` 等静默路径。关闭失败统一写入现有 `admin_audit_log`，至少记录动作 `job_alert_resolution_failed`、告警 ID、作用域、调用来源、错误和时间；`checkWorkerHealth` 汇总最近失败次数与最近错误，形成可查询健康证据，不另建审计表。
5. 自动关闭只处理活动状态，不改写 `acknowledged`；人工确认仍保留原状态和审计轨迹，待证据满足后由明确的人工或规则化流程处理。
6. 恢复通知继续使用稳定 `alertKey`，但取消自动路径中的 `force: true`：同一恢复事件已有成功发送时间时永久跳过，超过 6 小时也不得重发；只有从未成功发送或 `send_failed` 才走现有受控重试，人工重发接口除外。
7. 上线后仅在共享证据通过时定向收敛 `19892` 等历史告警，不执行无证据批量关闭，也不把本次部署本身当成恢复证据。

### 6.2 统一数据新鲜度策略

1. 不另造一套新鲜度框架：日期型任务继续复用 `freshnessMaxLagDays` 和现有 `expectedDataDate`；仅给 `hk_rate` 任务定义增加 `freshnessMode: 'max_age'` 与 `freshnessMaxAgeMinutes: 1440`。
2. `queryDataAsOf('hk_rate')` 必须在通用日期字典和 `.slice(0,10)` 之前提前返回完整 `MAX(fetched_at)` 时间戳；`isDataAsOfFresh` 接收可注入的 `now`，按 `0 <= now - fetchedAt < 24h` 判断。恰好 24 小时即过期，未来时间戳视为时钟/数据异常；不得用 `freshnessMaxLagDays=1` 近似。
3. 明确两个数据库字段的不同语义：`ops.job_schedule_slots.data_as_of` 是 `TIMESTAMPTZ`，对 `hk_rate` 保存 `fetchedAt`；`ops.dataset_partitions.data_as_of` 是 `DATE`，继续保存 `rateDate`，完整 `fetched_at` 写入分区 diagnostics。不得把时间戳截成日期后再参与 24 小时判断。
4. `ensureHkRate` 的结果摘要同时返回 `rateDate` 与 `fetchedAt`；页面仍显示业务汇率日期，并可依据抓取时间显示新鲜度。日频行情、交易日历等任务不改变日期水位规则。
5. 告警文案区分“没有抓取时间”“抓取时间已超过 24 小时”和“业务日期非当日但仍在有效时间窗内”，避免再次误报。

### 6.3 重构 IPO 两阶段同步

1. 不新增任务代码、外部数据源或调度模式，只把现有 `core/enrichment` 职责拆清：
   - `18:00 core`：执行阶段 A，获取 `new_share` 原始响应，落原始记录与基础事实，在同一阶段完成基础质量检查并提交，再由现有 `jobRunnerProcess` 发布 `ipo_history` 分区；不得调用 CNINFO、个股详情或首日表现补全。
   - 将现有 19:30 的 `new_share` 刷新职责改由同一任务的 `core` 模式执行并发布基础分区；现有 `enrichment` 模式顺延到 19:35，只处理阶段 B，不再重复调用 `_refresh_new_share_snapshot`。这只增加同一任务的顺序槽位，不增加一次 `new_share` 调用。
   - 19:30 核心槽位携带独立的 `freshnessGate=false` 调度标记，绕过统一水位短路；18:00 仍保留新鲜度门禁，防止前一轮成功误跳过晚间公告更新。
   - 18:05、19:45 的 `ipo_calendar_refresh` 只依赖对应时段的 `ipo_history` 基础分区 `quality_status=passed`，不再依赖 enrichment 槽位成功。
2. 每次 `new_share` 获取都新建现有 `ops.ingestion_runs` 记录，并将原始响应写入 `ops.raw_records`。`source_key` 使用稳定的 `ts_code`，`payload_hash` 使用字段有序的规范 JSON 计算；相同载荷幂等，变化载荷保留新版本。`start_ingestion_run` 每次生成新 `run_id`，不能用“复用当天 runId”或外层 `job_runs` 重试代替幂等依据。
3. 阶段 A 的固定顺序为：原始响应入库 → 基础事实 upsert → 校验源结果与事实表 → 更新游标/ingestion 状态并提交 → 发布基础分区。只有代码/名称缺失、关键日期非法、重复代码冲突、上游返回集合与事实表不一致等基础事实错误才阻断发布；尚未到披露时点的可选字段不得失败。
4. 当前 `publication_quality` 含有行业、主营和业务赛道条件，因此不是“保持原含义”，而是必须明确收窄为基础事实质量。分区 diagnostics 的 `quality_status` 只表示基础事实是否可发布；新增 `enrichment_quality_status`（`passed/partial/waiting_external/failed`）、`enrichment_missing_count`（按缺失股票数计）和 `enrichment_checked_at`。`ipo_history.data_quality_status` 继续记录行级增强状态。
5. 阶段 B 只在同一 `ipo_history` 表补充行业、主营、业务赛道及首日表现；`industry_pe` 为可选项，`source_unavailable` 不得阻断基础分区或日历。行业、主营、业务赛道缺失时，资料页明确显示“待补齐”，分析/推荐不得输出伪完整结论或估算值。
6. 阶段 B 按代码或小批次提交已完成结果。发生 `ExternalCallGuardError` 时必须立即停止后续外部调用，先提交已完成行及行级状态，再原样重新抛出包含 `source/apiName/recoverAt` 的异常；不得让外层 `publication_quality` 覆盖原因，也不得回滚阶段 A 或已完成的增强行。
7. 301716、920202 等目标代码复用现有 `--target-codes --apply-targeted` 定向入口，只补缺失字段，不重复拉取已成功事实；生产执行仍须 `--confirm-production`，并单独取得生产数据写入授权，不新增定时任务。

### 6.4 正确处理外部接口熔断

1. 跨进程字段桥已经存在：`server/jobs/ipoHistorySync.js` 的 `runWith` 已解析 Python stderr 最后一行 JSON，并有 typed 正则兜底；本次只修改 Python `ipo-report/ipo_history_sync.py` 的异常保留和结构化输出，不能重复实现 JS 传递机制。
2. Python 侧不得在资料补全得到 `ExternalCallGuardError` 后只返回 `stopped` 再让 `publication_quality` 覆盖原错误；完成第 6.3 节约定的提交后，沿用现有 JSON 字段输出 `errorCode`、`errorType`、`source`、`apiName`、`recoverAt`，让 Worker 保留真实原因。
3. CNINFO 403 按现有 Guard 分两条路径：
   - 连续次数小于 5 次：返回 `RATE_LIMIT`，沿用现有 30→60→120 分钟封顶的 `recoverAt` 退避；编排器现有白名单将其置为 `waiting_external`，不消耗普通业务重试次数。
   - 连续达到 5 次：升级为 `PERMISSION_DENIED` 且 `recoverAt=NULL`；编排器将当前槽位明确转为 `blocked`，写入 `requiresManualAction=true` 并停止自动重试。不得使用含糊的 `failed/blocked` 双状态，也不得修成“永远 waiting”。
4. 不新增探测频率或第二套熔断器；恢复探测继续使用现有 Guard 的退避、探测租约和接口级隔离。
5. 接口告警与数据质量告警分别收敛：成功受控探测且 `last_success_at` 晚于告警后，可关闭对应接口告警；必需字段确实写入且质量复检通过后，才能关闭数据质量告警。接口恢复不能替代字段质量，字段补齐也不能伪造接口成功。
6. 手工关闭熔断器只表示允许再次探测，不是上游成功证据，不得立即关闭接口告警。`source:*` 通配作用域只有在实际查询到至少一条匹配熔断记录、且同一 source/api 下所有 fingerprint 均已关闭时才算恢复；空查询必须返回未恢复。

### 6.5 收紧恢复判定

共享恢复证据必须按作用域执行，不能用一套“运行 + 分区 + 接口全部同时满足”的条件误伤无数据集任务：

| 告警作用域 | 最低关闭证据 | 明确禁止 |
|---|---|---|
| `slot` | 原失败槽位自身最终成功，或同一 `job_code + business_date + mode` 的后续替代槽位成功；若任务声明 `strictDatasetPublication`，还须其声明的分区已发布、未过期且质量通过 | 只凭日期水位、不同业务日或无关模式成功关闭 |
| `job` | 最近 3 个可比槽位成功；每个严格发布任务同时具备其声明的数据集证据。没有产出数据集的任务只验证运行证据 | 强迫所有任务提供分区，或用 3 条跨模式无关成功覆盖失败 |
| `dataset` / 数据质量 | 精确业务日期分区存在、已发布、未过期，并满足注册表声明的质量规则；同范围未解决质量问题已复检通过 | 空查询、普通任务成功或 3 次成功直接关闭 |
| `source_endpoint` | 实际查询到非空的匹配熔断记录；精确/通配范围内所有 fingerprint 均关闭，且至少一次 `last_success_at` 晚于告警 | 手工关熔断、配置禁用或空查询当成恢复 |
| 依赖阻断 | 被依赖任务/分区的精确失败证据已恢复，随后本槽位按现有依赖流程成功或安全续跑 | 只因上游槽位状态被人工改写就关闭 |

恢复摘要及 `admin_audit_log` 至少记录告警 ID、作用域、命中的 `runId/slotId`、数据分区或熔断 `last_success_at`；不适用的证据明确标记为“不适用”，不得伪造空值为通过。无法满足证据时保持原 `failed`、`waiting_external`、`blocked` 或 `degraded` 状态。
