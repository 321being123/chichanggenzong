# 股票与可转债分析数据新鲜度与快照失效统一方案

> 文档状态：已实施  
> 核对日期：2026-08-06  
> 适用范围：股债分析中的独立股票分析、单只可转债分析及其正股依赖  
> 架构权威入口：[`技术架构.md`](技术架构.md)  
> 本文职责：补充“各类数据何时刷新、输入变化后如何使分析快照失效”的实施规则，不另建第二套数据架构。

## 一、结论

本方案与网站现有整体架构一致，股票和可转债应使用同一套新鲜度判定框架，并分别配置专属数据依赖。大部分能力应直接复用，不需要为股票或可转债分别新建另一套数据层、行情缓存、公告表、快照表或定时任务体系。

现有架构已经具备：

- `ops / core / market / fundamental / event / analytics` 六层数据关系；
- Tushare、腾讯行情、巨潮/交易所公告等现有数据源；
- `ops.sync_cursors`、`ops.ingestion_runs`、`ops.data_quality_issues`；
- 股票主档、财报、分红、业绩预告、行业、控制人、行情事实和分析快照；
- 可转债主档、转股价历史、行情事实、评级、条款和分析快照；
- 股票每日20:30任务、可转债每日18:00主链与次日08:00补跑、PostgreSQL任务锁；
- 单股/单券刷新接口和失败后保留上一份快照的处理方式。

本次真正需要补充的是四项连接规则：

1. 股票和可转债分析前按数据集检查新鲜度，而不是只检查计算公式版本；
2. 主档、公告或行情变化后，自动判定哪些分析结果已经失效；
3. 只刷新过期的数据组，不重复拉取全部历史数据；
4. 股票估值与财务输入、转股价与转债/正股价格必须使用一致的时间口径重新计算。

因此，本方案属于现有股债分析和统一数据层的共同补强，不属于新功能域或数据架构重建。

## 二、问题实测

2026-08-05对当前项目连接数据库进行只读核查：

| 检查项 | 实测结果 |
|---|---|
| 湘佳转债主档转股价 | `13.80元` |
| 主档更新时间 | 2026-07-30 |
| 页面最新分析快照转股价 | `21.03元` |
| 快照创建时间 | 2026-07-23 |
| 快照转股溢价率 | 约134.60%（页面按当时行情显示约132.87%） |
| 2026-08-05 Tushare转股价 | `13.80元` |
| 2026-08-05 Tushare收盘转股溢价率 | `51.52%` |
| 可转债主同步最后成功日期 | 2026-07-30 |
| 2026-07-31主同步结果 | 失败，字段名仍引用旧的`conv_price` |
| 数据质量问题记录 | 未记录本次任务中断和快照错配 |

同一数据库中主档已经更新、页面快照仍然过期，证明当前缺口不是单一的数据源问题，而是：

```text
基础事实更新
    ↓
没有产生快照失效信号
    ↓
普通查询继续返回旧payload
    ↓
转股价值、溢价率、双低值和触发价继续使用旧转股价
```

当前已有分析快照的转债中还发现太平转债存在同类转股价错配，因此修复范围必须覆盖全部可转债分析快照，不能只修湘佳转债。

### 2.1 股票侧实测

2026-08-05对股票分析链路和当前项目连接数据库进行只读核查：

| 检查项 | 实测结果 |
|---|---|
| 股票分析快照记录 | 121条 |
| 当前所有股票快照水位 | 均只有`{"source":"legacy_projection"}` |
| 最近一次股票任务 | 2026-08-03，成功11只、失败0只 |
| 股票普通GET | 从数据库重算，并通过公共腾讯行情缓存叠加实时价格 |
| 股票手动刷新 | 已按财报、行情、估值、分红、预告和事件采集，但部分接口仍在每次刷新时重复拉取较大范围 |
| 股票快照失效判断 | 当前没有基于财报、分红、预告、行业、控制人或行情水位的统一判断 |

这说明股票分析虽然没有出现湘佳转债同样的“转股价”问题，但存在相同的结构性风险：快照无法证明自己使用的财报、估值、分红、业绩预告、行业和控制人仍是最新版本。

股票与可转债需要共用新鲜度框架，但不能把实时行情变化等同于基础快照失效：

- 财报、分红、预告、行业、控制人、转股价、条款等变化会使基础快照失效；
- 腾讯实时行情只生成实时覆盖层，不应每60秒重写一份基础分析快照；
- 页面最终响应可以由“最后成功基础快照 + 当前有效实时覆盖层”合成。

### 3.1 与现有架构没有冲突的部分

- 继续执行“外部数据先落库，页面再读库”的分层原则；
- 继续以`instrument_id`关联主档、行情、事件和分析结果；
- 继续使用`analytics.analysis_snapshots`作为页面发布结果；
- 继续使用股票财务、行情、估值、公司行动和事件的标准事实表；
- 继续执行空结果不覆盖、失败保留上一份成功数据；
- 继续复用现有20:30股票分析刷新任务；
- 继续复用同一份`cb_daily`供单债行情、周期和估值使用；
- 继续保持Web与Worker单一调度所有者及PostgreSQL咨询锁；
- 不改变持仓、打新、安全性、周期和估值模块的既有读写边界。

### 3.2 原方案需要调整的部分

“每次开始分析都重拉全部外部数据”不符合网站现有边界，应调整为“基础快照 + 实时行情覆盖层”：

当前还有一处必须如实记录的既有偏差：`技术架构.md`写的是公开分析页只读取数据库快照，但实际`GET /api/stock-analysis/:ts_code`会调用`buildAnalysis()`，并在腾讯缓存过期时访问上游、回写`market_quote_cache`。本方案不复制这条链路，目标口径明确为：Tushare和公告数据严格后台化；腾讯行情保留为唯一共享的读穿缓存例外。代码实施后，应把`技术架构.md`对应描述同步为“读取基础快照，可叠加共享行情缓存”，消除文档与运行事实的差异。

- 普通`GET /api/stock-analysis/:ts_code`和`GET /api/bond-analysis/:code`先读数据库快照和依赖水位；
- GET不得调用Tushare、交易所或公告接口，也不得写入主档、财务、事件等基础事实；
- GET可以复用现有`tencentQuote.js`读取60秒共享行情缓存；只有指定证券缓存过期时才由该共享服务补取一次实时行情；
- 实时价格只覆盖本次响应中受行情影响的字段，不因每次价格变化重写基础分析快照；
- 基础数据仍新鲜时返回`fresh`或`live_overlay`；基础数据过期时返回`needs_refresh`和具体原因；
- 登录用户由现有前端逻辑自动调用一次对应的`POST .../refresh`；
- Tushare和公告源只能由刷新服务或Worker调用，前端不得直接调用；
- 游客可以读取最后成功结果，但必须显示过期状态，不能把旧值标成最新值。

这样既保留股票分析当前已经使用的腾讯实时行情能力，又不会把页面请求变成全量采集任务。

## 四、符合网站整体关系的目标数据流

```text
Tushare / 腾讯行情 / 巨潮与交易所公告
                ↓
ops：采集批次、原始记录、同步游标、质量问题
                ↓
core：证券、公司身份及债股关联
                ↓
market：股票/转债行情、估值及复权事实
fundamental：股票财务与公司行动、可转债主档/条款/评级/转股价历史
event：公告文档与结构化事件
                ↓
分析输入水位检查 + 基础指标重算
                ↓
analytics.analysis_snapshots
                ↓
GET分析接口读取基础快照 + 腾讯共享行情覆盖层
```

### 4.1 当前转股价的数据库关系

| 角色 | 数据位置 | 用途 |
|---|---|---|
| 当前有效值 | `fundamental.convertible_bond_profiles.current_conv_price` | 页面计算和触发价计算的当前输入 |
| 历史变化 | `fundamental.convertible_bond_price_changes` | 记录调整前后价格、生效日、公告日和原因 |
| 公告证据 | `event.documents`、`event.company_events` | 保存正式公告和解析结果 |
| 上游原始数据 | `ops.raw_records` | 追溯Tushare或公告原始响应 |
| 页面结果 | `analytics.analysis_snapshots.payload` | 最终展示缓存，不得反向覆盖主档 |

页面快照是派生结果，不是当前转股价的权威来源。主档或已生效公告发生变化时，旧快照必须失效。

### 4.2 股票分析的数据库关系

| 角色 | 数据位置 | 用途 |
|---|---|---|
| 股票与公司身份 | `core.instruments`及现有公司/股票主档 | 名称、上市状态、行业关联和统一`instrument_id` |
| 日行情、估值、复权 | `market`标准事实表 | 历史行情、PE/PB、市值、换手率和复权计算 |
| 财务报表与指标 | `fundamental`标准事实表 | 盈利、现金流、资产负债和财务质量分析 |
| 分红、业绩预告等公司行动 | `fundamental`、`event`现有事实 | 股息、业绩变化和事件分析 |
| 实时行情 | `tencentQuote.js`共享缓存，后续按DATA-02收敛到`market.latest_quotes` | 只覆盖当前价及其派生展示字段 |
| 页面结果 | `analytics.analysis_snapshots.payload` | 基础分析缓存，不得反向覆盖标准事实 |

股票分析快照同样只是派生结果。新财报、更正报告、分红、业绩预告、行业/控制人变化或新交易日事实入库后，相关快照必须失效或重算。

## 五、分析请求和刷新职责

### 5.1 普通“开始分析”

普通查询执行以下检查和轻量覆盖：

1. 读取最新分析快照；
2. 按证券类型读取主档、行情、财务、事件及专属依赖的当前水位；
3. 对比快照`source_watermark`和数据库水位；
4. 通过现有腾讯共享缓存获取股票或债股配对的实时行情；
5. 只在响应层重算当前价、涨跌幅、当前估值、转股价值、溢价率等行情相关字段；
6. 返回`fresh`、`live_overlay`、`needs_refresh`、`stale_usable`或`unavailable`。

该GET过程不得调用Tushare或公告源；腾讯行情也只能经过共享缓存服务，不能在股票和转债模块分别实现客户端。

### 5.2 单股/单券刷新

`POST /api/stock-analysis/:ts_code/refresh`和`POST /api/bond-analysis/:code/refresh`继续作为单只证券刷新入口，但应从“每次重拉全部数据”改为“按数据组判断并增量刷新”：

1. 获取该证券的数据库任务锁；
2. 判断每个数据组是否过期；
3. 只请求过期或缺失的数据；
4. 外部获取完成后先校验，不在网络请求期间持有数据库事务；
5. 校验成功后用事务写入标准事实；
6. 使用数据库最新输入重算分析；
7. 原子更新分析快照和`source_watermark`；
8. 失败时保留旧快照并返回明确的过期原因。

同一只证券并发刷新时只允许一个任务访问上游，其余请求等待或复用任务结果，避免重复调用。

## 六、股票与可转债数据刷新矩阵

### 6.1 可转债专属及共用依赖

| 数据组 | 分析时必须检查 | 实际外部刷新条件 | 增量范围 | 不需要每次拉取的内容 |
|---|---|---|---|---|
| 转债和正股实时行情 | 是 | 腾讯缓存超过60秒 | 两只证券一次批量请求 | 不分别发送两次请求，不保存分钟历史 |
| 可转债当前主档 | 是 | 单券水位超过15分钟、手动强制刷新或全市场主链未完成 | Tushare `cb_basic`单只记录 | 不拉全部存续转债 |
| 转股价调整公告 | 是 | 转股价变化、公告检查超过30分钟或历史链存在缺口 | 上次成功公告日向前重叠7天 | 不扫描上市以来全部公告 |
| 转债日行情 | 是 | 数据库缺少预期交易日 | 缺失日期，并重叠最近5个交易日 | 不重复拉500天完整历史 |
| 正股日行情和估值 | 是 | 数据库缺少预期交易日 | 缺失日期，并重叠最近5个交易日 | 不重复拉完整历史行情和估值 |
| 财务报表 | 检查报告水位 | 出现新财报公告、新报告期或现有报告字段缺失 | 新报告期及必要更正窗口 | 不在每次分析时请求`income`、`balancesheet` |
| 分红数据 | 检查公告水位 | 新分红公告或PB/股息计算输入缺失 | 新公告及更正 | 不每次拉全部分红历史 |
| 评级历史 | 检查最新评级 | `newest_rating`变化、出现评级公告或评级表为空 | 新评级公告 | 不每次调用`cb_rating`全历史 |
| 条款和募集说明书 | 检查字段及解析版本 | 首次建档、字段缺失或解析器版本升级 | 指定文档 | 不重复下载已经解析成功的说明书 |
| 票息明细 | 检查字段及解析版本 | 首次建档、字段缺失或条款变化 | 指定债券 | 不作为每次分析的前置接口 |
| 基金持仓 | 检查报告期 | 新季度报告发布 | 新报告期 | 不每次调用高权限接口或重解析年报 |
| 转股价完整历史 | 检查历史连续性 | 新公告、当前价与历史末值不一致或历史缺口 | 缺失区间 | 以历史公告/定期报告解析为主，不调用 `cb_price_chg` |
| 安全性 | 检查快照日期 | 安全性独立任务更新或财务依赖变化 | 复用安全性任务 | 不在单债分析里再建安全评级模型 |
| 周期和估值 | 检查发布日期 | 由现有每日主链更新 | 复用现有结果 | 不由单债分析重复调用全市场接口 |

说明：TTL用于限制重复请求，不代表数据在TTL内必然正确。只要数据库已经发现主档、公告或行情发生变化，即使TTL未到也必须刷新或重算。

### 6.2 股票专属依赖

| 数据组 | 分析时必须检查 | 实际外部刷新条件 | 增量范围 | 不需要每次拉取的内容 |
|---|---|---|---|---|
| 股票实时行情 | 是 | 腾讯共享缓存超过60秒 | 当前股票一次请求，可与相关证券批量获取 | 不保存分钟历史，不因价格变化重拉财务 |
| 股票主档与上市状态 | 是 | 首次建档、字段缺失、每周校验到期或已发现名称/状态变化 | 指定股票当前记录 | 不每次调用`stock_basic` |
| 日行情、估值和复权因子 | 是 | 缺少预期交易日或质量检查发现缺口 | 缺失日期并重叠最近14天 | 不重复拉全部上市历史 |
| 财务报表 | 检查报告期、公告日和版本 | 新报告公告、报告更正、关键字段缺失 | 新报告期及最近120天更正窗口 | 不在每次分析时重复请求全部报告期 |
| 财务指标 | 检查报告期、公告日和版本 | 新报告公告、报告更正或指标缺失 | 新报告期及最近120天更正窗口 | 不重复拉全部指标历史 |
| 分红送转 | 检查公告水位 | 新分红公告、方案状态变化或当前股息计算缺输入 | 新公告及更正记录 | 不每次重拉全部分红历史 |
| 业绩预告/快报 | 检查公告水位 | 新公告、修正公告或当前报告期缺失 | 新公告及短重叠窗口 | 不每次重拉全部历史 |
| 行业归属 | 检查有效期和来源 | 首次建档、每周校验到期或正式变更 | 当前有效关系 | 不在每次分析时请求行业接口 |
| 实际控制人 | 检查公告日和有效期 | 首次建档、每周校验到期或正式变更 | 当前关系及新公告 | 不在每次分析时重复抓取 |
| 公司事件 | 检查事件水位 | 新公告、游标落后或解析缺口 | 从上次成功日向前短窗口重叠 | 不全量扫描上市以来公告 |
| 历史分位与统计 | 是 | 上述数据库事实变化或公式版本变化 | 直接从数据库重算 | 不为重算再次访问上游 |

当前`refreshStockAnalysis()`已实现日行情14天重叠、财务120天更正窗口和事件增量，应保留这些能力；需要补的是刷新前的数据组门控，避免分红、预告、行业和控制人每次手动刷新都重复拉取。

### 6.3 基础快照与实时覆盖层

- 基础快照保存财务质量、历史统计、事件结论、债券条款等低频结果；
- 实时覆盖层只重算当前价、涨跌幅、当前市值、当前PE/PB、股息率、当前分位、转股价值、溢价率和双低等价格敏感字段；
- 实时行情变化不触发基础快照失效，也不要求每60秒写一份新快照；
- 交易日收盘事实落库后，以新的日行情水位使基础快照失效，并生成可复现的新版本；
- 页面必须同时返回`base_snapshot_at`、`quote_time`和`as_of_trade_date`，避免把不同时间的结果混为一体。

## 七、快照失效规则

股票和可转债都必须从“只看快照是否存在或公式版本”扩展为数据依赖判断。股票侧现有121份快照只有`{"source":"legacy_projection"}`，不能证明输入仍然有效；可转债侧现有`getConvertibleBondSnapshot()`只按`formula_bundle_version`判断，也不足以发现转股价下修。

满足以下任意共用条件时，基础快照标记为`needs_refresh`：

1. 主档或证券状态`updated_at`晚于快照记录水位；
2. 最新标准日行情或估值日期晚于快照行情水位；
3. 最新财报、报告更正、分红或业绩预告晚于快照对应水位；
4. 行业、实际控制人、股本或其他关键公司关系发生变化；
5. 事件事实或解析版本发生变化；
6. 计算公式版本发生变化；
7. 快照缺少关键水位，无法证明仍然有效。

股票还需在新财报版本、复权因子、股本及估值事实变化时失效。可转债还需在以下任意条件满足时失效：

1. `payload.basic.convert_price`与`current_conv_price`不一致；
2. 最新已生效转股价公告晚于快照记录的公告水位；
3. 最新评级公告晚于快照评级水位；
4. 条款、剩余规模、到期/退市状态或解析版本发生变化；
5. 转债或正股收盘行情日期晚于快照对应水位。

实时腾讯行情时间晚于快照不属于基础快照失效条件，只产生`live_overlay`。若实时行情缺失，则退回同一交易日的数据库收盘事实。

## 八、股票与可转债专属计算口径

### 8.1 当前转股价选择

优先顺序：

1. 已生效的交易所/巨潮正式转股价调整公告；
2. Tushare `cb_basic.conv_price`；
3. 数据库上一份有效主档值；
4. 旧分析快照只能作为降级展示，不能反向覆盖主档。

如果公告的生效日期晚于分析日期，则在生效前继续使用旧转股价，到达生效日后自动切换。

如果`cb_basic`与已生效公告不一致：

- 定点重拉一次；
- 写入`ops.data_quality_issues`；
- 以正式公告为准；
- 页面显示核验状态；
- 禁止无限重试。

### 8.2 实时计算

只有腾讯转债价和腾讯正股价同时有效，且行情日期一致时，才计算盘中数据：

```text
转股价值 = 正股价格 ÷ 当前转股价 × 100
转股溢价率 = 转债价格 ÷ 转股价值 - 1
双低值 = 转债价格 + 转股溢价率百分点
```

如果任一实时行情不可用，则整组退回同一交易日的Tushare收盘数据。禁止混用实时转债价格、旧正股价格或旧转股价。

### 8.3 失败时的展示规则

- 同交易日收盘数据完整：可以展示，并标明“收盘数据”；
- 只有上一交易日完整数据：可以展示，并标明具体日期和“数据过期”；
- 当前转股价无法核验：转股价值、溢价率、双低和各触发价显示“暂不可用”；
- 旧快照可以保留用于追溯，但不能显示成当前有效结果。

### 8.4 股票分析口径

- 财务分析必须按公告日使用当时已经公开的报告，禁止用未来公告回填历史结论；
- 报表更正时保留来源版本，并使依赖旧版本的快照失效；
- 当前市值、PE、PB、股息率和相关历史分位优先使用同一时点的实时价覆盖；实时价不可用时统一退回同一交易日收盘口径；
- Tushare `daily_basic.total_mv`、`circ_mv`入库前从万元统一换算为标准层的元，禁止直接与元口径财务字段相除；
- 复权收益必须使用与行情日期匹配的复权因子，复权因子变化后重算受影响区间；
- 股本、市值和每股指标必须使用匹配报告期或交易日的股本口径，不能把当前股本直接套到全部历史日期；
- 行业和实际控制人使用当前有效关系，并在页面标明数据有效日；历史回测使用当时有效关系，不能用当前关系覆盖历史。

## 九、每日任务补强

股票继续复用现有20:30持仓/自选刷新任务，不新增第二个股票分析调度。任务内增加：

1. 刷新前按股票、数据组读取游标，只拉缺失或过期内容；
2. 检查目标交易日的日行情、估值和复权因子是否齐全；
3. 检查新财报、报告更正、分红、预告、行业、控制人和公司事件水位；
4. 只使输入发生变化的股票快照失效并重算；
5. 保存每只股票各数据组的成功水位、空结果原因和失败原因；
6. 对失败数据组只进行一次定点补跑，仍失败则保留旧快照并告警。

不得新建第二个可转债全市场刷新任务，应在现有18:00主链中增加：

1. 保存`cb_basic`前后的字段差异；
2. 输出转股价、剩余规模、评级、到期/退市状态变化的证券清单；
3. 对转股价变化证券定点补取正式公告；
4. 使受影响的分析快照失效；
5. 继续使用同一份`cb_daily`写入单债行情、周期事实和估值输入；
6. 写入数据集游标和质量结果；
7. 只对持仓、自选、已有快照或最近访问的转债预生成新快照，其余转债在首次访问时按需生成。

现有08:00完整性检查应从“周期、估值是否完成”扩展为：

- `cb_basic`主档同步是否完成；
- `cb_daily`是否达到预期交易日；
- 转股价变化证券的公告核验是否完成；
- 周期和估值是否完成；
- 受影响快照是否已失效或重算；
- 最后成功日期是否落后目标交易日。

任务失败后只允许一次定点补跑；仍失败则记录质量问题并告警，不无限重试。

## 十、同步游标和质量问题

继续复用`ops.sync_cursors`。单股/单券数据集使用可区分证券的`scope_key`，例如：

```text
scope_key = stock:600519.SH
dataset_code = stock_daily

scope_key = stock:600519.SH
dataset_code = financial_statements

scope_key = stock:600519.SH
dataset_code = company_events

scope_key = convertible_bond:357
dataset_code = cb_basic

scope_key = convertible_bond:357
dataset_code = conversion_price_announcements

scope_key = convertible_bond:357
dataset_code = cb_daily
```

建议新增的问题类型，但不新增问题表：

| 问题类型 | 含义 |
|---|---|
| `snapshot_input_mismatch` | 快照输入与当前主档不一致 |
| `snapshot_watermark_missing` | 快照缺少关键输入水位，无法证明有效 |
| `financial_version_mismatch` | 股票快照使用的财报版本已被更正 |
| `market_partition_incomplete` | 股票/转债预期交易日行情或估值分区不完整 |
| `corporate_action_stale` | 分红、预告或其他公司行动水位落后 |
| `conversion_price_source_conflict` | 公告与`cb_basic`当前价冲突 |
| `conversion_price_history_gap` | 当前价变化但历史链缺少对应记录 |
| `critical_dataset_stale` | 关键数据集超过预期更新时间 |
| `quote_pair_unsynchronized` | 转债与正股行情无法组成同口径数据 |
| `scheduled_refresh_failed` | 主链或补跑失败后仍未恢复 |

问题恢复后将对应记录更新为`resolved`，保留发现时间和恢复时间用于追溯。

## 十三、验收标准

### 13.1 湘佳转债案例

- 数据库主档为13.80元、旧快照为21.03元时，普通查询必须返回`needs_refresh`；
- 登录用户刷新后，页面转股价必须为13.80元；
- 转股价值和溢价率必须使用同一时间的转债价、正股价和13.80元转股价重新计算；
- 旧快照不得继续显示为最新结果；
- 最新转股价调整记录能够追溯公告日、生效日和来源。

### 13.2 股票分析

- 现有仅含`legacy_projection`水位的股票快照必须被识别为待补水位，不能永久视为最新；
- 新财报或更正报告入库后，相关股票基础快照必须失效；
- 新交易日行情、估值或复权因子入库后，相关历史统计必须重算；
- 腾讯行情只覆盖价格敏感字段，60秒内重复分析不重复访问上游，也不重写基础快照；
- 分红、预告、行业和控制人未变化时，重复手动刷新不再次全量请求；
- 实时行情不可用时，同组指标统一退回同一交易日收盘口径；
- 20:30任务失败时保留最后成功快照并记录具体失败数据组。

### 13.3 全体可转债对象

- 全部已有分析快照中，快照转股价与当前主档不一致数量为0；
- 主档更新时间晚于快照但未标记失效的数量为0；
- 已生效转股价公告与主档不一致且未记录质量问题的数量为0；
- 转债和正股实时行情不同步时，不计算实时溢价率；
- 同一交易日重复刷新不产生重复事实记录；
- 刷新失败不覆盖最后成功快照；
- 每只转债同一数据组在TTL内不会重复调用上游。
