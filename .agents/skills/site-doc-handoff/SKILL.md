# 存在小站文档更新与交接

适用：本仓库的文档修改、任务收尾、跨 Agent 或跨对话交接。
不适用：普通答疑（不产生文档）、纯代码修改（走各自任务流程）、生产发布（用 site-release-closeout）。

## 前置

1. 在 `portfolio-server` 仓库根操作。工作区父目录不是仓库，不要在那里改。
2. 记下当前分支、HEAD 和 `git status`，确认没有别人的未提交改动混进来。

## 流程

1. **定位权威位置**：读 `AGENTS.md` → `docs/知识索引.md` → `governance/knowledge-map.json`，按任务描述和实际改动文件匹配路由，只读命中的 `read` / `readSections`。不要全量读文档。
2. **判断必要性**：先搜已有结论，确认是新增、就地更新还是归档。同主题禁止另起第二份文档；架构现状写 `docs/技术架构.md`，机制细节留原专项方案，过程和历史不进正文。
3. **原位改正文**：改当前结论段本身，不在顶部追加日期流水。旧结论被替代要写明替代关系和生效版本；跨时点内容标清「当时 / 现在」。
4. **同步摘要与索引**：正文改了，知识索引对应摘要行、技术架构「最后核对日期」、必要的 `knowledge-map` 路由一起核对。
5. **跑门禁**：`npm.cmd run check:knowledge`（Windows 固定用 `npm.cmd`）。涉及代码、依赖、数据库、配置或部署行为时，还要 `npm.cmd run test:all`，外层超时至少 240 秒。
6. **语义复核**：门禁只证明结构和引用没坏。逐条确认：旧结论是否已被替换、摘要与正文是否同口径、「已部署 / 未部署」是否自相矛盾、证据能否定位。
7. **回填任务卡**：按 `docs/tasks/README.md` 写清实际改了哪些章节、证据、未验项和下一步。

## 必须交代

- 本次改了哪些文档的哪些章节，为什么；
- 哪些内容判断为「无需修改」，依据是什么（不接受只改日期凑差异）；
- 未验证的边界，以及谁接着验；
- 门禁的实际输出。

## 边界

- 门禁绿不等于语义正确，也不等于生产已验收。
- 不要把历史原文直接删掉：迁到对应的 `*历史记录_截至YYYYMMDD.md`，保留原证据与未验项。
- 多 Agent 协作时写前重读目标段落，局部合并，不覆盖他人增量。
