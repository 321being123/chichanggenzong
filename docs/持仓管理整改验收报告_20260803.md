# 持仓管理整改验收报告

> 验收日期：2026-08-03  
> 验收对象：提交 `cad9058`（版本 0.4.3.8）  
> 验收范围：持仓总览、交易录入与删除、持仓重算、现金重算、现金流、历史净值、数据迁移与一致性审计  
> 验收方式：代码只读核查、自动化测试、数据库结构核查、本地数据一致性审计；未启动浏览器、未修改业务代码和数据

## 一、验收结论

**验收不通过，暂不建议发布。**

本次整改已经完成了服务端交易事务、普通超卖校验、成交金额统一计算、移动加权成本、交易日期拆分和审计脚本等工作；项目现有自动化测试也全部通过。

但是，当前仍有 4 项阻断级问题：

1. 新交易接口没有同步账户数据版本号，旧页面仍能把刚写入的交易、持仓和现金流整体覆盖掉。
2. 持仓导入和直接编辑仍绕过交易账本；服务端又从 0 开始重放交易，遇到期初持仓或历史交易不全时会改错持仓。
3. 同日现金流净值边界逻辑实际没有生效，且前端快照字段未持久化到数据库。
4. 卖出校验没有账户级或持仓级并发锁，两笔同时卖出可能都通过校验并造成超卖。

此外，本地数据审计仍发现 **23 项严重问题**，不满足“整改后审计归零”的发布条件。

## 三、阻断级问题

### P0-1 新旧保存通道使用两套版本号，仍会覆盖交易账本

交易账本接口写入 `positions`、`trades`、`cash_flows` 后，只更新了 `accounts.version`，没有更新 `account_data.version`、`pos_version`、`trade_version`、`cashflow_version`。

但页面加载和旧的全量保存接口仍以 `account_data` 中的版本号做冲突校验，并继续采用“先删除、再批量插入”的方式保存持仓和交易。

因此会出现以下情况：

1. 页面 A、页面 B 同时打开，拿到相同的 `account_data` 版本号。
2. 页面 A 通过新账本接口新增交易，数据库交易和持仓已更新，但 `account_data` 版本号未变化。
3. 页面 B 使用旧快照执行一次普通全量保存，版本校验仍然通过。
4. 页面 B 删除并重建交易、持仓表，把页面 A 的新交易覆盖掉。

涉及位置：

- `server/services/tradeLedger.js:227-234`
- `server/db/accounts.js:53-60`
- `server/db/accounts.js:152-170`
- `server/db/accounts.js:196-224`

**整改要求：** 所有账本写操作必须在同一事务中同步提升对应的 `account_data` 总版本和数据集版本；更彻底的做法是禁止旧全量保存接口再写交易、持仓、现金流和净值表。

### P0-2 期初持仓没有入账，第一次交易可能把现有持仓改错

智能导入中的“持仓”仍直接修改 `data.positions`，然后调用全量 `saveData()`，没有生成期初持仓、持仓调整或成本调整事件。

服务端交易重算却只读取交易表，并从 `qty = 0` 开始重放。对于“有现有持仓、但历史交易不完整”的账户：

- 第一次买入后，持仓数量可能被改成“本次及现有交易净数量”，原期初数量丢失；
- 第一次卖出后，可能把整个持仓删除，而不是从真实持仓中扣减；
- 后台净值重放与页面当前持仓会继续不一致。

涉及位置：

- `public/shared/core-trade.js:603-638`
- `server/services/tradeLedger.js:67-95`

本地审计已经发现 1 个账户存在“持仓数量与交易净数量不一致”，说明这不是纯理论风险。

**整改要求：** 在启用交易重放前，必须为所有存量账户建立明确的期初日期、期初持仓、期初成本和期初现金；持仓导入和直接编辑必须转成可追溯的期初或调整事件，不能继续绕过账本。

### P0-3 同日现金流净值修复无效

前端计算同日现金流时，外层条件是：

```text
cf.date > lastDate && cf.date <= today
```

当当天净值已存在时，`lastDate === today`，所有同日现金流都会先被外层条件排除，后续的快照时间边界判断根本不会执行。

同时存在两个持久化断点：

- 前端把边界写入 `navHistory[].snapshot_at`，但 `nav_history` 表没有该字段，保存和加载均不会保留它；
- 迁移 044 增加的是 `account_data.nav_cash_cutoff`，账本服务只写交易日期，页面加载也没有读取并使用该字段。

页面刷新后，同日快照边界必然丢失。

涉及位置：

- `public/shared/core-returns.js:121-150`
- `server/db/accounts.js` 的 `nav_history` 查询与写入逻辑
- `server/services/tradeLedger.js:129-134`

**整改要求：** 只保留一套可持久化的快照时间边界，按完整时间戳比较现金流；补充“当天先记净值、再入金、再记净值、刷新页面后再次记净值”的端到端测试。

### P0-4 并发卖出仍可能超卖

`applyTrade()` 虽然在数据库事务中执行，但读取可卖数量时没有锁定账户或持仓行，也没有使用数据库条件更新。

两笔卖出请求同时到达时，可能同时读取到相同持仓、同时通过校验，然后分别写入卖出交易。普通顺序测试无法发现该问题。

涉及位置：

- `server/services/tradeLedger.js:145-169`

**整改要求：** 同一账户的交易写入必须串行化，可采用账户行 `SELECT ... FOR UPDATE`、事务级 advisory lock 或等价的数据库原子方案；必须补充两笔并发卖出总量超过可卖数量的测试，且只能有一笔成功。

## 四、其他未完成项

### P1-1 清空交易会立即制造账实不一致

`clearTrades()` 明确只清交易，不处理持仓；现金却会按“没有交易”重新计算。执行后，持仓仍存在、交易依据消失、现金发生变化，总资产会出现跳变。

涉及位置：`server/services/tradeLedger.js:296-309`。

处理建议：统一禁止清空，或把该操作定义为带期初结转的账本重建，不能只删交易表。

### P1-2 定时净值任务仍会漏掉带时间的当日交易

`server/jobs/navSnapshot.js` 仍使用 `t.date > date` 比较完整交易时间和纯日期。例如 `2026-08-03 10:00 > 2026-08-03`，当天交易会被排除。

涉及位置：`server/jobs/navSnapshot.js:57-75`。

迁移和 `replayNav.js` 的修复没有同步到定时快照任务，日期整改不完整。

### P1-3 删除、清空后的历史净值没有形成重算闭环

新增或删除交易只是写入 `nav_cash_cutoff` 标记，当前没有稳定消费者执行“从受影响日期开始重算”。删除现金流和清空交易也没有完整触发历史净值重算。

结果是当前现金或持仓可能已变，但历史净值仍是旧数据。

### P1-4 交易去重只在前端，服务端无法防止重试和并发重复

前端按证券、日期、方向、价格、数量检查重复，但服务端仍可接收业务内容相同、ID 不同的交易。接口重试、并发请求或其他客户端均可绕过前端去重。

本地审计已经发现 2 组重复交易，其中还包含整改调试账户。

处理建议：服务端对导入批次建立幂等规则，并为批次号和业务唯一键建立合适的数据库唯一约束。

### P1-5 数据库约束与迁移注释不一致

迁移 042 的注释声明校验 `direction/quantity/price/amount`，实际数据库仅存在方向约束：

```text
chk_trades_direction CHECK (direction IN ('buy','sell'))
```

当前没有数据库约束保证价格和数量为正、交易日期格式合法、金额与价格数量关系正确，也没有外键把交易、持仓、现金流统一关联到不可变账户 ID。

### P1-6 持仓直接编辑、删除和现金流新增仍走旧全量保存

交易新增和删除虽然接入了账本服务，但持仓编辑、持仓删除、持仓导入、现金流新增等入口仍调用 `saveData()`。系统目前是“部分接口化、部分全量快照”的混合架构，尚未达到统一写入口。

## 六、测试缺口

新增的 11 项账本测试只覆盖“空账户、完整交易历史、顺序执行”的正常路径，尚未覆盖以下关键场景：

1. 存量期初持仓没有完整交易历史。
2. 两笔卖出并发提交。
3. 新账本接口写入后，旧页面执行全量保存。
4. 同日净值与现金流在页面刷新后的持久化结果。
5. 定时 `navSnapshot` 对带时间交易的处理。
6. 清空交易后的持仓、现金、净值一致性。
7. 导入接口重试与相同批次幂等。
8. 整改后真实数据审计为零。

## 七、复验准入条件

以下条件全部满足后再申请复验：

- [ ] 所有持仓、交易、现金流写操作使用同一版本体系，旧页面无法覆盖新账本写入。
- [ ] 同一账户的交易写入有数据库并发锁，并发超卖测试通过。
- [ ] 存量账户已经建立期初持仓、成本和现金，持仓编辑与导入改为账本事件。
- [ ] 同日现金流快照边界写入数据库，刷新页面后结果不变。
- [ ] `replayNav` 与 `navSnapshot` 统一使用 `trade_date` 和明确的时间边界。
- [ ] 删除交易、删除现金流、清空或重建账本都会重算受影响日期后的净值。
- [ ] 服务端具备交易导入幂等和重复交易防护。
- [ ] 补齐价格、数量、日期等数据库约束，并使用不可变 `account_id` 关联业务表。
- [ ] 本地数据中的 23 项严重问题经过人工确认、备份和修复，审计退出码为 0。
- [ ] 删除整改调试账户或将其迁移到独立测试数据库。
- [ ] 新增上述测试缺口的自动化用例，完整测试继续保持全绿。

## 八、最终判定

本次整改属于“关键服务端账本能力已开始落地，但架构尚未闭环”。现阶段可以继续在本地整改和测试，**不能按持仓管理整体整改完成进行验收签字，也不建议直接发布到正式环境**。
