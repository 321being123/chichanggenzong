# 知识库公共规则

> 状态：现行公共规则。最后核对：2026-10-30（第11节持续维护、11.4月度复盘与规则沉淀、11.5架构和数据获取审查；原知识录入与协作规则保留，不代表业务或生产重新验收）。
> 适用：本仓库全部开发人员与 Agent。新增、修改、引用或归档项目知识前必须遵守；用户最新明确指令及项目授权边界优先。
> 本文是知识治理细则的唯一维护位置。AGENTS保留强制入口，技术架构2.1保留兼容指针；两处不再复制本规则全文。

## 0. 每次任务的最小必读

- 遵守已加载的AGENTS和用户最新指令；先看索引“快速入口”，只提取命中的路由，不默认全文加载索引、路由表和架构。
- 知识写入前读本节，再按本次动作读相关细则：普通录入2—4/9节，新增记录加5节，多Agent协作加6节，替代/归档加7节，调整结构/路由读1/8节。
- read文件必须核对“当前摘要＋相关完整章节/约束及直接依赖”，不默认通读整篇；不能把搜索片段、截断输出或目录当作读完规则。
- 优先修改原权威位置；状态带日期/范围/证据，原文、授权和未完成项保留；正文先于目录/索引，写前重读最新目标段。
- 根因不明、跨模块、数据/权限/安全/任务/部署风险，或发现冲突/引用缺失时扩大阅读，不能为节省Token跳过必要检查。
- 本会话已完整读取且未变化的章节复用；文件或指令变化时只补读受影响部分。压缩后规则缺失则重新读取，不把私有记忆当事实来源。

## 1. 结构设计与权威边界

沿用现有目录，按“公共规则 → 主题索引/机器路由 → 当前说明 → 证据与历史”组织。每个事实只有一个完整维护位置，其他地方写必要摘要和准确链接。

| 内容 | 唯一完整维护位置 | 不应放入 |
|---|---|---|
| 知识如何写、如何核对与协作 | 本文件；AGENTS仅保留强制入口和业务红线 | 技术架构的业务章节、私有记忆 |
| 去哪里找、当前关键边界 | 知识索引；机器匹配由knowledge-map维护 | 大段参数、执行过程和测试流水 |
| 当前技术机制、字段、读写合同 | 技术架构原业务章节 | 发布历史或任务卡作为唯一解释 |
| 功能目标、设计取舍、实施验收清单 | 原专项方案；重要长期技术选择另按ADR体例记录 | 同主题新建第二份方案、将设计直接当实现 |
| 重大或重复故障根因、同类范围及防复发 | 原Incident；没有同根因记录才新建 | 规则文件堆事故全过程 |
| 某次发布的版本、提交、授权、步骤结果 | 生产部署历史记录；功能专项证据回原方案/事故 | 现行部署步骤或全项目架构顶部 |
| 当前部署方法与环境操作边界 | 生产部署流程；本机环境按本地验证交接文档 | 旧安装示例代替现行步骤 |
| 跨会话未完成工作 | 原active任务卡；任务目录只放摘要和链接 | 多份TODO清单、私有记忆独占待办 |
| 用户可见版本、生成资料、分享材料 | 既有变更记录、生成文件、分享原文件 | 当作现役规范或人工修改生成结果 |

这是一套职责划分，不是要求新建上述所有文档。现有路径保持兼容；不为目录整齐批量移动、改名或重写方案。确需拆分大文档时，先明确独立主题与原入口不能承载的原因，再在本次范围内迁移、保留指针并修正路由。

技术架构只保留稳定机制和必要边界；案例计数、逐版本过程回证据正文。专项方案内部把“当前说明”“设计/验收清单”“历史执行记录”分开，已经被实现替代的设计必须标出偏差，不能整份盖章为全部完成。

## 2. 写入前的六项判断

1. **必要性**：是否改变当前行为、长期约束、数据口径、可复用根因或未完成边界？只有成功日志、临时计数或重复验收时，不新增规则或架构正文。
2. **归属**：先按上表及机器路由找到原位置；搜索主题、字段、规则编号和旧结论。没有找到，才判断是否新建。
3. **替代关系**：明确是原位更新、补证、纠错、合并、归档或不写；先修正旧当前结论，不能仅在文首/文末追加一段相反的“最新进度”。
4. **保留边界**：根因、来源原文、用户授权及范围、失败记录、生产验收和真实未完成项必须保留。不能因日期旧、活动告警为0或任务成功就删除。
5. **影响引用**：核对索引、目录、read/update、Markdown链接及证据锚点。历史记录不进入默认read；迁移前先确认消费者。
6. **交付结果**：说明新增为何必要、替代/归并/归档了什么、哪些未验项保留。不为证明做了判断再新建一份流水。

不变结论不反复复制。门禁要求同步核对时，优先复用已有说明；确需记录，局部注明核对范围与结论不变，不用反复改日期、堆回执或虚构实现凑文件差异。若路由持续要求无关文件变更，应核对并局部收窄路由，不能降低真实同步要求；本规则本身不改变检查脚本的判定方式。

## 3. 录入格式与最小信息

新建文档及本次实际修订的当前摘要采用下列信息；旧文档在被修改时逐步补齐，不批量刷头部。没有证据的字段写“待核验”，不能推测填写。

```md
文档职责：当前机制｜专项方案｜决策｜事故｜任务交接｜历史证据
截至日期及范围：YYYY-MM-DD；本次实际核对的章节、对象或环境
当前结论：一句话说明已确认行为或实际达到的阶段
权威与证据：原文档/章节或稳定锚点；涉及发布时附版本与提交
未验证/未完成：具体缺口、下一步；没有则按核对范围说明
```

- “最后修改”不等于“最后核对”。只改一节时写清范围，不把全篇日期刷新成所有事实今天都重新验证。
- 当前摘要控制在5行或一个简短表格单元格；索引同主题只留一行。大段参数、测试数字、槽位、哈希及过程写入唯一证据段。
- 一条机制说明只讲清规则、适用条件、失败边界与对应实现/证据，不把多个无关主题堆在同一段。
- 测试结果写执行日期、对应代码范围、检查名称、结果和未覆盖范围；不是本次执行的，注明“已有回执记载”，不得写成“本次实测”。
- 数量必须写明对象集合、业务日/报告期、统计含义。不同日期、全量/定向、元数据/详情的数量不能直接比较。
- 结论引用仓库内可长期找到的摘要、原文来源或证据锚点。忽略目录中的探针、截图、日志可辅助核对，但不能成为未来无法恢复的唯一结论来源。
- 密码、Token、私钥、个人数据和敏感连接串不进入文档、提交或回复；敏感配置仅使用环境变量名和受控位置说明。

## 4. 状态必须分开表达

文档的生命周期、功能实施和数据结果是不同维度，不能用一个“已完成”概括。

| 维度 | 允许表达 | 判定边界 |
|---|---|---|
| 文档生命周期 | 现行、待评审、历史、已替代（附替代位置） | 历史记录保留当时事实；不能作为今天的操作指令 |
| 功能实施 | 待实施、已本地实现、本地已验证、已提交/推送、已部署、线上专项已验证 | 只写实际达到阶段；代码存在不等于原方案全部通过，已部署不等于真机或专项通过 |
| 任务/数据 | 执行成功、质量恢复、运营确认、正常等待、仍缺失 | 按原槽/日期/对象/字段证据区分；acknowledged不等于数据恢复，NULL不等于零 |

实现与部署按本地代码和生产版本分别描述，不能写模糊的“已修复”却不说明环境。只有部署记录，没有目标接口/任务等专项证据时，只能写已部署。

“待核验”必须附不确定点、已有证据和下一步。旧授权不会因换Agent自动失效，也不能被扩大；记录授权日期/指令摘要、对象、模式和生产写入边界，禁止从一处修复推断获得全量授权。

原文证据、当前实现与生产回执各自证明不同问题：来源证明字段含义，代码证明实现机制，运行回执证明某版本在某范围的实际结果。不能靠提交说明、文档修改时间、私有记忆或测试绿灯跨维度裁决。证据矛盾时在原位置标待核验，保留双方证据，不按“最后写入者”定论。

## 5. 各类记录怎样写

| 类型 | 必须有 | 不应有 |
|---|---|---|
| 当前机制 | 适用条件、数据/调用边界、失败处理、实现位置 | 连续版本叙事和单次任务计数 |
| 专项方案 | 已有/复用/缺口、用户范围、架构对齐、分项实施与验收状态、未闭环 | 未实施设计冒充现役；重新写一份替代用户原方案 |
| ADR | 背景、决策、取舍、影响、重评条件、状态 | 顶部不断新增某次发布日志 |
| Incident | 根因链、同类核查、修复/回归证据、防复发与遗留 | 只有症状或一次成功就称根治 |
| 发布回执 | 版本/提交、实际授权与范围、执行结果、专项证据、剩余项 | “本次”不带日期；本地测试冒充生产验收 |
| 活动任务卡 | 当前目标、授权边界、阻塞、证据位置、下一步 | 将旧阶段待办长期当今天待办；复制完整实施过程 |

ADR、Incident、任务卡沿各目录README原模板；本文件规定共同字段，不另建第二套模板。普通短任务不强制建卡；由另一对话整合发布的改动属于跨Agent交接，按第6节建卡或续写原卡。普通修复不强制新建ADR/事故；同根因问题优先补原记录。新编号先检查全部文件名，既有INC-0002/0003同号异题按完整文件链接引用，不自动重编号。

## 6. 多Agent写入与整合顺序

用户工作方式固定为：**一个任务一个开发对话；需要发布时另开对话，提出“整合所有最近改动并部署”**。无需常驻整合对话，也不要求用户搬运各聊天记录。已有任务卡承载跨对话交接，Git与原权威文档提供证据，不新增平行任务系统。

### 6.1 开始任务与发现其他任务

1. 先确认仓库、Git HEAD、未提交改动、已有 worktree/分支及各自 `docs/tasks/active/` 的任务卡。开发者只读其他任务的目标、文件范围和资源占用，不全读其聊天/排错历史；同机用 `git worktree list --porcelain` 查目录，保留分支的交接用 Git 读取。以规范化仓库公共Git目录（`git rev-parse --git-common-dir`解析后的绝对路径）、任务卡相对路径及创建基线区分任务；克隆/异机仓库还须核对远端与原任务标识。新分支继承的旧卡不是新任务或新占用，以卡内负责分支/交接提交去重，不按看到的卡片份数计数。工作目录不存在、异机分支未推送或无法访问时记录缺口，不假定没有其他任务。
2. 默认复用适合本任务且未被占用的独立 worktree，否则优先用宿主原生工具创建，仅无该工具时手工创建；已隔离的目录不重复套建，子模块不当成独立任务worktree。手工建在仓库内须先核对目录被Git忽略；不复用另一活跃任务的目录，不在共享目录切换分支来冒充隔离。基线须包含现行协作规则，旧分支先同步规则；规则尚未提交时先记录接入阻塞，不能声称新worktree已自动获得规则。主目录留给统一整合/验收；新 worktree 不包含主目录未提交改动、.env、依赖、虚拟环境或本地数据，须按任务核对环境和基线已有失败，依赖其他任务时先查清归属和提交依赖，不直接复制整份工作区。
3. 每个有待统一发布改动的任务，首次写业务文件前在自己的工作目录创建或续写唯一任务卡；同日同名先核对既有卡，避免误认任务。按 `docs/tasks/README.md` 登记负责人、工作目录/分支、基线、允许修改范围、依赖及资源。任务卡早提交到自己的分支；不为登记而并发改主目录总表。
4. 文件范围重叠先判断是否涉及相同接口、字段、算法或正文段落；真正耦合的修改明确先后及依赖提交，由一个任务先交付，另一个基于它继续。区分“可先开发”和“可独立发布”，不兼容的接口/迁移与调用方登记为必须一起发布；依赖缺失、循环依赖或上游交接提交变化时重新核对，不能沿用旧待整合结论。独立目录能隔离写文件，不能消除逻辑冲突；未协调前暂停重叠部分，继续不依赖它的工作。

### 6.2 并行时的资源边界

| 对象 | 开发对话的边界 |
|---|---|
| 代码、依赖与Git | 只在自己目录修改、安装依赖、精确暂存和提交；不操作其他目录的index，不在主分支并发合并/推送，不用全局reset/clean/stash收走他人修改。worktree仍共享多数refs及默认仓库配置，开发任务不擅改remote、core.hooksPath、共享钩子或执行setup:hooks/全局配置/强推/他人分支维护；需要时登记交由整合负责人处理。 |
| 公共代码与文档 | 在自己的分支局部更新原文件；写前重读最新段落，保留双方有效增量。公共组件/接口变更登记受影响任务，发布对话统一合并共享规则、架构、索引及路由，不能整文件选“我的版本”覆盖。 |
| 端口与进程 | 按任务卡登记独立PORT，启动前核查实际监听者；只重启可核实属于本任务的PID。3000端口共用验收服务由发布对话管理，禁止全局结束Node/Python/PG进程。 |
| 数据库与文件数据 | 写数据、迁移或重置测试使用任务独立开发/测试库与DATA_DIR，不能同时改共用portfolio库。测试库按现有防护保留test/migtest标识，统一入口设置独立PGTESTDATABASE；只改PGDATABASE不能假定测试库已隔离。配置从本任务受保护的.env读取，不提交密钥、数据或备份。 |
| 登录态与Redis | 不同端口不能隔离同主机名Cookie；本项目使用默认会话Cookie及Redis的sess:前缀。运行验收使用独立Cookie容器，浏览器仍按授权和低性能规则执行；配置Redis时另核对独立逻辑库，未配置则保留现有内存模式，不为隔离另装Redis。未隔离时顺序验收，不共享登录态、不清空共用缓存，不假称已支持会话前缀环境变量。 |
| 测试与本地运行 | 继续遵守原测试要求和低性能模式；耗资源全量测试同机顺序执行，先核对实际运行进程及占用，同一测试库不能并跑。未获资源就记录等待，不把未执行写成通过；目录独立不代表电脑性能独立。 |
| 调度与外部接口 | 本地Web保持NODE_ENV=development、DISABLE_SCHEDULER=1，测试进程由现有入口设置NODE_ENV=test，不启动生产Worker。优先复用已入库数据/原文缓存；相同来源及窗口的必要增量只由一个任务经现有受控入口采集落库，其他任务复用结果，不各自重复拉取。 |
| 版本与生产 | 开发对话留下用户可见变更摘要，发布对话统一递增版本、生成发布记录、部署及反馈回写；已有生产写入授权边界不因多Agent扩大。 |

任务卡用于声明占用，不能作为互斥锁；登记声明时间、最近检查点和实际释放依据。检查点在改范围、交接、中断/退出前更新，不为此新建定时心跳。卡片陈旧、对话结束或约定占用时间到期均不等于资源已释放；接手先核对进程、数据库活动、未提交文件和分支提交，保存原进度并登记接手依据，无法确认时停止该项操作。写库、重启、重测试前仍核对真实环境；Git的worktree lock只防止元数据被清理，不锁业务文件或发布操作。无法满足运行条件的任务保持待验收，不抢用他人环境。通用服务只保留一套；独立库和工作目录用于开发隔离，不新建业务事实链路。

### 6.3 文档随任务录入与交接完成条件

1. 开始时登记本任务需要核对/更新的权威位置。实施中形成已确认结论、范围变化或阻塞时及时更新原正文/任务卡；中断、换对话前保存当前进度，不能等部署才首次录入。
2. 开发交接前在自己的分支完成代码、专项正文、架构对应章节及路由要求的必要更新，明确“本地实现/验证、未部署”。顺序为**原正文和当前摘要 → 事故/任务目录 → 知识索引 → 必要路由 → 检查及Git差异复核**。整合者负责合并公共内容，不代替开发者事后回忆事实。
3. 交接写清任务代码提交/依赖提交、实际文件、测试日期/范围/结果、相关文档章节、未验项和生产影响；不贴完整聊天或重复原文。每项文档填写“已更新及位置”“核对后无需改及原因”或“待补及缺口”。有待补、归属未明、依赖未齐或必需验证未通过时不能标“待整合”。
4. 开发交接状态依次为“开发中 → 待整合 → 已整合待发布 → 已部署待验收 → 已验收”，阻塞单列原因；这是交接阶段，不替代第4节功能/数据状态。代码与文档提交后才进入待整合，最终交接提交可通过分支HEAD查询，不要求把提交自身哈希写进自身内容。异机交接还须推送自己的任务分支；不得代替统一发布推送master。
5. 待整合后冻结本次交接提交。新增改动另行标回开发中并登记新提交，发布对话仍只处理已固定的交接范围；不自动吸收开发中的后续变化。发布/专项未验项继续保留，不能因已部署就关闭任务或删除分支/worktree。

### 6.4 新发布对话的固定动作

1. 以当前实际运行SHA/版本和成功发布/回滚回执交叉确认基线，核对主目录、可见worktree/任务分支及任务卡；比较提交和差异发现“已交接未发布”“进行中/阻塞”“无卡/归属不明”“已发布”四类。不能按文件时间、聊天结束时间或卡片状态单独决定；squash/cherry-pick会改变提交号，须核对原任务提交→整合提交→运行SHA的映射及实际代码，不能仅凭祖先关系判漏发或重发。旧分支也可能有漏发任务；不可访问的异机/远端内容须明确报告。
2. 在现有任务卡/本次发布记录固定候选任务、交接提交、依赖、纳入/未纳入原因及截止点。无卡的旧改动先用代码/测试/原文档补证据，不猜完成；当前共用主目录的混合改动先确认归属和可分离性。未经核实不能把“所有最近改动”解释为git add全部文件；有遗漏不得宣称全量完成，用户明确要求全量而有阻塞时不得擅自改为部分发布。
3. 同一批次只由一个发布对话负责，在原任务卡/发布记录注明负责人及整合目录；另一个发布对话发现正在整合时先等待，不并发操作master或整合目录。确认资源归属后逐项合并固定提交与对应文档，核对公共接口、迁移编号/顺序、依赖锁文件、共享资源和权限。冲突必须保留各任务有效行为并重验；主目录有他人未提交修改时不覆盖、不全局暂存，可用干净整合worktree完成核验，再按现有正式发布要求推送master。生产仍使用已有发布锁，该锁不保护本地Git整合。
4. 合并后复核各任务原验收条件和跨任务影响，运行原要求的全量测试与知识检查，绑定被测提交/实际差异及环境，再统一定版，按《生产部署流程》执行；已有单任务测试不能代替最终发布树验证。测试后代码、依赖或迁移变化须按原门禁重验，纯版本元数据按AGENTS既有例外检查；推送与持生产发布锁后重新核对远端/实际运行基线，出现其他发布变化先重新对齐，不强推覆盖。最后以实际发布SHA逐项回写代码部署、线上专项验证、文档状态和失败/剩余范围；回滚保留失败证据并将受影响任务恢复为待发布，专项未过不标已验收，未纳入任务继续保留。
5. 发布对话只加载当前批次任务卡摘要、相关正文及必要代码/证据；按任务分批核对，当前批次/已整合提交/待办写回原记录。换新对话读取这些指针和实际Git继续，无需累积所有开发聊天。已有任务记录找不到证据时标待核验，不靠摘要补猜。

### 6.5 现有现场与约束能力

这些是Agent必须执行的协作流程；目前没有新增任务发现程序、全局资源锁、自动文档锁或语义合并功能，check:knowledge也不能证明交接完整。新对话按入口执行；已运行的旧对话、旧worktree和未提交改动不会自动迁移或停笔，接入时先确认归属并补交接，不能宣称已隔离。流程不授权向其他聊天发消息或清理他人分支/数据库。平台私有Memory仍只做原规则允许的接续指针。

## 7. 证据引用、替代与归档

- 同一实测段只维护一份完整原文。优先留在原专项/事故；当前合同需要放架构时，架构保留机制，事故保留案例证据。其他位置用摘要和精确链接，不复制整份回执。
- 已引用的evidence锚点保持稳定。发现证据记录错误时，注明更正原因、原结论及替代证据，不能静默改写成原先就成功；新的一次执行建立新的证据段，不覆盖旧执行。
- 当前事实改变时先更新原段落，再同步摘要；旧过程有审计价值则标历史或归档，没有独立价值的重复描述合并为引用。没有最终证据的旧待办继续跟踪。
- 历史文件写明覆盖日期、职责和当前入口。不要把新日期内容继续塞入标题“截至旧日期”的归档；需要续档时建立下一期归档并保留旧文件和链接，不为升级日期批量改名。
- 任务结束前先把结论回写权威位置，未完成项明确去向，再按tasks流程压缩归档；移动/删除仍遵守项目授权要求，不自动清场。
- 文件移动、合并或拆分必须同时核对链接、锚点、目录和read/update。附件不存在时保留原路径并标缺失，不留下假装可用的链接，不编造恢复结果。

## 8. 阅读与路由管理

### 8.1 三层读取

| 层级 | 读取范围 | 何时需要 |
|---|---|---|
| 短入口 | 已加载AGENTS、本规则0节、索引快速入口、匹配路由 | 每次任务；已在有效上下文中的内容不重复全文读 |
| 主题正文 | read文件当前摘要、本次完整相关章节、直接依赖；按readSections定位 | 已明确目标后，执行前读；多个路由的重叠章节合并一次 |
| 扩展证据 | 原方案验收、事故根因、指定历史/代码/运行回执 | 根因或边界不清、跨模块/高风险、摘要冲突、证据不足时；按问题扩展而非全库扫读 |

read表示必须查阅该文件的相关当前依据，不等于每篇必须从头到尾读取。AGENTS或用户明确要求全文/指定章节时照做；readSections只提供候选起点，不是阅读白名单，不降低强制约束。

先按任务描述匹配主题，再按实际变更路径补匹配；合并read和checks，避免同一文件被多个路由重复加载。不要仅因“接口/服务/任务”等泛词就加载全部模块，也不能只凭短描述漏掉真实影响。

### 8.2 如何定位与停止

1. 先查当前摘要与标题；用rg在相关文件内定位字段、错误、路由或实现符号，再读取命中的完整章节及必要上下文。不要默认用Get-Content -Raw输出几十万字符。
2. knowledge-map优先通过JSON解析筛选命中路由，输出该路由的read/readSections/update/checks/expandOn，不把整个JSON塞入上下文。只调整规则/路由或匹配不明时扩大到相关定义。
3. readSections是Agent使用的章节定位元数据，当前check:knowledge不自动执行章节读取或检查语义。标题不存在、同号多标题、命中范围太大时，先查实际标题并按主题消歧，不凭章节号猜内容。
4. 读取到足以确认“适用规则、当前链路、修改位置、验收与未闭环边界”即可停止。只有缺口、引用或风险触发下一层；不为证明认真默认遍历历史。
5. 截断表示读取未完成；缩小输出范围并补读缺失内容，不能不断重发同一大文件。相关必读与高风险核查没有固定字数上限，不能为了省Token跳过。

### 8.3 增量复用与交接

本会话维护简短已读指针：文件＋章节/主题、适用结论、核对时的Git或文件变更标识。无需为每次阅读新建仓库日志、缓存表或平台Memory；指针不是独立事实副本。

相同版本的同一章节不重复读取；本地未提交文件还须核对磁盘变更，不能仅凭HEAD未变判断内容未变。指令变化、目标扩展或有并发修改时补读对应章节；写入前仍必须重读最新目标段。

压缩或跨Agent交接仅保留目标/授权边界、当前进度、已确认结论及准确指针、未知项和下一步。接手者重读必要规则和将修改的段落，不默认重读全部历史；上下文未保留的强制规则不能仅靠“前面读过”略过。

### 8.4 路由维护与写入配合

公共规则正文变更由knowledge-common-rules路由要求同步核对AGENTS入口、索引、架构2.1和路由；普通业务/文档更新不强制改公共规则。read列必要当前依据，readSections列候选章节，update列必须同步核对的位置，checks按实际风险配置；生成矩阵仍由现有生成器维护。

默认阅读不包括历史、生成报告、审查清单和分享材料；需要证明具体结论时再沿证据指针读取。共享代码命中多模块时，各模块只写自身变化/不变边界与源证据链接，不复制同一回执。

读取定位优先使用专题路由：notification-center承载通知身份、事务和投递；feedback承载反馈与附件；market-cycle承载市场周期账户就绪及日期/数据边界。通用前端默认读共享控件、移动端公共规则和权限，模块适配记录按主题回查；生产部署必须补齐其完整流程，不因读取量较大省略。

本次优化了主题路由和章节边界，没有新增自动检索、缓存、文件锁或语义检查程序。未来标题/职责改变时同步维护readSections；定位优化复用既有问题及冻结检查点对照，并另核对权限、阶段和授权边界，不改样本去凑通过。不要另建与机器路由重复的完整手工目录。

## 9. 收尾核对清单

- 已找到原权威位置，并完成必要性、归属、替代关系和保留边界判断。
- 正文、顶部摘要、索引和目录不再给出相反的当前结论；未完成和授权边界有去向。
- 实现、部署、验收与数据结果分开；日期和数量带范围，旧回执没有冒充本次验证。
- 原始证据仍完整，引用/附件/锚点可定位；没有新增重复流水或私有事实副本。
- 已复核并发增量、实际Git差异和相关路由；检查范围只覆盖本次工作，未吞并其他Agent改动。
- 纯文档运行 `npm.cmd run check:knowledge` 并核对本次链接/格式；涉及业务实现另按AGENTS执行相关测试和运行验收。

现有门禁校验入口、路由更新、矩阵及部分实现符号；**不能自动证明语义一致、证据真实、无并发覆盖或专项验收完成**。本规则是公共写入约束，不是新增自动锁、自动语义审查或业务测试程序。

## 11. 持续更新与周期复核

采用“变更当次更新＋发布对齐＋周期复核”。任务交付和发布对齐是必做动作；周/月复核是维护责任人的计划工作，首次执行时登记范围和基线。此规则不代表已创建定时任务、自动巡检或语义审查程序。

### 11.1 触发、范围与责任

| 触发时机 | 负责角色 | 必做范围 | 记录位置 |
|---|---|---|---|
| 每次任务交付前 | 本任务开发者/Agent | 用实际Git差异匹配read/update；原位修正行为、链路和旧状态，核对标题与引用 | 原架构/专项、原任务卡；索引仅短摘要 |
| 每次统一发布后 | 本次发布负责人 | 按固定提交与实际运行证据，对齐已部署、待发布、专项通过/未验；删除当前入口中已被证据替代的状态 | 原任务卡发布栏、相应期间部署回执；同步原正文与索引 |
| 每周一次（建议周五，上海时间） | 本次指定的文档复核负责人 | 从上次复核基线到本次HEAD检查受影响文档；查相反摘要、失效链接、旧未部署/待发布和无证据关闭项 | 复用文档治理核查记录；跨对话事项回原任务卡 |
| 每月一次（建议首个工作周，复盘上月） | 统一维护负责人 | 按11.4—11.5完成项目总结、问题归因、规则沉淀、架构/分层/代码健康与数据获取审查；扩查部署/环境/任务/路由，超过30天无进展项标久悬、下一步或凭证据归档 | 当月项目复盘作摘要与证据索引，结论回原权威文件与任务卡；保留失败/授权/未验边界 |
| 重大重构完成后、终态确认前 | 重构整合负责人 | 核对数据源→数据访问→业务→协议→页面/任务全链路；重写变动的当前说明，逐项确认设计、实现、部署、验收差异 | 原分层/业务方案、技术架构、相关路由与回执 |

没有约定常驻负责人时，由用户发起维护的对话担任本次复核负责人，并在原任务卡登记；不把无人认领的计划写成已经按时执行。需自动调度时按用户明确安排另行创建，未执行的复核不刷新“最后核对”日期。

### 11.2 复核动作与完成标准

1. 固定Git基线、日期与核对章节；检查已有任务归属，按第6节隔离修改。不以文件修改时间判断事实先后。
2. 检索原权威正文，对照实际代码与版本/运行证据。已实现、已部署、专项已验及数据恢复分别判断；证据矛盾时保留双方指针和具体待核验动作。
3. 先修改正文和当前摘要，再更新目录/索引，最后修路由。索引同主题一行；当前摘要不超过5行，不以版本流水代替现状。确认未变时说明本次核对范围，无需制造无意义差异。
4. 旧过程有审计价值则迁入对应期间历史或留在原专项的历史区；原文、锚点、来源、失败与授权范围不丢失。已完成项不继续占待发布入口，未验项不因上线消失。
5. 运行 `npm.cmd run check:knowledge`，检查本次引用/标题和Git差异；纯文档不启动服务或重复全量业务测试。代码、依赖、配置或部署行为发生变化时仍按AGENTS执行原验收。
6. 交接记录核对基线、范围、修正位置、保留缺口和检查结果。正文、摘要、索引、路由及发布证据一致才算本次维护完成；有未验业务不影响如实完成文档核对，但不得写成业务已验收。

### 11.3 自动检查的能力边界

现有 `scripts/check-knowledge.js` 和CI负责入口、路由更新、章节及部分实现符号检查；不能证明语义、金融口径、生产证据或页面行为正确。周期复核复用这些工具并进行内容核对，不另建规则副本或平行事实清单。

### 11.4 月度项目复盘与规则沉淀

月度维护同时承担项目总结和研发改进。固定复盘月份、上海时区起止时间、起止Git提交及可取得证据范围；月中执行须标“截至某日”，不能冒充整月。跨月遗留明确原登记时间，不重复算成本月新增问题。尚未执行月度复盘时不预填成果或宣称已完成。

#### 月度复盘必须覆盖的内容

| 内容 | 必须回答的问题 | 证据与落点 |
|---|---|---|
| 项目进展 | 本月新增/改进了什么，哪些已实现、已发布、已验收，哪些延期；是否改变架构、数据源或用户使用方式 | Git差异、版本与发布回执、原方案；机制变化写回技术架构 |
| 问题与根因 | 哪些故障、用户反馈和返工反复出现；是否跨模块同根因；为什么原有测试、规则或交接没能阻止 | 原Incident、反馈专项和失败/回归记录；按根因归类，不把不同症状拆成多条规则 |
| 架构与代码健康 | 需求增长后是否出现职责混杂、重复实现、依赖循环、过度拆分或难以修改的热点；各层是否值得优化 | 按11.5对照代码、依赖与变更热点，区分静态合规、职责正确和设计合理 |
| 数据获取与恢复 | 本地缺记录是否被误判为上游没有；缺失/过期数据能否由现有网关或任务按情形自动补取，补后是否真正可用 | 按11.5核对缺失分类、来源适配、自动触发、去重、质量发布与恢复全链路 |
| 规则与防复发 | 应执行/补强已有规则，还是存在真正规则缺口；哪些经验不能泛化；检查是否实际可执行且能发现原失败 | 按下方判断流程处置；完整事故仍留原位置，不塞进AGENTS |
| 项目健康与债务 | 数据质量、任务稳定性、性能/安全、测试与验收缺口、文档漂移和技术债的趋势如何；有没有持续未闭环项 | 用同范围证据比较；缺少数据写待核验，不补造指标，不为总结主动触发生产采集或写入 |
| 下月行动 | 最值得优先处理的少量事项是什么，完成标准、负责人/待认领人、依赖和下一检查点是什么 | 写回原任务卡/专项，月报只引用；没有证据的项目不标完成 |

#### 从问题到规则的判断流程

1. 从原事故、反馈、提交和回归结果确定根因及影响范围。高频同类或一次暴露系统性缺口的问题都可评估；问题数量本身不作为新增规则的目标。
2. 先查AGENTS、公共规则、技术架构、专项合同与规则追踪。已有同义规则时，分析为何未执行、不可定位或缺少检查，优先补入口、说明或执行证据，不叠加同义禁令。
3. 只有具备可复用根因、明确适用范围和可执行预防动作时才补新规则。写明触发条件、必须动作、适用边界/例外及验证方法；某证券、某来源的字段特例不能升级成全项目通则。证据不足时列待评估及补证动作。
4. 按职责归位：知识维护/协作细则写本公共规则；稳定技术与数据合同写技术架构；领域约束写原专项；跨项目模块的强制入口或红线才补AGENTS；长期技术取舍按需要写ADR。事故证据回Incident，月报不成为第二套规则或唯一事实来源。
5. 检查能否由已有测试或门禁验证。能验证时登记具体检查及原失败反例；尚未自动覆盖则明确人工核对方式和后续任务，不把“规则已写”写成“门禁已实现”。实施测试/门禁代码仍按原开发、资源与全量验收要求执行，不由月度总结自动扩大实施范围。
6. 同步原正文、短摘要、索引与必要的read/update/readSections；新规则与现规则冲突时说明替代关系，保留证据。下一月复查规则是否执行、问题是否复发、是否需要收窄或淘汰无效规则。

#### 月度交付与记录格式

沿用已有同月份项目复盘；没有时才创建 `docs/项目月度复盘_YYYYMM.md`。这是特定月份的汇总与证据索引，不替代技术架构、规则、Incident或任务卡；不把新月内容持续追加进旧日期的历史报告。本规则只定义未来交付，本次未生成未执行的月报。

月报至少包含：月份/核对范围与代码基线、项目进展、问题与共同根因、规则处置、架构/分层/代码健康、数据获取与恢复、健康与遗留、下月重点及未核验范围。规则处置逐项填写下表，可选择“补强已有”“新增”“不泛化”“待补证”，不能只列建议而没有去向：

| 问题/根因及证据 | 已有规则与执行缺口 | 处置及适用边界 | 权威落点 | 验证方式/实际覆盖状态 | 下一检查点 |
|---|---|---|---|---|---|

完成条件是月报结论可沿链接复核，采纳的规则已在原权威位置更新，未实施防护与后续事项已回原任务跟踪，并通过11.2的文档检查。月报提交不代表其列出的全部业务整改已经实施或上线。

### 11.5 月度架构、代码健康与数据获取审查

每月从本月改动热点、重复事故和用户受阻链路开始，核对其相邻依赖；核心持仓/净值、分析、采集与后台调度链路轮换覆盖。报告列明已审与未审范围，不能用抽查结论给全站盖章。先明确已有能力、可复用能力和真正缺口，再提出优化；不能因为代码行数多或目录齐全就判定架构差或好。

#### 架构与代码退化检查

| 检查面 | 必查问题 | 判断依据 |
|---|---|---|
| 总体结构与演进 | 原架构是否仍能承载现需求，新增功能是否出现第二套事实、状态、采集或调度；抽象是否过多、旧兼容路径是否仍必要 | 技术架构、真实调用链、ADR与近期改动；比较扩展现有能力和新增结构的代价 |
| 数据访问/适配 | SQL和来源映射是否回流业务/路由，仓储是否夹业务规则或主动联网；同一数据是否重复采集、选择或落库 | 仓储、网关、适配器、原始记录/标准表及来源合同，不能只看文件名 |
| 业务模型/编排 | 金融公式是否重复或耦合数据库/HTTP；混合服务是否继续膨胀，事务、失败和幂等边界是否清楚 | domain、application实际角色、返回合同与行为回归；优先隔离确有变化压力的职责 |
| 协议/任务入口 | 路由和任务是否重做业务判定或持有数据源细节，补偿是否另造平行链路，目标日/作用域是否贯穿 | 路由、Runner、任务合同、租约和分区发布；失败路径同样核对 |
| 前端API/Presenter/View | 取数是否回流View，Presenter是否夹DOM或金融计算；状态/缓存是否重复，迟到响应是否越过账户隔离 | 页面加载契约、真实调用与异步场景；不能把拆文件/角色登记当职责完成 |
| 可维护性与验证 | 高频修改的大函数、深嵌套、依赖循环、同类补丁、重复转换和吞错是否使修改越来越困难；测试是否只验实现文本而漏行为 | 变更与事故热点、依赖及具体代码证据；大小/复杂度是定位线索，不能按数字机械拆分 |

对每个问题判断是本月新增退化、原有技术债、合理例外还是证据不足；写明实际影响、建议边界、收益/成本、回归风险及验收方式。能局部整理则不扩大为全站重构；保持现状的决定也应说明原因。静态越界为0只能证明扫描覆盖内合规，不能代替职责与架构审查。

#### 数据缺口与自动补取检查

审查目标是让系统能识别“为什么缺”和“下一步怎么恢复”。本地没有记录不能直接证明上游没有；但数据库读取函数也不应因此隐式联网。按技术架构6.1/8/10/11及原ADR的默认只读、唯一采集入口、质量发布和Guard边界评估以下链路：

1. **先分类**：区分本地未采集、过期/中间日期缺口、字段或身份映射错误、解析失败、上游未披露、来源不支持、权限不足、临时失败/熔断。查询为空不得直接写成“未披露”或“上游无数据”；用户界面应能解释已确认状态和待恢复动作。
2. **检查已有事实与来源**：核对标准表、缓存/原文、必需字段、时点/单位、来源优先级和适配器是否真正接线。已有合法零值不能当缺失；已有质量通过的历史事实不能被失败/空结果覆盖。
3. **按情形选择恢复方式**：对已获准的按需刷新，评估由既有业务编排/网关在限时内补取；耗时采集、历史区间和解析重算优先复用原Runner自动排队/续跑，页面返回已有数据及准确状态。官方未披露按证据与复查日等待，来源不支持/权限缺失进入明确阻塞或已准入备源，禁止持续空重试。
4. **核对自动触发是否完整**：缺口是否有人发现、什么条件触发、由谁去重与领取任务、失败何时重试、何时停止；用户反复打开页面不能造成重复外采。检查并发合并、租约、幂等、超时与真实外部额度/权限、熔断恢复约束。需要改变现有只读或手动刷新策略时，写明影响和实施方案，不在月度复盘中静默改代码。
5. **确认补后闭环**：API成功不等于事实可用；须核对身份、字段完整性、日期、来源证据、标准化落库、质量分区和页面/任务重读结果。检查是否存在“取到了但未落库”“落库了但仍读旧快照”“任务成功但缺口未消失”。
6. **明确缺口与后续**：已有能力未接通时优先接线；能力不足再解释为什么不能扩展现有网关/任务。方案须覆盖数据源→仓储/标准事实→业务→接口→页面/任务，列明自动补取条件、允许来源、失败状态与验收场景。生产采集/写入、来源准入及实现仍遵守原授权边界。

#### 优化建议的交付和验证

架构及数据获取建议单独列入月报，不能全部折算成“新增规则”。每项至少包含下表；范围内未发现问题时列实际检查证据，未审部分留待核验：

| 现象/代码或运行证据 | 已有能力与真正缺口 | 优化方案及涉及层 | 收益、成本与风险 | 优先级与实施去向 | 验收场景/下次复查 |
|---|---|---|---|---|---|

优先处理数据错误、跨账户/权限问题、阻断用户操作和重复事故；纯结构整洁按收益排序。数据恢复验收应覆盖本地命中、缺失可补、已过期、官方未披露、权限/故障、重复与并发请求、补取后重读等适用情形；架构优化同时验证成功与失败路径的行为等价。这里只要求审查和形成可执行改进项，不宣称每月自动实施所有重构或补数。
