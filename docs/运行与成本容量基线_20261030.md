## 9. 当晚已执行的两项（2026-10-30 19:30 前后，用户授权）

采集后立刻做了两件事，都是"限容"类变更，不改业务逻辑、不动数据事实。

### 9.1 journal 限容（4.0G → 961M）

- 做法：新建 drop-in `/etc/systemd/journald.conf.d/99-size-limit.conf`（`SystemMaxUse=1G`、`SystemMaxFileSize=100M`），原 `/etc/systemd/journald.conf` 备份为 `journald.conf.bak-20261030`；`systemctl restart systemd-journald` 后按新上限滚动。
- 结果：`journalctl --disk-usage` 4.0G → **961.4M**；`/var/log/journal` 962M。原日志最老到 2026-08-13（约 2.5 个月），限容后按当前写入量约保留 2 周。业务日志另有 `/opt/portfolio/logs`（33M），不受影响。
- 回滚：删掉 drop-in 后 restart 即可恢复无上限（原配置未改）。

### 9.2 PDF 原文缓存清理（5.0G → 2.0G）

- 先确认策略：缓存**本来就有**清理机制——`server/services/documentPdfCache.js` 定义 TTL 30 天 + 上限 5GB，每次写入后 `cleanupDocumentPdfCache()` 按 mtime 从旧到新删到上限以内；注释写明"只保存可重新获取的官方原文，不承载业务事实"。所以 5.0G 不是失控，是**顶到设计上限**。
- 做法：改用同一函数、把上限临时收到 2GB 执行一次：`sudo -u portfolio-app env DOCUMENT_PDF_CACHE_MAX_BYTES=2147483648 node -e "require('./server/services/documentPdfCache').cleanupDocumentPdfCache()"`。
- 结果：`deletedExpired=0`（说明没有超过 30 天的）、`deletedOverflow=490`、保留 834 个 PDF、目录 5.0G → **2.0G**。
- **注意**：这只是本次执行的上限，`/opt/portfolio/.env` 仍未设置 `DOCUMENT_PDF_CACHE_MAX_BYTES`，运行时上限还是默认 5GB，会慢慢涨回去。要长期压到 2GB，需要在 systemd 单元加 `Environment=DOCUMENT_PDF_CACHE_MAX_BYTES=2147483648` 并重启服务——属于部署动作，留待下次发布一起做。

## 11. 备份保留组数的核查与处置（2026-10-30 21:00 前后）

采集时发现"磁盘只剩当天 5 组、文档说保留 14 组"，当天查清并处理：

**5 组是否相同**：不是完全相同，但差异很小。5 组是当天 5 个时间点的全量快照（00:10、00:35、03:42、14:31、17:07），数据库密文大小分别 351011739 / 351023368 / 350978775 / 352227128 / 353711859 字节（约 335MB，最大差 2.7MB），说明数据在变但结构一致。

**为什么会有这么多组**：三处都会触发备份——① 每日定时 `portfolio-db-backup.timer`（03:41，对应 03:42 那组）；② **每次部署前**，`deploy/deploy_password.py` 会先 `systemctl start portfolio-db-backup.service`（对应 17:07 那组，0.9.1.5 发布）；③ 其余（00:10、00:35、14:31）来源未逐条核实，可能是手工或其它流程触发。所以一天 3—5 组是正常的，不是重复拷贝。

**为什么只剩 5 组而文档写 14 组**：`scripts/backup_db.sh` 里 `group_base()` 只剥一层后缀，`X.sql.gz.gpg.sha256` 会被剥成 `X.sql.gz.gpg`（而不是 `X`）。prune 按"基名"取前 14 个，同组文件占掉多个名额，实际只保留 3—4 组。**这是文档与事实不一致的根因，不是有人手工清理。**

**处置**：
1. `group_base()` 改为循环剥离，直到剥不动（每组所有产物归到同一个基名）。
2. 保留组数改为可配、默认 **3**：`BACKUP_KEEP_GROUPS`（原来硬编码 14）。
3. 服务器脚本同步更新（上传后需去 CRLF——本次上传过一次 CRLF 版本导致 `bash -n` 报错，已立即 `sed -i 's/\r$//'` 修复并确认 `SYNTAX_OK`），原脚本备份为 `backup_db.sh.bak-20261030b`。
4. 立即清理到 3 组：保留 17:07 / 14:31 / 03:42，删除 00:10 与 00:35 两组。目录 1.7G → 1.0G，磁盘可用 33G。
5. 用假目录验证新 prune：造 5 组 25 个文件 → 跑一次 prune 后剩 3 组，同组 5 个文件整组保留、没有只删校验文件的情况。

**过程中出现并已修复的问题（如实记录）**：清理用的临时脚本把 `X.sql.gz.gpg.sha256` 当成独立组，误删了 3 个保留组的 `.sha256` 校验文件（共 6 个）。已按各组的 `.manifest.sha256` 里记录的 `database_sha256` / `attachments_sha256` 重新生成，6 个哈希与新算值逐一比对一致，`sha256sum -c` 全部 OK——备份文件本身没有被损坏，只是校验文件重建。
