## 四、详细问题与整改要求

### P0-1：A 股总市值同步链路错误

#### 当前问题

`server/jobs/marketVolatilitySync.js` 在循环同步目标交易日时：

1. 命中 `stock_unified` 后设置了 `securityCount`，最终写库却仍引用只在回退分支内声明的 `rows.length`，产生 `ReferenceError`。
2. `stock_unified` 每只股票只取“自身最新一条估值”，不能代表循环中的目标历史日期。
3. 本地 326 只有市值股票的日期分布在 4 个交易日，属于混合截面，不能直接求全市场某日市值。
4. `market.daily_valuations.total_market_cap` 标准化后按“元”保存，现代码注释和换算却按“万元”处理。
5. 统一视图覆盖 326 只股票，远低于全市场快照的 5528 只，不满足全市场聚合要求。

#### 风险

- 当前状态：任务直接失败，相关市场周期数据不能正常更新。
- 只修复 `rows` 变量后：可能把混合日期、部分股票、错误单位的结果写入历史月份，风险高于直接失败。

#### 整改方案

1. 将总市值读取接口改为显式接收 `tradeDate`，只聚合该交易日的完整分区。
2. 历史补齐必须按目标日期读取，不得使用“每只证券最新值”。
3. 标准表中的市值按“元”处理，写入 `total_market_cap_100m_yuan` 时除以 `100000000`。
4. 写库统一使用 `securityCount`，禁止引用分支局部变量。
5. 增加覆盖完整性门禁：证券数量未达到合理全市场范围时，拒绝使用统一表并回退到对应交易日的 Tushare `daily_basic`。
6. 回退数据也必须验证交易日、数量、总值和空值比例，异常时保留上一份有效数据。
7. 审计重构后写入的 `market.a_share_market_cap_daily` 和 `analytics.m2_market_cap_daily`，发现异常日期或异常数量级时先列出修复范围，获得用户同意后再重算或清理。

#### 验收标准

- `market_volatility_sync` 连续两次执行成功，无 `rows is not defined`。
- 任一历史目标日只使用该日数据，不出现混合日期。
- 证券数量满足完整性门禁，并与上游同日数量在合理误差内。
- 统一表与 Tushare 同日聚合结果的市值误差在预设容差内。
- M2 市值比重算前后有数量级检查，异常数据不会发布到页面。
- 新增“统一表命中、统一表不完整回退、历史日期、单位换算”四类自动测试。

### P1-1：可转债正股代码丢失

#### 当前问题

`bond_unified` 的 `stock_code` 只取关联的正股 `core.instruments.canonical_code`，没有使用 `bond_history.stk_code` 兜底。

同时，`bootstrapBondsFromHistory()` 只处理 `core.instruments` 中尚不存在的债券。对于已经有债券主档、但尚未建立正股关联的历史数据，不会再次调用统一 upsert 完成关联。

本地实测有 639 条记录在 `bond_history` 中存在正股代码，但通过统一视图读取时为空。

#### 整改方案

1. 将历史回填从“只处理不存在的债券”改为“对缺字段或缺关联的债券执行幂等补齐”。
2. 统一视图增加迁移期兜底：正股关联为空时返回规范化后的 `bond_history.stk_code`。
3. 正股代码补后缀时统一复用证券代码映射规则，不在视图和服务中分别手写多套判断。
4. 保留 `bond_history`，完成回填和双读核对前不得删除或停止写入。

#### 验收标准

- 对所有 `bond_history.stk_code` 非空记录检查，统一视图 `stock_code` 缺失数为 0；明确不适用的私募/定向债单独列出。
- 随机抽查沪市、深市、已退市和新上市债券，债券与正股关联正确。
- 重复执行回填不会新增重复证券、重复关联或覆盖更完整的新数据。
- 打新报告、历史接口、可转债详情的正股代码一致。

### P1-2：统一数据层实际接入不完整

#### 当前问题

`server/services/bondDataService.js` 注释称打新、股债分析、估值、安全性和周期都通过该服务读写；实际只有 IPO 读取和部分主同步引导使用。

`server/services/stockDataService.js` 注释中提到不存在的 `checkStockData()`，并称 `server/services/market.js` 是唯一写入入口；实际标准化估值主要由 `server/services/financialDataArchitecture.js` 和可转债正股同步写入。

#### 整改方案

1. 建立“数据集—权威写入者—读取者—回退链—单位—更新频率”矩阵。
2. 先修正文档和注释，使其只描述当前真实状态。
3. 再逐模块迁移调用方，每迁移一个模块都进行双读核对，不一次性删除旧链路。
4. 对仍需直接读取事实表的分析模块，明确其属于正常分层，不强行套用单一服务。
5. 删除旧表或旧写入必须另行申请，至少稳定运行一个完整数据周期后再决定。

#### 验收标准

- 统一服务导出的每个函数都有真实调用方或明确用途。
- 文件注释、技术架构文档和代码调用关系一致。
- 搜索直接访问旧表和外部 API 的位置，每一处都有保留原因或迁移结论。
- 不存在两个模块对同一标准字段使用不同单位或不同证券代码规则。

### P1-3：迁移与运行态未闭环

#### 当前问题

当前代码已经新增迁移 `034_bond_profile_list_date`，但本地 `schema_migrations` 尚无该记录。新 upsert SQL 依赖 `fundamental.convertible_bond_profiles.list_date`，运行态未更新时仍可能失败。

#### 整改方案

1. 先核对 034 迁移幂等性和现有表结构。
2. 在本地按项目规则重启服务，使启动迁移执行。
3. 查询 `schema_migrations` 和 `information_schema.columns` 双重确认。
4. 执行可转债主同步相关测试和一次受控本地刷新。
5. 生产执行数据库结构变更前，按项目规则向用户说明影响并获得明确同意。

#### 验收标准

- `schema_migrations` 存在 `034_bond_profile_list_date`。
- `convertible_bond_profiles.list_date` 存在且类型为 `DATE`。
- 可转债主同步不再出现 `conv_price`、`current_conv_price`、`list_date` 字段错误。
- `/health`、相关 API 和本地应用版本与当前代码一致。

### P2-1：IPO 债券代码格式兼容

#### 当前问题

旧接口从 `bond_history.security_code` 返回六位代码；新服务直接把 `bond_unified.bond_code` 映射为 `security_code`，返回值变成 `113039.SH`、`128129.SZ` 等格式。

#### 整改方案

1. 明确 IPO API 对外契约：`security_code` 继续保持六位代码。
2. 如页面需要标准代码，新增独立 `canonical_code` 字段，不复用并改变旧字段语义。
3. 检查前端交易所判断、报告链接、搜索和导出是否依赖六位代码。

#### 验收标准

- 旧调用方继续获得六位 `security_code`。
- 新增字段时保持向后兼容。
- 沪市、深市债券的前端交易所标识和报告查询正确。

### P2-2：测试覆盖不足

#### 当前问题

现有市场周期测试主要检查源码中是否包含相应调用，IPO 测试只检查字段是否存在，没有验证：

- 缓存命中后的变量作用域。
- 同一目标日期的完整分区。
- 市值单位换算。
- 统一视图历史回填与字段兜底。
- `security_code` 格式兼容。

#### 整改方案

新增以下测试：

1. `stockDataService`：指定日期聚合、覆盖不足回退、元转亿元。
2. `marketVolatilitySync`：统一表命中和 Tushare 回退两条分支。
3. `bondDataService`：纯代码和标准代码查询、历史接口字段格式。
4. PostgreSQL 集成测试：已有债券主档但缺正股关联时可幂等补齐。
5. 迁移测试：空库和已有旧表两种场景均能执行 031—034。

验收时测试必须实际执行，不能以 SKIP 冒充通过。
