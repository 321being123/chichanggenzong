## 19. 新股判不可评估与 PB 窗口性能优化（2026-11-07，0.9.2.31）

### 19.1 背景：A 方案（补新股数据）不可行

补数后 CN 仍剩 16 只待补，查实为：**7 只是 2026-10-09 ~ 11-03 当月上市的新股**，`financial_reports=0`、`corporate_actions=0`——客观上还没有年报和分红，官方接口也不会有，补数无解。另 1 只 601916.SH 财报 140 条、分红 14 条，数据齐备，只是 PB 窗口仍有缺口（可后续定向补）。

结论：这不是数据没采，是「客观上不存在」，必须从判定口径纠正，而不是继续补数。

### 19.2 R04 改判（产品规则）

`evaluateDividendYield` 的 `perShare === null` 分支：若 `facts.annual.years` 为空（公司一份年报都没有）且未核验零分红，判 `NOT_APPLICABLE / no_annual_report_not_evaluable`；有年报但无分红证据的仍判 `PENDING / dividend_unavailable`（不放过真缺口）。与 R05 的 `equity_not_evaluable_no_report` 同口径。V2 复用 V1 该函数，一处生效。

### 19.3 PB 窗口 SQL 性能优化

`loadPbWindow` 的 `expect` CTE 原写法有两个问题：①停牌豁免是逐证券**相关子查询**（每次 computeSelection 跑 5749 次）；②同一个子查询在 `expected_days` 与 `exempt_days` 里**重复写了两遍**（每只证券算两次）。日历补齐到十年后（应有日 5749×2672≈1536 万行），这两点成为主要耗时来源（CN 由 17.6s 升至 132.7s）。

改为独立 `exempt` CTE（按 `instrument_id` 一次聚合，`GROUP BY 1`）+ `expect` 用 `LEFT JOIN exempt` 取值；`expected_days` 与 `exempt_days` 由同一列派生。语义不变：仅「停牌且当天没有 PB」才豁免、`exemptDays` 继续单独留证、`GROUP BY` 改为显式列名。
