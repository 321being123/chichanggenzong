## 1. 背景与范围

用户《存在小站体验反馈》PDF（2026-10）中"录入交易—智能导入（图片）"共 7 条问题：多图不支持、只识别一张图、不知道该截哪种图、没有成本价、港币混淆（经用户确认是**两个错误**：港股识别成了 A 股 + 港币价格被当人民币）、数量带 "-" 号、确认录入卡死。

以上为原方案保留的来源转述，本次未复核附件及历史确认对话。第 3 节将其拆为 10 个检查项，不代表原 PDF 有 10 条反馈；“只识别 3 条”和扫码细节同样待原图/现场复核。当前授权仅为核查、优化文档，不包含代码实施、建反馈单或部署。

**本方案范围**：图片智能导入的识别质量、批量录入、确认录入稳定性、上传引导、手机扫码上传。

**明确不含**（用户指令）：
- 大模型/接口配置调整——用户确认现用大模型可用，不动；
- PDF 第 1 条"仓位差距对比"需求——独立功能，另案立项；
- Excel 导入通道的结构化直解析逻辑——保持现状，只对齐 AI 兜底口径。

## 2. 架构对齐结论

按"已有能力、可复用能力、真正缺口"核对现行代码：

| 分类 | 内容 |
|---|---|
| 已有能力 | 单图 `/api/vision-parse`；Excel 结构化优先、AI 兜底；`callAiFallback` 及重试；图片魔数校验/限流；共用 `code-classify` 已识别 1—5 位数字港股，`normalizeImportedItems` 对部分六位补零歧义调用主档，**并非所有记录都查主档或补币种** |
| 可复用能力 | 完整批量入口 `POST /api/accounts/:name/ledger/position-events/batch?version=…`，支持 open/adjust 单事务；复用现有数值清洗思路但补严校验；账本已有 `quote_currency` 和历史汇率，不能只增加未被账本读取的 `currency`；沿用共享分类、表格和账户版本状态 |
| 真正缺口 | 持仓成本/市价语义、数值与身份冲突校验、多图队列和有条件合并、失败结果透传、删行后索引重排、稳定幂等键、数量单位、扫码整批交付及容量限制；2000 tokens 可能不足但尚未证实为少识别的实际原因 |

**结论**：在现有链路上局部扩展，不新增平行任务、数据源、事实表或调度器。常规正价建仓按现有结构实施；零/负成本按用户裁决直接入账，禁止转正或取绝对值（见 4.1 第 4 条）。识别及预览均不写账户，只有用户确认才走原账本。

## 4. 整改设计

### 4.1 P0 识别指令与输出整改（对应 #4 #5 #6 #7）

改造 `/api/vision-parse` 的识别指令（`import.js:171`），并同步修改 Excel AI 兜底指令（`import.js:303`）统一口径：删除 Excel 指令现状的“没有成本价则填市价，必须大于0”（与本次裁决直接矛盾），两通道持仓成本统一为——缺失填 null、允许零与负、不拿市价冒充成本；Excel 结构化直解析的表头列映射（成本列就是成本）不受影响：

1. **持仓字段扩充**：在 code/name/price/quantity 基础上增加：
   - `cost`（成本价）与 `avg_buy_price`（买入均价）——截图两列都取，缺哪列填 null，两者均允许零与负（做T摊薄为负属正常）；
   - `currency`（币种，只允许 `"CNY"` / `"HKD"` / `null`）——按明确币种文字/符号及上下文判断，单独“¥”不足以确认；其他币种或判断不了填null并标待核对，禁止猜；
   - `market_value`（市值，供交叉校验，可 null）。
2. **交易字段增加** `currency`，规则同上。
3. **格式硬约束**：数值输出 JSON number 或 null，不带货币前缀、千分位、单位；成本允许保留零和负号；数量原样提取，并增加 `quantity_unit`（股/张/手/份/null），不让模型擅自取整、取绝对值或换单位。交易保留 direction、日期、金额及原有全部税费/费率字段，不因补字段丢掉已有能力。
4. **成本与市价分开**：图片持仓新增明确的 `market_price`，`cost`、`avg_buy_price` 各自保留；旧 `price` 不在图片与 Excel 之间静默改义。预览分列显示成本、市价和“拟录入成本来源”；成本选择顺序：有 `cost`（含零/负）优先，缺失用 `avg_buy_price`（含零/负），两者均缺时**保持空值**——不用市价估算、不自动替代，该行提交前必须由用户补填成本。确认选定的成本映射到建仓事件price，截图市价不直接写positions.price，仍由原行情刷新负责。
   **零/负成本入账（用户2026-10-26裁决，本次实施）**：现状拦截链共四处——服务端 `validateTrade` 对 open 抛"交易价格必须为正数"（`tradeLedger.js:50`）；数据库 `chk_trades_price` 对 open 不豁免（`era01CoreSchema.js:2073`）；`chk_trades_amount` 无条件 `amount>=0`（2075行，负成本 open 的 amount=price×quantity 为负必被拦）；重放 adjust 的 `p > 0 ? p : 旧cost` 会静默忽略零/负成本（`tradeLedger.js:104`，形成"以为改了成本实际没改"的不一致）。整改落点：① `validateTrade` 的 price 正数校验收窄到 buy/sell，open 允许有限数值（含零/负），数量仍为正；② 重放 adjust 的成本更新从 `p > 0` 放宽为 p 为有限数值即生效；③ 新增一条迁移，仅对 open 豁免 `chk_trades_price` 与 `chk_trades_amount` 的符号约束（buy/sell 约束不动；金额一致性触发器 174 本已豁免 open/adjust）；④ `positions.cost` 无非负约束、建仓 price 写 0 待行情刷新，无需改动。费用四项仍非负；open 的 amount 为负属期初快照语义，交易历史如实展示。重放移动加权对负价数学自洽（`tradeLedger.js:98-101`），open/adjust 净额为 0，现金与净值不受影响。
5. **输出完整性**：将图片请求的 `max_tokens` 暂定由 2000 调至 6000，仅调整本路由输出预算，不改后台模型、供应商或密钥。在现有调用函数上增加可选返回元数据，保留旧调用方返回文本的兼容性，供本路由判断 `finish_reason`；是否支持及实际 token 用量按现有模型实测，不能保证6000一定完整。区分明确空数组、输出截断、JSON错误、结构错误和上游失败；错误不当作零条成功，也不提交可疑半截数组。只有确认为截断才提示分段；其他失败提示对应原因。完整JSON仍可能漏行，须用原图逐行对照验收。
6. **证券代码原样提取**：保留 H 前缀、交易所后缀与前导零，不让模型补位或改市场；另输出 `market_hint`（HK/SH/SZ/BJ/null），避免与现有服务返回的 `market` 小写值混用。保留截图日期；持仓无日期时由预览明确选择快照日期，交易无日期或方向不明时待用户补全，不默认今天或买入。

### 4.2 P0 识别结果清洗（对应 #5 #6 #7 #9，服务端统一规则）

在图片及 Excel AI 兜底结果进入 `normalizeImportedItems` 前增加导入专用校验；身份规则继续复用共用分类器与主档，不把数值、队列和去重塞进证券身份服务。Excel 结构化直解析行为保持现状，新增规则只接 AI 分支；现有结构化、港股身份回归必须继续通过。服务端为最终校验方，前端只呈现同一结果并在用户编辑后重新校验。

1. **数字清洗**：复用 `parseNumericCell` 思路，但它目前只截取首段数字，不能直接充当严格校验。仅容忍明确格式如 HK$4.155、1,234.56、300股；空白、单独“-”、多段数字、NaN/Infinity、未知单位不得变成0。“-300”数量保留原值并标待核对；交易有明确卖出证据且经用户确认后才转正，不能全局取绝对值；小数数量不截尾，按当前品种能力校验。成本负号保留。
2. **单位只转换一次**：统一以股/张/份提交；债券截图明确“手”时按现有规则换算，明确“张”时不乘10，未知时让用户选择。核对现有 `normalizeQuantity`、费用预估和确认载荷，避免清洗后又按券商配置重复乘10；持仓与交易走同一单位结果。
3. **身份归一**：1—5位数字港股沿用现有规则；H+5位数字只在导入边界解析为港股候选，再交共用规则处理，禁止全局删字母猜代码。账本/页面 `code` 仍为五位港股代码，主档查询使用 `.HK` 标准代码，避免改坏下游。六位歧义继续用 `resolveAmbiguousSecurity`，保留平安银行等A股防误改测试。名称、代码、市场证据矛盾或主档查询失败影响歧义判断时标待核对，不盲信模型或名称匹配，不反写主档。
4. **币种及传递**：截图 `currency` 是识别证据，统一映射为账本读取的 `quote_currency`，同时给出一致的 type/subtype。HK$/HKD、人民币/RMB可归一；单独¥需结合截图语境，不单凭符号断定。无冲突且身份明确时才从主档/分类推导币种；显式币种与身份冲突时保留双方值、标待核对并阻止提交，不能覆盖数值后假称纠正。预览原币价格不乘汇率；账本按交易/快照日期使用已有汇率链路生成人民币金额，缺失汇率不得冒充有效CNY。
5. **校验与提示**：服务端返回规范值、原始相关字段、`issues` 及状态（可确认/待核对/无效）；只有能够证明的格式或身份修正才标“已纠正”。校验 kind、代码、日期、方向、有限数值、单位和金额关系，覆盖所有已提取税费，缺失费用保持null、明确0仍为0。buy/sell 成交价必须正数；open/adjust 的成本价允许零与负，按 4.1 第 4 条入账，空成本行阻止提交并要求补填；明确空仓可展示但不自动生成清仓事件。用户修改代码、数量、日期或币种后重新校验，旧问题状态不能直接沿用。

### 4.3 P0 多图批量识别与合并去重（对应 #1 #2）

1. **前端入口**：`public/index.html` 的 vision-input 加multiple；`core-trade.js` 选图、拖拽、粘贴及扫码统一进入队列。每图稳定 imageId，显示缩略图、文件名、状态及失败重试/删除；读取文件前校验，不让新结果直接覆盖已有预览或用户编辑。
2. **复用单图接口**：保持 `/api/vision-parse` 的 `{image}` 请求，前端并发固定为1，逐图独立处理；不新增整批图片识别接口，避免放大HTTP请求和单次等待。现有每分钟10次限流保持，遇429按服务端提示暂停，保留队列；失败只重试失败图，成功结果在本次会话复用，不重新调用模型。移除/取消后忽略在途结果，不能声称取消前端请求就终止了上游模型。
3. **容量边界（待实施值）**：每批最多6张、每张原始文件≤6MiB；手机单次整批原始图片合计≤6MiB。仓库Nginx请求体为10m、Node为15mb，Base64约增加1/3，原有“单张10MB”并不等于可穿过代理。前后端按同一边界检查，JSON字节数仍须校验；不为多图调大全局请求上限，不默认压缩致文字模糊，超限提示分批/重新截图。部署前只读确认实际代理限制，不能把仓库配置当生产实测。
4. **持仓合并条件**：只在同一用户、账户、同一快照日期、同一证券身份、币种和数量单位范围内，且数量/已知成本等共同字段一致时合并跨图重复行；补齐空字段，保留来源“图1+图2”，数量不相加。相同代码不同名称先核对主档；不同日期、子账户或字段冲突均保留为待核对候选，由用户选择，不按上传先后覆盖。没有身份或来源日期证据时不自动合并。
5. **交易不按持仓规则合并**：同证券同价同量也可能是不同成交；只对同一原图重复上传等可证明的重复输入复用识别结果。跨图疑似重复交用户核对；现有交易去重键不含成交编号、可能挡住真实同值成交，需在预览明确提示，不把“跳过”算新录入，也不在本方案中静默放宽原唯一约束。
6. **状态隔离与汇总**：队列和预览绑定账号、账户及批次。切换账户/退出使旧请求失效、停轮询并清理截图；切页后不能由旧响应恢复旧预览。汇总分别显示图片成功/失败、原始行数、合并数、待核对数、可录入数，不能用合并后的条数证明识别完整。

### 4.4 P0 确认导入稳定性（对应 #9，与识别整改一起交付）

2026-10-28 本地将批量持仓提交和事件核对请求转交既有客户端，并修正两项验收缺口：按用户名、账号实体、账户及切换代数隔离异步导入；事件核对读取服务端顶层交易列表，缺列表不能使用旧缓存判成功。原 ID、用户确认日期及未确认状态保持，细节见 [INC-0044](incidents/INC-0044-智能导入账号切换与事件核对.md)；跨标签页、浏览器和生产未验。

1. **明确提交结果**：局部修改 `addTradeInternal` / `confirmSmartItem`，返回已保存、已存在、失败或结果待确认；不能只依赖try/catch，因为现有内部catch/return会吞掉失败。仅明确保存成功才移除；已存在单独标记供用户处理，网络超时留行核对。逐行失败继续执行不依赖它的交易；401/403/409等会话/账户版本问题暂停队列，重新加载后由用户确认续办。
2. **持仓批量**：复用完整账户批量接口，确认前一次收集当前编辑值、检查全部待提交行，并保留已有证券adjust（目标数量）/新证券open语义；不把相同证券全部当open叠加。无效/冲突行先修正或明确排除，再提交其余持仓；单事务失败持仓全留，成功后一次同步全部版本与数据。行错误至少能定位稳定rowId；行情刷新失败按现有契约展示“持仓已保存，行情待刷新”，不能当账本回滚。
3. **顺序和范围**：同一轮确认中同证券同时含持仓快照及交易时先阻止并列出冲突，由用户确定录入范围/日期；不自动把快照和其已包含的成交再算一次。交易按已确认日期、可得成交时间排序，完全相同时间保留原顺序；历史卖出若缺期初持仓应失败保留，不绕过超卖校验。持仓原子提交不等于混合交易整批原子成功，完成提示分别统计。
4. **稳定索引与编辑值**：优先采用最小修改：提交前保存所有编辑值到状态，删行后重新渲染并重排索引；用稳定rowId/imageId关联来源、问题和提交状态。复测“先确认第一/中间条，再点剩余条”和中间条失败后重试，不能只验证逆序全部录入。
5. **幂等及防重**：批次创建时固定batchId，每行首次提交前生成并保留event/trade id；普通重试复用同一id和相同载荷，不再每次uid()或重新生成批次。按钮在提交中禁用、finally恢复。结果未知时先按原id核对，禁止修改同id载荷后盲重试；编辑后的新提交须确认旧请求未落库。现有 `applyTradesBatch` 先校验版本、后逐条查id，整批成功但响应丢失后带旧版本重试仍可能409：先加载账户并核对整组id，全部存在才标已保存，不能仅宣称复用id已解决批量重试。
6. **费用与日期**：费用计算使用当前编辑后的代码、方向、价格、标准数量及原币，不再引用旧item价格/数量。保留截图税费与现有设置的区别；日期缺失要求补全，持仓日期显式确认。历史净值重算失败与交易已保存分别提示，不能因此重录交易。

### 4.5 P1 上传引导（对应 #3）

1. 上传区按类型提示：持仓截图需包含代码、名称、成本价/买入均价、持仓数量、单位及日期；交易截图需包含代码、名称、成交价、数量、买卖方向、日期及可见税费。提示截持仓明细/交割单，避免首页行情总览；涉及账户隐私可遮住账号，不遮表头和证券字段。
2. 识别为空或失败时提示同样指引（替换现在的"未能识别出交易或持仓信息"单句）。
3. 示例小图保留为可选建议，本轮不默认制作；先用清楚文案，不增加无必要素材。

### 4.6 P1 手机扫码上传整改（对应 #10）

1. 手机选图框加multiple，先本地选择、预览、删除，再点“上传N张”；本批确认后一次请求提交 `images`，全部校验成功后原子写入token，不能边上传边由电脑消费。兼容旧 `{image}` 上传为单元素数组；同token重传相同批次可复用，内容不同明确报冲突，禁止静默覆盖。
2. 每批最多6张且原图总量≤6MiB，保留魔数/MIME及每图校验，整个JSON不得越过4.3容量边界。token保留5分钟TTL、每用户1个和全局50个；另为全局已保存Base64字符串设置64MiB字节上限（按实际字节累计，非只数token），超限拒绝且不删其他有效批次；消费、过期、替换均释放计数。以上为待实施限额，不冒称现有代码已有。
3. 上传、页面访问、轮询都即时检查过期，不只依赖每分钟清扫；有效期从生成起算，不靠重复上传续命。上传token仅允许交付图片，不能读账户或提交账本；轮询继续校验所属登录用户，先鉴权再返回状态，不扩大现有免登录上传的权限。
4. `/api/vision-check` 返回整批 `images` 及批次标识；旧 `image` 仅在一张时提供，电脑端统一入4.3队列。沿用一次性消费，不引入新的会话表；轮询响应丢失仍存在交付失败边界，电脑应显示可重新生成二维码并上传，不能假称上传成功等于识别成功或保证断网自动恢复。手机重复点击、上传后继续追加、过期后重试均有明确状态。
5. 桌面与手机均复用原生选图入口和现有共享样式，不复制业务逻辑；宽预览表只在容器内横滑，手机操作区≥44px、输入字号16px，保留缩放，不沿用模板的user-scalable=no。新增脚本按现行CSP加载要求处理，不能为手机上传放宽全站安全头。

### 4.7 P2 长截图切分识别（观察后决定，不默认实施）

4.1–4.3 上线后用真实长截图回归，若仍识别不全，再做"长图按高度切段（段间重叠一行）→ 分段识别 → 跨段去重合并"（合并逻辑直接复用 4.3 的去重）。**若补字段 + 提高输出上限后已识别完整，本项不做**（KISS，避免过度设计）。
